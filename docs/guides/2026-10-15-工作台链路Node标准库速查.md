## 1. node:child_process 的 spawn——执行外部命令

`executor.ts` 的地基。`runDocker` 里：

```ts
const proc = spawn("docker", args, { stdio: ["ignore", "pipe", "pipe"] });
```

### 1.1 spawn 是什么

启动一个**子进程**跑外部命令。三个参数：

| 参数 | 本项目的值 | 含义 |
|---|---|---|
| command | `"docker"` | 可执行文件名（在 PATH 里找） |
| args | 数组 | **逐个**作为 argv 传给命令 |
| options | `{ stdio: [...] }` | 标准三流的接法 |

**安全核心：args 是数组、不经 shell**。对比 `exec("docker run " + cmd)`——那会
经过 `/bin/sh -c`，用户输入可以被 `;`、`$(...)`、反引号劫持成宿主命令。spawn
的数组形式里，模型的命令字符串只是 `bash -lc` 后面的**一个**参数，宿主 shell
永远看不到它。这是"命令注入出不了容器层"的第一道实现。

### 1.2 stdio 数组：三个标准流各接一根管

`stdio: [stdin, stdout, stderr]`，每格可以是：

- `"ignore"` — 丢弃。stdin 用它：任务不需要交互输入，命令等待键盘输入会直接 EOF；
- `"pipe"` — 接一根管道回 Node。stdout/stderr 用它，后面 `.on("data")` 收数据；
- `"inherit"` — 直接接到当前进程的终端（本项目没用，调试时有用）；
- fd 数字 / Stream — 接到已有流。

### 1.3 返回的 proc 是什么：EventEmitter + 三根流

`proc`（ChildProcess）是一个事件发射器，同时挂着三个流对象：

```ts
proc.stdout.on("data", (chunk: Buffer) => { ... });  // stdout 管道有数据
proc.stderr.on("data", (chunk: Buffer) => { ... });
proc.on("error",  (err) => { ... });   // 启动失败（命令不存在/无权限）——注意不是"命令报错"
proc.on("close",  (code) => { ... });  // 进程结束 + stdio 流都关了；code 是退出码（被信号杀时 null）
proc.on("exit", ...)                   // 进程结束，但流可能还有数据——收输出要用 close 不用 exit
```

两个易混点：

- **error ≠ 命令失败**。`docker run` 返回非零退出码走的是 `close`（code≠0）；
  `error` 是 Node 层面根本没启动起来（ENOENT：docker 没装）。executor 用
  `failedToStart` 区分这两者，因为处理策略完全不同（环境坏了 vs 命令失败了）。
- **close ≠ exit**。exit 时 stdout 管道里可能还有没读完的数据。收输出必须挂
  `close`（它保证流已 flush）。本项目只用 close。

### 1.4 proc.kill() 与信号

`proc.kill("SIGKILL")`：向子进程发信号。默认 SIGTERM（可捕获、可清理），
SIGKILL（9 号）不可捕获不可忽略——立即死。executor 的三处 kill：

- 宿主超时兜底：docker CLI 自身卡死时强杀；
- abort 监听：/stop 时杀 CLI 进程（容器由任务级 docker rm -f 回收）。

被 SIGKILL 的进程 `close` 事件的 code 是 **null**（不是 0 也不是负数）——所以
finish 里有 `code ?? -1` 的归一化。

### 1.5 Promise 包装模式（runDocker 的形状）

spawn 是事件风格的，调用方要 await——标准包装：

```ts
return new Promise((resolve) => {
  const proc = spawn(...);
  // 挂事件 → 多路结束都汇到 finish() → settled 守卫保证 resolve 一次
});
```

"settled 守卫 + 单收口"是必须的：close / error / 超时 timer / abort 四条路
几乎可能同时触发，谁先到谁收尾（详见 executor.ts 的 finish 与文档外讨论）。

## 2. node:crypto 的 createHash——目录名哈希

`paths.ts`：

```ts
const hash = createHash("sha256").update(tenantKey(event)).digest("hex").slice(0, 32);
```

链式三步：`createHash("sha256")` 建哈希器 → `.update(数据)` 喂内容 →
`.digest("hex")` 出结果（十六进制字符串，64 字符，取前 32）。

用途：把 `group:ABC123` 这样的租户键变成 `a3f0…` 目录名——不可逆（openid 不
泄露到文件系统）、定长（不吃文件系统名字长度限制）、无特殊字符（路径安全）。

同类对比：`randomBytes(16)` 生成随机字节（项目里没用，容器名的 runId 用的
`Math.random().toString(36)`——随机性要求低，够用）。

## 3. node:fs——文件系统全家桶

工作台用到的全部是**同步**版本（`xxxSync`）。为什么同步可以：工具是串行执行的
（子 Agent 图的 tools 节点是 for 循环不是 Promise.all），同步 IO 不存在并发
阻塞问题；而且文件都 ≤1MB、目录 ≤200 文件，微秒~毫秒级，不会卡事件循环。

### 3.1 读侧

```ts
readFileSync(path): Buffer           // 整个文件读进内存。read-file.ts 用它 + toString("utf8")
readFileSync(path, "utf8"): string   // 直接按文本读。grep/edit 用
readdirSync(dir, { withFileTypes: true }): Dirent[]
                                     // 列目录。withFileTypes 拿到的是带类型判断的
                                     // 条目对象（isDirectory()/isFile()），比只拿
                                     // 文件名数组少 N 次 stat。glob/grep/usageOf 用
statSync(path): Stats                // 文件元数据：size、mtimeMs、mode…。
                                     // read 的 mtime 排序、grep 的体积预检、write 的回显 size 用
lstatSync(path): Stats               // stat 的"不跟随链接"版——路径段是 symlink 时
                                     // 返回链接自己的信息而不是目标。resolveWritePath
                                     // 的逐段防逃逸检查靠它（stat 会跟过去，就查不出"这段是链接"）
realpathSync(path): string           // 解析所有符号链接 + 归一化，返回"真身路径"。
                                     // 路径裁决的核心：比较发生在文件系统真相世界
existsSync(path): boolean            // 存在性检查（write 判断新建/覆盖）
```

**stat vs lstat vs realpath 三兄弟**（review 路径安全时的关键区分）：

```text
/workspace/leak → symlink → /etc/passwd

statSync("/workspace/leak")     → /etc/passwd 的信息（跟随了链接）
lstatSync("/workspace/leak")    → "这是个符号链接"这个事实本身
realpathSync("/workspace/leak") → "/etc/passwd"（字符串形式的最终真相）
```

防逃逸三件套用法：写路径逐段 **lstat**（发现段是链接即拒）→ 读路径
**realpath** 后做前缀裁决（真身必须在 workspace 内）。

### 3.2 写侧

```ts
mkdirSync(dir, { recursive: true })  // 多级创建不报错（已存在也 OK）。workspaceDirFor 建租户目录、write_file 建子目录
writeFileSync(path, content, "utf8") // 整体写入。注意：不是原子的（见下方坑）
renameSync(from, to)                 // 原子改名。同一个文件系统内是原子的——
                                     // "临时文件写完再改名"实现原子写
unlinkSync(path)                     // 删文件。写失败时清临时文件用
```

**原子写模式**（write-file/edit-file 都是这个形状）：

```ts
writeFileSync(tmpPath, content);   // 1. 先写临时文件（中途崩了留下的是 .tmp- 垃圾，不是半截正式文件）
renameSync(tmpPath, realPath);     // 2. 原子改名——读者要么看到旧全文，要么看到新全文，没有中间态
```

为什么要绕这一圈：writeFileSync 直接写目标文件，进程中途死掉会留下**半截内
容**；rename 在文件系统层是原子操作。glob/grep 遍历时跳过 `.tmp-` 前缀的文件
就是在配合这个模式（临时文件不是产物）。

### 3.3 chmodSync 与八进制权限

```ts
chmodSync(dir, 0o777)   // 显式改权限位
```

`0o777` 是八进制字面量（ES2015+ 写法；老代码的 `0777` 在严格模式非法）。三位
分别 = 属主/属组/其他人，每位是 r(4)+w(2)+x(1) 的和：7=rwx。`mkdirSync` 的
`mode` 选项受 **umask** 影响（root 默认 022 会吃掉写位），所以创建后再补一次
显式 chmod 才可靠——这是目录属主错位问题的根治代码。

## 4. node:path——跨平台路径操作

```ts
join("a", "b/c", "..", "d")     // 智能拼接 + 归一化 → "a/b/d"。比手写 + 稳（处理分隔符/边界）
relative(from, to)              // 从 from 到 to 的相对路径。glob 输出 "notes/data.csv"
                                // 而不是绝对路径，靠它
sep                             // 平台分隔符常量（Linux "/"，Windows "\\"）。
                                // 前缀裁决写 rootReal + sep 而不是裸 startsWith，
                                // 堵 "/ws/hash-evil" 误判在 "/ws/hash" 内的经典边界
dirname("/a/b/c.txt")           // → "/a/b"。原子写找临时文件该落的目录
```

**注意**：path 的归一化是**纯字符串操作**，不看文件系统——`join(root, "a/../b")`
会算出 `root/b`，但它不知道 `a` 在磁盘上是不是个链接。这就是为什么路径安全
不能只靠 path.join，必须叠加 realpath（§3.1）。两套世界的分工是 paths.ts 的
设计核心：**字符串层归一化（path）+ 真相层裁决（fs.realpath）**。

顺带：Windows 上 path 用 `\\`，本项目在解析用户输入时先 `replace(/\\/g, "/")`
归一（防模型手滑），输出给模型时用 `relative().replace(/\\/g, "/")` 归一——
生产在 Linux 无感，这些是本地开发/测试的兼容。

## 5. Buffer——字节的世界

```ts
Buffer.byteLength(content, "utf8")   // 字符串编码后的字节数。write 的配额检查用它——
                                     // 注意 string.length 是 UTF-16 码元数，中文 1 字
                                     // length=1 但字节=3，配额必须按字节算
chunk.toString("utf8")               // stdout data 事件给的是 Buffer，转字符串
content.includes(0)                  // Buffer 的 includes 数字 = 查字节值。0=NUL，
                                     // 二进制检测（git 同款启发式）
```

Buffer 是 Node 的二进制容器（定长、堆外内存）。工作台对它的使用都浅：字节计
数、编码转换、NUL 探测。需要记住的只有一件事：**文本长度 ≠ 字节数**，所有
限额（单文件 1MB、输出 64KB）都是字节口径。

## 6. RegExp——六件套里的模式匹配

glob 的段匹配把通配符翻译成正则：

```ts
pattern
  .replace(/[.+^${}()|[\]\\]/g, "\\$&")  // ① 先转义字面量里的正则特殊字符
  .replace(/\*/g, "[^/]*")               // ② * → 不跨分隔符的任意串
  .replace(/\?/g, ".")                   // ③ ? → 单字符
```

顺序有讲究：必须**先转义再替换** `*`/`?`——反过来的话第一步会把刚生成的
`[^/]*` 里的字符再转义一遍，规则全毁。grep 工具直接吃模型给的正则
（`new RegExp(pattern)`），编译失败 catch 后返回可自纠的错误文案。

## 7. 贯穿模式：同步 fs + 异步 spawn + 单事件循环

review 时容易疑惑的点，这里统一说透：

**为什么 fs 全同步、docker 全异步？**

```ts
const content = readFileSync(full, "utf8");        // 同步：阻塞到读完
const proc = spawn("docker", args);                // 异步：立刻返回，事件驱动
const result = await runDocker([...]);             // 异步包装成 Promise 后 await
```

- 文件操作微秒~毫秒级、串行执行——同步最简单，没有回调；
- docker 命令**秒级到分钟级**——必须异步，否则一条 60s 的 exec 会冻结整个 bot
  进程（事件循环被阻塞，webhook 收不了消息、QQ 会判定回调超时重推）。

同步 IO 在 Node 里是"知道自己在干什么"的特权用法：服务器主进程里长时间同步
IO 是大忌，工作台的用法成立仅因为操作小且串行。若将来 workspace 配额放大到
千 MB 级，usageOf 的递归统计（同步 walk）就该改异步或改增量记账。

**chunk 是什么**：`proc.stdout.on("data", chunk => ...)` 的 chunk 是 Buffer 片
段——流不保证按行、按字符边界交付，一坨一坨来。runDocker 的累积+截断逻辑
（`stdout += chunk.toString("utf8")`）在多字节字符被 chunk 边界切开时理论上
可能产生半个字符（utf8 变长编码）——64KB 截断场景下尾巴最多烂一个字符，对
"给模型看的输出"无害，工程上接受。（严格做法要 StringDecoder，这里不需要。）
