## 0. 全景：这次重构在解决什么

旧架构的一切问题可以追溯到同一个根源：**上下文是"每轮现场拼的快照"，而
不是"一条历史的稳定视图"**。滑动窗口让快照每轮都变（缓存全灭）；三条
调用路径各拼各的快照（system 家族分裂、碎念、token 双付）；记忆、身份、
指令混在快照里互相污染（长期记忆插队、昵称前缀烙进原文、finalize 重引
历史）。重构把它倒过来：**库是一条 append-only 的事件流（唯一真相），
每次模型调用时的上下文是这条流的一个无状态投影**。窗口、压缩、身份、
注入位次全部变成"投影时的读取规则"，流本身永不改写。

## 1. 上下文拼接：从滑动快照到稳定投影

### 旧的功能怎么样

存储层虽然 append-only，但读取用 `ORDER BY id DESC LIMIT 20` 的滑动窗口：
每来一条新消息（群聊里旁观者消息每条都入库），窗口头部就掉一条旧消息。
DeepSeek 的 KV 缓存按"从头开始的前缀完整匹配"计费生效（命中价约为
未命中的 1/50），窗口一滑，前缀从第一条历史消息处整体漂移——**跨轮命中
恒为零，只有 system 那一段能命中**。分析报告的量化示例：8k token 历史的
群每天 20 轮，稳定前缀本可以 19 轮全命中（约 $0.0009），现状全部按未命中
计（约 $0.046，50 倍）。且命中率直接影响首 token 延迟——秒回体感也吃这个亏。

另外三条路径的 user 侧各有污染：闲聊重答路径把长期记忆召回文本作为 user
消息插在数组**第二位**——每轮内容都变的召回排最前，等于每轮主动炸掉整个
前缀；工具收尾路径把历史**重新引用成一段平文本**塞进一条巨型 user 消息，
历史 token 双付、消息结构（工具配对、说话人边界）全部丢失，"这句话是谁
说的"在收尾时实际上是丢的。

### 新架构怎么解决

每次触发时从库**重新投影**出上下文：历史 user 消息渲染成
`{"speaker":"名字","content":"内容"}` 的 blob 行、按 bot 回复天然分批，
当前消息（u_now）独立成条恒在末位。投影是无状态的纯函数——同一批库行
永远渲染出同一批字节。缓存收益由此从结构上成立：无人插话的一问一答里，
上一轮的 u_now 下一轮原字节落进批里、上一轮的成品回复位置不变，**直通轮
每轮只 miss 新输入一条，与普通 agent 的理论最优持平**（工具轮因过程对
不跨轮投影，多付一次性的成品 miss，换不来更便宜，但换来了不发送过程对
= 不为几十 KB 的工具废料付缓存价）。

压缩不再动流：v10 终版只有两条纯投影规则——候选行超 200 条保留最近
200 行；行的创建时间距装配时刻超 2 小时离开投影。库永远全量，截断点每次
现算，规则可逆可调。旧设计里"写 reset 标记行永久清空"的方案（以及摘要
压缩计划）被整体废弃——标记行把截断持久化进流里，历史被永久丢弃且不可
恢复；纯过滤让同样的截断变成零迁移成本的查询行为。

已知残余（记录在案，接受）：群@消息与显式命令的批行字节与当轮 u_now 不
一致（库存原文含 `<@openid>` 标记/命令词），使该批行及其后进入一次性
miss（直通轮 1 块变 3 块）；修复方向（渲染端归一化）已留档未实施。

## 2. 记忆层级：一张表混两种职责 → 单表双投影

### 旧的功能怎么样

同一张表同时扮演两个角色：热窗口（20 条，拼进上下文）与冷档案（300 条，
recall_memory 检索）。两种角色对"什么该入库"的要求互相冲突，付出过三笔
实打实的学费：

1. **双写 bug**：入库决策分散在三个文件靠注释约定对齐，自动路由上线后
   约定静默失效——单聊说"你好"会被记两次（观察者记一遍、Agent 轮再记
   一遍）；
2. **覆盖缺口**：bot 出站消息没有统一落库点，/help、定时提醒推送、扑克
   快照等大量回复从不入库——冷档案号称"了解历史背景"，实际 bot 侧只有
   两个命令的输出存在，用户问"你上次推给我的那个"时半盲；
3. **检索切片污染**：表里混着 tool 过程行，冷检索按行号切区间时把工具
   原始输出误渲染成"assistant：{JSON}"——模型读到的历史背景里混着从没
   说出口的机器输出。

工具过程行跨轮进上下文还有协议暗雷：中断轮（/stop、宕机）会留下没有
配对的孤儿 tool 消息，投影出去 DeepSeek 直接 400，且此后该会话每条消息
都 400 直到人工修库——旧架构为此养着一个读取后修孤儿的补丁函数。

### 新架构怎么解决

一张 `conversation_events` 总表做唯一真相，两种**读取口径**分层：
**L2（转录层）**= QQ 窗口里实际出现过的一切（用户发言 + bot 成品回复，
不论出自哪个子系统）——QQ 没有历史消息 API，这是自建的地面真相，负责
recall 回查与未来长期记忆素材；**L1（上下文层）**= 每次模型调用实际注入
的 prompt（system + 历史投影 + u_now + 轮内过程段）。L2 单调累积永不
压缩；L1 每轮现算、带 v10 两条压缩规则。

根治手段是**每类事件恰好一个写入者**：入站在 dispatcher 收口（重推由
UNIQUE 约束吸收），出站在 QQ 发送层收口（发送成功才记，markdown 回退链
只记成功那次，瞬时进度提示显式排除）——双写与覆盖缺口从结构上消失，
/help 回复、提醒推送、扑克快照全部入档。agent 过程行改为图节点**就地**
写入（写到哪算哪，中断轮不再整轮丢失），且**永不跨轮投影**（v7 决议）：
跨轮只见成品（用户说了什么、bot 答了什么），孤儿配对问题结构性不可能，
修孤儿补丁随之退役。这个取舍的依据是场景判断：QQ 闲聊里上一轮的工具
过程对下一轮没有延续价值（成品回复已是蒸馏，缺细节重查一次即可），而
编码型 agent 的工具结果是工作材料本身必须跨轮——场景不同，取舍不同。

QQ 的消息重推（同一事件推两次）也在这层解决：`UNIQUE(key, qq_msg_id)`
+ INSERT OR IGNORE，重推静默吸收，天然去重。

## 3. Agent 运行时：三场景接力 → 单场景直通

### 旧的功能怎么样

一轮 /Agent 走五节点三场景：judge（纯功能规则判断要不要调工具）→
工具循环 → plainReply（换人设 system 重答）或 finalize（收尾 system 重述）。
三套 system 意味着三个缓存家族，每轮至少付两次全量 prefill。更深的伤在
真机上暴露：**碎念问题**——plain/finalize 的输入末位是 judge 的中间输出
（"我需要搜索一下…"），模型把这段尾随 assistant 当成"自己说到一半的
话"续写，用户收到的回复只剩后半句。v6 曾试图保留碎念（作为"正在思考"
的体验），真机证实提示词层无法根治——**结构信号强于文字信号**，只要
末位还是那段半截 assistant，续写错觉就不消失。此外 finalize 把 thinking
打开后撞上 DeepSeek 协议坑：思考模式要求 assistant 历史回传
reasoning_content，而重述路径永远拿不出这个字段，直接 400。

### 新架构怎么解决

v9 直通架构把三场景合并为一个 `agent_unified`：唯一的模型节点带全部工具
调用——不需要工具时输出**就是**最终回复（带人格直出），需要时进工具循环；
轮次触顶且模型还在要工具时走 forcedFinalize 降级分支（同一 system、同一
消息数组、撤掉 tools 字段 + 注入恒定终止信号，协议级逼出文本）。收益是
三重的：碎念作为中间产物**结构上不存在**（没有"换人设重答"的环节，就
没有半截话可续写）；system 家族统一（轮内各次调用共享完整前缀，第二次
调用起全命中）；降级指令与提示词里的终止信号语义同源（一处常量两处
消费，测试锚定一致）。保留 MAX_TOOL_TURNS=2 作为轮次兜底——token 预算
判定要等 usage 实测校准估算器后再上，未校准的估算器不做路由决策。

## 4. 提示词体系：两段拼接 → 模块化装配

### 旧的功能怎么样

system = 人格 + 单块功能文本。v9 合并三场景时把工具规则、说话人说明、
图片说明、收尾规则、输出格式全揉进一段，无层次可言——改任何一处都要
通读全文；说话人焦点规则在人格行为准则和功能文本里各写一遍（语义重复）；
降级指令在代码里硬编码一份、提示词场景里又存一份（双源漂移风险）；
说话人说明自标注"过渡版"， blob 格式的解释停在猜测阶段。

### 新架构怎么解决

仿 Claude Code 的模块化组织，system 分四段装配：**M1 核心身份与输入
格式**（我是谁 + blob 行格式契约 + 真实示例 + 图片转写说明 + 消息焦点：
末位单独成条 = 当前任务）；**M2 工具判断与规则**（通用准则 + 四个工具的
强触发细则 + 两条重点：不需要工具就直接答、见到终止信号立即停）；**人格
槽**（按租户注入，/set_personality 整块替换）；**M3 输出格式**。三个设计
决议值得记录：人格**中置**使 M1+M2 成为全部租户的公共前缀字节（挽回
v9 时"按租户各建缓存"损失的部分跨租户共享）；blob 示例与代码的行渲染
函数**测试锚定**（提示词说一套代码渲染另一套是最隐蔽的翻车）；降级
信号收口为单一导出常量。主 Agent 的 system 用专用装配函数直拼，不走
通用场景表——人格存取、模块常量、拼装逻辑同文件闭环。

## 5. 图片链路：占位符烙进原文 → 引用列外挂

### 旧的功能怎么样

旧设计把 `[图片:id]` 占位符**写进 content 原文**，读取时正则解析展开。
三个实证问题：多图消息的 UNIQUE 约束按文件名去重，而 QQ 一次 N 图的
N 个附件文件名/宽高可以全同——**静默丢 N-1 张**（真机日志见案发）；
内容与引用耦合，原文被占位符污染；图片清理（prune）的时机在消息行
落库**之前**——新图片刚入库还没有任何消息引用它，被清理逻辑当成孤儿
删掉（真机表现：日志说"图片入库"十张、表里空空、消息的引用列悬空）。

### 新架构怎么解决

content 只存 QQ 原文（含表情标签，一字不改），图片走独立附表 + 消息行的
引用列关联；UNIQUE 改为 (key, 消息id, 事件内序号) 钉死多图；识图描述
写后永不重写（同一行永远渲染同一个字符串——缓存前缀的确定性红线）；
prune 挂到消息行落库**之后**（引用已建立，新图不会被误判孤儿）。展开
时机一分为二：历史行懒展开（进窗口才识图），当前消息当轮展开（"当轮
就要看"）。视觉开关关闭时降级为裸 `[图片]` 标记，提示词按完整形态恒定
书写、不随部署配置分叉。

## 6. 可观测性：盲飞 → usage 直读

### 旧的功能怎么样

模型调用层只解析 choices，usage 字段（含 DeepSeek 特有的缓存命中/未命中
token 数）直接丢弃——缓存命中率、真实 token 成本、估算器偏差全部不可见，
重构收益无法证实。文件日志侧用内容指纹去重（同一段提示词当天只落盘一次
全文）——对排查友好，但多轮 Agent 的输入高度重复，全量持久化既没必要
也没法读。

### 新架构怎么解决

usage 四元组（prompt/completion/cache_hit/cache_miss）每次调用落一行
trace 日志——这是缓存契约从"理论推导"变成"可观测事实"的转折点（本轮
会话里正是官方文档 + usage 字段的存在让我们修正了一处缓存账的错误认知：
DeepSeek 每次请求固化两个前缀单元，用户输入末尾与**模型输出末尾**各一个，
模型输出本身是可缓存字节）。日志通道分工重排：全量请求输入/输出打
**控制台**（看现场用，不持久化），文件日志只保留**模型返回全文**
（解析出什么打什么——content、tool_calls 完整 JSON）+ usage 行；指纹
去重机制随之置空。

## 7. 这套新架构现在值多少分

工具调用准确率实验（85 场景 × 3 采样 = 255 次真实调用）给出第一份量化
基线：**有效工具选择准确率 92.6%、误调用率 0%、JSON 合法率与 schema
合规率 100%**。零误调用意味着"该不该调"的判断底线扎实（失败全是调多/
调少，没有乱调）；协议层零错误验证了 v7（过程不跨轮）与 v9（直通）的
结构正确性。实验同时暴露了两个非架构类的发现：金标装置本身欠维护
（get_time 前置规则是提示词 v2 新增的，旧金标没跟上——模型在服从我们的
规则却被判错）；以及**记忆真空期行为**——没有记忆工具时模型对"记一下
我怕辣"会口头承诺"记下了"，但当前架构兑现不了这个承诺（投影里只有
"说过承诺"，没有"被记的事实"），偶尔还会创造性代偿成几天后的提醒。
前者是装置债，后者是 M4 长期记忆落地前的真机风险点。

## 8. 遗留与后续

按方案文档与实验结论归档的未竟事项：token 驱动截断（等 usage 实测校准
估算系数后把条数判定换成 token 判定，上限刻意设低于模型上下文一半——
接近上限时模型能力会下降）；M2.2 工具细则按真机误判样本打磨（实验已给
出候选清单：get_time 触发词两向毛边、重复调用抑制、无 URL 场景的搜索
引导）；M4 长期记忆 skill 式 system 注入（插槽与纪律已预留——恒在
system 尾部、低频更新、体积设限，顺带消解记忆真空期问题）；A/B 对照
实验作废（架构换代使旧对照实例不可复现，本轮实验即新基线）；真机四项
验收（重推恰一行、两发命中、recall 出摘要、/stop 不留投影）待部署后
执行。
