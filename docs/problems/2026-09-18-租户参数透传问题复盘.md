# 复盘：租户身份参数的透传问题——从 kb_search 的 scope 注入说起

> 日期：2026-09-18
> 状态：§4.1 的泛化已于同日实施完成（统一注入表 + schema 剥离，见 §6 重构落地）；"通用租户上下文"（AsyncLocalStorage）仍是待办，按 §4.4 触发条件推进
> 关联：`2026-09-02-MCP接入层设计方案.md` §6.2、`2026-09-04-知识库RAG-MCP方案.md` §6.2、bridge.ts / adapters.ts / registry.ts / tools/arg-injectors.ts

## 1. 问题是什么

一句话：**工具需要知道"现在是替谁做事"（租户身份），但我们从来没有一个受控的通道把这个身份传进工具调用——模型能看到的参数模型就能填，而模型填的租户身份不可信。**

具体到这次撞上的实例：`kb_search(query, top_k, scope)`。scope 标识"查哪个群/哪个人的知识库"，是租户隔离键。它出现在工具参数里，意味着模型对它有填写权——而模型会瞎编、会猜、会把上一个会话的 scope 带过来。只要 server 相信了这个参数，A 群的用户就能诱导模型查出 B 群的知识库。**租户隔离不能建立在模型自觉上。**

这个问题的普遍形态：

```
工具参数 = 模型可填部分（query、top_k、提醒内容…）
         + 模型不可填部分（scope / owner / openid / 页面池键…）   ← 后者从来没有受控通道
```

## 2. 为什么现在才暴露

三层原因，层层递进：

1. **原生工具靠"schema 缺失"隐式防御**：`set-reminder`、`add-memory` 的 inputSchema 里根本不声明 openid/owner 字段，模型塞不进函数调用参数。工具实现在 run 里自己调 `sessionKey(ctx.event)` 算身份。能防住，但这是**靠巧合不靠机制**——某天 schema 手滑声明了身份字段，防线静默消失。
2. **MCP 工具的 schema 不可控**：`parameters: mcpTool.inputSchema` 从 server 的 tools/list 原样透传给模型。kb_search 必须在 server 端声明 scope（server 要知道查哪个库），于是 scope 字段**必然**出现在模型眼前——原生工具能藏，MCP 工具藏不了。
3. **现有两层加工机制都做不到"改参数"**：
   - 适配器层（adapters.ts）拿到的是**调用结果**——查询已经发出去了，改参数晚了；
   - client 层（client.ts）是哑管道，故意不知道业务语义。
   - 缺的是**调用前的参数改写点**。

## 3. 已落地的最小修复（MCP 侧）

bridge.ts 新增**前置参数注入器**，与适配器层（后置结果加工）镜像：

```ts
type ArgInjector = (args, ctx) => Record<string, unknown>;
const argInjectors = new Map<string, ArgInjector>();        // key: "server:tool"

registerArgInjector("kb:kb_search", (args, ctx) => ({
  ...args,                      // 模型保留 query/top_k 的发言权
  scope: kbScope(ctx.event),    // scope 无条件覆盖：从当前消息事件算出
}));

// wrapMcpTool 的 run 内、callTool 之前：
const finalArgs = injectMcpArgs(serverName, toolName, args, ctx);
```

性质：**opt-in**（没注册的工具原样透传，其他服务器零影响）；与适配器一前一后夹住 callTool，补全"桥接层管语义"的拼图。server 端 kbSearch 对 scope 格式的二次校验保留（纵深防御，两端不互信）。

## 4. 未解决的部分（本复盘的真正产出）

### 4.1 机制只覆盖 MCP，原生工具体系没有对应物（✅ 已于同日重构解决，见 §6）

`runTool(name, args, ctx)`（registry.ts）直接分发 `tool.run(args, ctx)`，没有参数净化点。原生工具的身份获取散落在各工具 run 里自调 `sessionKey(ctx.event)`——重复、无强制、依赖 schema 不声明身份字段的默契。

~~泛化方向（已明确但未实施）：把注入点提到 `runTool`，原生与 MCP 工具共用一张注入表。~~ **触发条件提前兑现**：当日即完成了这个泛化（机制设计过程中确认它值得立即做，而非等第三个工具），方案与落地见 §6。

### 4.2 更根本的：我们缺一个"租户上下文"的载体（本次讨论的核心开放问题）

注入器解决的是"在调用前改写参数"，但它内部调 `kbScope(ctx.event)` / `sessionKey(ctx.event)`——**身份的源头仍然是 MessageContext 显式传参这条老路**。设想这些场景它就不够用了：

- 工具内部再调子服务（如工具调 embedding、调另一个工具），身份要一路手动透传；
- 将来流水线/异步任务（worker 处理某条目时）不在消息处理的调用栈里，ctx 不存在；
- 多处需要同一身份时（scope、sessionKey、页面池键），各算各的，口径可能漂移。

自然的想法是"搞个全局单例，工具随时读"——**这正是单例模式的经典误用场景**。单例意味着"当前租户"是全局状态：并发处理两个会话的消息时互相踩踏（Node 单线程但 async 交错，A 的 await 间隙 B 写了全局变量）；异步任务跨 await 后读到的是别人的身份；测试无法隔离。**并发安全地"随取随用"，答案业界已收敛：请求级上下文（per-request context）——AsyncLocalStorage。**

### 4.3 候选方案：AsyncLocalStorage 作为租户上下文载体

Node 内置的 `AsyncLocalStorage` 提供的正是"看起来像全局、实际按异步调用链隔离"的语义：

```ts
// tenant.ts（设想）
import { AsyncLocalStorage } from "node:async_hooks";
export const tenantALS = new AsyncLocalStorage<{ scope: string; sessionKey: string }>();

// 入口（handler 处理消息处）建立上下文——整条异步链（工具/子服务/await）都能读：
tenantALS.run({ scope: kbScope(event), sessionKey: sessionKey(event) }, async () => {
  await runCommand(ctx);   // 或 runObservers / agent loop
});

// 任何深度的工具实现里：
const tenant = tenantALS.getStore();   // 拿到本调用链的身份，并发链互不可见
```

它满足"像全局单例一样随时看"的体感，又天然避开单例的三个坑：并发链隔离（每条异步链一份 store）、跨 await 稳定（同一链内不变）、测试可各自 run 独立上下文。**这正是"我知道该用什么但还不知道叫什么"的那个东西的名字。**

取舍与边界（诚实记录）：
- AsyncLocalStorage 有微小性能开销（V8 已优化到可忽略的量级）；
- 它只覆盖"同一条异步链"——**真正的后台任务（worker、cron）没有请求上下文**，身份必须作为任务数据的一部分显式携带（我们的 worker 正是这么做的：scope 存在 entries 表行里，不依赖上下文）——这不是缺陷，是"请求态进 ALS、持久态进数据"的正确分层；
- MCP server 端（MCP_RAG 项目）是另一进程另一端点，不存在 ALS 传播——跨进程的身份永远走参数（scope）+ 鉴权（token），这也是两端各校验一次的原因。

### 4.4 建议的演进路径（不急着做，按触发条件推进）

1. **现在**：MCP 注入器（已上线）+ 本复盘归档。原生工具维持现状（schema 不声明身份字段 + run 内自查）。
2. **触发条件 A**（第三个需要注入的工具出现，或某原生工具 schema 必须声明身份字段）：把注入表上浮到 `runTool`，统一原生/MCP。
3. **触发条件 B**（出现"工具的深层调用也需要身份"或"身份获取口径开始漂移"）：引入 tenant.ts（AsyncLocalStorage），入口建立、深层读；注入器和工具实现改为从 ALS 取，`kbScope(ctx.event)` 退化为入口处的种子。
4. **永不变化的两条底线**：身份永远不信任模型参数（注入器/ALS 在调用链入口确立，模型传的同名参数一律覆盖）；跨进程（bot→端侧 server）身份永远走参数+鉴权双通道。

## 5. 经验沉淀

- "模型能看到的参数模型就能填"——给模型声明参数时先问一句：这个字段我信得过模型的填写吗？不信就移出 schema（原生工具）或加注入器（MCP 工具）。
- 适配器（后置加工）和注入器（前置改写）是镜像机制，一个工具调用链的两端护栏；只补一端就会出现这次的"拿到结果才发现参数错了"。
- "全局随时可读"的需求先别上单例——并发下当前值属于谁？答案几乎总是 per-request context（Node 侧即 AsyncLocalStorage），后台任务则把身份显式存进任务数据。
- 防御要机制化：靠 schema 缺失、靠工具自觉，都是把安全性寄托在每个人的记性上。

## 6. 重构落地（2026-09-18 同日）：统一参数注入表 + schema 剥离

§4.1 的泛化当日实施。设计前参考了 armani_agent（内部成熟项目）的同类机制，采纳其"保留字三点联动"的分层思想（schema 隐藏 → 分发前过滤 → 分发时注入），明确不采纳其 MCP 进程级静态身份（单租户凑合解，我们的多租户 scope-per-call 更正确）。

### 6.1 机制：一张表、两个切面

新建 `src/agent/tools/arg-injectors.ts`——统一注入表，与工具实现解耦（注入器集中注册，key 用注册表里的工具名；MCP 工具即 `mcp_<server>_<tool>` 包装名，与全局注册表同一命名空间，bridge 私有的 `server:tool` 键空间退役）：

```ts
export interface ArgInjectorEntry {
  inject: (args, ctx) => Record<string, unknown>;  // 调用前改写；返回值无条件覆盖模型传参
  hideFromModel?: readonly string[];               // 这些字段从发给模型的 schema 里剔除
}
```

接线三处，全部在分发/渲染层，工具自身零感知：

1. **runTool 净化切面**：`agent/registry.ts` 与 `deep-search/registry.ts` 的 runTool 在 `tool.run` 之前 `applyArgInjector(name, args, ctx)`——原生与 MCP 工具经同一处分发，机制一体生效（与 progressNote 切面并排，runTool 成为统一的切面汇聚点）；
2. **schema 渲染剥离**：`toolSchemas()` 渲染时过 `stripHiddenParams(tool.name, parameters)`——properties 剔除 + required 同步剔除 + 浅拷贝不动原对象（MCP 的 inputSchema 来自 server，保持原样利于比对）；
3. **MCP 包装接线**：`wrapMcpTool` 的 `parameters` 同样过 stripHiddenParams——server 端声明的 schema 我们改不了，渲染时剥是唯一机会。

### 6.2 与 §3 最小修复的差异

| | §3 最小修复（已退役） | §6 重构（现行） |
|---|---|---|
| 覆盖范围 | 仅 MCP | 原生 + MCP 统一 |
| key 空间 | bridge 私有 `server:tool` | 注册表工具名（一张表） |
| 防线 | 注入覆盖（单层） | schema 隐藏 + 注入覆盖（两层：模型看不见字段 → 填了也被覆盖） |
| 注册位置 | bridge.ts 内 | arg-injectors.ts 集中声明 |

kb_search 的注入器原样迁入（scope 无条件覆盖语义不变），新增 `hideFromModel: ["scope"]`——模型从"看得见但填了会被覆盖"升级为"根本看不见"。

### 6.3 明确不做

- 原生记忆工具（add/delete/clear/recall）不加注入器：它们的身份获取（schema 本就不声明身份字段 + run 内自算 `memoryKey(ctx.event)`）本来就是正确形态，机制就位、按需注册，不为重构而重构；
- 不做 armani_agent 式的签名白名单过滤（它是 Python 动态语言的便利；我们是显式 schema 对象，hideFromModel 清单写在注入器注册处即可达成同语义）；
- AsyncLocalStorage 仍按 §4.4 触发条件 B 挂起——注入器签名继续吃 ctx（调用链里现成），ALS 是"深层调用也需要身份/口径漂移"出现时才值得引的一层。

### 6.4 验证

七项断言全过（test 临时脚本，已清理）：模型伪造 scope 被覆盖为当前会话的、query/top_k 发言权保留、未注册工具参数原样透传、scope 从 properties 剔除、required 同步剔除、原 schema 对象未被修改（浅拷贝语义）、未注册工具 schema 原样。typecheck 通过。行为变化仅一处且是收紧：模型调 kb_search 时不再能看到 scope 参数。
