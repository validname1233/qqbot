## TL;DR

1. **存储层本来就是 append-only 的**（SQLite 行只插入不修改）。"滑动窗口"是**读取口径**（`ORDER BY id DESC LIMIT 20`）造成的：窗口一滑，请求前缀就从第 1 条历史消息处漂移，缓存全部失效。群聊里观察者每落一条 bystander 消息窗口就滑一格，所以现状命中率≈只有 system prompt 那一段。
2. user message 数组的污染源有三处：写入时烙进 content 的「昵称：」前缀、`plainReply` 里插在数组前部的长期记忆文本、`finalize` 里把历史重新引用成的大段提示文字。前缀是数据（需要保留语义但要结构化），后两处是真问题。
3. DeepSeek 缓存**默认开启、无需参数**，规则是**前缀完整匹配**；命中价格是未命中的 **1/50**（flash：$0.006 vs $0.30 / 百万 token）。设计约束只有一条：**稳定的东西放前面，每轮变化的东西放后面，压缩是唯一允许的前缀重置点**。
4. 目标消息形态：`[system(恒定)] + [摘要槽(仅压缩时变化)] + [逐字历史(append-only)] + [动态注入(不落库)] + [当前消息]`。身份标注从"content 前缀"升级为结构化方案（`name` 字段或渲染层标注，需先做探针）；finalize 改为直接复用真实消息数组，不再重新引用历史。
5. 用户未覆盖、本文补充的问题：缓存淘汰与低流量的现实预期、`name` 字段支持度未知、说话人标注可伪造（现状用户自己就能打出「张三：」冒充别人）、渲染确定性不变量（图片描述缓存）、三套 system 缓存家族并存的成本、append-only 后的 token 预算闸门、旧数据迁移。见 §6。

## 1. 现状盘点：上下文今天是怎么拼出来的

### 1.1 存储层：已经是 append-only 的行存储

`src/agent/memory/sqlite.ts`，表 `short_term_messages`（`sqlite.ts:46-62`）：每条消息一行，带 `key`（租户键）、`role`、`content`、`tool_calls`、`tool_call_id`，user 消息额外带 `author_openid` / `author_name`。**写入只有 INSERT**（`append`，`sqlite.ts:181-199`），旧行从不修改。表无限累积，"20 条热窗 / 300 条冷窗"都只是读取口径（文件头注释 `sqlite.ts:5-9`）。

也就是说：**用户想要的 append-only，存储层已经具备**。问题出在后面两层。

### 1.2 读取层：热窗口

`get()`（`sqlite.ts:164-179`）用 `ORDER BY id DESC LIMIT 20` 取最新 20 条再反转。这就是"滑动窗口"的实现：每来一条新消息，窗口头部就掉一条旧消息。

配套的防御：`dropOrphanToolHead`（`loop.ts:129-137`）——窗口切割可能把 `assistant(tool_calls)` 和它的 `tool` 回话切开，头部留下没有爹的孤儿 tool 会让 DeepSeek 直接 400，所以读取后丢弃头部连续孤儿（2026-09-24 事故的修复）。

### 1.3 组装层：三条调用路径的 messages 形状

/Agent 一轮流程（`loop.ts` 五节点图）中，实际发给模型的 messages 有三种形状：

**路径 A —— judge（工具判断）**，`prepareContext` 拼装（`loop.ts:111-115`）：

```
[ system(agent_judge，纯功能规则，全租户相同) ,
  ...history(≤20条，content 已带「昵称：」前缀、图片已展开) ,
  当前 user 消息(带「昵称：」前缀) ]
```

**路径 B —— plainReply（没调工具的闲聊重答）**（`loop.ts:250-256`）：

```
[ system(人格+daily规则) ,
  user("以下是关于当前对话的长期记忆（可能有助于理解上下文）：…") ,   ← 每轮内容都变
  ...history ,
  当前 user 消息 ]
```

**路径 C —— finalize（调过工具后的收尾）**，`synthesizeFinalReply`（`loop.ts:176-213`）：不发消息数组，而是把历史**重新引用成一段平文本**，塞进一条巨型 user 消息：

```
[ system(agent_finalize，人格+收尾规则) ,
  user("以下是最近的对话记录（供参考上下文）：\n{role}：{content}…
        \n\n用户现在想要实现的需求是：{userText 原文}
        \n\n以下是为完成这个需求而调用工具得到的结果：…
        \n\n请你根据以上对话记录和工具结果，直接给用户一段完整、自然的最终回复…") ]
```

另外每条路径内部：judge 调完工具后带着追加了的消息再进 judge（轮内 append-only）。

### 1.4 提示词层

`getSystemPrompt(event, scene)`（`builder.ts:29-42`）= 人格（租户自定义或默认）+ 功能规则（按场景），纯功能场景（`agent_judge` 等）只返回功能规则。system 侧本身是干净的、每租户每场景内容恒定——**system 没有问题，问题全在 user 侧的动态注入**。

## 2. 问题分析

### 2.1 缓存为什么命中不了（对应诉求 1）

**DeepSeek 缓存机制要点**（官方文档）：

- 硬盘 KV 缓存，**默认开启、无需任何参数**；
- 命中判定是**前缀完整匹配**：每个已落盘的缓存前缀是独立完整单元（受 Sliding Window Attention 影响），部分重叠不算命中；
- 前缀落盘时机：请求边界（用户输入结束处、模型输出结束处）、**跨请求公共前缀检测**、长文本按固定 token 间隔；
- 构建秒级；不用后数小时到数天自动清空（尽力而为，不保证命中）；
- `usage` 返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 可观测；
- 价格（每百万 token，峰值）：flash 命中 $0.006 / 未命中 $0.30（**50 倍**）；pro 命中 $0.044 / 未命中 $1.32（30 倍）。输出不计缓存。

**逐路径分析现状：**

| 路径 | 前缀稳定性 | 结论 |
|---|---|---|
| A judge 跨轮 | 第 N 轮发 `[S, m1..m20]`，第 N+1 轮窗口滑成 `[S, m2..m21]`——从 m1 掉出窗口那一点起全部漂移 | 只命中 `[S]`（约 1k token）。**群聊里 memory-log 观察者（`memory-log.ts:32-53`）每条非命令消息都 append 一行，窗口每条消息都在滑**，judge 跨轮命中恒为 system 一段 |
| A judge 轮内（工具循环） | messages 只在尾部追加 | **现状唯一稳定命中的受益者**，保持 |
| B plainReply | 长期记忆 user 消息插在 index 1，每轮 query 不同→召回内容不同 | 从第 1 条消息就漂移，**全 miss**（除 system 段） |
| C finalize | 每次都是两条全新消息 | 天然无可复用前缀；且把历史引用成平文本重复支付了整段 history 的 token |

**量化示例**：一个群 8k token 的有效历史、每天 20 轮 /Agent。若前缀稳定，19 轮可以命中（flash：19 × 8k × $0.006/1M ≈ $0.0009）；现状窗口滑动使这 19 轮全按未命中计（≈ $0.046）。绝对值不大（个人 bot 流量低），但**比例是 50 倍**，且命中还直接降低首 token 延迟（省掉 prefill 计算）——对"群聊里 @bot 秒回"的体感是有意义的。

**根因一句话**：滑动窗口让"前缀"变成了"最近 N 条"，而缓存的契约是"从头开始一字不差"。两者数学上不兼容，不是参数问题，是结构问题。

### 2.2 user message 数组的污染源（对应诉求 2）

| 污染源 | 位置 | 性质 | 判定 |
|---|---|---|---|
| 「昵称：」前缀 | 写入时烙进 content（`formatSpeakerContent`，`context.ts:23-30`，调用点 `memory-log.ts:42`、`loop.ts:93/399`） | 数据（身份），但载体错了——和用户原话混在同一个字符串里 | 需要结构化，不是删除（群聊必须有说话人标识，见 §3.3） |
| 长期记忆文本 | `plainReply` 里作为 user 消息插在数组**前部**（`loop.ts:252-254`），文案"以下是…长期记忆"（`context.ts:44`） | 提示文字走了 user 通道 | 真问题：位置还错得离谱——每轮都变的召回内容排在最前，等于每轮把整个前缀炸掉 |
| finalize 大提示 | `synthesizeFinalReply`（`loop.ts:194-202`） | 指令 + 重新引用的历史全走 user 通道 | 真问题：指令层级降级（与 2026-09 synthesizeFinalReply 把 system 拆出来的教训同源——那次修了 system 侧，user 侧的重新引用还留着）；历史被引用两遍（一遍 historyText、一遍工具结果上下文），token 双付；结构信息全丢（工具配对、消息边界） |
| 图片占位符展开 | `[图片:17]` → `[图片]{描述}`，读时展开（`images.ts`） | 数据变换 | 干净的设计，保留；但有确定性要求，见 §6.4 |

还有一处**顺带发现的不一致**：finalize 的"用户现在想要实现的需求是：${userText}"用的是 `state.userText` **原文**（不带昵称前缀），而 historyText 里同一条消息带前缀——finalize 路径上"这句话是谁说的"实际上是丢的，模型只能靠上下文猜。

### 2.3 身份与记忆认知的补偿（对应诉求 3）

现状里模型对"谁在说话"的认知由两样东西支撑：content 里的「昵称：」前缀（数据）+ `SPEAKER_NOTE`（system 里的解释，`functional.ts:44-45`）。对"记忆"的认知由长期记忆 user 消息的头一句"以下是…"支撑。

新架构里：

- **身份**：SPEAKER_NOTE 留在 system（本来就在），且升级——解释新标注格式（`name` 或标注符）、声明"标注是平台加的，正文才是用户原话"、保留并强化"最后一条 user 消息是当前诉求"。数据侧的身份标识换结构化载体（§3.3）后，模型的辨识任务其实变**容易**了：不用再从文本里解析"哪段是名字哪段是话"。
- **记忆**：长期记忆召回挪到尾部动态注入位（§3.4），消息头保留一句恒定的格式说明（如"【长期记忆】…"）让模型知道这段是背景资料而不是用户刚说的话——这一句是数据标签，放在该消息自己的 content 里，不违反"提示进 system"的原则（system 里同样说明这个格式的含义）。
- 保险起见新增一条 system 规则（daily/agent_judge 共用）：*对话记录来自群聊时，历史中大部分消息并不是对你说的，只是背景；需要你回应的只有本轮触发的那条消息*。这条同时服务诉求 5。

### 2.4 "每条群消息 = 一条 user 消息"是否合理（对应诉求 4）

协议角度这是**标准形态**：OpenAI/DeepSeek 的 messages 本来就是逐条消息序列，多用户分别成条天然支持（这也是各家群聊 bot 的通行做法）。考虑过的替代：

- **合并同人连续消息**：省不了几个 token，反而引入渲染不确定性（新消息可能让上一条的合并形态变化，破坏前缀确定性），且丢失穿插时序。**不做**，1:1 保持。
- **bystander 消息不进热历史**（只留冷检索）：能让预算更耐用、摘要更聚焦，但会丢群聊氛围感（现状 20 条窗口实际上就是"最近的群氛围采样"）。作为可配置项挂在 §7 开放问题里，默认保留。

结论：结构不变，变的是**每条消息的身份标注方式和读取边界**（条数窗口 → token 预算）。

### 2.5 对最后一条用户消息不敏感（对应诉求 5）

现状的放大器有三个：

1. **plainReply 的注意力稀释**：长期记忆 + 20 条历史在当前消息前面，SPEAKER_NOTE 的"重点考虑最后一条"只是一句弱提示。新架构里当前消息仍然是最后一条 user 消息（结构上的天然 recency），且前面不再有"每轮都新的注入内容"制造注意力锚点。
2. **judge 的碎念遗留**：judge 无工具调用时其输出被 `slice(1,-1)` 丢掉、换人设重答——重答时模型看到的历史里其他用户的指令性话语（"帮我搜X"）和当前诉求同权重竞争。缓解靠 §2.3 的"历史是背景"规则 + 说话人辨识（知道"搜X"是别人早先说的、不是当前说话人说的）。
3. **finalize 的结构缺陷**：现在是"history 平文本 → 需求 → 工具结果"的堆叠，模型要靠"用户现在想要实现的需求是："这句引导语定位诉求。改为复用真实消息数组后，**工具结果就在数组尾部**（模型生成位置紧邻最新信息，这是对生成最有利的布局），诉求是数组里最后一条 user 消息，末尾再跟一条**恒定的**收尾指令。位置信号替代文字引导。

一句话：末条敏感问题的根治不是加更强的提示词，而是**让结构自己说话**——当前消息恒在尾部、身份可辨、历史明确降级为背景、动态注入不再插队。

## 3. 目标架构

### 3.1 总原则：稳定前缀 + 尾部追加

```
┌─────────────────────────────────────────────────────────────┐
│ system prompt          恒定（每租户×每场景一个字符串）          │  ← 缓存家族锚点
├─────────────────────────────────────────────────────────────┤
│ 摘要槽（可选）          仅压缩发生时变化                       │  ← 唯一的合法前缀重置点
├─────────────────────────────────────────────────────────────┤
│ 逐字历史 verbatim      append-only，token 预算内全量带入       │  ← 缓存主体
├─────────────────────────────────────────────────────────────┤
│ 动态注入（长期记忆）     每轮变化，不落库，只在尾部             │  ← 永不污染前缀
├─────────────────────────────────────────────────────────────┤
│ 当前消息               恒为数组最后一条 user 消息              │  ← 诉求焦点
└─────────────────────────────────────────────────────────────┘
```

三条路径的目标形态：

```
judge:    [S_judge,              ...verbatim,                    u_now]
plain:    [S_daily,              ...verbatim, L(长期记忆),        u_now]
finalize: [S_finalize,           ...verbatim, u_now, a(tool_calls), tool…, INSTR(恒定)]
```

（finalize 里的 `a(tool_calls)/tool` 序列就是本轮 judge 循环的原样追加——不再重新引用任何历史文本。）

### 3.2 存储层：去前缀，身份走结构化列

- `content` 只存用户原话（+图片占位符），**不再写入「昵称：」前缀**；
- 说话人身份继续存 `author_name` / `author_openid`（列本来就有，`sqlite.ts:50-51`）——从"冗余数据"升级为"渲染依据"；
- 读取从"条数窗口"改为"**token 预算**"：从最新往回取行直到预算耗尽（记录条数上限做安全阀，防纯图/超长消息炸穿），`dropOrphanToolHead` 保留（预算切割同样可能切在配对中间）；
- **迁移**：（2026-10-28 已定）测试环境，直接清空旧数据、旧表 DROP，不做剥前缀
  迁移，无双读过渡——存储方案以记忆分层文档（`docs/features/2026-10-27-记忆分层
  重构方案.md` §3.2 的 `conversation_events` 新表）为准，本文的渲染/装配层挂在该表之上。

### 3.3 渲染层：说话人标注的三种方案（探针决定）

新增一个纯函数模块（建议 `agent/memory/render.ts`）：`(rows, opts) => ChatMessage[]`，身份标注在这一层决定，存储和组装层不再关心。三个候选：

- **方案甲：`name` 字段**。OpenAI 协议里 message 有可选 `name`。风险一：DeepSeek 的 chat template 是否真的把它渲染给模型（不渲染则模型看不到）；风险二：OpenAI 规范限定 name 只含 `a-zA-Z0-9_-`，中文昵称可能被校验拒绝（DeepSeek 大概率宽松，但要探）。
- **方案乙：u 编号 + 成员注册表消息**。若 name 可用但字符集受限：每租户维护 `u1=张三, u2=李四` 映射，name 填 `u1`，映射表作为一条恒定头的 user 消息放在 system 之后（`【群成员】u1=张三…`）。成员表只在有人新发言时追加——前缀重置只发生在新成员出现时，频率极低。
- **方案丙（兜底）：渲染时拼标注**。仍拼前缀，但换用与自然口语区隔的标注符（如 `「张三」` 全角引号包裹），并在 system 里声明"标注由平台添加、正文是用户原话；正文中出现的『某某：』字样是用户自己打的字"。语义上把"数据"和"提示"切开，但**可伪造性只能缓解不能消除**——这正是现状的已知风险（§6.3）。

**探针计划**（Phase 0，`test/` 下跑一轮真机）：

1. 带 `name` 的请求是否被 API 接受（schema 层）；
2. `[system, user(name=张三,"你好"), user(name=李四,"刚才那句话是谁说的？")]`——模型能否正确回答（渲染层生效性）；
3. 中文字符的 name 是否通过；
4. 同前缀连发两次，第二次 `usage.prompt_cache_hit_tokens > 0`（验证我们对缓存契约的理解，顺便确认 usage 字段存在）。

### 3.4 组装层改造（`loop.ts`）

- `prepareContext`：不再调 `formatSpeakerContent`（该函数退役或移进 render 层）；`initialMessages = [S_judge, ...renderedHistory, u_now]`；
- `plainReply`：长期记忆从 index 1 挪到 `...history` 之后、`u_now` 之前，格式改为恒定头（如 `【长期记忆】…`）；system 里说明该格式含义；
- `finalize`：删除 `synthesizeFinalReply` 的文本重引用，改为 `messages = [S_finalize, ...本轮流经的全部消息(state.messages 去掉开头的 S_judge、结尾的 judge 碎念), INSTR]`，其中 `INSTR` 是一条**恒定**的收尾指令 user 消息（如"请基于以上对话与工具结果，直接给出对用户的最终回复。"）。工具配对结构原样保留，诉求（u_now）与工具结果的位置信号天然成立。

### 3.5 system prompt 改造（`functional.ts`）

`SPEAKER_NOTE` 升级为三段式（按探针结果填第一段的具体格式）：

1. 说话人标注格式说明（name / 「」标注，平台添加、正文为原话）；
2. 群聊背景规则：历史大多不是对你说的，只回应本轮触发的那条消息；
3. 焦点规则：最后一条 user 消息是当前诉求（保留现有表述）。

`agent_finalize` 里"你能看到的是…对话记录和工具结果"的措辞同步微调（新结构下模型看到的是真实消息序列）。

### 3.6 压缩管线（概要设计，细节留待后续）

- **触发**：verbatim 段 token 估算超过预算（如 8k~12k，config 项）时压缩——不是按条数。估算用字符启发式（中文 ≈0.6 token/字、英文 ≈0.3 token/字符，×1.2 安全系数；不需要精确 tokenizer，预算闸门允许粗估）；
- **形态**：把最老的一段（如 verbatim 的前半）交给 LLM 生成摘要，摘要落库为一条 user 角色、恒定头（`【早期对话摘要】`）的消息，占据"摘要槽"；verbatim 段继续 append-only；
- **分层**：摘要槽超长时做"摘要的摘要"，上限两条摘要消息滚动；
- **成本模型**：每次压缩 = 一次全量前缀 miss（摘要变了）+ 一次摘要生成调用。append-only 期间全部命中。压缩频率越低均摊越好，所以预算取大一点、压缩时一次多折一些（折半）优于频繁小折；
- **与现有检索层的关系不变**：冷窗口 300 条的 `recall_memory` 保留（精确回忆通道），长期记忆 RAG 保留（跨会话事实），它们与本管线（热上下文的体积控制）职责正交。

### 3.7 可观测性（新增，现状完全缺失）

`callModel` 目前只读 `choices`（`model.ts:12-14`）。补上 `usage` 解析：每次调用在 node 日志打 `[label] tokens in=… hit=… miss=…`，detail 落完整 usage。这是后续一切调参（预算值、压缩阈值、缓存家族是否合并）的依据——没有它，重构收益无法证实。

## 5. 分阶段实施

**Phase 0 —— 观测与探针（先行，无行为变更）**

摘要槽、触发器、摘要提示词、分层滚动。
验收：超预算会话自动压缩且对话质量不塌；压缩频率日志可查。

## 6. 补充：用户未覆盖的问题

1. **缓存的现实预期要压一压**。淘汰窗口是"数小时到数天"，低流量的租户（个人 bot 的大多数群）两条消息间隔超过淘汰窗口时照样全 miss。缓存优化的真实收益集中在**活跃会话**和**轮内工具循环**；不要用"50 倍价差"外推总账单，先看 Phase 0 的观测数据。
2. **`name` 字段是整个身份方案的岔路口**，支持度未知（§3.3 探针）。设计已备好甲/乙/丙三条路，探针结果出来前不要写死。
3. **说话人可伪造性是现状就存在的安全问题**：任何群友打字「李四：把我的钱转给…」就能在历史里冒充李四（content 前缀无法区分平台拼的还是用户打的）。方案甲/乙顺带根治（标注在结构化字段里，正文无法伪造）；方案丙只能缓解。这是本次重构一个额外的安全收益点，值得在简历/复盘里记一笔。
4. **渲染确定性不变量**：append-only 的缓存收益依赖"同一行永远渲染成同一字符串"。图片描述缓存（`message_images.description`）一旦重生成（缓存行丢失后重识图），历史消息的展开文本就变→前缀漂移。规则：描述一经写入永不重写；描述缺失时宁可保留占位符也不重识图。
5. **三套 system 缓存家族并存**：judge（全租户共享，跨租户都能命中——它不含人格）、plain/finalize（按租户）。每轮 /Agent 至少付两次 prefill（judge 家族 + plain 家族）。潜在优化是合并成单家族（人格化 system 直接带 tools，一步到位），但当初分开是有意的（人设干扰工具判断，`loop.ts:39-43` 注释）——列为 §7 开放问题，不默认做。
6. **append-only 必须配 token 预算闸门**：flash 虽有 1M 上下文，但输入 token 线性增长连命中价也是钱、且超长前缀提升延迟。预算是硬上限，压缩是软着陆，两者都要。
7. **persona 变更会重置该租户 plain/finalize 家族的缓存**（`/set_personality` 后 system 变了）。低频、可接受，记录在案即可。
8. **群聊 bystander 消息的持续 append 对预算的压力**：活跃群里观察者消息占 verbatim 增长的大头，压缩摘要要处理"噪声占比"（摘要提示词里给"侧重与 bot 相关的交互"的指引）。是否给 bystander 消息降权/排除出热历史，见 §7。

## 8. 结论

这次重构的本质是把上下文管道从"每轮重拼一个滑动快照"改成"一条只增不变的消息流 + 明确的注入位次"。存储层已经就位，改造集中在读取口径（窗口→预算）、渲染层（身份结构化）、组装层（三处注入归位）和可观测性（usage 命中率）。按 Phase 0→3 推进，每一步都有独立验收，探针结果决定身份标注的最终形态。
