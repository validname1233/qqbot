# 问题复盘：模型对当前时间无感知（get_time 工具）

> 日期：2026-09-18
> 涉及文件：`src/agent/tools/get-time.ts`（新增）、`src/agent/loop.ts`（MAX_TOOL_TURNS 1→2）、`src/services/prompts/functional.ts`（agent_judge 编排规则）、`src/agent/tools/search.ts`（description 配对提示）
> 状态：已实现并验证；由它引出的路由问题另见同日复盘《调工具后答案被丢弃路由误判plainReply》

## 1. 问题

模型对"今天几号、现在几点"没有可靠感知——训练数据有截止日期，推理时也没有任何时钟输入。后果：

- 用户问"今天星期几""现在几月"，模型静默编造一个日期；
- 用户要"最近的 XX 新闻"，模型不知道"最近"锚定在哪，搜索词里的时间范围也是编的。

## 2. 解决：get_time 工具（无参数，返回结构化时间）

```json
{"datetime": "2026-09-04T10:01:23+08:00", "date": "2026-09-04", "timezone": "Asia/Shanghai"}
```

实现要点：

- **时区写死 Asia/Shanghai**，不取服务器系统时区（部署环境不可控，用户在国内）——输出稳定可复现；
- `Intl.DateTimeFormat` 的 `formatToParts` + `shortOffset` 精确拼装 ISO 格式，offset 一位数补零（`+8` → `+08:00`）；
- description 明确写了防幻觉引导："你对当前时间的推测不可靠，不要凭感觉回答"。

## 3. 触发链路的三处协同

光有工具不够，模型得知道"什么时候该调"。三处提示词协同：

1. **get_time description**：直接问时间（今天/星期几/距今多久）要调；**间接需要时间**（"最近/最新/今年/近期"等相对时间表述）也要先调；
2. **search description 配对**："先用 get_time 获取当前日期，把具体时间范围（如『2026年8月』）融进搜索词，不要把『最近』直接当搜索词"——这同时是查询质量问题，裸搜"最近 XX 进展"远差于带年月的搜索词；
3. **agent_judge 编排规则**：决策层的同款纪律（三处读到同一条规则，措辞一致）。

## 4. 连带改动：MAX_TOOL_TURNS 1→2

"先拿日期、再把日期融进搜索词"是**串行依赖**——search 的 query 取决于 get_time 的返回值，不可能在同一批 tool_calls 里完成。单轮预算下这条链走不通，所以把 MAX_TOOL_TURNS 升到 2（loop.ts 头注释预留的旋钮，图结构零改动）。注释同步写明语义："允许一次串行依赖；不需要串行的请求模型第一轮就收尾，不会白付第二轮成本。"

**这个改动的连锁反应**：升到 2 解锁了"调完工具后主动停"这条以前不可达的路径，暴露了 afterLlmCall 路由的判据歧义，引发了 LanceDB 答案被丢弃的事故——那次问题的完整复盘见同日另一份文档。教训：**升级预算参数等于解锁新路径，相关条件边要跟着重审**。

## 5. 遗留观察点

- get_time 是瞬时本地工具，**刻意不配 progressNote**（推送反而添噪）；
- recall_memory 同样是串行依赖型（翻完记忆再决定要不要搜），与 get_time 共用 2 轮预算——"get_time → recall → search"三步链装不下，若实测有这种需求再考虑升 3；
- 实机验证方式：问"最近的 XX 新闻"，debug 日志里应看到第一轮 `get_time()`、第二轮 `search({"query":"…2026年9月…"})` 的串行轨迹。
