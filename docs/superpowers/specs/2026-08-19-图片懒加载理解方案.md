# 图片懒加载理解方案：短期记忆图片池 + /Agent 触发时批量识图

> 状态：已实现（占位符内联版，见文末「实现变更记录」）
> 前置依赖：`src/services/vision.ts`（千问识图，已跑通）、事件层 attachments 解析（已完成）
> 日期：2026-08-19

## 1. 背景与目标

用户诉求的三层矛盾：

1. **成本**：日常聊天图片非常频繁，每张都调视觉模型，token 消耗不值得；
2. **笨重**：只解析 `/Agent` 命令当条消息附带的图片，又太窄——"先发一张图，再问 /Agent 这图上有什么"这种最自然的用法会失效（图片在历史消息里，不在当前命令消息里）；
3. **体验**：希望 Agent 能"看见"最近聊天里出现过的图片，像人一样有短期画面记忆。

结论：采用**懒加载（lazy evaluation）**——平时只"收下"图片（低成本），`/Agent` 触发时才"理解"图片（高成本集中爆发一次）。

## 2. 核心决策：下载要急，理解要懒

原始设想是"平时存 URL，触发时再下载+识图"。**这个设想有一个致命漏洞：QQ 附件 URL 带签名（rkey 参数）且有时效**。图片发出来 2 小时后用户才 `/Agent`，URL 大概率已失效，届时下载失败，懒加载形同虚设。

所以修正为两段式：

| 时机 | 动作 | 成本 |
|---|---|---|
| **收到消息时（急）** | 下载图片字节 → 存本地文件 + 记一条元数据 | 一次普通 HTTP 下载（几百 ms，免费） |
| **/Agent 触发时（懒）** | 读窗口内图片文件 → 调 `describeImage` → 描述注入上下文 | 视觉模型调用（贵，但只在真正需要时发生） |

下载和理解的分离保住了懒加载的成本目标；下载前置解决了 URL 时效问题。**QQ 群图片通常几十~几百 KB，20 条窗口内最多几张，磁盘占用可以忽略。**

## 3. 数据设计

### 3.1 新表 `message_images`（与 short_term_messages 同库）

```sql
CREATE TABLE message_images (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  key TEXT NOT NULL,              -- 会话键，与短期记忆同款（group:<openid> / c2c:<openid>）
  qq_msg_id TEXT NOT NULL,        -- QQ 消息 id（天然唯一，防同一消息经多事件重复入库）
  filename TEXT NOT NULL,
  content_type TEXT NOT NULL,
  width INTEGER, height INTEGER, size INTEGER,
  file_path TEXT NOT NULL,        -- data/images/<qq_msg_id>-<序号>.<扩展名>
  description TEXT,               -- 识图结果缓存（首次 /Agent 触发时填充，之后复用）
  created_at INTEGER NOT NULL,
  UNIQUE(key, qq_msg_id, filename)
);
```

两个设计点：

- **图片文件存磁盘不存 BLOB**：`data/images/` 目录（`data/` 已在 .gitignore），库里只存路径。避免每次读短期记忆都拖着二进制列，也方便直接删文件清理。
- **`description` 列是描述缓存**：用户连问三次"这图里的猫是什么品种"，只调一次视觉模型。这是懒加载方案的第二重省钱——不只是"延迟理解"，还是"理解一次、多次复用"。

### 3.2 窗口对齐与清理（"超出 20 条就删"）

短期记忆的读取窗口是"最近 20 条消息"（`sqlite.ts` 的 MAX_MESSAGES，旧消息仍留在库里不删）。图片的存活窗口与之对齐：

- **判定规则**：一张图片属于窗口内，当且仅当它的 `created_at >= 窗口内最旧一条消息的 created_at`（时间对齐，不需要外键关联——`short_term_messages` 不存 qq_msg_id，加列改造成本高且收益低）。
- **清理时机**：两处天然触发点，都在"本来就要碰这个 key"的时候顺手做，不需要定时任务：
  1. **入库新图片时**（persist 末尾）——防止无 /Agent 的闲聊群图片无限堆积；
  2. **/Agent 查询图片时**——保证查询结果天然就是窗口内的。
- 清理动作 = 删文件 + 删行。时间对齐有同毫秒边界的理论误差（一两条消息内的偏差），对"最近几张图"的语义无害。

## 4. 接入点：两个写入点，一个触发点

### 4.1 写入点（复用现有记忆写入路径，零 handler 改动）

关键洞察：**当前写短期记忆的入口正好覆盖全部需要记图片的消息**——

| 消息类型 | 现有记忆写入点 | 图片写入点（新增调用） |
|---|---|---|
| 普通消息（无命令） | `services/memory-log.ts`（observer） | 同一个 observer 里追加 `persistEventImages(ctx.event)` |
| `/Agent ...` 消息 | `agent/loop.ts` runAgentTurn 末尾 | `services/agent.ts` handle 开头 `await persistEventImages(...)` |
| 其他命令（/新闻等） | 不写短期记忆 | **同样不写图片**（没有记忆行可挂靠，语义一致） |

这样还顺带解决了顺序问题：`/Agent` 消息自带的图片必须在 runAgentTurn 之前下载完成（当轮就要用），放在 `agentService.handle` 里 await 天然满足；普通消息的图片没有实时性要求，observer 里慢慢下。

### 4.2 触发点（Agent 链路）

`runAgentTurn`（`agent/loop.ts`）在进图之前增加一步：

```
history = sqliteMemoryStore.get(key)          // 现有
imageContext = await buildImageContext(key, ctx.event)   // 新增
agentGraph.invoke({ ..., imageContext })
```

`buildImageContext` 做三件事：

1. 查窗口内图片行（含 `description` 缓存）；
2. 未缓存的图片读文件 → `describeImage`（**Promise.all 并发**，单张失败单独降级）→ 回写 `description` 列；
3. 拼成注入文本，同时把**当前 /Agent 消息自带的图片**（`ctx.event.attachments`，刚在 handle 里持久化过，直接读文件识图）排在列表末尾并标注"本次消息附带"。

注入文本形态（对齐长期记忆的注入风格）：

```
最近对话中出现了以下图片（按时间从早到晚，可能与此刻的问题相关）：
- 图片1（photo.jpg，2026-08-19 14:32）：<描述文本>
- 图片2（meme.png，2026-08-19 14:35，本次消息附带）：<描述文本>
```

### 4.3 State 与节点改造（loop.ts）

- `AgentState` 加一个 `imageContext: z.string().default("")` 字段，与 `longTermContext` 完全同款；
- **注入位置**：`prepareContext` 把它作为一条 user 消息插在 system 之后、history 之前。与 longTermContext 不同的是，**llmCall（工具判断）也要看到图片描述**——"帮我搜搜图里这个景点在哪"这种需求，judge 节点看不到图片内容就没法正确决定调搜索工具。plainReply / finalize 的注入方式与现有 longTermContext 一致。

## 5. 新模块 `src/agent/memory/images.ts`

与 `sqlite.ts` 同目录（它是短期记忆的伴生数据）。导出三个函数：

```typescript
// 下载 event.attachments 里的图片（isImageAttachment 过滤），存盘 + 建行 + 顺手清理窗口外图片。
// 单张失败：log + 跳过（那张图之后就是不存在的，agent 无感知降级）。
persistEventImages(event: BotEvent): Promise<void>

// 查窗口内图片 → 未缓存的并发识图并回写缓存 → 返回注入文本。
// VISION_API_KEY 为空时直接返回 ""（功能整体关闭）。
// 张数上限 VISION_MAX_IMAGES（超出取最近的 N 张，防一次 /Agent 爆量）。
buildImageContext(event: BotEvent): Promise<string>

// 窗口外图片的文件+行删除。persist 和 build 内部都会调，不单独导出时机。
```

下载超时 10s、单文件大小上限 10MB（超限跳过并 log，对齐千问 Base64 7MB 建议留余量）。

## 6. 降级路径（每层独立失败，互不拖垮）

| 故障点 | 行为 |
|---|---|
| `VISION_API_KEY` 未配置 | `buildImageContext` 返回空串，Agent 纯文本运行，无任何感知差异 |
| 收图时下载失败 / 超时 / 超大 | 该图片不入库，log 一条；后续 /Agent 看不到它 |
| 识图调用失败（限流/超时） | 该图片描述标"（该图片暂时无法识别）"，其余图片正常，Agent 仍能回答 |
| 识图返回被截断 | vision.ts 已有截断标记逻辑，沿用 |
| 同一 key 并发两次 /Agent | description 缓存可能出现双写竞态——两次各调一次模型，结果一样，浪费但无害，不值得加锁 |

## 8. 成本特性小结

- **闲聊期零 API 成本**：只有图片下载（免费带宽）；
- **/Agent 触发时才付费**：且只处理窗口内、上限 N 张；
- **描述缓存复用**：连续追问同一批图片只付一次钱；
- **写描述进短期记忆吗？不**——描述只在触发时作为 imageContext 注入，不污染消息流；短期记忆里文本消息保持原样（含 `[图片]` 占位与否见 §9）。

## 9. 明确排除 / 后续扩展

- **语音、视频**：`parseAttachments` 已把 `voice_wav_url` / `asr_refer_text` 解析进类型，将来做语音时 asr_refer_text 可直接白嫖官方 ASR 转写，本方案结构（入库+懒触发）可直接复用；
- **msg_elements 嵌套附件**（引用消息里的图）：不做，非"用户发给我"的语义；
- **发图能力**：不在本方案范围。

## 10. 实现变更记录（2026-08-21）：独立图片块 → 占位符内联

初版按 §4.2 实现（imageContext 独立块插在 history 前），实现后发现三个语义缺陷：
图片脱离对话流（位置错）、无作者、无时序。重构为**占位符内联**方案：

- **写入时**：`persistEventImages` 返回图片 id 列表，content 拼成 `[图片:17] 看这只猫` 落库（存"引用"不存描述）；
- **/Agent 触发时**：`prepareContext` 调 `expandImagePlaceholders`，把 history user 消息和当前消息里的 `[图片:17]` 展开成 `[图片]{橘猫趴在沙发上…}`（花括号包裹描述，可读性更好）；群聊昵称前缀套在外面，作者/位置/时序全部天然正确；
- **描述缓存**：展开时 description 为空的逐张识图（并发），回写 `message_images.description`；`runAgentTurn` 末尾 append 存的仍是**占位符版**（懒加载语义：描述不落库）；
- **降级**：查不到行（prune 误差兜底）→ `[图片]`；超 `VISION_MAX_IMAGES`（只识图 id 最大的 N 张）→ `[图片]`；识图失败 → `[图片]{该图片暂时无法识别}`；key 未配置 → 全部 `[图片]`；
- **注入简化**：llmCall / plainReply / finalize 不再需要任何图片特判——描述已在消息里；`buildImageContext` 删除；
- **提示词**：agent_judge / agent_finalize / daily 增加 IMAGE_NOTE——告知模型 `[图片]{...}` 是预解析的图片内容，可直接讨论（不带说明模型可能当成乱码占位符）。

各场景占位符示例：

| 场景 | 落库 content | /Agent 展开后 |
|---|---|---|
| 纯图 | `[图片:17]` | `小明：[图片]{橘猫趴在米色沙发上…}` |
| 图+文字 | `[图片:17] 看这只猫` | `小明：[图片]{橘猫趴在米色沙发上…} 看这只猫` |
| 多图 | `[图片:17] [图片:18] 对比一下` | `小明：[图片]{…} [图片]{…} 对比一下` |
