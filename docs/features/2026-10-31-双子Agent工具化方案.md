# 双子 Agent 工具化方案（deep_search 与 workspace_task）

> 2026-10-31。目标：把深度检索与工作台两个子 Agent 纳入主 Agent 的工具表
>（委派式调用），与既有的显式命令（裸调用）并存、互不冲突；同时补齐子 Agent
> 的过程归档（process 行）与进度推送的嵌套语义。
>
> 依据：`2026-10-30-子Agent状态传递与记忆层级调研/`（业界模式确认：tool 调用
> + 规格书是主流；子过程应"归档但默认不可见"）、提示词方案 §10.2（委派类工具
> 七模块描述格式）。
> 现状：workspace_task 已工具化（本方案给它补归档与清理）；deep_search 尚未
> 工具化（本方案主体）。

## 1. 实现结构：双入口共用一个核心

```
裸调用（显式命令）                      委派调用（主 Agent tool call）
/深度检索 问题    ─┐                   @bot "深度调研一下X" → 主 Agent llmCall
                  │                     → tool_calls: deep_search(question="X")
                  │                     → toolsNode 并发执行
/代码 任务       ─┤                   → 主 Agent 同轮继续 → 转述报告 → END
                  │
                  │   ┌────────────────┴──────────────┐
                  └──►│ runDeepSearch(q, ctx, opts)   │◄── 工具壳（新文件）
                      │ runWorkspaceTask(t, ctx, opts)│◄── 工具壳（已有）
                      └───────┬───────────────────────┘
                              │ opts.ownFlow 二选一：
              裸调用：ownFlow=true（自己登记并发闸）
              委派调用：ownFlow=false（反查 currentFlowSignal 借父闸/父 signal）
                              │
                    子图执行（各自的 LangGraph 图）
                              │
              中间过程 → conversation_events 落 process 行（origin 标记子Agent身份）
                              │
              报告返回（裸调用→直接回群；委派→tool result 进主 Agent 轮内）
```

**不冲突、不重复的保证**（三重）：

1. **并发闸同一把**：两条路径最终都经 beginControlledFlow / currentFlowSignal
   操作同一个租户闸——委派时主 Agent 已持闸，子 Agent 借用（不二次登记，
   避免自锁）；裸调用自己登记。同会话的第三个请求（无论形态）都被闸拒绝；
2. **入库不重复**：chat_user 行由 dispatcher 入站收口唯一写入（两种路径都只
   一次）；报告的 chat_bot 行只在**裸调用**路径产生（出站收口）——委派路径
   报告是 tool result（轮内蒸发），落库的是主 Agent 转述后的最终回复（一条
   chat_bot）。子过程两种路径都落 process 行（永不投影，v7），不构成重复；
3. **进度推送不重复**：emit 按 tenantKey 找当前订阅者——裸调用是子 Agent 的
   订阅，委派是主 Agent 的订阅（嵌套栈顶，见 §2.4）。工具壳**不声明**
   progressNote（避免与子 Agent 内部文案连发）。

## 2. 更改的功能

### 2.1 deep_search 工具壳（新建）

- 七模块描述（提示词方案 §10.2 格式）：[Purpose]/[Usage]/[NotFor]/[Brief]/
  [Params]/[Expect]/[Limits]；schema 单参数 `question`（深检是单文本输入，
  无需结构化——与 workspace 的 task 规格书不同，它要的就是"调研问题"本身）；
- `progressNote` 不声明（§2.4）；
- run：`runDeepSearch(question, ctx, { ownFlow: false })`；返回值直接是报告
  （报告头部由深检核心自带状态行的话术，见 §2.3 附带）；中止返回中止说明
  （照抄 workspace_task 的 `[任务被中止]` 话术）；
- 注册：agent.ts（受 workspaceEnabled 同款 config 总开关控制？——否，深检无
  外部依赖，恒注册）。

### 2.2 runDeepSearch 的 ownFlow 模式（改造）

照抄 runWorkspaceTask 的既有模式（run-task.ts:4-6 注释即规格）：

- 签名加 `opts?: { ownFlow?: boolean }`；
- `ownFlow !== false`（默认 true，向后兼容裸调用路径）：现有行为不变——
  beginControlledFlow 登记失败返回"上一个任务还在跑"；
- `ownFlow === false`（委派）：**不登记、不 endControlledFlow**，signal 从
  `currentFlowSignal(flowKey)` 反查父流程（主 Agent 持闸者）挂进图
  （interruptSignal 接线已全就位——节点 196/269/314 行传 signal、条件边
  443/451/461 行检查 aborted 转 synthesize，零改动）；
- AbortError 顶层 catch：与 runAgentTurn 同款（isAbortError → return ""），
  两路径共用。

### 2.3 子 Agent 过程归档（process 行，两图同构）

- **深检图**：browseLlm 每次模型输出落 process 行（role=assistant，
  content+toolCalls JSON，origin="deep-search"）；browseTools 每个工具结果落
  process 行（role=tool，content 全文+toolCallId，origin="deep-search"）；
  searchNode 的改写调用与 synthesize 的报告生成调用同款落法。写入形态与主
  链路 llmCall/toolsNode（loop.ts:92/129）完全同构；
- **workspace 图**：子图的 LLM 节点输出与工具（exec/grep 等）结果同款落
  process 行（origin="workspace"）；
- **身份标记用 origin 列**（不加新列）：主链路 process 行 origin="agent"
  已有先例，三值（agent/deep-search/workspace）即可区分归属。调研里说的
  "agent 命名空间列"留 M4 再议——origin 语义吻合（来源标记），零 schema 改动；
- **两种触发路径都记**（委派与裸调用走同一个图核心，落库写在节点内部，
  天然统一）；
- 不变量保持：process 行永不投影（chatRowsAll 的 kind IN 过滤天然无视），
  v7 语义不破；写入失败不炸图（照抄主链路的 try 容忍——查一下 loop.ts 是否
  有 try，实施时对齐）。

### 2.4 progress-bus 栈式订阅（修 latent bug）

- `listeners: Map<key, Listener>` → `Map<key, Listener[]>`（栈）；
- subscribe = push 自身实例；退订 = indexOf 定位 + splice（只弹自己，嵌套
  异常顺序退订也不误伤）；emit = 取栈顶（最内层订阅者，与现单值语义一致）；
- 修复的窗口：委派链路"子 Agent finally 退订后，主 Agent 后续轮次的
  progressNote emit 静默 no-op"——裸调用从未嵌套所以没暴露过，工具化首次
  出现嵌套；
- 调用方 API 形状不变（subscribeProgress 返回退订函数），零调用方改动。

### 2.5 文案清理

- workspace_task 的 `progressNote: "正在委派工作台任务…"` 删除（2026-10-15
  随 workspace 本体引入；run-task.ts:68 内部的"工作台任务开始：正在准备执行
  环境…"信息量更大且紧随其后，两条连发构成重复推送）；
- deep_search 工具壳按 §2.1 不声明 progressNote，同理。
