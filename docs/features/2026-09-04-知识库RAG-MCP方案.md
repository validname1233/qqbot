# QQ 知识库 RAG（端侧 MCP 服务）方案分析

日期：2026-09-04
状态：方案讨论稿（未实施）

## 1. 需求与三个纠结点的回应

设想的使用形态：群里发 `/知识库` → bot 回一条 URL → 浏览器打开知识库管理页（上传/下载/浏览条目）→ 端侧设备存数据 → Agent 通过 MCP 检索（召回）知识库内容，按会话隔离（一群一库、单聊一人一库）。

三个原始纠结点逐一回应：

1. **群文件自动入库 vs 命令模式**：两者都不用选——QQ 官方 bot 平台根本没有文件上传事件（intents 只有 C2C/GROUP 消息类，见 §2），"监听群文件"在官方 API 下做不到，纠结不存在。Web UI 上传是唯一可行路径，而且人肉选择入库天然解决了一刀切问题。
2. **云服务器 40G 容量**：知识库整体放端侧设备，云上零存储，bot 侧只多一条命令和一个 MCP 配置。
3. **向量库运行负担**：也随数据一起挪到端侧。且按 §5 选型，嵌入式向量库（LanceDB）零独立进程，embedding 走免费 API 不跑模型——端侧的实际负担远小于"装个向量数据库"的直觉。

结论：这个"上传管理走 Web、检索走 MCP、数据在端侧"的架构方向是对的，下面是把它落细。

## 2. 平台硬约束（决定方案形态）

- **官方 bot 收不到文件事件**：可订阅的 intent 只有消息类（含 @ 消息、普通群消息需申请）和少量通知类，没有文件上传推送。消息 attachments 也只覆盖图片等富媒体，拿不到文件本体。所以任何"从聊天流截文件"的思路在官方 API 下都不可行，上传必须走外部界面（Web UI）。
- **被动回复 5 分钟窗口**：`/知识库` 是轻命令，秒回，无压力。
- **链接会发进群里**：任何群成员都能看到并点开，这要求链接本身承载鉴权（§6.1），不能是裸 URL。

## 3. 总体架构

```
┌─ 云服务器（qq-bot，40G）──────────┐      ┌─ 端侧设备（公网 IP + 域名）─────────────┐
│                                  │      │                                         │
│  /知识库 命令 service             │      │  ┌─ Web 前端（管理页）────────┐          │
│    └─ MCP 调 kb_issue_link ──────┼──────┼─▶ │ 上传/下载/条目浏览        │          │
│                                  │ HTTP │  │ 链接 token 鉴权           │          │
│  Agent 图 / 深检图               │      │  └────────────┬─────────────┘          │
│    └─ MCP 工具 kb_search ────────┼──────┼─▶ ┌─ MCP server（Streamable HTTP）┐    │
│       （scope 由适配器强制注入）  │      │  │ kb_search / kb_issue_link   │    │
│                                  │      │  │ Bearer key 鉴权            │    │
└──────────────────────────────────┘      │  └────────────┬─────────────┘          │
                                          │  入库流水线：解析→切块→embed→入向量库 │
                                          │  存储：原始文件 + LanceDB + SQLite 元数据│
                                          └─────────────────────────────────────────┘
```

职责切分的原则：bot 云侧只做"入口"（发链接、把召回工具交给模型），端侧做全部重活（存储、解析、检索）。两端只通过两条 MCP 调用通信。

会话隔离键沿用现有 sessionKey 的思路但粒度不同：知识库是**群粒度**（一个群共享一个库），即 `kb:group:<groupOpenid>` / `kb:c2c:<authorOpenid>`。注意这和 session/interrupt 的人粒度 key 不是一回事，MCP 适配器里单独算（§6.2）。

## 4. 现有选型调研（复用 vs 自研）

结论先行：**没有现成项目能直接干净满足"Web 管理 + MCP 检索 + 按租户隔离"三项，建议自研一个薄服务**（体量不大，见 §8）。调研事实：

| 项目 | 状态 | 满足度与硬伤 |
|---|---|---|
| SurfSense（16.1k★） | 活跃 | 最接近：Web 管理 + MCP + Bearer key + RBAC。但 MCP 工具面偏"连接器抓取"而非纯 KB 检索，50+ 格式/连接器全家桶对家用太重，改造量中等 |
| arkon（1.26k★） | 活跃度下滑 | 架构最正（MCP 工具级 scope + 租户隔离），但 PolyForm Internal license 禁止对外提供服务，且 7 容器部署太重 |
| kotaemon（25.7k★） | 活跃 | Web UI 和中文解析好，但**无 MCP 支持** |
| FastGPT / MaxKB / Yuxi | 活跃 | 多租户 + Web 管理最成熟，但对外检索走自家 REST API，MCP 只是客户端角色；可行折中是"平台 + 外包薄 MCP 壳"，等于还是要写壳，还背上了平台本身的重量 |
| basic-memory（3.8k★） | 活跃 | Markdown+SQLite+MCP，但偏个人记忆，无上传 UI 无多租户，AGPL |
| haiku.rag / mcp-local-rag 等 | 小型 | 纯检索 MCP server 无管理台，MCP 仅 stdio，无鉴权无租户——可当检索内核参考，不适合直接用 |

自研的底气：这个服务的核心其实很小——"收文件 → 流水线入库 → 向量检索 + Web 页面读写 SQLite/LanceDB + 两条 MCP 工具"。用 FastAPI（或 Hono）+ 一页前端，比改造 SurfSense 的全家的包袱轻得多。MCP 鉴权按规范走静态 Bearer key（社区自托管主流做法，符合 MCP 安全规范"暴露在 HTTP 上的 server 必须要求某种 token"；OAuth 2.1 全流程对无人值守场景无意义，不追）。

## 5. 技术栈推荐（端侧）

按"几千~几十万 chunk、单台家用设备"的量级：

| 组件 | 推荐 | 理由 |
|---|---|---|
| 向量库 | **LanceDB** | 嵌入式零进程、磁盘式索引内存最省、单目录数据（备份=拷目录）、自带全文+过滤；几十万 chunk 舒适区。备选 sqlite-vec（更极简但 pre-v1 且暴力扫描），Chroma 明确不推荐（HNSW 全内存） |
| 元数据 | SQLite | 条目表、token→scope 映射表、处理状态 |
| 文档解析 | **pypdfium2（数字版 PDF）+ markitdown（Word/PPT/网页）** | 都极轻；中文扫描件/复杂表格的 PDF 将来用 MinerU 离线批处理（16G 内存要求，按需再上） |
| Embedding | **硅基流动 bge-m3 API（免费档）** | 中文顶级效果、8192 窗口、免费限速对家用绰绰有余；DeepSeek 没有 embedding API。隐私硬要求才转本地 bge-small-zh（CPU 可跑但 512 窗口） |
| Rerank | 硅基流动 bge-reranker-v2-m3 API | 召回 top 30 → 重排 → 取 top 5，免费档成本趋近零，不吃端侧 CPU |
| 服务框架 | Python FastAPI + FastMCP（或 Node 单栈） | 解析生态（pypdfium2/markitdown）在 Python 侧最顺；MCP SDK 两种语言都有 |

磁盘估算：1 万个文档 × 平均 20 chunk = 20 万 chunk，bge-m3（1024 维 float32）向量约 800MB + 原始文件若干 GB，端侧设备无压力；将来量级上去 LanceDB 可开量化再省 4 倍。

## 6. 关键设计细节

### 6.1 管理页链接的签发与鉴权

链接发在群里 = 群成员人人可见，所以链接本身必须带凭据。做法：

- server 端 `kb_issue_link(scope)` 工具（MCP 调用，带主 Bearer key）：生成随机 token，存 `token → scope` 映射进 SQLite，返回 `https://kb.example.com/g/<token>`。
- bot 的 `/知识库` 命令调它拿 URL 回群。**同一 scope 重复签发返回同一 token**（链接长期稳定，群成员可收藏），token 只在 server 重置时轮换。
- Web 页面所有写操作（上传/删除）和下载都验 token；纯浏览同权（一期不做"只读链接"，预留）。
- bot 云侧不持有 Web 凭据的任何秘密——签发走 MCP，主 key 只存在于两端的环境变量里。

### 6.2 MCP 工具面与租户隔离（适配器注入）

工具分两类，正好用现有 MCP 层的闸门（MCP_EXPOSE）区分：

- **`kb_search(query, top_k)`——暴露给模型**：进全局工具表，日常 Agent 和深检都能用。租户不靠模型传参（模型会乱传/瞎猜 scope），**靠适配器在 run 内强制注入**：`wrapMcpTool` 的包装层里从 `ctx.event` 算出 `kb:group:<groupOpenid>` 覆盖进 args——和 interact_page 远程内核"桥接层管语义、模型只管意图"是同一个模式，也是当初把适配器落点设计在 bridge run 内的直接兑现。
- **`kb_issue_link(scope)`——不暴露**：不进 MCP_EXPOSE，只有 bot 的 `/知识库` 命令代码直调（client.ts 的 callTool），模型永远看不见它。

### 6.3 入库流水线与召回格式

- 上传后异步流水线：存原文件 → 解析 → 切块（500~800 token，带文档名+章节标题前缀）→ embed → 入 LanceDB；Web 页面显示每个条目的处理状态（排队/处理中/可检索/失败）。
- `kb_search` 返回给模型的是文本块：每条 = 文档名 + chunk 原文 + 简短来源行；适配器做"原文透传、格式整形"，不丢字段（interact_page 远程内核还要用原始结构，保持 client 哑管道的约定）。

### 6.4 解析器层：格式解析的可插拔注册表

> 补记（2026-09-16）：端侧实现已定为 Node 单栈（阶段一落地时拍的板，MCP/鉴权/文档管理已跑通），本节接口以 TS 表述；§5 的 Python 生态建议保留作对照——最终仍需要 Python 的只有 MinerU，而它本来就是外部进程，与主服务栈无关。

流水线里"文件 → 文本"这一步是变化最快的环节（新格式、更好的库、外部服务），把它做成注册表与框架解耦：框架只认统一契约，解析实现按格式注册、可替换、可外挂到进程外的服务。

**契约（框架与解析器之间的唯一约定）**：

```ts
interface KbParser {
  name: string;        // 注册名（日志/回退链引用）
  formats: string[];   // 声明可处理的扩展名（小写，如 ["pdf"]）
  parse(input: { filename: string; mime: string | null; data: Buffer }): Promise<{
    text: string;      // 全文纯文本。空文本视为失败——扫描件误走数字解析器的典型症状
    sections?: Array<{ heading?: string; text: string }>;  // 可选结构，供切块加章节标题前缀（§6.3）
  }>;
}
```

职责边界：解析器只救"格式读得出来"，切块/embedding/入库留在框架侧。契约一旦膨胀到"返回向量或切块"，进程内库和外部服务就没法共用一个接口，解耦就名存实亡。

**注册与匹配**：

- 注册表：`Map<name, parser>`（与 bot 侧 adapters.ts 同款模式），另维护扩展名 → 候选解析器列表；
- 匹配：扩展名优先；未注册的扩展名回落 plain-text 解析器直读，读出乱码判 unsupported（条目状态与 failed 区分）；
- **回退链**：候选按序尝试，抛错或文本量过低（如 <100 字/MB）自动降级下一个候选。"数字版 PDF → MinerU（扫描件）"就靠这条链路由，用户无需手动声明文件类型。

**进程内 vs 外部**：外部解析器（本地 Docker 的 MinerU、云端解析 API）用 HTTP 适配器包成同一接口，差异只在框架侧多加超时与体积上限；外部不可用时沿回退链降级或标 failed。隐私注意：外部解析器拿到的是文档原文——云端服务需明审，家用默认只挂自部署端点。

**配置**：解析器在代码内注册，不引入解析器配置文件/DSL（避免第二种配置语义）；外部端点走 .env（如 `MINERU_URL`）。

**分期落地**：阶段二 = 注册表 + 回退链机制 + 内置解析器（txt/md 直读、PDF 用 pdf-parse、docx 用 mammoth），全部进程内；阶段三 = MinerU 外部解析器与更多格式，只加注册项不动框架。

**TODO：组合解析器（解析器编排解析器）**（2026-09-22 讨论定稿，暂不实施）：

思想：契约是递归友好的（`parse(data) → {text, sections?}` 不问输入出处），
一个解析器可以在内部调用其他解析器，自己只做编排——模块**使用**模块而非融合，
每个子解析器仍独立注册/独立可测。

首个目标场景：mineru 解析带图 PDF 时，zip 里的 images/*.jpg 与
image/chart 条目的 caption 字段当前被静默跳过（实测确认）。将来接入方式：

```
mineru.ts（编排者）
  ├─ text/title 条目 → sections（现状）
  ├─ image/chart 条目 → 图片字节 + image_caption/chart_caption 文本
  │     └─ 调用图片解析器（VLM 生成描述，如"柱状图：D 集吞吐最高 4800 ops/s"）
  └─ caption + VLM 描述拼进相邻 section → 图表变成可检索的自然语言
```

实现护栏（届时遵守）：
1. **防递归环**：注册表加调用深度防御（mineru→图片天然无环，机制性防御备用）；
2. **成本显式**：编排者层面计量子调用次数（MinerU 一次 + VLM 每图一次）；
3. **失败局部**：单图 VLM 失败 try-catch 降级（只用 caption 或占位），
   不让整个文档 failed——框架回退链管不到组合解析器内部的子调用。

近期先做的低成本修复（组合解析器的前置）：mineru.ts 的 content_list 消费补上
`image_caption/chart_caption/chart_footnote` 数组 join 进相邻文本——不调 VLM、
零成本保住图注的检索语义（"Figure 3.1 说的是吞吐对比"能被召回）。

**单次解析的路由过程**（`src/parsers/registry.ts` 的 `parseDocument`，从上传到选定解析器）：

```
上传文件（filename + bytes）
  │
  ├─ 1. 扩展名提取：filename 末段 . 后部分，小写（"报告.PDF" → "pdf"；无扩展名 → 空）
  │
  ├─ 2. 查候选链：formatChains.get(ext)
  │     ├─ 命中：返回该格式的候选列表（后注册者排前——专门解析器优先，兜底在后）
  │     └─ 未注册：直接抛 ParseError"不支持的文件格式"→ 条目 failed（错误文案列出已支持格式）
  │        ※ 设计选择：不做"未注册扩展名回落 plain 直读"——宁可明确失败也不把二进制读成乱码
  │          （plain 自己有乱码检测，但明确的报错信息比事后检测更友好）
  │
  ├─ 3. 回退链逐个尝试（for candidate of chain）：
  │     ├─ 调 candidate.parse({filename, mime, data})
  │     ├─ 抛 ParseError（如 plain 的"不是 UTF-8 文本"）→ 记入 skipped，试下一个
  │     ├─ 解析"成功"但 text.trim() < 10 字 且文件 > 1KB → 疑似解析错对象
  │     │     （扫描件 PDF 走数字解析器的典型症状）→ 记入 skipped，试下一个
  │     └─ 正常 → 返回 { doc, usedParser, fellBackTo }
  │
  └─ 4. 链上全部失败：抛最后一个 ParseError → worker 捕获 → 条目 failed，error 进
        entries.error（管理页红字展示）；文件本体保留，可修复解析器后重新入队
```

现状示例（当前注册表）：`xxx.txt` → 链 `[plain]` 一步命中；`xxx.pdf` 现在 → 未注册直接 failed，pdf 解析器上线后 → 链 `[pdf-parse]`，将来挂上 MinerU 后 → 链 `[pdf-parse, mineru]`（数字版一步出，扫描件自动降级）。

## 7. bot 侧改动清单（云服务器）

1. 新 service：`services/knowledge-base.ts`——`/知识库` 命令，调 `kb_issue_link`（直调 MCP client，不经模型）拿 URL 回复；server 不可用时回复降级文案（同现有 MCP 可用性隔离语义）。
2. 适配器：`agent/mcp/adapters.ts` 加 kb_search 的 scope 强制注入（按事件类型算 kb key）。
3. 配置：`MCP_SERVERS` 加 `kb=https://kb.example.com/mcp`，`MCP_EXPOSE` 加 `kb:kb_search`（不含 issue_link）。
4. 前置依赖：client.ts 的 Bearer key 支持（"名字=地址|Key" 格式 + requestInit headers，已在 MCP 鉴权讨论中定型，尚未实施——本功能是它第一个真实用户）。
5. 文档：操作手册加"知识库"章节；命令速查表加 `/知识库`。

## 8. 端侧 server 改动清单

1. 单进程服务：Node http + 官方 MCP SDK 挂 `/mcp`（Streamable HTTP + Bearer key，2026-09 实现口径；FastAPI 为早期设想，未采用）。
2. 存储：SQLite（`data/kb.sqlite`，node:sqlite 内置）四张表 + 文件落盘 `data/files/<scope>/<id>/<文件名>`（见 §8.1 实际表结构）。
3. 流水线 worker（进程内异步队列即可，不必上消息队列）：解析（走 §6.4 解析器注册表）→切块→智谱 embedding-3 embed→向量落库。
4. 检索：向量召回 top 30 → rerank API → top 5 返回。
5. 前端一页：条目列表（状态/删除/下载）+ 上传控件（已上线；搜索框随 kb_search 阶段加）。不做内容浏览（用户已明确一期不做）。
6. HTTPS：暂缓——当前经 Higress 网关 HTTP 暴露，升 HTTPS 由网关侧配置解决。

### 8.1 实际表结构（2026-09-18 与 omen6 生产库核对）

> 实现为 Node 单栈。元数据与原文在 SQLite（`data/kb.sqlite`，node:sqlite 内置零依赖）；
> 向量在 LanceDB（2026-09-18 已上线，`@lancedb/lancedb`，替换早期的 SQLite JSON 桩）。

**LanceDB `chunks_vec` 表 —— 向量索引（第五张"表"，目录即库）**

```text
data/vectors.lance/chunks_vec/          ← 一个目录 = 一张表（备份 = 拷目录）
├── data/*.lance                        ← 数据分片：列式存储，文件不可变
├── _versions/*.manifest                ← 每次写操作一个版本快照（类 git 版本链）
└── _indices/                           ← 向量索引（量大了建 IVF_PQ，当前暴力扫描够用）
```

schema（列定义）：

| 列 | 类型 | 作用 |
|---|---|---|
| `vector` | fixed-size-list\<float32\>[1024] | 检索主列：search(q) 即与该列算距离 |
| `entry_id` | int | 定位回 SQLite chunks（复合键之一） |
| `idx` | int | 同上 |
| `scope` | string | 租户隔离：.where() 过滤，其他库的向量不进候选集 |

操作方式：非 SQL——面向对象的 API（table.add / table.delete / table.search），
SQL 表达式仅用于 `.where()` 过滤谓词。列式布局（同列数据连续存放，与行式的
Excel/SQLite 相反）使"只扫 vector 列"的检索成为顺序大块读。写操作不可变：
add 写新分片、delete 打删除标记，新版本走 Manifest——天然带快照历史。

与 SQLite 的一致性：跨两个存储无法做原子事务（没有能横跨 kb.sqlite 文件与
lance 目录的事务协议），worker 采用**幂等 upsert**（先清后写：delete entry_id
→ add 新行）保证最终一致——中途崩溃则条目停在 processing，重启扫表重新入队，
整条流水线重跑收敛到正确状态，不留脏数据。检索时 LanceDB 只出"哪几块命中"
（scope 过滤 + 距离排序），`searchable` 状态核对与原文拼装都回 SQLite——
LanceDB 是索引不是内容库，原文单一来源在 chunks 表。

**tokens —— 管理链接凭据（阶段一）**

```sql
CREATE TABLE tokens (
  scope      TEXT PRIMARY KEY,   -- kb:group:<群openid> / kb:c2c:<用户openid>
  token      TEXT UNIQUE NOT NULL, -- base64url 24 字节随机；同 scope 幂等复用
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

**entries —— 文档条目，流水线状态机载体**

```sql
CREATE TABLE entries (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  scope       TEXT NOT NULL,          -- 隔离键：所有查询必带（SQL 层强制隔离）
  filename    TEXT NOT NULL,          -- 展示/下载用的原始文件名
  stored_path TEXT NOT NULL,          -- data/files/ 下相对路径（入库后回填）
  size        INTEGER NOT NULL,       -- 字节
  mime        TEXT,                   -- 上传时的 Content-Type（可选）
  status      TEXT NOT NULL,          -- queued → processing → searchable / failed
  error       TEXT,                   -- failed 时的可读原因（解析器 ParseError 文案）
  created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_entries_scope ON entries(scope);
```

注：线上库的 status 默认值仍是早期建的 'ready'（建表时还没有流水线），代码插入时
显式传 'queued'，实际值不受默认值影响；重建库时默认值会修正。

**chunks —— 切块元数据与原文（检索结果的内容来源）**

```sql
CREATE TABLE chunks (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  entry_id INTEGER NOT NULL,          -- 所属条目（删除条目联动清理）
  idx      INTEGER NOT NULL,          -- 条目内序号
  heading  TEXT NOT NULL DEFAULT '',  -- 章节/sheet 名（md 标题、xlsx sheet、MinerU 章节）
  prefix   TEXT NOT NULL DEFAULT '',  -- 面包屑前缀（文档名 · 章节，召回展示用）
  text     TEXT NOT NULL              -- chunk 原文（表格为序列化行；不含前缀，分开存）
);
CREATE INDEX idx_chunks_entry ON chunks(entry_id);
```

**vectors 桩表 —— 已退役（2026-09-18）**

```sql
-- 历史结构（已被上方 LanceDB chunks_vec 替代，迁移脚本 DROP）
CREATE TABLE vectors (
  entry_id INTEGER NOT NULL,
  idx      INTEGER NOT NULL,
  vector   TEXT NOT NULL,             -- 1024 维 float 数组的 JSON 序列化
  PRIMARY KEY (entry_id, idx)
);
```

表间关系与生命周期：`tokens.scope = entries.scope`（一对多）；`entries.id ← chunks.entry_id`（一对多）；`chunks (entry_id, idx) ↔ LanceDB chunks_vec 行`（一对一）。删除条目时四处联动清理（entries 行 + chunks 行 + LanceDB 行 + 文件目录）；worker 重跑条目时 chunks 在 SQLite 事务内先清后写、向量在 LanceDB 事务外幂等 upsert（见上方一致性说明）。

检索时的隔离与可见性：LanceDB 侧 `.where(scope)` 过滤候选，回 SQLite 核对 `status = 'searchable'`——处理中的文件对检索不可见，不召回半个文档。

## 9. 分阶段实现方案

切分原则：先跑通"存储与访问"的价值闭环（不依赖任何 RAG 组件），检索能力作为增量叠加。阶段一砍掉 LanceDB、文档解析、embedding/rerank——端侧只剩 FastAPI + SQLite 两张表 + 文件目录 + 一页前端，§5 技术栈表里的向量库/解析/embedding 组件自阶段二才引入。

### 阶段一：纯知识库（无 RAG，先能用起来）

目标：群里 `/知识库` 拿链接，浏览器上传/下载/浏览条目，数据按会话隔离地存在端侧。

- 前置依赖：client.ts 的 Bearer key 支持（`名字=地址|Key` + requestInit headers，MCP 鉴权讨论已定型）。
- 端侧 server：
  - FastAPI 单进程：`/g/<token>` 管理页（静态一页）+ 上传/列表/下载/删除四个 HTTP API（均验 token）。
  - SQLite 两张表：`entries`（id/scope/文件名/存储路径/大小/上传时间）、`tokens`（token → scope，同 scope 重复签发返回同一 token）。
  - 文件本体按 scope 分目录落盘（`data/kb/<scope>/...`），不做任何内容解析。
  - `/mcp` 端点挂 FastMCP，只实现 `kb_issue_link(scope)` 一个工具，主 Bearer key 鉴权。
- bot 侧（云服务器）：
  - `services/knowledge-base.ts`：`/知识库` 命令，直调 MCP client 的 `kb_issue_link` 拿 URL 回复；server 不可用回降级文案。
  - 配置：`MCP_SERVERS` 加 kb 条目；`MCP_EXPOSE` 本阶段**不配 kb**（唯一工具是签发，不进模型工具表）。
- 验收：群里发 `/知识库` 收到链接；浏览器能上传、刷新见条目（文件名/大小/时间）、下载、删除；两个群的库互不可见。
- 本阶段不做的：内容提取、内容浏览（条目列表即可）、搜索、只读链接、入库通知。

### 阶段二：RAG 检索（kb_search 上线）

目标：Agent 能按会话召回知识库内容，深检/日常问答可用。

- 端侧：加 `chunks` 表（向量 id ↔ 条目 ↔ 原文）；LanceDB 嵌入式向量库；入库流水线（解析→切块→硅基流动 bge-m3 embed→入向量库，进程内异步队列）；`entries` 表加处理状态字段，管理页显示 排队/处理中/可检索/失败；新增 `kb_search(query, top_k)` 工具（向量召回 top 30 → rerank API → top 5，rerank 可在本阶段后段再加，先纯向量召回也能用）。
- 上传的文件走"存储即入队"，已上传的存量文件补一个"重建索引"按钮（或启动时自动补跑）。
- bot 侧：`MCP_EXPOSE` 加 `kb:kb_search`；适配器加 scope 强制注入（从 ctx.event 算 `kb:group:<groupOpenid>` / `kb:c2c:<authorOpenid>` 覆盖进 args）。
- 格式（统一经 §6.4 解析器注册表接入）：Markdown/TXT（内置直读）、数字版 PDF（pdf-parse）、Word（mammoth）；PPT/网页可顺带，属低成本项。
- 验收：上传一个 PDF 后问 Agent"知识库里关于 X 说了什么"，回答引用了该文档内容且只看到本会话的库。

### 阶段三：增强（按需挑选）

- Word/PPT/网页之外的格式：扫描版 PDF 走 MinerU 离线批处理。
- 只读链接（浏览不给下载/删除）、`/重置知识库链接` 命令（换 token，旧链失效）。
- 深检图把 kb_search 纳入起点（进深检注册表，preflight 前先查本地知识库）。
- 本地 embedding 全离线模式（bge-small-zh），隐私硬要求时替换硅基流动。
- 删除联动清向量（阶段二删除条目时向量标记孤儿，这里做物理清理）。

## 10. 风险与预留

- **token 泄露**：链接即凭据，转发即授权。家用场景可接受；将来要收紧时加"重置链接"命令（换 token 旧链失效），server 端已有映射表，改动很小。
- **免费 API 限速**：硅基流动免费档限速影响的是入库速度（排队变慢），不影响正确性；量大了转 Pro（¥0.07/百万 tokens，百万 chunk 入库约 ¥35）。
- **端侧设备下线**：MCP 层已有"连不上降级跳过"语义，Agent 检索不到知识库不炸；`/知识库` 命令回复降级文案。知识库是增强能力不是核心依赖，与家里其他 MCP 节点同待遇。
- **QQ 侧无感知**：入库后群里没有通知。一期不做（Web 页面能看到状态）；将来想要可以加 bot 主动推送，但主动消息有频控，价值存疑。
