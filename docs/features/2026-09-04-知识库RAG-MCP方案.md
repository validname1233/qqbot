# QQ 知识库 RAG（端侧 MCP 服务）方案分析

日期：2026-09-04
状态：方案讨论稿（未实施）

## 1. 需求与三个纠结点的回应

设想的使用形态：群里发 `/知识库` → bot 回一条 URL → 浏览器打开知识库管理页（上传/下载/浏览条目）→ 端侧设备存数据 → Agent 通过 MCP 检索（召回）知识库内容，按会话隔离（一群一库、单聊一人一库）。

三个原始纠结点逐一回应：

1. **群文件自动入库 vs 命令模式**：两者都不用选——QQ 官方 bot 平台根本没有文件上传事件（intents 只有 C2C/GROUP 消息类，见 §2），"监听群文件"在官方 API 下做不到，纠结不存在。Web UI 上传是唯一可行路径，而且人肉选择入库天然解决了一刀切问题。
2. **云服务器 40G 容量**：知识库整体放端侧设备，云上零存储，bot 侧只多一条命令和一个 MCP 配置。
3. **向量库运行负担**：也随数据一起挪到端侧。且按 §5 选型，嵌入式向量库（LanceDB）零独立进程，embedding 走免费 API 不跑模型——端侧的实际负担远小于"装个向量数据库"的直觉。

结论：这个"上传管理走 Web、检索走 MCP、数据在端侧"的架构方向是对的，下面是把它落细。

## 2. 平台硬约束（决定方案形态）

- **官方 bot 收不到文件事件**：可订阅的 intent 只有消息类（含 @ 消息、普通群消息需申请）和少量通知类，没有文件上传推送。消息 attachments 也只覆盖图片等富媒体，拿不到文件本体。所以任何"从聊天流截文件"的思路在官方 API 下都不可行，上传必须走外部界面（Web UI）。
- **被动回复 5 分钟窗口**：`/知识库` 是轻命令，秒回，无压力。
- **链接会发进群里**：任何群成员都能看到并点开，这要求链接本身承载鉴权（§6.1），不能是裸 URL。

## 3. 总体架构

```
┌─ 云服务器（qq-bot，40G）──────────┐      ┌─ 端侧设备（公网 IP + 域名）─────────────┐
│                                  │      │                                         │
│  /知识库 命令 service             │      │  ┌─ Web 前端（管理页）────────┐          │
│    └─ MCP 调 kb_issue_link ──────┼──────┼─▶ │ 上传/下载/条目浏览        │          │
│                                  │ HTTP │  │ 链接 token 鉴权           │          │
│  Agent 图 / 深检图               │      │  └────────────┬─────────────┘          │
│    └─ MCP 工具 kb_search ────────┼──────┼─▶ ┌─ MCP server（Streamable HTTP）┐    │
│       （scope 由适配器强制注入）  │      │  │ kb_search / kb_issue_link   │    │
│                                  │      │  │ Bearer key 鉴权            │    │
└──────────────────────────────────┘      │  └────────────┬─────────────┘          │
                                          │  入库流水线：解析→切块→embed→入向量库 │
                                          │  存储：原始文件 + LanceDB + SQLite 元数据│
                                          └─────────────────────────────────────────┘
```

职责切分的原则：bot 云侧只做"入口"（发链接、把召回工具交给模型），端侧做全部重活（存储、解析、检索）。两端只通过两条 MCP 调用通信。

会话隔离键沿用现有 sessionKey 的思路但粒度不同：知识库是**群粒度**（一个群共享一个库），即 `kb:group:<groupOpenid>` / `kb:c2c:<authorOpenid>`。注意这和 session/interrupt 的人粒度 key 不是一回事，MCP 适配器里单独算（§6.2）。

## 4. 现有选型调研（复用 vs 自研）

结论先行：**没有现成项目能直接干净满足"Web 管理 + MCP 检索 + 按租户隔离"三项，建议自研一个薄服务**（体量不大，见 §8）。调研事实：

| 项目 | 状态 | 满足度与硬伤 |
|---|---|---|
| SurfSense（16.1k★） | 活跃 | 最接近：Web 管理 + MCP + Bearer key + RBAC。但 MCP 工具面偏"连接器抓取"而非纯 KB 检索，50+ 格式/连接器全家桶对家用太重，改造量中等 |
| arkon（1.26k★） | 活跃度下滑 | 架构最正（MCP 工具级 scope + 租户隔离），但 PolyForm Internal license 禁止对外提供服务，且 7 容器部署太重 |
| kotaemon（25.7k★） | 活跃 | Web UI 和中文解析好，但**无 MCP 支持** |
| FastGPT / MaxKB / Yuxi | 活跃 | 多租户 + Web 管理最成熟，但对外检索走自家 REST API，MCP 只是客户端角色；可行折中是"平台 + 外包薄 MCP 壳"，等于还是要写壳，还背上了平台本身的重量 |
| basic-memory（3.8k★） | 活跃 | Markdown+SQLite+MCP，但偏个人记忆，无上传 UI 无多租户，AGPL |
| haiku.rag / mcp-local-rag 等 | 小型 | 纯检索 MCP server 无管理台，MCP 仅 stdio，无鉴权无租户——可当检索内核参考，不适合直接用 |

自研的底气：这个服务的核心其实很小——"收文件 → 流水线入库 → 向量检索 + Web 页面读写 SQLite/LanceDB + 两条 MCP 工具"。用 FastAPI（或 Hono）+ 一页前端，比改造 SurfSense 的全家的包袱轻得多。MCP 鉴权按规范走静态 Bearer key（社区自托管主流做法，符合 MCP 安全规范"暴露在 HTTP 上的 server 必须要求某种 token"；OAuth 2.1 全流程对无人值守场景无意义，不追）。

## 5. 技术栈推荐（端侧）

按"几千~几十万 chunk、单台家用设备"的量级：

| 组件 | 推荐 | 理由 |
|---|---|---|
| 向量库 | **LanceDB** | 嵌入式零进程、磁盘式索引内存最省、单目录数据（备份=拷目录）、自带全文+过滤；几十万 chunk 舒适区。备选 sqlite-vec（更极简但 pre-v1 且暴力扫描），Chroma 明确不推荐（HNSW 全内存） |
| 元数据 | SQLite | 条目表、token→scope 映射表、处理状态 |
| 文档解析 | **pypdfium2（数字版 PDF）+ markitdown（Word/PPT/网页）** | 都极轻；中文扫描件/复杂表格的 PDF 将来用 MinerU 离线批处理（16G 内存要求，按需再上） |
| Embedding | **硅基流动 bge-m3 API（免费档）** | 中文顶级效果、8192 窗口、免费限速对家用绰绰有余；DeepSeek 没有 embedding API。隐私硬要求才转本地 bge-small-zh（CPU 可跑但 512 窗口） |
| Rerank | 硅基流动 bge-reranker-v2-m3 API | 召回 top 30 → 重排 → 取 top 5，免费档成本趋近零，不吃端侧 CPU |
| 服务框架 | Python FastAPI + FastMCP（或 Node 单栈） | 解析生态（pypdfium2/markitdown）在 Python 侧最顺；MCP SDK 两种语言都有 |

磁盘估算：1 万个文档 × 平均 20 chunk = 20 万 chunk，bge-m3（1024 维 float32）向量约 800MB + 原始文件若干 GB，端侧设备无压力；将来量级上去 LanceDB 可开量化再省 4 倍。

## 6. 关键设计细节

### 6.1 管理页链接的签发与鉴权

链接发在群里 = 群成员人人可见，所以链接本身必须带凭据。做法：

- server 端 `kb_issue_link(scope)` 工具（MCP 调用，带主 Bearer key）：生成随机 token，存 `token → scope` 映射进 SQLite，返回 `https://kb.example.com/g/<token>`。
- bot 的 `/知识库` 命令调它拿 URL 回群。**同一 scope 重复签发返回同一 token**（链接长期稳定，群成员可收藏），token 只在 server 重置时轮换。
- Web 页面所有写操作（上传/删除）和下载都验 token；纯浏览同权（一期不做"只读链接"，预留）。
- bot 云侧不持有 Web 凭据的任何秘密——签发走 MCP，主 key 只存在于两端的环境变量里。

### 6.2 MCP 工具面与租户隔离（适配器注入）

工具分两类，正好用现有 MCP 层的闸门（MCP_EXPOSE）区分：

- **`kb_search(query, top_k)`——暴露给模型**：进全局工具表，日常 Agent 和深检都能用。租户不靠模型传参（模型会乱传/瞎猜 scope），**靠适配器在 run 内强制注入**：`wrapMcpTool` 的包装层里从 `ctx.event` 算出 `kb:group:<groupOpenid>` 覆盖进 args——和 interact_page 远程内核"桥接层管语义、模型只管意图"是同一个模式，也是当初把适配器落点设计在 bridge run 内的直接兑现。
- **`kb_issue_link(scope)`——不暴露**：不进 MCP_EXPOSE，只有 bot 的 `/知识库` 命令代码直调（client.ts 的 callTool），模型永远看不见它。

### 6.3 入库流水线与召回格式

- 上传后异步流水线：存原文件 → 解析 → 切块（500~800 token，带文档名+章节标题前缀）→ embed → 入 LanceDB；Web 页面显示每个条目的处理状态（排队/处理中/可检索/失败）。
- `kb_search` 返回给模型的是文本块：每条 = 文档名 + chunk 原文 + 简短来源行；适配器做"原文透传、格式整形"，不丢字段（interact_page 远程内核还要用原始结构，保持 client 哑管道的约定）。

## 7. bot 侧改动清单（云服务器）

1. 新 service：`services/knowledge-base.ts`——`/知识库` 命令，调 `kb_issue_link`（直调 MCP client，不经模型）拿 URL 回复；server 不可用时回复降级文案（同现有 MCP 可用性隔离语义）。
2. 适配器：`agent/mcp/adapters.ts` 加 kb_search 的 scope 强制注入（按事件类型算 kb key）。
3. 配置：`MCP_SERVERS` 加 `kb=https://kb.example.com/mcp`，`MCP_EXPOSE` 加 `kb:kb_search`（不含 issue_link）。
4. 前置依赖：client.ts 的 Bearer key 支持（"名字=地址|Key" 格式 + requestInit headers，已在 MCP 鉴权讨论中定型，尚未实施——本功能是它第一个真实用户）。
5. 文档：操作手册加"知识库"章节；命令速查表加 `/知识库`。

## 8. 端侧 server 改动清单

1. 单进程服务：FastAPI（HTTP：页面+上传下载 API）+ FastMCP 挂 `/mcp`（Streamable HTTP + Bearer key）。
2. SQLite 三张表：entries（条目/状态/文件路径）、chunks 元数据（向量 id ↔ 条目）、tokens（链接 token → scope）。
3. 流水线 worker（进程内异步队列即可，不必上消息队列）：解析→切块→硅基流动 embed→LanceDB。
4. 检索：向量召回 top 30 → rerank API → top 5 返回。
5. 前端一页：条目列表（状态/删除/下载）+ 上传控件 + 简单搜索框（复用检索 API 自测）。不做内容浏览（用户已明确一期不做）。
6. HTTPS：域名已有，前置 Caddy 自动证书即可。

## 9. 分阶段实现方案

切分原则：先跑通"存储与访问"的价值闭环（不依赖任何 RAG 组件），检索能力作为增量叠加。阶段一砍掉 LanceDB、文档解析、embedding/rerank——端侧只剩 FastAPI + SQLite 两张表 + 文件目录 + 一页前端，§5 技术栈表里的向量库/解析/embedding 组件自阶段二才引入。

### 阶段一：纯知识库（无 RAG，先能用起来）

目标：群里 `/知识库` 拿链接，浏览器上传/下载/浏览条目，数据按会话隔离地存在端侧。

- 前置依赖：client.ts 的 Bearer key 支持（`名字=地址|Key` + requestInit headers，MCP 鉴权讨论已定型）。
- 端侧 server：
  - FastAPI 单进程：`/g/<token>` 管理页（静态一页）+ 上传/列表/下载/删除四个 HTTP API（均验 token）。
  - SQLite 两张表：`entries`（id/scope/文件名/存储路径/大小/上传时间）、`tokens`（token → scope，同 scope 重复签发返回同一 token）。
  - 文件本体按 scope 分目录落盘（`data/kb/<scope>/...`），不做任何内容解析。
  - `/mcp` 端点挂 FastMCP，只实现 `kb_issue_link(scope)` 一个工具，主 Bearer key 鉴权。
- bot 侧（云服务器）：
  - `services/knowledge-base.ts`：`/知识库` 命令，直调 MCP client 的 `kb_issue_link` 拿 URL 回复；server 不可用回降级文案。
  - 配置：`MCP_SERVERS` 加 kb 条目；`MCP_EXPOSE` 本阶段**不配 kb**（唯一工具是签发，不进模型工具表）。
- 验收：群里发 `/知识库` 收到链接；浏览器能上传、刷新见条目（文件名/大小/时间）、下载、删除；两个群的库互不可见。
- 本阶段不做的：内容提取、内容浏览（条目列表即可）、搜索、只读链接、入库通知。

### 阶段二：RAG 检索（kb_search 上线）

目标：Agent 能按会话召回知识库内容，深检/日常问答可用。

- 端侧：加 `chunks` 表（向量 id ↔ 条目 ↔ 原文）；LanceDB 嵌入式向量库；入库流水线（解析→切块→硅基流动 bge-m3 embed→入向量库，进程内异步队列）；`entries` 表加处理状态字段，管理页显示 排队/处理中/可检索/失败；新增 `kb_search(query, top_k)` 工具（向量召回 top 30 → rerank API → top 5，rerank 可在本阶段后段再加，先纯向量召回也能用）。
- 上传的文件走"存储即入队"，已上传的存量文件补一个"重建索引"按钮（或启动时自动补跑）。
- bot 侧：`MCP_EXPOSE` 加 `kb:kb_search`；适配器加 scope 强制注入（从 ctx.event 算 `kb:group:<groupOpenid>` / `kb:c2c:<authorOpenid>` 覆盖进 args）。
- 格式：Markdown/TXT/数字版 PDF（pypdfium2）；Word/PPT/网页（markitdown）可顺带，属低成本项。
- 验收：上传一个 PDF 后问 Agent"知识库里关于 X 说了什么"，回答引用了该文档内容且只看到本会话的库。

### 阶段三：增强（按需挑选）

- Word/PPT/网页之外的格式：扫描版 PDF 走 MinerU 离线批处理。
- 只读链接（浏览不给下载/删除）、`/重置知识库链接` 命令（换 token，旧链失效）。
- 深检图把 kb_search 纳入起点（进深检注册表，preflight 前先查本地知识库）。
- 本地 embedding 全离线模式（bge-small-zh），隐私硬要求时替换硅基流动。
- 删除联动清向量（阶段二删除条目时向量标记孤儿，这里做物理清理）。

## 10. 风险与预留

- **token 泄露**：链接即凭据，转发即授权。家用场景可接受；将来要收紧时加"重置链接"命令（换 token 旧链失效），server 端已有映射表，改动很小。
- **免费 API 限速**：硅基流动免费档限速影响的是入库速度（排队变慢），不影响正确性；量大了转 Pro（¥0.07/百万 tokens，百万 chunk 入库约 ¥35）。
- **端侧设备下线**：MCP 层已有"连不上降级跳过"语义，Agent 检索不到知识库不炸；`/知识库` 命令回复降级文案。知识库是增强能力不是核心依赖，与家里其他 MCP 节点同待遇。
- **QQ 侧无感知**：入库后群里没有通知。一期不做（Web 页面能看到状态）；将来想要可以加 bot 主动推送，但主动消息有频控，价值存疑。
