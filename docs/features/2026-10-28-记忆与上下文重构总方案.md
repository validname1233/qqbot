## 模块一：新记忆层级（L1 上下文层 × L2 转录层）

### 1. 实现结构

#### 1.1 存储：一张表，两种投影

新表 `conversation_events`（库文件沿用 `data/memory.sqlite`，模块加载时建表）：

```sql
CREATE TABLE IF NOT EXISTS conversation_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  key TEXT NOT NULL,                     -- 租户键 group:<gid> / c2c:<openid>（session/key.ts）
  kind TEXT NOT NULL CHECK(kind IN
    ('chat_user', 'chat_bot', 'process', 'reset', 'summary')),
                                         -- reset=窗口清空标记；summary=预留（延迟实现）
  author_openid TEXT,                    -- chat_user 必填；其余为 NULL
  author_name TEXT,                      -- 同上
  role TEXT NOT NULL,                    -- 投影到 ChatMessage 的 role：
                                         --   chat_user→user, chat_bot→assistant,
                                         --   process→assistant(tool_calls)/tool, reset→不投影
  content TEXT,                          -- v8：chat 行存 QQ 原文（顶层 content 原样，
                                         --   含 faceType 标签；不掺任何我方占位符）
  attachment_ids TEXT,                   -- v8：JSON 整数数组，指向 message_images.id
                                         --   （该消息自带的图片，纯文字消息为 NULL）
  tool_calls TEXT,                       -- process 行专用（JSON 字符串）
  tool_call_id TEXT,                     -- process 行专用
  qq_msg_id TEXT,                        -- chat_user 行必填；process/reset 为 NULL
                                         --   （SQLite UNIQUE 对 NULL 视为互不相等，多行 NULL 合法）
  origin TEXT,                           -- 来源标记：agent/deep-search/poker/reminder/help/
                                         --   unknown-command/restart-gap/…，排查用
  created_at INTEGER NOT NULL,
  UNIQUE(key, qq_msg_id)                 -- chat_user 去重（QQ 会重推同一条事件）
);
-- 投影/reset 定位走 (key, id)（UNIQUE(key,qq_msg_id) 的左前缀只帮 key 过滤，帮不了 id 排序）；
-- L2 回看与 kind 过滤走 (key, kind, id)。当前规模两者都非必需，一行成本先备好。
CREATE INDEX IF NOT EXISTS idx_conv_key_id      ON conversation_events(key, id);
CREATE INDEX IF NOT EXISTS idx_conv_key_kind_id ON conversation_events(key, kind, id);
```

| kind | 谁写 | 投影为 | 内容 |
|---|---|---|---|
| `chat_user` | dispatcher 入站收口 | user 消息 | QQ 顶层 content **原文**（含 faceType 标签；图文混合时文字全文在此，图文相对顺序平台不给）+ `attachment_ids` 引用列指向 message_images 行（**v8：占位符退役**，content 不再掺 `[图片:id]`） |
| `chat_bot` | `qq/messages.ts` 出站收口 | assistant 消息 | bot 实际发出的最终文本（markdown 或纯文本的成功那次） |
| `process` | agent 图节点就地 | **不跨轮投影**（v7；轮内 state.messages + 库内存档） | judge 碎念、tool_calls、tool 结果**原文全文**（零策略，不塑形） |
| `reset` | 装配层（预算溢出时） | 不投影为消息 | 空内容；投影从最新 reset 行之后开始 |
| `summary` | （延迟实现） | user 消息（摘要槽） | phase1 不写入 |

两种读取口径：

- **L1 投影**：最新 reset 行之后的 **chat 行**（排除当前消息 + 渲染 + 预算，
  process 行不投影——v7），供模块二装配；
- **L2 读取**：`WHERE kind IN ('chat_user','chat_bot')`，供 recall_memory。

**v7 动机（2026-10-29 补记）**：QQ 聊天场景中，跨轮次对话的 tool calls 与
assistant 中间信息没有多少延续价值——下一轮真正需要 bot"记得"的，是用户
说过什么（u_n）与 bot 答过什么（最后一条 assistant 成品）；工具过程服务于
当轮查询，成品回复已是当轮信息的蒸馏，细节缺失时重查一次工具即可。这与
编码型 agent 相反：它们的工具结果（文件内容、grep 输出）就是工作材料本身，
必须跨轮保留——场景不同，取舍不同。因此投影口径只取 chat 行：
**后续轮次能看见的本轮痕迹 = u_n + 最后一条 assistant**，过程对仅存
process 档案（L2 审计可查、投影永不读取）。

**v7 缓存账（2026-10-29 查证修正）**：DeepSeek 官方文档（guides/kv_cache）
明确每次请求产生**两个**缓存前缀单元——"用户输入末尾"与"模型输出末尾"
各一个，后续请求完全匹配即可命中。即**模型输出本身是可缓存字节**：下一轮
把它作为 assistant 消息回放进请求，就命中"输出末尾"那个单元（官方多轮
示例正是此形态）。据此核算本架构：
- **直通轮（无工具）零损失**：u_now 恒为单行 blob（与批内行同构），下一轮
  原字节落批；末位 assistant 成品位置不变、字节相同，照样命中。每轮 miss
  仅新 u_now 一条——与普通 agent 的 n-1 等价。
- **带工具轮付一次尾部 miss**：过程对（assistant(tool_calls)/tool）从
  u_n 与成品之间移除，成品位置前移；缓存是位置性的（KV 状态依赖前文），
  无法命中当轮任何单元。miss = 成品 + 新 u_now 两条，一次性代价，下一轮起
  该前缀永久稳定。
- 代价的另一面是收益：过程对不进请求 = 不占预算、不付缓存价（普通 agent
  每轮为几十 KB 过程对付约 1/10 价的命中费，直到压缩），且孤儿配对 400
  结构性不可能（reset 边界恒在轮间）。
- **已知批回退场合（2026-10-29 决议：不修，接受）**：两类消息的批行字节
  ≠ 当轮 u_now 字节——①群@消息（GROUP_MESSAGE_CREATE 路由，库存
  `<@openid>` 原文，u_now 是 stripAtBotMention 后文本）；②显式 `/命令`
  触发（库存含命令词，u_now 是 args）。回退使该批行进入 miss，并连带其
  后全部字节：直通轮 miss 由 1 块（新 u）变 3 块（上轮 user 批行 + 上轮
  成品 + 新 u——本可命中的成品被拖下水）；工具轮由 2 块变 3 块。miss
  一次性：下一轮起该行按库原文确定性渲染、字节稳定，回写缓存即为永久
  前缀，每条此类消息只让下一轮多付一次。群聊旁观者插话使批增长属同类
  （新增行一次性 miss），是记录全部消息的固有代价，非可修复回退。
  修复方向留档不实施：投影渲染端归一化（renderBlobLine 前套 @ 剥离/
  命令词剥离，使批行与 u_now 恒同字节；库存原文不动，L2 保真不受影响）。

#### 1.2 写入点（每类事件恰好一个写入者）

| 事件 | 写入点 | 细则 |
|---|---|---|
| 入站消息 | `events/dispatcher.ts` 的 `dispatch()`，handler 调用**之前**，`await` 完成后再分发 | 先 `persistEventImages`（按事件内**数组序**逐张入库，UNIQUE 改 `(key, qq_msg_id, 序号)`——2026-10-28 实测钉死：一次 N 图 = 1 条事件 N 附件，filename/宽高/大小可全同、fileid 每张唯一，旧约束 `(key,qq_msg_id,filename)` 会静默丢 N−1 张，日志已见案发）拿 id 列表 → 写一行 chat_user：content=QQ 原文、attachment_ids=id 数组；纯附件空文本也落行（content 空串合法）。**串行 await 是有意的**：保证 chat_user 行的 id 恒小于本轮 process/chat_bot 行（时间线正确）；代价是带图消息的回复延迟一次图片下载（≤10s 上限，常态 1~2s）。UNIQUE(key, qq_msg_id) 吸收 QQ 重推 |
| 出站消息 | `qq/messages.ts` 8 个发送函数，`traceOut` 留痕处同步写 | 发送成功才写一行 chat_bot（带 origin）；markdown 回退链只记成功那次；push 系函数加可选参 `opts?: { record?: boolean }`，**progress-bus 调用时传 `record:false`**（进度提示不进任何层），其余调用方默认记录；扑克 DM effect 写入该玩家自己的 c2c 租户键（2026-10-28 决议：效果 DM 视同永不失败，不区分部分成功语义） |
| agent 过程 | `agent/loop.ts` 节点就地 | `llmCall`：每拿到一次模型输出写一行 process（assistant，content+tool_calls）；`toolsNode`：每条工具结果写一行 process（tool，全文）；`plainReply`/`finalize` **零写入**（最终回复由出站收口记唯一的 chat_bot，轮次闭合） |
| 预算溢出 | 装配层（模块二 §1.1 第 6 步） | 现场追加一行 reset |
| 进程启动 | ~~写 restart-gap 断痕行~~（**2026-10-28 撤销**：断痕机制整体摘除——设计初衷是标记"进程宕机期间的 L2 空洞"，但空洞本身不可记（事件没到过 bot），标记只是"记一个无"；真机首跑还因 kind 误定 chat_bot 进了 L1 投影引发 bug。`writeRestartMarkers`/`distinctChatKeys` 已删，重启的 L2 空洞接受静默存在） | — |

#### 1.3 读取路径

**L2（recall_memory v4，重写为零参数工具）**：

```
入参：无（schema = { type:"object", properties:{} }）
流程：取最近 N 条 chat 行（正序）
  → 渲染文本包（"昵称：…" / "bot：…"；[图片:id] 作为字面文本保留，不触发识图）
  → 文本包 < RECALL_SUMMARY_MIN_CHARS：原文直返，不过 LLM
  → 否则 flash 模型（callModel, config.aiModel）：提示词锚 = 用户当前问题
    （runTool 的 ctx.args 原话），产出 ≤200 字摘要 + 自选 ≤5 条最相关原文行（逐字）
  → 摘要调用失败：返回固定短语"记忆检索暂时失败"（绝不倾泻文本包）
```

**图片（message_images 表，v8 改造）**：

- **schema 改动**：新增 `fileid TEXT`（图片全局唯一身份，排查/跨消息比对用，
  不做约束键）、`seq INTEGER`（事件内数组序）；**UNIQUE 从 `(key, qq_msg_id,
  filename)` 改为 `(key, qq_msg_id, seq)`**——同消息多张同元数据图（实测
  filename/宽高/大小可完全相同）不再被 OR IGNORE 静默吞掉。改法：测试环境
  直接改 DDL 重建表（无兼容负担，与主表 DROP 同批处理）；
- **prune 锚点**从 `COLD_MESSAGES`（旧表 300 行）改为：最近 N 条 **chat 行**
  内被 `attachment_ids` 引用的图片保留（N 与 recall 同源 `RECALL_DEPTH_N`），
  窗口边界查询改打 `conversation_events`；
- **描述确定性规则不变（缓存红线）**：description 一经回写永不重写（行丢失
  时宁可降级 `[图片]` 也不重新识图，保前缀字节稳定）；
- **IDOR 顾虑消失**：引用在结构化列里，用户手打 `[图片:101]` 不再可能引用
  他会话的图（那只是无害的用户文本）。

**富媒体事实模型**（2026-10-28 三轮真机实验钉死，设计依据）：一次 N 图 =
1 条事件 N 附件（attachments 为该消息全量）；fileid 每张唯一、filename 等
元数据可全同；图文混合时顶层 content 带文字全文，**图文相对顺序平台不给**
（content 为纯文本无内嵌标记）——render 的"文字前图后"是自定义规范顺序，
无保真义务；纯图消息 content 含 faceType 表情标签（原样保留在 L2）；
多图叠加 QQ 重推由两层 UNIQUE 各自吸收（events 层 `(key,qq_msg_id)`、
images 层 `(key,qq_msg_id,seq)`）。

**长期记忆：置空**。`buildLongTermContextText` 注入删除；add/delete/clear 三
个记忆工具不再注册（表与数据原样保留）；未来按 skill 式注入 system prompt
（拼进租户稳定前缀段），另期设计。

**deep-search 边界（2026-10-28 确认）**：进程内消息流（browseLlm 的编号
链接/思维链）完全不动、不进 L1；唯一要求是**结果进 L2**——问题行由
dispatcher 入站收口记（用户发的 `/深度检索 xxx` 是普通 chat_user），报告由
出站收口记 chat_bot，两条路径自动覆盖，深检自身零改动（手拼入库段删除即可）。

## 模块二：上下文注入

### 1. 实现结构

#### 1.1 装配管线（新增 `src/agent/assembly.ts`）

**无状态**：每次 /Agent 触发时从 L1 重投影，跨轮无内存态（LangGraph state 只
活在单次 invoke 内；轮内 state.messages 是唯一的活动副本）。管线为纯函数序贯
执行，步骤顺序及理由：

| # | 步骤 | 规则 | 顺序理由 |
|---|---|---|---|
| 1 | 取数 | 最新 reset 行之后的 **chat 行（kind IN chat_user, chat_bot）**——**process 行永不跨轮投影**（v7，见 §1.2 决议块） | reset 之外的行不读；process 不读，预算全部留给对话 |
| 2 | 排除当前消息 | `qq_msg_id` 等于本轮事件的 chat_user 行不投影 | u_now 恒由 ctx 构造（恒在末尾、带当轮标注与展开；防 bystander 插入抢占末位） |
| 3 | 说话人标注 | chat_user 行渲染加标注（形态由探针定：甲 `name` 字段 / 乙 u-registry / 丙 `「昵称」`包裹 / 丁 每条消息 content 包装成 `{"speaker":"…","content":"…"}` JSON 对象——前三者全失败时的兜底，历史与 u_now 形成"JSON=背景、明文=现场"的带内判据） | — |
| 4 | 图片渲染（v8：引用列驱动） | 遍历该行 `attachment_ids` → 批量查 `message_images`（含 description 缓存，未识图的此刻识图并回写）→ 按规范顺序拼渲染文本：**文字在前、图片段在后**（`看这只猫 [图片]{描述1} [图片]{描述2}`；超 `VISION_MAX_IMAGES` 降级 `[图片]`）。占位符正则解析退役——入口从"扫 content 字符串"变为"遍历结构化 id 列" | 先于估算——展开会变长，后算会低估 |
| 5 | token 估算与预算闸门 | 对投影总量估算（字符启发式纯函数：中文≈0.7 token/字、ASCII≈0.25 token/字符，×1.2 安全系数）。**超 `CONTEXT_TOKEN_BUDGET` → 追加 reset 行，投影清空**（system + u_now 恒保留）；条数安全阀 `CONTEXT_MAX_MESSAGES` 同样触发 reset；**静默分段触发**：距上一条 chat 行超过 `SESSION_IDLE_RESET_HOURS` 小时，本轮装配前先追加 reset（会话自然分段，时序截断的缓存友好形态——见 §1.2 决议块） | 最后一步：前四步的产物才是被预算约束的对象 |

（v5 版的"尾部闭合过滤"步骤**删除**：process 行不再投影后，残缺轮、悬空配对、
中断轮补插缓存异常三个问题结构性消失，无需过滤。）

#### 1.2 三条调用路径的消息形态

**v9 决议（2026-10-28，直通架构）：三场景合并为单一 `agent_unified`，
plainReply 节点删除，finalize 改造为轮次触顶的按需降级分支。**
起因：真机证实 v6"保留碎念"是错误决议——plain/finalize 的输入末位是
judge 的 assistant 输出，模型将其当作"自己说到一半的话"续写（回复只有
后半句）。提示词层无法根治（结构信号强于文字信号），只能架构性消灭：
直通后无工具路径由 llmCall 直接产出带人格的最终回复，碎念作为中间产物
结构上不存在。参考 dsh/Claude Code 的单节点直通 + 按需强制收尾模式；
**轮次上限暂保留 MAX_TOOL_TURNS**（token 预算判定属二期，未校准的
估算器不做路由决策——触发器二期再换）。

```
新图（四节点）：
START → prepareContext → llmCall ──(有 tool_calls 且轮次未满)→ tools ─┐
                            ↑                                         │
                            └─────────────────────────────────────────┘
             ├──(无 tool_calls)→ 直出最终回复（带人格）→ END
             └──(轮次触顶且最后是 tool)→ forcedFinalize → END

forcedFinalize（降级分支）：
  输入 = state.messages 原样（同 system、同模型——缓存家族不分裂）
  + 不传 tools（协议级逼出文本：无工具可选，只能作答）
  + 末尾注入恒定降级 user 消息（"工具调用轮次已用尽，请基于已获得的
    工具结果直接给出最终回答"——文本恒定，缓存伤害最小化）
主动停路径（看完工具结果输出纯文本）：该输出即最终回复，直接 END，
不经过 forcedFinalize（天然有内容可出）。
```

**system 合并**：`agent_unified` ≈ 人格（继承 daily）+ 工具使用规则
（继承 judge 但重写措辞）+ 输出格式 + 图片/说话人说明 + **收尾规则前置**
（"不提及调用过工具""专业内容收语气"从 finalize 场景改为全程行为准则）。
≈2000 字（现 judge 673 的 3 倍）。收益：每轮省第二次调用的 system miss
（~1000 token）；judge 家族失去跨租户共享（按租户各建缓存）。
已知赌注：人设干扰工具判断（旧实测结论，直通翻案——mock e2e 的
tool_calls 准确率用例验证）。

**提示词总纲（2026-10-28 定稿）：System 管"怎么读"，user 管"读什么"。**
所有预制指令（人格、格式规则、说话人说明、意图推断框架、收尾指令——
**INSTR 已取消**，收尾职责并入 `agent_finalize` 的 system 文本）一律住
system；user 侧 100% 是数据，零例外。system 按"租户×场景"恒定（人格可被
/set_personality 低频覆盖，此外不得含任何逐轮变化的内容——时间戳、召回
结果、消息数都禁止，这是缓存家族的锚）。

**层级口径澄清（v7 后的准确表述）**：user 侧装载的是 **L1 投影**——每轮
从 L2 的 chat 行装配出的工作副本（不落库）；L1 不是库里的行，process/reset/
chat 行都是"源"，L1 是它们的视图。"L1 入库"在 v7 后不存在。

```
judge:    [S_judge,    ...L1投影(历史), u_now]                          （带 tools）
plain:    [S_daily,    ...L1投影, u_now]                                （无 tools）
finalize: [S_finalize(含收尾指令), ...L1投影, u_now, ...本轮 assistant/tool 序列]
```

- **形态 A（per-message）**：逐条投影，每条 QQ 消息一个数组元素，说话人走
  结构化标注（探针定甲/乙/丙/丁）；
- **形态 B（追加式 blob，2026-10-28 终版：批仅含用户行，bot 行以裸 assistant
  隔断）**：chat 行流中 **chat_user 行**（含 bystander）按分批规则打成 user
  消息批（结构化数组文本，`{"speaker":"小明","content":"…"}` 逐行）；
  **chat_bot 行不进批**，以裸 assistant 消息投影——语言顺序即聊天顺序
  （user 批 → bot 回复 → user 批 → …），数组时间线自然、缓存纯尾部追加：

  ```
  [S][ B_1(user行…) ][ a(bot回复) ][ B_2 ][ a ][ … ][ B_k(…+u_now) ]
  ```

  - **分批锚 = chat_bot 行**：批 = 两个 bot 回复之间的 user 行段；一轮产生
    多条 chat_bot（命令回复 + 观察者回复，handler 逐条 seq=1,2,3 发送）时，
    **连续 chat_bot 序列整体作一个隔断**（第一条封批，其后不开空批；连续
    assistant 协议安全已在 v6 决议块实证）；
  - **u_now 独立成条（2026-10-28 实现定稿，取代"末批末位"的方案原文）**：
    u_now 由装配层构造为独立的最后一条 user 消息（blob 单行格式与批内行
    同构）。判据从"批内末行 = 当前诉求"（依赖装配时序，末批边界不总可靠）
    升级为"**全数组唯一单独成条的消息 = 当前请求**"（位置 + 形态双重锚定，
    不依赖装配时序）。提示词方向句（终稿待真机样本后定）："历史消息以结构化
    数组（多条对话打包成一条消息）给出，每行形如 {\"speaker\"…,\"content\"…}；
    最后一条单独的消息是用户当前的请求，请结合上方历史理解它的语境，然后
    回应这一条——历史消息只是背景，不要逐条回应。"连续 user 消息的协议安全
    已实证（v6 决议块探针用例 A/C）。工具循环的裸 assistant/tool 序列紧跟
    u_now（协议层）；
  - **增量追加天然成立**：bot 回复生成于第 N 轮数组末尾，第 N+1 轮仍在原位
    （其后只是尾部新增新批），无中部插入；每轮 miss = 上次装配以来的新增行，
    断点只在 reset；
  - **单聊不退化**：c2c 场景 speaker 字段同样保留——身份字段噪声极小且提供
    称呼锚点，统一语义为将来垂直领域微调节约数据清洗成本；
  - **取舍记录**：blob 不是群窗口的逐字镜像（不含 bot 行），是"用户侧发言流"；
    镜像职责由 L2 承担，L1 投影给模型的是工作视图。"下一条 user 评论 bot
    回复"的上下文诉求由裸 assistant 就在批间满足。
  - **变体探索记录（均已否决）**：①全镜像批（bot 行进批）——批需在下一轮
    吸收 bot 行续写，等效中部插入，每轮断点退到倒数第一批；②双重出现
    （批内 bot 字段 + 裸 assistant 并存）——裸 assistant 恒被夹在"旧批末、
    新批头"的缝隙（第 N 轮在数组末尾、第 N+1 轮在中部），必须移动即前缀
    改写，数学不可行。两者教训同源：任何"已发送内容需要在下轮改位/续写"
    的形态都破坏追加式。

**实验设计（2026-10-28 定稿：双 branch 离线对打，非配置开关）**：形态 A 的
可测实例 = 现状 main（20 条热窗口 + 昵称前缀，per-message 精神；注意其窗口
是滑动的，缓存预期低——这本身是待证实项）；形态 B = 新开 branch 实现。
评测为**离线脚本对打**：一份脚本分别 import 两个 branch 的装配函数，喂同一组
测试输入（多说话人/指代/追问/闲聊干扰的群聊消息序列 + /Agent 触发点），对比
三项——①意图与身份识别质量（judge 的 tool_calls 判定、说话人指认，人工
评分）；②`prompt_cache_hit_tokens` 占比（API usage 直读）；③token 成本。
已知局限：测的是"A朴素 vs B"；"B vs 缓存修好的 A"（打包粒度的净贡献）是
二期可选实验，需要 A 满配（append-only + reset），一期不做。两形态共享本
管线其余全部设计，B 胜出后 per-message 分支仅存档。

```
judge:    [S_judge,    ...chatHistory(per-message, 标注), u_now(明文)]      （带 tools）
plain:    [S_daily,    ...chatHistory, u_now]                              （无 tools）
finalize: [S_finalize, ...chatHistory, u_now, ...本轮 assistant/tool 序列, INSTR]
```

- chatHistory 里的 assistant 行来自 chat_bot（bot 的最终回复）——**过去轮的
  工具痕迹（process）不跨轮出现**，"上轮我搜过什么"由最终回复承载（结论吸收，
  深检"只落问题+报告"的同款取舍）；轮内工具循环不受影响（state.messages）；
- `u_now` 由 `buildCurrentUserMessage(event, userText)` 构造：userText +
  `[图片:id]` 占位符（按 key+qq_msg_id 查 message_images，dispatcher 已持久化）
  → 走与历史行相同的标注/展开规则，但**不加大意标注包装**（保持明文，维持
  背景/现场的形态判据）；
- plain 不再有长期记忆注入位（置空）；
- **plainReply 不再 slice 碎念（v6 决议，2026-10-28 实证加固：选项二保留）**：
  旧逻辑 `slice(1,-1)` 在新架构下自然消失（plain 从投影重建，而投影是轮首
  快照，本轮碎念此刻尚未生成）。judge 的无工具碎念**保留在 plain 的输入里**
  （作为 L1 存储中的思维链痕迹）。**连续 assistant 协议安全已实证**：
  `test/probe-consecutive-assistant.mts` 四用例（历史连续 assistant×2/末位
  assistant 续写形态/连续×3/对照）全部通过，DeepSeek 仅校验 tool 配对（孤儿
  tool 才 400），连续 assistant 无限制——9-18 记忆中的"连续 assistant 报错"
  系两问题串线。**碎念塑形升级为固定话术**（本轮决议）：agent_judge 指示
  无工具路径输出"这是一条普通消息，正常回复即可"式的一句话——固定话术
  使碎念永远完整自洽（杜绝半截话引发 plain 续写倾向），且形态可被提示词
  识别（daily 的 system 可声明"上一条 assistant 若为该判断话术，它是路由
  中间产物，请无视其表达、直接回答用户最后的问题"）。备用方案（plain 构造
  时 filter 掉碎念）降级为实测出续写怪话时的补救，一行代码的事；
- finalize 复用真实消息序列（`state.messages` 去掉开头 S_judge），末尾追加
  **恒定**的收尾指令 `INSTR`（一条 user 消息，文案固定如"请基于以上对话与
  工具结果，直接给出对用户的最终回复。"）；不再把历史重引用成平文本；
- S = 既有 `getSystemPrompt(event, scene)`，builder 不动。

#### 1.3 system prompt（functional.ts）改动

- `SPEAKER_NOTE` v2（三段）：①说话人标注格式说明（按探针结果填写；声明标注
  由平台添加、正文是用户原话）；②群聊背景规则（历史大多不是对你说的，只回应
  本轮触发的那条消息）；③焦点规则（最后一条 user 消息是当前诉求）+ 功能性
  bot 消息说明（历史 assistant 可能含扑克/提醒等功能消息）；
- `agent_judge`：**开头增加意图推断框架句（v7）**："结合上方带说话人标注的
  历史消息，推断用户当前的意图；再思考这次回复是否需要调用工具——需要则
  准确识别工具名与参数，不需要则不输出任何 tool_calls。"；**提示词纪律
  （2026-10-28 决议）：system 中不写任何具体工具的特征识别指引**（如
  "遇到最近/最新的信息先调 get_time"这类逐工具编排句）——工具的选用由
  tools 列表的 description 自描述，system 只给通用判断框架；逐工具编排是
  无谓噪声，且工具增删时提示词会静默过期；删"（关键词用对话里可能出现的
  原词）"句；recall_memory 编排句**随本纪律一并删除**（description 自足）；**无工具路径改写（v6 终版：固定话术）**：把
  "请不要调用任何工具，直接以普通文字回答"改为"若确认无需调用任何工具，
  请只输出固定的一句：『这是一条普通消息，正常回复即可』，不要在此时展开
  正式回答——正式回答由后续环节生成"。固定话术的作用：①永远完整自洽，
  杜绝半截话引发 plain 路径的续写倾向；②形态可被提示词识别——daily 的
  system 声明"上一条 assistant 若为该判断话术，它是路由中间产物，请无视
  其表达、直接回答用户最后的问题"（连续 assistant 协议安全已实证，见
  §1.2 v6 决议块）；
- `agent_finalize`：措辞对齐真实消息序列（不再是"你能看到的是…收集到的"）。

#### 1.5 边界与不变量

- **窗口 = 查询，不存在窗口管理器（2026-10-28 终版原则）**：窗口是
  `SELECT … WHERE id > 最新reset AND kind IN (chat…)` 的动态结果，每次装配
  现算、算完即弃；**所有窗口操作（预算清空、二期静默截断、二期压缩）一律
  收敛为"往 append-only 流写标记行"**（reset / 未来 summary）——流的边界由
  标记定义，标记与消息同库同流，没有第二本账、没有缓存失效、没有竞态；
  failover 天然一致（新实例读到同一标记即得到同一窗口）。曾讨论过的"窗口
  管理器/内存台账/增量装配"方案作废——那是为压缩预设计的缓存，而压缩本身
  也能用标记行表达，缓存失去存在理由；进程内不做任何跨装配的窗口状态。
- reset 边界恒在轮与轮之间 → tool 配对永不被切断（孤儿结构上不可能）；
- 同一行恒渲染同一字符串（描述不重写、标注确定性）→ append-only 期间前缀
  字节稳定，缓存命中；
- 中断轮被后续 chat_bot 闭合后重新进入投影 → 补插点一次前缀 miss，自愈（接受）；
- bystander 行与 reset 写入的竞态（装配读快照后、reset 落行前插入的行会被
  一并清掉）：罕见，接受；
- 轮内增长（tool 结果追加）不受预算约束，由 `MAX_TOOL_TURNS=2` 兜底；
- 预算小于单条消息的退化：投影可为空，system + u_now 恒在。

### 二期：优化与精细化（一期跑稳后，逐项独立排期）

- **静默分段**（`SESSION_IDLE_RESET_HOURS`）：config 键一期就建、默认 0
  （关闭），二期开启并调参——纯开关行为，零代码改动；
- **blob 优化**：一期 blob 按固定 n 条分批，二期可做按 token 自适应分批
  （批大小随消息密度调整）、批内消息数上限与预算的联动；

  原则下，实现形态就是"断点处写 summary 行"，管线加一条投影规则即可）；
- **usage 观测与估算校准**：callModel 补 `usage` 解析（hit/miss 落日志），
  实测值反哺 `estimateTokens` 的启发式系数；预算/reset 频率调参；
- **"B vs 缓存修好的 A"对照实验**（§1.2 已记录的可选实验）：量化打包粒度
  的净贡献；
- **长期记忆 skill 式 system 注入**、**新结构日志方案**：另期设计（v5 决议）；
- **failover 存储**：双机热备时 SQLite 的同步方案（共享存储/复制/全新实例
  三选一，2026-10-28 讨论已记录方向：窗口侧零改动，复杂度全在存储层）。

### 分期边界原则

一期只做"正确性必需"，二期收纳"优化项"；判断标准——**砍掉它一期行为是否
错误**：blob 不去重 → 每轮多付重复 token（贵但正确）→ 可二期；UNIQUE 不修
→ 丢图（错误）→ 必须一期；静默分段不做 → 只是上下文多带旧会话（正确但冗余）
→ 可二期；reset 不做 → 预算失控（错误）→ 必须一期。
