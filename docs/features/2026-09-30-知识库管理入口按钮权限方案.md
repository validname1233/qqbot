## 0. 背景与已验证事实

需求：群场景下，知识库管理页入口只对**群主/管理员**开放；普通群员不得进入管理页（上传/删除）。检索（kb_search）不受影响，保持全员可用。

方案演进过程中的已验证平台事实（全部真机，2026-09-30）：

| # | 事实 | 验证方式 | 对方案的影响 |
|---|---|---|---|
| 1 | 群事件**不下发** `author.user_openid` | /私聊我 探针命令（结果①），author 原文进了 detail 日志 | "群里认出管理员→主动私聊发密码"死路 |
| 2 | 同一账号的 `member_openid` 与 `user_openid` **相同**（单样本） | parseEvent 两行 info 日志（群/单聊各发一条，对比 authorOpenid） | 文档"场景隔离"语义与真机不符；type=0 `specify_user_ids` 备选因此可行 |
| 3 | `member_role` 官方声明随 User 下发（member/admin/owner） | 文档类型表+示例；真机 detail 日志待 grep 复核（见实验 0） | 命令层身份判断的数据来源 |

被否决的路径：私聊发密码（事实 1 阻断，事实 2 其实复活了它但按用户决策走按钮）、邮箱通道（太重，用户否决）、纯短时效链接（可用但是备选）。

**选定方案**：管理入口链接通过**消息按钮（keyboard）的跳转动作（type=0）**下发，按钮 `permission.type=1`（仅管理员可操作）由平台在客户端强制执行。

## 1. 架构原则：QQ 权限归 QQ 端，MCP 零改动

> 所有 QQ 相关的权限控制留在 QQ 机器人端；MCP 端保持干净的内容服务。

MCP_RAG 端（mcp.ts / web.ts / db.ts）**一个文件都不改**。它不知道"群管理员"是什么，也永远不学：

- **不加**角色字段、**不加**管理密码、**不加** token 过期、**不加**管理员名单；
- 保留现状：`kb_issue_link` 幂等签发（scope → token）、web 层 token 即凭据、SQL 层 scope 硬隔离。

理由：`member_role`、群、按钮是 QQ 的社交语境概念；RAG 是通用检索服务，感知上游平台角色只会污染它的模型（将来接别的客户端时这些字段全是死重）。权限的全部语义由 QQ 侧两道闸承担（见 §2）。

## 2. 权限模型总览：两道闸 + 一个不变量

```
群员发 /知识库管理
   │
   ▼
① 命令层闸（bot 代码，knowledge-base.ts）
   event.authorRole ∈ {admin, owner} ？
   ├─ member / null → 回拒绝文案；不调 kb_issue_link，不签发任何东西（fail-closed）
   └─ 通过 ↓
② 签发（MCP，无权限概念）kb_issue_link(scope) → URL（幂等，同 scope 同 token）
   │
   ▼
③ 平台闸（客户端强制，messages.ts + qq/keyboard.ts）
   回一条 Markdown 消息 + 跳转按钮（action.type=0，data=URL，permission.type=1）
   链接藏在按钮 action 数据里，客户端只渲染按钮文字，URL 永不以文本落地群聊
   非管理员点不动（即便从群历史里翻出这条老消息）
   │
   ▼
④ 管理页（web.ts，现状不动）：token 鉴权，进入即用
```

- **双保险**：① 是我们代码判断（明确拒绝文案 + 不为普通成员签发 token，保持 tokens 表干净）；③ 是平台判断（客户端级强制，撤职实时生效）。两者缺一都有明确缺口：只留 ③ → 普通群员拿到一个永远点不动的按钮，体验差且 kb_issue_link 白签发；只留 ① → 链接以文本落地群聊，回到原点。
- **不变量（本方案的核心红线）**：管理页 URL **永远不以文本形式出现在群聊消息里**——包括一切失败降级路径（见 §4.3）。
- **单聊**：同样以按钮下发（type=2 permission——单聊无管理员概念，消息天然只有本人可见可点）。降级与群聊刻意不同：单聊通道私密，按钮发送失败时回退纯文本链接（红线只约束群聊）。2026-09-30 实施时按用户决策统一为按钮形态。

## 3. 各层改动明细

### 3.1 QQ 端·事件层（events/GROUP_MESSAGE_CREATE + GROUP_AT_MESSAGE_CREATE）

干净事件新增一个字段：

```typescript
authorRole: "member" | "admin" | "owner" | null;
```

- 提取自 `raw.d.author.member_role`；守卫类型签名加 `member_role?: string`；
- 非法值/缺失 → `null`（**fail-closed**：调用方把 null 当 member 拒绝，绝不默认放行）；
- 两个群事件定义对称改；C2C 事件不动（单聊无角色概念）；
- `services/scheduler/cron.ts` 的 fake 事件补 `authorRole: null`；
- 不加 `authorUserOpenid`（事实 1 已关闭该路径，不为死路留字段）。

### 3.2 QQ 端·发送层（新文件 qq/keyboard.ts + qq/messages.ts）

**qq/keyboard.ts（新）**——按钮的框架知识，与 messages.ts 同层（"按钮长什么样"是传输层知识，不进业务）：

```typescript
// 跳转按钮（action.type=0）：data 填 URL，客户端点击后打开
export function jumpButton(
  id: string, label: string, url: string,
  permission: { type: 0 | 1 | 2; specify_user_ids?: string[] } = { type: 2 },
): KeyboardButton;

// 包装成 keyboard 字段的长形式
export function keyboardOf(rows: KeyboardButton[][]): { content: { rows: ... } };
```

实现要点：label ≤10 字符（超限错误码 40034029，5×5 上限同源）；permission **显式传**，不赌省略默认值（详解文档 §5 注意事项）。

**qq/messages.ts**——新增一个带键盘的群 Markdown 被动回复：

```typescript
export async function replyGroupMarkdownWithKeyboard(
  groupOpenid: string,
  markdownContent: string,
  keyboard: { content: { rows: unknown[] } },
  msgId: string,
  msgSeq = 1,
): Promise<void>;
```

body 结构 = `replyGroupMarkdown` + `keyboard` 字段（`msg_type:2` + `content:""` + `markdown.content` + `keyboard.content.rows` + `msg_id/msg_seq`）。带 msg_id 走被动回复，不占主动推送频控。

### 3.3 QQ 端·命令层（services/knowledge-base.ts）

群分支重写为"验角色 → 签发 → 自发按钮消息 → 返回 null"：

```typescript
async handle(ctx) {
  const event = ctx.event;
  if (群事件) {
    // 闸①：fail-closed，null 视同 member
    if (event.authorRole !== "admin" && event.authorRole !== "owner") {
      return "知识库管理只能由群主或管理员使用哦～";
    }
    const outcome = await callTool("kb", "kb_issue_link", { scope: kbScope(event) });
    // …失败回降级文案（现状逻辑）
    const url = …;
    try {
      await replyGroupMarkdownWithKeyboard(
        event.groupOpenid,
        "**本群知识库管理入口**\n点击下方按钮打开管理页（仅群主/管理员可点击）",
        keyboardOf([[jumpButton("kb_open", "打开管理页", url, { type: 1 })]]),
        event.msgId,
      );
      return null;            // 已自行发送，抑制 handler 的默认回复
    } catch (err) {
      logger.warn("kb", `管理入口按钮消息发送失败: ${…}`);
      return "管理入口发送失败了，稍后再试～";   // ★ 降级文案不含 URL（红线）
    }
  }
  // 单聊分支：维持现状（纯文本链接回复）
}
```

两个关键点：

1. **返回 null 抑制默认回复**：handler 的 for-loop 会把返回字符串用 `replyGroupMarkdown` 发——它不带 keyboard 参数，发不出按钮。所以按钮消息必须命令层自发，返回 null 后 handler 自然静默（`replies` 过滤掉 null，不发任何消息）。
2. **失败降级不走 handler 的"Markdown 失败回退纯文本"链**：那条链会把正文用纯文本重发——URL 就落地了。命令层自己 catch，降级文案只说"失败了"，绝不带 URL。

### 3.4 QQ 端·速查表（docs/features/2026-08-31-命令速查表.md）

`/知识库管理` 行补充：群聊仅群主/管理员可用，入口以按钮下发。

## 4. 关键设计决策与理由

### 4.1 为什么命令层不省（全托给平台按钮）

普通群员触发时，命令层给出明确文案"只能由群主或管理员使用"，比一个点不动的按钮体验清楚；更重要的是**不为无权者签发 token**——tokens 表只反映真实管理者的签发历史，审计干净。

### 4.2 为什么平台闸不省（只留命令层）

命令层挡住的只是"当场领链接"；已签发链接以文本落地群聊后，撤职、退群、转发都管不住。平台按钮闸恰好补上：链接永不落地文本，点击资格客户端实时判定。

### 4.3 降级链路的特殊性（与全局"Markdown 失败回退纯文本"的例外关系）

handler 对普通回复的降级是保内容可达（纯文本重发）。本命令的消息**内容本身就是敏感载荷**，降级目标从"内容可达"变为"URL 不泄露"——宁可这次不发（管理员稍后重试），不可把 URL 裸发进群。这是对全局降级策略的一个显式例外，原因写进代码注释。

### 4.4 残余风险的接受边界

- token 依然是 bearer 凭据：本方案防"链接落地群聊被任何人翻出"，**不防**管理员定向泄露（转发 URL、浏览器历史/收藏）。与家用安全模型一致，web 层不加会话概念（保持 MCP 干净）。
- 存量群历史里的旧纯文本链接依然有效。若要作废：重置 token（tokens 表 DELETE 该 scope 行后重新签发即得新 token，旧链自然 404）。是否做一次性清理，部署后另行决定。

## 5. 可行性验证方案（真机实验，先于正式实现）

依据 keyboard 详解文档的【文档未说明】清单，共 5 项实验，按依赖顺序执行：

### 实验 0（零成本前置）：member_role 是否随群事件下发

```bash
grep "author 原文" data/logs/*.log
```

dm-probe 探针当时把两个群事件的 author 整段 JSON 写进了 detail 日志（14 天保留期内都在）。看 `member_role` 在不在。

- **在** → 闸①数据源确认，继续。
- **不在** → 闸①失效。降级：a) 只靠平台闸（普通群员也签发但点不动——违背 4.1，最后手段）；b) .env 配 `KB_GROUP_ADMINS=<member_openid,...>` 白名单（家用场景群主就是自己，可接受）。

### 实验 1：自定义 keyboard（长形式）能否发送——方案的生死开关

详解文档 §2：长形式标注【内邀开通】，社区实践不少 bot 能直接用，报错则是未开通。

探针命令 `/按钮测试`（群聊触发，临时 service，dm-probe 模式，验证完删）：

```typescript
await replyGroupMarkdownWithKeyboard(
  event.groupOpenid, "**按钮链路测试**",
  keyboardOf([[jumpButton("test_open", "打开测试页", "https://bot.q.qq.com", { type: 1 })]]),
  event.msgId,
);
```

- **按钮渲染可见** → 长形式可用，继续实验 2。
- **HTTP 报错（未开通类错误码）** → 本方案整体作废，退回短时效链接备选（见 §7）。

### 实验 2：permission.type=1 的"管理员"判定范围（文档明标【未说明】）

同一测试按钮，三种角色各点一次（群主、普通管理员、普通群员）：

| 角色 | 预期 | 若实际不可点 |
|---|---|---|
| 群主 owner | 可点，跳转 | type=1 语义严重偏离，转 type=0 |
| 管理员 admin | 可点 | 判定为"仅机器人管理员"（开放平台后台配置的概念）→ 转下述 type=0 |
| 普通群员 member | 点不动 | — |

**备选 type=0 + specify_user_ids**：`{ type: 0, specify_user_ids: [<member_openid>] }` 精确放行。事实 2（两种 openid 相同）+ 事实 3（member_role 随事件下发）使它完全可行：bot 观察群消息即可维护"当前群的管理员 openid 集合"（每条消息的 authorRole 实时刷新），发按钮时填进 specify_user_ids。代价：多一张 role 缓存表，仅在 type=1 语义不符时启用。

### 实验 3：无权限用户点击的体验（与实验 2 同批完成，零额外成本）

member 点击后是置灰、无反应还是 toast 报错（详解文档【未说明】）。只影响拒绝 UX 文案，不影响安全性——顺手记录即可。

### 实验 4：QQ 内置浏览器里管理页是否可用

跳转按钮大概率唤起 QQ 内置 webview。需要真机走一遍管理页核心流：页面加载（token 从 URL 路径进 localStorage）→ 上传 → 列表 → 删除 → 下载。重点观察 webview 的 localStorage 隔离行为（刷新/二次进入是否还认得 token）。若有问题，属前端改造（page.ts 层面），不伤权限架构。

### 判定汇总

| 实验 | 验证什么 | 通过判定 | 失败后果 |
|---|---|---|---|
| 0 | member_role 下发 | author 原文含该字段 | 白名单降级 |
| 1 | 长形式 keyboard 可用 | 按钮渲染可见 | **方案作废** → 短时效链接 |
| 2 | type=1 语义 | 群主+管理员可点、member 不可 | 转 type=0 + specify_user_ids |
| 3 | 拒绝 UX | 记录形态 | 仅影响文案 |
| 4 | webview 管理页 | 上传/删除全流程正常 | 前端改造，架构不变 |

## 6. 实施顺序

- **Phase A（验证先行，dm-probe 模式）**：qq/keyboard.ts + messages.ts 的 `replyGroupMarkdownWithKeyboard` + 临时命令 `/按钮测试`。跑实验 0-4，记录结论到本文档附录。
- **Phase B（正式接线）**：事件层 authorRole → knowledge-base.ts 闸门+按钮化 → scheduler fake 事件补字段 → 速查表更新 → 删 `/按钮测试`。typecheck + 断言（authorRole 提取三形态：有值/缺失/非法值）。
- **Phase C（可选清理）**：存量群历史旧链接的一次性 token 重置。

Phase A 的产出（keyboard.ts、发送函数）在 Phase B 原样复用，探针只有命令本身是临时的。

## 7. 备选路径（实验 1 失败时）

短时效链接档：tokens 表加 `expires_at` 列，kb_issue_link 每次签发新 token（TTL 15 分钟）并作废旧 token，web 层验过期。命令层闸①不变。效果是"群历史里翻到的永远是死链"，但不防 TTL 窗口内抢开，且 MCP 端要动（违背 §1 原则，故为末选）。事实 2 还使"私聊发密码"原始方案复活（群事件 authorOpenid 即单聊 openid），但用户已决策不走该路，仅存档备查。
