# MCP 接入层设计方案：桥接模式 + 适配器加工 + 闸门暴露控制

> 状态：设计稿（未实现）
> 起因：云服务器 IP 被小红书/微信公众号等站点风控，需要把浏览器等能力下沉到家用节点（家宽公网 IP）；MCP 作为远程能力协议，同时为将来接入 GitHub/数据库等现成 MCP 服务器铺路
> 关联：总设计 `docs/superpowers/specs/2026-08-24-deep-web-browsing-design.md`（browse 层与三档演进）、fetch_tool 方案（工具双注册模式）
> 日期：2026-09-02

## 1. 背景与选型结论

### 1.1 要解决的问题

- **IP 风控**：阿里 ECS 公网 IP 段被部分国内站点屏蔽，fetch 和无头浏览器都被拦（小红书 300012 "IP存在风险"、微信文章读不到）。家里有绑域名的公网 IP，能力下沉可解；
- **能力扩展**：MCP 生态有大量现成服务器（playwright-mcp、GitHub、数据库），标准化接入避免每个远程能力手写协议。

### 1.2 形态选型（为什么是桥接而不是原语直出）

三个候选形态的对比结论：

| 形态 | 家里跑什么 | Agent 怎么用 | 结论 |
|---|---|---|---|
| A：代理隧道 | WireGuard/代理 | fetch.ts 加 proxy 参数 | ✅ 第一步先做（解决 fetch 风控） |
| B：远程浏览器（CDP） | chromium --remote-debugging | browser.ts 换 connectOverCDP | ✅ 备选（浏览器搬家的最短路径） |
| C：MCP 服务器 | MCP server + 无头浏览器 | 桥工具转发 | ✅ 本方案（协议标准化，为多服务器生态铺路） |

**否决"原语直出"**（把 MCP 工具 schema 与原生工具平级合并直接给模型）：粒度从"任务级"翻转为"操作级"会废掉现有导航智能——深检图靠"三段式摘要 + link 编号"让模型凭摘要决策，换成 navigate/click 原语后模型要自己处理等待时序、全量 DOM 快照（几万 token）、错误恢复，写后读拼接/动作串行化/自愈文案等设计失去挂载点。

**采用桥接**：MCP 工具被包装成本项目的 `Tool` 契约（或作为现有工具的远程内核），任务级粒度、三段式摘要全部保留。模型对 MCP 的存在无感知。

## 2. 架构总览：五层结构

```
┌─ 编排层（不变）─────────────────────────────────────┐
│  loop.ts / deep-search.ts → runTool / toolSchemas   │
└──────────────────────┬──────────────────────────────┘
                       │ Tool 契约（name/description/parameters/run）
┌──────────────────────▼──────────────────────────────┐
│ ⑤ 闸门 gate：哪些 MCP 工具暴露进工具表（配置驱动）      │
├─────────────────────────────────────────────────────┤
│ ④ 适配器 adapter：对结果做加工（默认直通，按需注册）     │
├─────────────────────────────────────────────────────┤
│ ③ 拍扁 flatten：MCP 结构化 content → 字符串           │
├─────────────────────────────────────────────────────┤
│ ② 桥接 bridge：MCP 工具定义 → 本地 Tool 对象           │
├─────────────────────────────────────────────────────┤
│ ① 连接 client：长连接单例、tools/list、tools/call、    │
│    断线重连、超时控制                                  │
└─────────────────────────────────────────────────────┘
```

各层职责单一：client 是哑管道（收发原始结果），bridge 做契约转换，flatten 解决 `Promise<string>` 契约，adapter 做满意度加工，gate 管暴露边界。加工逻辑不进 client（避免污染 interact_page 远程内核路径），不进编排层（图只认 ChatMessage）。

## 3. 各层设计

### 3.1 连接层 `src/agent/mcp/client.ts`

模块级单例（类比 browser.ts 的定位）。用官方 `@modelcontextprotocol/sdk`：

- 按服务器名持有连接（`Client` + `StreamableHTTPClientTransport`，指向家里节点经隧道的地址）；
- `connectAndList(server)`：建连 → `tools/list` → 返回工具定义数组（name/description/inputSchema）；
- `callTool(server, tool, args)`：查连接 → 转发 → 返回原始结构化结果；断线时重连一次再试（家里设备重启场景）；每次调用设超时上限（防远程卡死拖垮深检 60s 预算）；
- 服务器不可用不抛异常到启动流程：记 warn、该服务器标记不可用，后续调用返回友好文案。

### 3.2 桥接层 `src/agent/mcp/bridge.ts`

`wrapMcpTool(serverName, mcpTool): Tool`——把 MCP 工具定义包成本项目 Tool 契约：

```ts
{
  name: `mcp_${serverName}_${mcpTool.name}`,   // 前缀防与原生工具撞名
  description: mcpTool.description,
  parameters: mcpTool.inputSchema,              // 同构直传（都是 JSON Schema）
  async run(args, ctx) {
    const result = await mcpClient.callTool(serverName, mcpTool.name, args);
    const flat = flattenMcpResult(result);
    return getAdapter(serverName, mcpTool.name)(flat, { server: serverName, tool: mcpTool.name, args }, ctx);
  },
}
```

要点：工具名加 `mcp_<server>_` 前缀（防撞车，DeepSeek 工具名字符集 `^[a-zA-Z0-9_-]+$` 安全）；`ctx` 传给适配器（浏览器类适配器需要 `ctx.event` 做页面池的人粒度隔离——B 档演进口子）。

### 3.3 拍扁层（bridge 内函数）

MCP `tools/call` 返回结构化 content 列表（text/image/resource 块），而 Tool 契约是 `Promise<string>`：

- text 块 → 取 `.text`；多块拼接；
- image 块 → 占位说明（本链路识图走懒加载管线，不吃 base64）；
- `isError: true` → 包成可自愈错误文案（**不抛异常**——抛了会撞全局 runTool 的"工具执行失败"统一兜底，抹掉细节）。

### 3.4 适配器层 `src/agent/mcp/adapters.ts`

对"MCP 返回内容不满意"的加工层，**可插拔、默认直通**：

```ts
type McpAdapter = (
  raw: string,
  info: { server: string; tool: string; args: Record<string, unknown> },
  ctx: MessageContext,
) => Promise<string>;

// 注册表：key 为 "server"（粗粒度）或 "server:tool"（细粒度）
// 缺省 identity：不加工（对 GitHub/数据库类原语无害服务器零成本接入）
```

核心用例——浏览器服务器的 snapshot 工具返回原始 HTML，适配器复用现有提取层：

```ts
adapters.set("home-browser:snapshot", async (raw, { args }, ctx) => {
  const page = extractPage(raw, String(args.url ?? ""));
  savePage(ctx.event, String(args.url ?? ""), page);        // 入页面池，link 编号机制自动覆盖远程页面
  return formatPageForModel(page, String(args.url ?? ""));
});
```

**这是本方案的关键设计**：三段式摘要、link 编号、页面池等导航智能通过适配器完整延续到远程能力——当初否决原语直出时要保留的"封装"，落点就在这里。

适配器的边界：只救"格式不满意"（太长/太原始/结构不对），救不了"信息已丢失"（服务器返回的内容本身缺信息——那种要在 args 传参或换工具层面解决）。

### 3.5 闸门层（配置驱动）

浏览器原语（browser_click/browser_navigate）若与原生 open_page/interact_page 同时暴露，模型选择会不稳定。暴露规则进 .env：

```text
MCP_SERVERS=home-browser,github            # 启用的服务器列表（每行一个或逗号分隔）
MCP_EXPOSE=github:*                        # 暴露规则：github 全放行
                                           # home-browser 不进表——只做 interact_page 的远程内核
```

两种模式并存：

- **吸收模式**（github:*）：MCP 工具 wrapMcpTool 后 registerTool 进全局表，模型直接可用；
- **内核模式**（home-browser）：MCP 工具不进表；`interact_page` 的 run 内部改调 `mcpClient.callTool`，作为远程执行内核（A 档 browser.ts 的本地 launch 替换）。

### 3.6 初始化序列

`webhook.ts` 启动区加一行（与 initializeNewsCron / initializePersonalities 同款模式）：

```ts
await initializeMcpTools();   // 内部：遍历 config.mcpServers → connectAndList
                              // → 闸门放行的 → wrapMcpTool → registerTool（写进活 Map）
```

时序安全性来自注册表的模式：`tools` 是 const Map（锁指向不锁内部），初始化跑在首次 `toolSchemas()` 之前；Map 是活的，将来做断线重连+重新吸收，下一次 toolSchemas() 调用自动看到新工具，编排层零改动。

## 4. 安全设计（必做项）

- **传输**：ECS ↔ 家里的链路不走公网裸 HTTP。首选 WireGuard 隧道（MCP 地址用隧道内网 IP）；退而求其次 HTTPS + token；
- **鉴权**：MCP 服务器带认证（家宅节点暴露在公网会被扫描爆破，几小时内就有尝试）；
- **家宽 IP 漂移**：域名 + DDNS 保底，MCP 配置用域名不用 IP。

## 5. 实施切分（两步，各自独立可验证）

**第一步：转发内核**（解决眼前的 IP 问题，工具表零变化）

1. 家里节点：起 MCP 服务器（playwright-mcp 或自封装）+ WireGuard；
2. ECS：`npm i @modelcontextprotocol/sdk`，实现 client.ts（连接/callTool/重连/超时）；
3. `interact_page` 的 run 改走 `mcpClient.callTool`（内核模式，闸门不放行任何工具）；
4. 验证：深检对微信文章跑 interact_page，确认家宽出口可达。

**第二步：schema 吸收层**（生态能力）

5. bridge.ts + flatten + adapters（identity 缺省）+ 闸门配置解析；
6. initializeMcpTools 挂启动序列；

## 7. 如果要自己实现一个 MCP 服务器，需要遵守什么规范

（依据 modelcontextprotocol.io 官方规范，2026-07-28 版；配合本项目 client.ts 的实现口径整理。用官方 TS SDK 的 `McpServer` 实现时下述大部分由 SDK 自动满足，本章按"裸写需要知道什么"整理。）

### 7.1 基础协议：JSON-RPC 2.0

MCP 的所有消息都是 JSON-RPC 2.0 格式（`{jsonrpc, id, method, params}` / `{jsonrpc, id, result}` / `{jsonrpc, id, error}`）。服务器核心要处理两类请求：

- **initialize**（握手）：客户端建连后第一个请求，响应里必须给出 `protocolVersion`、`capabilities`、`serverInfo`（名称/版本）；
- **notifications/initialized**：握手完成通知，无需响应。

### 7.2 capabilities 声明与 tools 能力

提供工具的服务器**必须**在 initialize 响应中声明 `tools` 能力：

```json
{ "capabilities": { "tools": { "listChanged": false } } }
```

`listChanged: true` 表示工具列表变化时会主动推送通知（本项目 client 不依赖它，吸收是启动时一次性的——声明 false 即可）。工具集合不得因连接不同而不同（每次 tools/list 返回一致的集合），且应保持确定性顺序（利于客户端缓存）。

### 7.3 tools/list：工具定义的硬性要求

响应的 `tools` 数组里，每个工具：

| 字段 | 要求 |
|---|---|
| `name` | 必填。1~128 字符，大小写敏感，只允许 `[A-Za-z0-9_-]` 和点；服务器内唯一。**注意桥接后会加 `mcp_<server>_` 前缀，原名别太长** |
| `description` | 必填（实践上）。给模型看的自然语言，直接决定工具被调用的时机——写清楚"什么时候该用"，本项目桥接后原样透传给模型 |
| `inputSchema` | 必填，**必须是合法 JSON Schema 对象**（不能是 null）。无参数工具用 `{"type":"object","additionalProperties":false}`。未标 `$schema` 时默认 2020-12 版 |
| `title` / `annotations` / `outputSchema` | 可选，本项目桥接不消费 |

### 7.4 tools/call：执行与返回

请求带 `name` + `arguments`（按 inputSchema 校验后的对象）。响应的 result：

```json
{
  "content": [
    { "type": "text", "text": "结果文本" }
  ],
  "isError": false
}
```

- `content` 是内容块数组，支持 text/image/audio/resource 等类型；**本项目拍扁层只消费 text 块**，其它类型会给占位说明——为机器人写的服务器**优先返回 text**，图片等富内容慎用（链路吃不了 base64）；
- **错误二分法（重要）**：
  - **协议错误**（未知工具/请求畸形/服务器内部炸）→ 标准 JSON-RPC error（`{code, message}`），模型难以自愈；
  - **工具执行错误**（参数不合法、外部 API 失败等模型可修正的问题）→ 正常 result 里 `isError: true` + content 写明**可行动的失败原因**（"日期必须是未来时间"而非"调用失败"）。本项目桥接层会把它包装成自愈文案透传给模型——服务器写得越具体，模型恢复成功率越高；
- 长任务不阻塞：单次 call 应尽快返回（本项目客户端 30s 超时；超时的调用会被放弃）。

### 7.5 Streamable HTTP 传输（本项目采用的传输）

- 端点接收 **POST**（JSON-RPC 消息）与可选的 **GET**（服务器推送流）/ **DELETE**（会话终止）；
- 两种实现形态：
  - **无状态**（最简）：每个 POST 独立处理，响应 JSON 即可——本项目测试脚本里验证过的形态，用 SDK 的 `StreamableHTTPServerTransport({ enableJsonResponse: true })` 不设 sessionIdGenerator；
  - **有状态**：initialize 时分配会话，客户端后续请求带 `mcp-session-id` 头，服务器校验；
- Content-Type 用 `application/json`（或 SSE 流式 `text/event-stream`）；
- **安全基线（规范 MUST 项）**：校验所有工具输入、实现访问控制、对调用限速、对输出做净化。暴露在公网（即使走隧道）的服务器必须带鉴权。

### 7.6 状态管理：句柄模式

MCP 没有协议级会话——**服务器不能依赖"同一连接"来关联两次调用**（本项目的无状态客户端每次调用都可能是新请求）。跨调用要保状态（浏览器 context、购物车、事务）时，规范推荐**句柄模式**：创建类工具返回一个 handle（如 `basket_id`），后续调用把它作为参数传回来，服务器按 handle 查状态。handle 要：不可猜测（足够熵）、有声明在工具描述里的生命周期、过期时返回明确的可自愈错误。**这条对将来的浏览器 MCP 服务器尤其重要**——B 档"每会话一个浏览器 context"的落地方式就是句柄。

### 7.7 与本项目对接的检查清单

自己写的服务器要被本项目顺利吸收，逐条对照：

1. Streamable HTTP 端点（无状态形态即可），地址填进 `MCP_SERVERS`；
2. initialize 正常握手、声明 tools 能力；
3. tools/list 返回的工具名符合字符集约束、description 写清使用时机；
4. tools/call 的业务错误用 `isError: true` + text 块返回可行动原因；
5. 返回内容以 text 为主（富媒体块本项目会占位省略）；
6. 需要加工返回格式的（如原始 HTML → 三段式），在本项目 `adapters.ts` 注册适配器，服务器侧不用迁就。

最小实现参考：`test/deep_research/verify-mcp.ts` 里的模拟服务器（SDK 十几行起一个合规服务器），以及官方 SDK 文档的 server quickstart。

## 8. 明确排除 / 后续扩展

- **不做原语直出**：MCP 工具 schema 不与原生工具平级合并给模型（§1.2 已论证）；
- **运行时动态撤下工具**不做（模型上轮见过的工具消失，行为未定义）；动态**新增**（重连吸收）允许；
- **后续扩展候选**：B 档会话隔离时用 `serverName + sessionKey(ctx.event)` 做远程浏览器 context 路由（bridge 的 ctx 参数已留口）；多 MCP 服务器的健康检查与并发吸收。
