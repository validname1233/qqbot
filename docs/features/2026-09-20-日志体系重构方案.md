# 日志体系重构方案：全局双维度日志（控制台轨迹 + 文件全量流水）

> 状态：设计方案（需求已对齐，未实施）
> 起因：现有 logger 只有控制台一个出口——开 debug 看全量但 LLM 明细与节点事件混流刷屏，关 debug 清爽但事后什么都查不到；日志跟着 pm2 走，没有自主的持久化
> 日期：2026-09-20（同日二次修订：需求对齐——全局覆盖、detail 内容清单、提示词去重、初始化/运维日志原样保留）
> 现状盘点：`services/logger.ts` 全项目 59 处调用、15 个模块、18 处手工截断；三段前缀 `[HH:mm:ss] [level] [module]` 为既定格式

## 0. 需求（已对齐）

1. **全局日志，不只 Agent 部分**：bot 所有环节（事件入口、命令分发、图片、定时任务、MCP、深检、Agent、QQ 发送……）都在日志视野内；
2. **控制台（trace 视图）**：只保留运行的节点名称 + 时间戳，精简到不含正文内容；
3. **文件持久化（detail 流水）**：存到服务器 `data/logs/` 下按天滚动的 log 文件；
4. **detail 内容清单（三项）**：大模型 content 输出、tool_calls 输出（JSON）、tool 节点的工具结果——全部不截断；LLM **输入**也要存，但提示词重复问题需要专门设计（见 §2.3）；
5. **解耦**：logger 与输出目标分离（sink 机制，同 progress-bus 的思想）；
6. **兼容性硬约束**：现有运维日志与初始化日志**按原样保留**——`[images] 图片入库…`、`[scheduler] 已恢复 1 条定时任务`、`[mcp] 服务器 kb 就绪…`、`[webhook] 监听 http://…` 这些行重构前后逐字不变（它们本来就是合格的 trace）。

## 1. 核心设计：两个正交维度 + sink 分发

现有体系一个级别轴（debug/info/warn/error）把"多细"（verbosity）和"多要紧"（severity）混在一起——"想看节点轨迹就得连 LLM 全文一起看"的根源。拆开：

- **verbosity**：`trace`（轨迹——节点/命令/工具的进出事件，一行一事）/ `detail`（流水——大块头原文：LLM 输入输出、tool_calls JSON、工具结果）；
- **severity**：沿用 debug/info/warn/error（要紧程度），不变。

**事件模型**（logger 内部的"待分发物"）：

```ts
interface LogEvent {
  verbosity: "trace" | "detail";
  severity: "debug" | "info" | "warn" | "error";
  module: string;      // "agent" / "model" / "images" / …
  message: string;
  ts: number;
}
```

**sink 分发**（解耦诉求）：logger 不再直接 console，而是把事件广播给 sink 列表，每个 sink 自己决定收不收、怎么格式化：

```
                ┌→ console sink：trace + 全部 warn/error；格式 [HH:mm:ss] [level] [module] msg（不变）
LogEvent ──分发─┤
                └→ file sink：trace + detail + warn/error 全收；ISO 时间戳，detail 不截断
```

未来加第三个出口（网页日志面板等）= 注册一个 sink，内核与其他 sink 零改动。

**API 设计（兼容第一）**：

- `logger.debug/info/warn/error(module, msg)` ——**签名与语义都不变**：59 处现有调用零迁移，自动映射为 trace 事件；
- `logger.node(module, msg)` —— trace 的语义化入口（节点/命令进出专用，= info 的别名，可读性别名）；
- `logger.detail(module, msg)` —— detail 事件，只进文件。

## 2. 全局覆盖：59 处现有调用的分类入座 + 新增点

### 2.1 运维/初始化日志：原样保留（需求 6）

这批调用本就是"一行一事的状态变更"，天然 trace，**一行不改**（格式与级别都不动）：

| 模块 | 代表日志（重构后逐字保留） |
|---|---|
| events | `收到事件: GROUP_MESSAGE_CREATE` |
| images | `图片入库 …（2903字节，key=…）`、`清理窗口外图片 1 张` |
| scheduler | `已恢复 1 条定时任务`、`任务 1 触发（… 6:30）` |
| prompts | `已加载 3 条自定义人格到缓存` |
| mcp | `服务器 kb 就绪：发现 2 个工具，吸收 1 个`、`MCP 吸收完成` |
| webhook | `监听 http://127.0.0.1:3000（经 nginx 反代…）`、签名校验失败（warn） |
| boot | token/网关五条启动链路 |
| 各类 warn/error | 图片下载失败、任务执行失败、观察者出错……（severity 直出双 sink，本来就对） |

### 2.2 现有 debug 调用的分流（混流问题的解法）

59 处里 debug 约 25 处，分两类：

- **轨迹型 debug → 升为 trace 的 node/info**：`searchNode 检索词改写: …`、`fetchPage 完成 …(829202B)`、`interact_page 完成 …(+71ms)`、`mcp 工具完成 返回 N 字`、`webSearch "…" → 6 条 (+312ms)`——这些是一行结论，正是你要的控制台视图内容。**升级后控制台在 info 档位就能看到**（不再需要开 debug）；
- **流水型 debug → 改走 detail（撤掉截断）**：`model.ts` 的请求/返回明细（150 字截断解除）、深检思维链全文、`webSearch 失败 detail=…（300 字截断解除）`——只进文件，控制台清爽。

### 2.3 detail 内容清单（需求 4 的三项 + 输入去重设计）

**工具结果（不截断）**：`runTool` 切面处（两个注册表）——`logger.detail("tool", \`name=… args=…\n${result}\`)`，一行日志含工具名、净化后参数、完整返回。这里与 progressNote/arg-injector 同层，切面汇聚点现成。

**LLM content 输出 + tool_calls 输出（不截断）**：`model.ts` 的返回处——`logger.detail("model", …)` 带 label（哪个节点发起）、完整 content、tool_calls 的 JSON.stringify（含参数全文）。

**LLM 输入（提示词去重——本节的核心设计）**：你的顾虑成立：每轮请求的 system（人设+功能规则，数百字）与历史消息高度重复，全量落盘 = 同一段提示词一天写几百遍，文件膨胀且没法读。解法是**内容指纹缓存**：

```
detail 记录输入时，对每条 message.content 算指纹（简单 hash，如 FNV 或 sha1 前 8 位）：
  - 指纹当天首次出现 → 写完整内容块：[msg#3 sha=a3f2c1d8] {全文}
  - 指纹已见过       → 只写引用行：    [msg#3 sha=a3f2c1d8] （同前，略）
文件里每条消息可按 sha 溯源到当天首次出现的全文。
```

性质：人设/系统提示词/旧历史在当天的**第一次**请求中全文出现一次，之后全是单行引用；真正每次变化的部分（当前用户消息、刚产生的工具结果）天然是 新指纹，每次全量。磁盘占用从"每请求 N KB"降到"每请求约 200 字节 + 新内容"。缓存是进程内 Map（重启后指纹表清空，当天文件里同内容可能再全文出现一次——可接受，不跨进程维护指纹状态）。

### 2.4 新增的轨迹点（控制台视图的主角）

| 位置 | trace 内容（一行） |
|---|---|
| loop.ts 各节点 | `prepareContext 完成 (+8ms)`（现有计时日志转正为 trace）、`llmCall 第1轮 → tool_calls: search`、`finalize 收尾` |
| deep-search.ts | `searchNode 起点装配完成`、`planNode 计划生成`、`浏览第2轮 → open_page(link:3)`、`synthesize 报告 N 字` |
| registry.ts runTool | `→ search(query=…) 完成 (+312ms)`（参数摘要 ≤60 字；全文在 detail） |
| services/agent.ts | `[/Agent] 收到 → 回复 N 字 (+8.2s)`（入口/出口合并行） |
| qq 发送层 | `回复群消息 seq=1 N 字` / `主动推送 N 字`（现在发送成功是静默的，加一行轨迹） |

控制台节奏约定（防刷屏）：**状态变更才打**；browseLlm⇄browseTools 循环体合并为"第 N 轮 → 工具名"一行；与 progress-bus 的分工——bus 管给用户的推送，logger.node 管给运维的轨迹，同一动作各说各话不重复内容。

## 3. 文件 sink 设计

- 路径：`data/logs/bot-YYYY-MM-DD.log`（data/ 已 gitignore，与聊天记录同隐私口径）；
- 按天滚动：写入前比对当前日期，跨天换目标文件（次日首条触发，无需定时器）；
- 行格式：`2026-09-20T14:32:05+08:00 [info] [agent] planNode 进入`（控制台保持 HH:mm:ss，文件侧 ISO 全量——跨天文件需要日期自包含）；
- 顺序保证：模块级 Promise 串行链（`writeChain = writeChain.then(() => appendFile(...))`，browser.ts 的 withPage 同款手法），进程退出钩子 flush 在途写入；
- 保留策略：`LOG_RETENTION_DAYS`（默认 14，0=永久），启动时清理过期文件；
- 故障降级：文件写入失败（磁盘满/权限）→ console error 一条后禁用 file sink 自身，绝不让日志故障炸主流程；
- 配置：`LOG_DETAIL=file|off`（默认 file，回退开关）。

## 4. 分阶段实施

### 阶段一：logger 内核 + 双 sink + detail 三件套（核心）

改 `logger.ts`（事件模型/sink 注册表/node+detail API/文件 sink 全套）+ `config.ts`（LOG_DETAIL/LOG_RETENTION_DAYS）+ 三个 detail 首站：`model.ts`（输入指纹去重 + content/tool_calls 全文）、两个 `runTool` 切面（工具结果全文）。

**难点重点**：
- **A. 串行链的退出 flush**：pm2 restart 信号处理（SIGINT 钩子里 await writeChain），漏了会丢最后几行——最可能丢的恰是崩溃前的现场；
- **B. 指纹缓存的一天边界**：跨天后旧指纹仍有效（文件是当天的新文件，引用会指向不存在的 sha）——简单解法：滚动文件时**同时清指纹缓存**，新文件从零积累，逻辑闭环；
- **C. detail 的 API 传参**：`logger.detail(module, msg)` 收拼好的字符串——指纹去重逻辑收在 model.ts 的调用侧（它知道消息结构），logger 不做内容解析（保持哑管道）。

### 阶段二：全局轨迹覆盖（控制台体验成型）

§2.2 的 debug 分流（约 25 处调用逐个归类改级）+ §2.4 的新增轨迹点。

**难点重点**：
- **A. 分类的判断纪律**：一行结论（有起止/数量/耗时）→ trace；大块原文 → detail。改错类别的后果只是"控制台多一行/少一行"，可运行期观察调整，不必一次完美；
- **B. 控制台节奏验收**：一次 /Agent 控制台 5~8 行、一次深检 10~15 行（含每轮浏览一行）；超了合并，少了补——以"任何一步卡住能从最后一行定位在哪个节点"为准。

### 阶段三：观测配套（可选）

- correlation id：一次交互（/Agent、深检、cron 任务）共享短 id（如 `a3f2`），文件行带 `[a3f2]` 前缀——`grep a3f2` 提取全流水。改动面：两张图的 State 加 runId 字段 + 入口生成；
- `/logs <n>` 管理命令：取最近 n 条 warn/error 推给管理员（触发条件：ssh 不便时；不进一期）；
- 隐私边界写死：日志文件不进版本库、不进任何外部上报。

## 5. 明确排除

- **不引入 winston/pino**：需求（双维度 + 按天滚动 + 串行追加 + 指纹去重）原生 fs + 百行内核覆盖；换库的触发条件是出现按大小滚动/压缩/远程上报；
- **不做 JSON 结构化**：消费方式是人眼 + grep（detail 里的 JSON 内容本来就结构化，行格式保持文本）；
- **不做日志面板**：sink 留口子，不实现；
- **不动 severity 语义**：warn/error 的"单点降级/需介入"约定不变，双 sink 都收。

## 6. 验收清单

1. 控制台（LOG_LEVEL=info）：初始化日志与现状逐字一致（需求 6）；一次 /Agent 约 5~8 行轨迹；不含 LLM content/工具结果正文；
2. `data/logs/bot-YYYY-MM-DD.log` 存在且增长；同一天的第二轮请求中，人设/系统提示词以 sha 引用行出现（不重复全文）；
3. 文件中 LLM content、tool_calls JSON、工具结果均为全文无截断；
4. `LOG_DETAIL=off` 后行为回到"只有控制台"；文件写失败（chmod 演练）主流程不受影响；
5. 跨零点（或手动改系统时间演练）自动换文件且指纹缓存重置。
