# 进度推送 Bus 设计方案：请求作用域的事件总线，工具/节点执行时向用户推送即时反馈

> 状态：实现方案（未实现）
> 起因：/Agent 和 /深度检索 的完整响应需要 10 秒到 3 分钟，用户在收到最终回复前没有任何反馈，体验上像机器人"卡死了"
> 日期：2026-09-10
>
> 现在我们来做一个新的需求，我觉得不管是Agent还是深度检索，我们一次请求的响应时间都太长了，也就是qq机器人的回复很慢，当然我认为这是一个难以避免的情况，所以我觉得需要解决的问题是，用户在收到最终请求之前，需要得到一些即时的反馈，就如同深度检索中的“正在规划路线”。因此我想做一个，在进行每个tool时，都往群里（或私聊）推送一条消息，表示正在进行某项工作，于是就会遇到两个问题： 1. 私聊和群聊，推送消息的底层函数不一样 2. 每个tool，用于推送的消息不一样 但是不管怎么样，tool进行时要推送消息的操作是统一的，因此我认为这可以用一种面向切面编程的思路来解决。具体而言，我在其他的项目中学到一种“event bus”的做法，不管处理什么事件（在我们这里是不管处理什么tool），都通过一个bus，装载需要推送的信息，通过bus里的回调函数，把消息推送出去。这样形成了推送与不同的tool，不同的聊天场景解耦。你觉得这个想法怎么样？请仔细结合我的代码，先简单评价一下，或者给出一些意见。

## 1. 设计动机

### 1.1 问题：响应慢本身不可避免，但"无反馈的慢"可以治

长流程的耗时是结构性的：一次 /Agent 要经历多轮"模型调用 → 工具执行 → 再调用"（现在 MAX_TOOL_TURNS=2，串行工具链如 get_time → search 要跑两轮）；一次 /深度检索 全程 1~3 分钟（起点检索 → 计划 → 6 轮浏览 → 收尾报告）。**压缩耗时没有多少空间（每步都是必要的外部调用），但用户的等待体验可以改善**——在最终回复到达前，让用户知道"机器人正在干什么、没死"。

深检已经做过第一段实验：planNode 开始时主动推送一条"---正在规划路线---"（deep-search.ts，主动消息 + catch 静默）。本方案把这个模式推广到**每一次工具执行**。

### 1.2 两个横切的耦合点

"每个工具执行时推一条消息"这个需求，若直接写进每个工具的 run 里，会在每个工具内部重复两段与工具职责无关的代码：

1. **发送目的地分支**：群聊走 `pushGroupMessage(groupOpenid, ...)`，私聊走 `pushC2CMessage(authorOpenid, ...)`——同款 if/else 已经在 `pushMemoryNotice`（context.ts）和深检 planNode 里各写了一遍，第三遍就会出现在每个工具里；
2. **文案定制**：每个工具的进度文案不同（search 是"正在联网搜索…"，open_page 是"正在打开网页…"），但"要推送"这个动作完全一致。

横切关注点（进度推送）与业务逻辑（工具执行）的解耦——这是面向切面编程（AOP）的标准场景。

### 1.3 选型：event bus

用户提出的 event bus 模式：工具/节点不直接发消息，只往 bus 里装载事件（"我正在干什么"），bus 的订阅侧回调负责真正推送。这带来三层解耦：

| 解耦维度 | bus 之前 | bus 之后 |
|---|---|---|
| 事件源 vs 发送方式 | 工具内部写群/私聊分支 | 事件源只 emit 一个字符串；分支只存在于发送适配器一处 |
| 事件源 vs 会话上下文 | 工具要拿到 event 才知道发给谁 | 订阅与 ctx 绑定（请求作用域），事件源无感 |
| 事件源 vs QQ 频控/失败策略 | 每个工具自己 catch | 适配器统一 fire-and-forget + warn 日志 |

**切面插入点的选择**：不在每个工具里埋 emit，而是在**两个注册表的 `runTool`**（`agent/registry.ts`、`agent/deep-search/registry.ts`）统一拦截——所有模型发起的工具调用都经过这里，一处埋点全覆盖；而 searchNode 的 URL 预读（loadPage 直调）天然不经过 runTool，恰好符合"预取不发进度"的语义（用户自己给的 URL 不需要被告知"正在打开"）。

**为什么是"请求作用域订阅"而不是全局广播**：一次请求期间，进度消息的接收者是发起这次请求的那个会话；请求结束订阅必须失效——否则 A 在群甲发起的深检还没跑完，B 在群乙触发了一个工具，进度发到群甲去了。所以 bus 的核心形态是：**入口函数订阅（绑定 ctx）→ finally 退订**，会话隔离由作用域天然保证，/stop 中断与异常路径由 finally 兜住。

## 2. 实现方案

### 2.1 模块：`src/services/progress-bus.ts`（新文件，全项目唯一的 bus 实现）

```typescript
// 事件：纯字符串载荷。"哪个工具、什么文案"的映射在 emit 侧完成（见 2.2），
// bus 不认识任何具体工具/节点——它只负责"把字符串送到当前订阅者的会话"。
type Listener = (text: string) => Promise<void>;

// 请求作用域订阅：Map 的 key 用 sessionKey（人粒度）——同一人同一会话的
// 并发请求本来就被 /stop 的并发闸挡住了（beginControlledFlow 拒绝并发），
// 所以"一个 key 至多一个活跃订阅"与现有的并发模型一致，不会互相覆盖。
const listeners = new Map<string, Listener>();

export function subscribeProgress(event: BotEvent, listener: Listener): () => void;
// 返回退订函数；重复订阅同 key 时新替旧（防御性，正常流程不会发生）

export function emitProgress(event: BotEvent, text: string): void;
// 无订阅者时是 no-op（深检未接入、或请求已结束后的迟到事件——直接丢弃）；
// listener 抛错在这里 catch 成 warn 日志，绝不向上传播。
```

设计要点：

- **同步 emit、异步送达**：`emitProgress` 本身同步返回，listener 的 Promise 在 bus 内部 catch——事件源（runTool）永远不 await 推送，QQ 接口抖动不影响工具执行时长；
- **人粒度 key 的一个已知边界**：群聊里 A 发起 /Agent 期间，B 的普通消息不触发工具所以无事件，不受影响；但深检浏览是"整群共享记忆"语义而进度订阅是人粒度——A 发起的深检，进度只发给 A 所在的会话（群 OpenID 相同，实际都能看到），语义正确。

### 2.2 文案：Tool 契约声明式字段（与 skipMemory 同款风格）

```typescript
// agent/tool.ts
export interface Tool {
  // ...现有字段...
  // 可选：执行前推送的进度文案。缺省 = 不推送（既有工具行为不变）。
  progressNote?: string | ((args: Record<string, unknown>) => string);
}
```

- **静态文案**：`progressNote: "正在联网搜索…"`（大多数工具够用）；
- **动态文案**：`progressNote: (args) => \`正在打开网页：${args.url}\``（open_page 这类参数有信息量的）；
- 文案声明与工具实现同文件、进版本库——和 skipMemory 一样，避免任何外部配置表造成的两处真相。

### 2.3 发送适配器：订阅侧的统一分支

```typescript
// progress-bus.ts 内部（或订阅工厂函数）
// 群/私聊分支全项目从此只此一份（pushMemoryNotice 的既有分支保留不动，
// 那是它的职责；新代码一律走 bus）。
function makeListener(event: BotEvent): Listener {
  return async (text) => {
    if (event.type === "GROUP_AT_MESSAGE_CREATE" || event.type === "GROUP_MESSAGE_CREATE") {
      await pushGroupMessage(event.groupOpenid, text);
    } else {
      await pushC2CMessage(event.authorOpenid, text);
    }
  };
}
```

- **全部走主动推送**（push 路径，不带 msg_id）：不消耗被动回复额度（群聊每条消息仅 5 次回复），且不受 5 分钟回复窗口约束——长流程的进度消息天然可能落在窗口外；
- 失败策略：fire-and-forget（catch → warn），用户关闭"允许主动消息"开关时静默降级，只是没进度提示，不影响结果。

### 2.4 切面埋点：两个注册表的 runTool

```typescript
// agent/registry.ts 的 runTool 内，tool.run 之前：
const note = tool.progressNote;
if (note !== undefined) {
  emitProgress(ctx.event, typeof note === "string" ? note : note(args));
}
```

- deep-search/registry.ts 的 runTool **同样加**（bus 是基础设施，两个注册表都具备能力；**但深检暂不订阅**——见 §4 实施计划）；
- 同一轮多个 tool_calls（browseTools 并发执行）会各自 emit：一期不聚合，逐条发送——单轮并发工具很少超过 2 个，频控余量充足（见 §3）；若日后观察到刷屏，再加"同轮合并成一条"的聚合层（bus 形态天然支持，emit 侧加缓冲即可）。

### 2.5 订阅生命周期：入口函数挂载

```typescript
// loop.ts 的 runAgentTurn（/Agent 唯一入口）：
const unsubscribe = subscribeProgress(ctx.event, makeListener(ctx.event));
try {
  // 现有图调用
} finally {
  unsubscribe();
  endControlledFlow(flowKey, controller);
}

// 深检的 runDeepSearch 暂不挂订阅（§4）。
```

订阅在 beginControlledFlow 之后建立（并发闸先挡住重复请求，订阅的作用域与闸的作用域对齐）；finally 退订保证 /stop 中断、异常、正常完成三条路径都清理。

## 3. 频控预算（主动消息）

已调研的 QQ 官方限制（docs 2026-09-04 富媒体/频控调研）：群聊主动消息 30~60 qpm（按认证等级）、**单群 20 qpm、每日 1000 条/群**；用户可在客户端关闭"允许主动发送"（关闭后发送失败，fire-and-forget 兜住）。

一次 /Agent 的进度推送量：最多 2 轮工具 × 每轮 ≤2 个并发工具 = **≤4 条/次请求**，远低于 20 qpm 的单群上限。个人 bot 场景下每日 1000 条也无压力。深检（6 轮）若未来接入，峰值 ≤12 条/次，仍在预算内。

## 4. 实施计划（分期）

**一期：/Agent 流程接入（本次实施范围）**

1. 新建 `src/services/progress-bus.ts`——subscribeProgress / emitProgress / makeListener；
2. `agent/tool.ts`——Tool 契约加 `progressNote?` 可选字段；
3. `agent/registry.ts`——runTool 埋 emit 切面；
4. `agent/loop.ts`——runAgentTurn 挂订阅（finally 退订）；
5. 给现有 7 个工具补 progressNote 文案（search/召回/识图相关先行，纯本地工具如 get_time 可不配——瞬时完成，推送反而添噪）。

**二期：深检接入（暂缓，明确不在本次范围）**

深检已有 planNode 的"正在规划路线"推送先行满足最低需求；浏览循环节点的进度（"正在阅读第 N 个页面"）等 bus 在 /Agent 上验证稳定后再迁。迁移内容：runDeepSearch 挂订阅 + planNode 的硬编码推送改走 bus + browseLlm/browseTools 按轮 emit。**先不做的理由**：深检一次最多 6 轮，逐工具推送的频控和刷屏风险都比 /Agent 高，值得等一期的实机反馈（推送时机、文案长度、用户是否觉得吵）再定节奏（比如改成按轮聚合）。

**验证方式**：

- 本地：typecheck + 构造 mock ctx 直调 emitProgress（无订阅 no-op、有订阅送达、listener 抛错不传播）；
- 实机（QQ 端）：群里发 `/Agent 帮我搜搜最近的XX新闻`，预期收到 2~3 条进度（正在联网搜索…等）后接最终回复；私聊同验；关闭主动消息开关的用户侧验证降级不报错。

## 6. 明确排除 / 后续扩展

- **不做持久化事件队列**：进度消息是即时性的，错过即无价值（请求都结束了还补发"刚才在搜索"是骚扰），迟到事件直接丢弃；
- **不做进度消息的 Markdown 排版**：纯文本短句（"---正在搜索---"风格），Markdown 模板审核成本不值得花在临时消息上；
- **不做节流/聚合层**（一期）：单次请求 ≤4 条在频控预算内；二期深检接入时若实测刷屏，加"同轮聚合"缓冲；
- **后续扩展候选**：深检浏览节点接入（按轮聚合成"正在阅读第 2/6 个页面…"）；进度事件带上轮次序号让文案可组合；图文进度（富媒体上传通道就绪后）。
