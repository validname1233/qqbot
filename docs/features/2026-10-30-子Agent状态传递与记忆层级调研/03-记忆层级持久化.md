# 主/子 Agent 的持久化记忆层级调研

> 2026-10-30。子 Agent 网络调研产出（官方文档实抓，URL 随文）。
> 对照基线：我们的单表 conversation_events（append-only 事件流）+ L2 全量
> 视图 + L1 无状态投影。
> 姊妹篇：01-框架与理论、02-DSH源码专篇。

## 1. Claude Code 的记忆体系

URL: https://code.claude.com/docs/en/memory 、/sub-agents

**持久记忆两层并存**：

- **CLAUDE.md 四级层级**（托管策略 → User `~/.claude/CLAUDE.md` → Project
  `./CLAUDE.md` → Local）：逐级叠加不覆盖，上限 4MiB；**子目录的 CLAUDE.md
  按需加载**（实际读写该目录时才注入）；`@path` 递归导入（4 层）；
  `.claude/rules/` 支持 `paths` glob 的**路径限定规则**；
- **Auto memory**（Claude 自己写的记忆）：`memory/MEMORY.md` 索引（前 200
  行或 25KB 随会话注入）+ 主题文件按需读取；分 user/feedback/project/
  reference 四类。

**Subagent 的记忆（与本题最相关）**：

- 对话转录**不共享**（全新 context window）；
- 但**策划过的持久记忆（CLAUDE.md）共享**——子 Agent 初始上下文包含主对话
  加载的各级 CLAUDE.md（可 `omitClaudeMd: true` 跳过）；
- 子 Agent 转录单独持久化：`agent-{agentId}.jsonl` 存于会话目录的
  `subagents/` 下，**主对话压缩不影响它**、重启可 resume、默认保留 30 天；
- subagent 定义可加 `memory` 字段开启**独立持久记忆目录**（user/project/
  local 三级，官方推荐 project 级可入库共享）——注入该子 Agent 自己的
  MEMORY.md 并自动开放文件读写工具。

## 2. LangGraph：Store 与 checkpoint 分层

URL: https://docs.langchain.com/oss/python/langgraph/persistence 、/stores 、/use-subgraphs

**双层职责严格分开**：

| 维度 | Checkpointer（会话内） | Store（跨线程） |
|---|---|---|
| 持久化对象 | 完整图状态快照 | 自定义键值数据 |
| 范围 | 单 thread | 跨所有 thread |
| 用途 | 会话连续/HITL/回溯/容错 | 用户偏好/事实/共享知识 |

Store 结构 = namespace（任意字符串元组，如 `(user_id, "memories")`）+ key +
value；`search` 按前缀匹配（搜共同前缀即实现跨 agent 共享）；可配语义索引。

**子图三种 checkpointer 模式**（多 agent 场景的直接答案）：

- `per-invocation`（默认，官方推荐）：子图继承 checkpointer 但**每次调用
  独立命名空间、从零开始**——并行调用无冲突；
- `per-thread=True`：跨调用累积状态，但并行写会冲突，需限制并发；
- `stateless=False`：无中断无恢复。

官方明确：**跨图/父子图边界共享数据推荐走 Store**（子图 checkpoint 命名空间
独立，父图看不到子图状态更新）。

## 3. OpenAI Agents SDK 的 Sessions

URL: https://openai.github.io/openai-agents-python/sessions/

- Session = SDK 端自动会话记忆：run 前自动取回历史前置、run 后自动追加；
  后端可插拔（SQLite/Redis/Mongo/Dapr/OpenAI Conversations）；
- **`SessionSettings(limit=N)`：只取回最近 N 条——读时裁剪，存储仍全量
  append**（与我们 L2/L1 的"全量存储+读时投影"同构，官方实现验证了这条路）；
- `session_input_callback(history, new_input)`：自由过滤/重排后返回最终发给
  模型的 items；SDK 仍只持久化真正新增的 items；
- 自动压缩（CompactionSession）：每轮后检查阈值；"自动压缩会阻塞流式输出
  数秒"——低延迟场景建议禁用自动、空闲时手动压缩；失败恢复旧历史、并发写
  串行化保护（我们 reset/summary 管线可直接参考的工程细节）；
- `create_branch_from_turn(turn)`：从某一轮分叉新分支——提示 reset/summary
  可以是"分叉"而非"断裂"；
- 多 agent 顺序复用同一 session 文档明确支持；**同 run 内 handoff/as_tool
  子 agent 的 session 归属官方未规定**——业界默认由编排方显式决定共享或
  隔离，没有自动共享一说。

## 4. Letta (MemGPT) 的分层记忆

URL: https://docs.letta.com/guides/agents/memory 、/memory-blocks 、
https://docs.letta.com/concepts/shared-memory/ 、/agent-sdk/memory/

**经典三层**：

- **Core memory（memory blocks）**：唯一保证在窗口内的层（"pinned to the
  system prompt"）；block = `{label, description, value, limit}`，agent 用
  内置 memory 工具**自主编辑**（core_memory_append/replace），可 read_only；
  默认 persona + human 两块；
- **Conversation/recall memory**：完整历史，逐出上下文后靠 API/检索工具取回；
- **Archival memory**：上下文外长期存储，检索访问。

**多 Agent 共享（关键机制）**：

- **Shared memory blocks**：同一 block attach 到多个 agent——**"update once,
  visible everywhere"**；并发写 last-write-wins，所以组织策略块设 read_only；
  官方用例：**父 agent 实时观察子 agent 的 result block**；
- 新版演进：记忆 = agent 拥有的 **git 仓库（MemFS）**——`system/` 目录每轮
  进 system prompt（= core），其余文件按需读（= archival），编辑须 commit+push
  才成为记忆；**共享记忆仓库**（组织级 repo attach 多 agent）取代 shared
  blocks 成为推荐；
- **Dreaming**：后台子 agent 回顾近期对话提炼记忆，触发器为 step-count 或
  **compaction-event**（压缩时顺便触发记忆整理——异步蒸馏管线）。

## 5. Anthropic《Effective Context Engineering for AI Agents》

URL: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

- **Context rot**：token 越多回忆越差（attention 摊薄）——"find the smallest
  set of high-signal tokens"；
- 三大解法：**Compaction**（摘要重启；最轻量安全的形式是清除工具调用原始
  结果）；**Structured note-taking**（笔记持久化到上下文外，需要时拉回——
  to-do list、NOTES.md、file-system memory tool）；**Just-in-time retrieval**
  （只持轻量引用，运行时按需加载，**从不把完整数据载入上下文**）；预加载
  与 JIT 构成混合策略；
- **子 Agent 架构的核心论述**：子 agent 在干净独立窗口执行深度工作，"每个
  子 agent 可能消耗数万 token 探索，但**只向主 agent 返回 1,000–2,000 token
  的浓缩摘要**"——详细噪声隔离在子 agent 内；
- **"我们'规格进、报告出、过程丢弃'的设计被明确背书"**——问题不在过程不
  进主上下文，而在过程彻底消失：应沉淀为结构化笔记（持久层），主 Agent 只
  消费浓缩报告，需要时按需（JIT）拉取细节；**引用即元数据**（路径/时间戳
  本身是信号）。

## 6. 总结：业界共识形态

**一句话原则：上下文隔离、记忆共享、交换蒸馏。** 四层拆解：

1. **对话转录默认隔离**——没有人把主 Agent 的 L2 全量转录喂给子 Agent
   （Claude Code 全新窗口 / LangGraph per-invocation 默认 / Anthropic 明说
   隔离噪声是子 Agent 的意义）；
2. **共享一小层"策划过的"持久记忆**——小、稳定、结构化、蒸馏产物（人设/
   用户画像/项目约定）：CLAUDE.md 注入每个子 agent、Letta shared blocks、
   LangGraph Store 共同前缀。**对应我们：主 Agent 的事实/摘要层（而非 L2
   全量）+ 规格书 = 唤起子 Agent 的固定注入**；
3. **子 Agent 有独立持久记忆命名空间**——Claude Code `agent-memory/<name>/`、
   LangGraph `(user, "subagent", name)` namespace、Letta 私有 MemFS；运行
   转录单独归档（agent-{id}.jsonl 不受主压缩影响）。**对应我们：
   conversation_events 加 agent 维度或新增 kinds（subagent_call/report），
   过程从"丢弃"变"归档在子命名空间、默认不进主视图"**；
4. **主/子交换走"蒸馏 + 指针"**——入：规格书 + 共享记忆块；出：1-2k token
   浓缩报告 + 可选 result block + 指向后端细节的引用（JIT 拉取）；写入侧
   蒸馏由后台任务承担（Letta dreaming on compaction-event——我们的 summary
   事件可顺带触发）。

**对我们最实用的一条结论**：不要在"共享 vs 独立"里二选一——**同一个持久层
（append-only 事件流），用命名空间划分归属**：转录按 agent 隔离、蒸馏记忆按
作用域共享、交换只走蒸馏报告+指针。单表 conversation_events 可以继续做唯一
事实源（加作用域/agent 维度），不必另起存储。
