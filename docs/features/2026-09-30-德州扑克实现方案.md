# 德州扑克实现方案（v1）

日期：2026-09-30
前置验证（全部真机定案，2026-09-30）：

| # | 事实 | 验证方式 |
|---|---|---|
| 1 | 同一账号 `member_openid === user_openid` | 群/单聊各发一条消息，对比 parseEvent 日志的 authorOpenid |
| 2 | 用群事件里的 openid 主动推单聊**可达** | /私聊我 探针：pushC2CMessage(authorOpenid) 真机送达 |

这两个事实合起来 = "群聊认人、私聊发牌"的双通道架构成立。探针已删，代码库无残留。

## 0. v1 规则裁剪（先定边界，避免实现发散）

完整德州规则很大，v1 裁成休闲局最小集：

- **单桌 2~8 人**，固定大盲注 100（无前注），每人初始筹码 10000（每局重置——v1 不做跨局积分）；
- **标准流程**：发底牌（2/张，私聊）→ 翻牌前下注轮 → 翻牌（3 张公牌，群聊）→ 下注轮 → 转牌（1 张）→ 下注轮 → 河牌（1 张）→ 下注轮 → 摊牌 → 分池；
- **行动**：弃牌 / 过牌 / 跟注 / 加注到 X / 全下；不支持 straddle、边池按标准规则实现（all-in 不足跟注时按贡献切池——这是唯一绕不开的复杂规则）；
- **无计时器**：超时自动弃牌需要 setTimeout 挂在状态机外、进程重启即乱（内存 store），v1 靠群里催；所有人的行动都来自群消息；
- **解散**：任何人任何时候可发「解散」，整局作废、无结算（用户决策：所有人都可以）；
- **单聊只发不收**：私聊回话不会进牌局（其 conversationKey 是 `c2c:<openid>`，键不上 `group:<gid>` 这桌），落回普通 Agent 聊天，无害。v1 明确不做"私聊里行动"。

## 1. 整体架构

### 1.1 消息流（复用现有状态机框架）

```
群消息 → webhook → dispatcher → handler → runCommand
  → runSession（session/runner.ts）
      conversationKey = group:<gid>        ← 已改：群粒度
      ├─ 桌在进行中 → holdemMachine.step(state, ctx)
      │     ├─ 是游戏行动 → 转移状态，产出 Effects
      │     └─ 是闲聊/其它命令 → passThrough，落回普通路由
      └─ 没在进行 → /德州扑克 → holdemMachine.start(ctx)
  → runCommand 拿到 Transition 后执行 Effects（新副作用层）
```

### 1.2 双通道消息分发（本功能的核心架构点）

| 通道 | 内容 | 发送函数 | 时机 |
|---|---|---|---|
| 群聊 | 公牌、行动提示（"轮到 XX"）、下注播报、摊牌结果 | replyGroupMarkdown / pushGroupMessage | 每次转移后 |
| 私聊 | 每人自己的两张底牌 | pushC2CMessage(openid) | 仅发牌时，每玩家一条 |

私聊发送靠事实 1+2：openid 直接取玩家入桌时记录的群事件 authorOpenid。

### 1.3 纯 reducer 纪律的保持与突破

框架铁律"step 不发消息不 await"对扑克依然成立且更重要（并发覆盖状态）。做法：

- `step` 仍是**同步纯函数**：`(state, ctx) → { nextState, effects }`；
- 副作用全部**描述**成数据（effects 数组），由 runCommand 统一执行；
- 发牌的随机性：牌堆洗牌放在 `start`/转移函数内部用 `Math.random`（guess.ts 同款先例，够用；真要可测再注入 RNG 种子，v1 不做）。

## 2. 核心代码实现思路

### 2.1 框架扩展（三处，全部向后兼容）

**① `Transition` 加 `passThrough?: boolean` 和 `effects?: Effect[]`**（machines/types.ts）：

```typescript
export type Effect =
  | { kind: "dm"; openid: string; text: string }            // 私聊（发底牌）
  | { kind: "group-push"; groupOpenid: string; text: string }; // 主动群推（超5分钟窗口时）

interface Transition<S> {
  nextState: S | null;
  reply: string;              // 主回复（回群，被动回复，现状语义）
  passThrough?: boolean;      // true = 这条消息不归我，放行回普通路由
  effects?: Effect[];         // 额外副作用，由 runCommand 执行
}
```

**② `runSession` 的 passThrough 完整实现**（session/runner.ts）——放行分支放在"情况1"里拿到转移结果之后、写回 store 之前：

```typescript
// 情况1：该会话正在某状态机中 → 交给它 step，接管这条消息。
if (active !== undefined) {
  const { machine, state } = active;
  const t = machine.step(state, ctx);

  // passThrough：机器说"这条不归我"。状态原样留在 store（局还在），
  // 返回 NOT_HANDLED——runCommand 继续走普通命令路由：
  // 闲聊不回、/help 照常出速查表、/Agent 照常能触发。
  if (t.passThrough === true) {
    return NOT_HANDLED;
  }

  if (t.nextState === null) {
    store.delete(key);
  } else {
    store.set(key, { machine, state: t.nextState });
  }
  // 正常接管后把 effects 透传出去
  return { handled: true, reply: t.reply, effects: t.effects };
}
```

三个语义要点：

- **放行 ≠ 结束**：store 里那份状态原封不动（牌局还在进行），只是**这一条**消息机器选择不消费；下一条群消息进来 key 还是锁着的，照样进 step，机器每条消息重新决定收不收；
- **情况2（开局）不需要此分支**：开局由 `/德州扑克` 命令触发，命中即锁定，没有"要不要放行"的歧义。passThrough 只对"已锁住之后的每条消息"有意义；
- **observers 照常跑**：放行回到的是 runCommand 的正常路径，而观察者（记忆入库）在 handler 里是与 runCommand 并行的维度，不经过 runSession——牌局期间的聊天照样进记忆，这是对的行为。

**guess.ts 的适配**（1 行改动，修群粒度回归）：

```typescript
// 改前：非数字输入，吞掉并提示
return { nextState: state, reply: "发一个整数来猜嘛，别的我看不懂～" };
// 改后：非数字输入，放行
return { nextState: state, reply: "", passThrough: true };
```

扑克机器里 passThrough 是识别逻辑的自然出口：`ctx.text` 不是行动指令、或是指令但说话人不是 `currentIdx` 玩家 → `passThrough: true`。

**③ `runCommand` 执行 effects**（registry.ts，runSession 返回后）：

```typescript
for (const e of effects) {
  await pushC2CMessage(e.openid, e.text) 或 pushGroupMessage(...);
  // 每条独立 catch + logger.warn：一个玩家私聊失败（拒收/未加好友）
  // 不能连累整局——标记该玩家 unreachable，牌局照走
}
```

**passThrough 的实现是否重量级？——不重，三处小改，估计 30 行以内**：types.ts 加一个可选字段（1 行）、runner 加一个 if 分支放行（约 5 行）、runCommand 透传+执行 effects（约 15 行）。guess.ts 的 `step` 在非数字输入时改返回 `{ nextState: state, reply: "", passThrough: true }`（1 行改动）——顺带修复"群粒度下猜数字吞闲聊"的回归。真正的成本不在 passThrough 本身，而在**每个机器的 step 里要写好"什么算游戏行动"的识别**（扑克：行动指令词 + 谁在说话）——这是业务判断，框架帮不了。完整实现见上方②。

### 2.2 牌局引擎（machines/holdem/engine.ts，纯函数、零 QQ 依赖）

独立于消息层，可脱离 QQ 单测（框架"能脱离 QQ 单测规则"红利的兑现）：

```typescript
// 牌与牌堆
type Suit = "♠" | "♥" | "♦" | "♣";
type Rank = 2..14;                      // 14=A
type Card = { suit: Suit; rank: Rank };
function shuffledDeck(): Card[];        // 52 张洗牌

// 玩家
interface Player {
  openid: string; name: string;
  chips: number; betThisRound: number;  // 本轮已投入
  hole: Card[]; folded: boolean; allIn: boolean;
}

// 桌（= 状态机的 State）
interface TableState {
  phase: "waiting" | "preflop" | "flop" | "turn" | "river" | "showdown";
  players: Player[];
  deck: Card[]; community: Card[];
  dealerIdx: number; currentIdx: number;    // 轮到谁（含弃牌/all-in 跳过）
  pot: number; currentBet: number; minRaise: number;
  lastAggressorIdx: number;                 // 一轮结束的判定：行动回到最后加注者
  actedThisRound: Set<number> 等价物;       // JS 里用 number[] 或 Set
}
```

**下注轮结束判定**（引擎最容易写错的一处）：从最后一次加注者起，其余未弃牌未全下的玩家都行动过一次 → 本轮结束，进入发下一张牌/摊牌。全员 all-in 时跳过下注轮直接发完公牌摊牌。

**牌力评估**（engine 同文件或 evaluation.ts）：7 选 5 最强组合。实现就一层枚举：C(7,5)=21 种五张组合，每种算一个可比较的分值（类别码 << 20 | kickers），取最大。约 60 行，不引第三方库。平分池按标准 tie 规则（side pot 切分在 settle 时按贡献排序处理）。

**行动解析**（不是引擎的活，是机器适配层，见 2.3）：把中文指令转成 `Action` 结构给引擎。

### 2.3 机器适配层（machines/holdem.ts）

StateMachine<TableState> 实现，把 QQ 消息翻译成引擎调用：

```
start(ctx)：校验群场景 → waiting 阶段（"发 /加入 上桌，2 人开局，庄家发 /开始"）
step(state, ctx)：
  ctx.text 解析：
    "加入"   → waiting: 玩家入座（记 openid+name）
    "开始"   → waiting→preflop：洗牌、发底牌（effects: 每人一条 dm）、群发开场
    "跟注" "过牌" "弃牌" "加注 500" "全下"
             → 只当 ctx 作者是 currentIdx 玩家时生效；不是他 → passThrough（别人说话）
    "解散"  → 任何人 → nextState: null 结束
    其它    → passThrough（闲聊放行）
  引擎返回新 TableState + 事件描述 → 拼群播报 reply + 底牌等 effects
```

**指令冲突的处理原则**：行动指令只在"轮到的人"说才算数，其他人说"跟注"当闲聊放行——不骂、不提示，保持群里自然（想提示谁行动就在每次转移的 reply 里带"轮到 @XX"）。

**私聊内容模板**（effects.dm.text）：

```
🂡 你的底牌：A♠ K♠
本局盲注 100，翻牌前第一个行动的是你。
（牌局进行中请回群里行动；这里回复不会进牌局）
```

### 2.4 防作弊与展示细节

- 底牌只进私聊，群消息永远不含任何人的底牌（摊牌时才公开未弃牌者的牌）；
- 群播报用 Markdown（`**公牌** ♠A ♥K ♦7`），replyGroupMarkdown 现成；
- 玩家中途退群检测：v1 不做（没有群成员变更事件订阅），靠"解散"兜底；弃牌后离场无影响。

## 4. 实施顺序（建议两批合入）

- **第一批（框架扩展，先行独立合入）**：types.ts + runner.ts + registry.ts 的 effects 执行 + guess.ts passThrough 适配。合入后全功能回归：猜数字变成群协作版，闲聊/命令不再被吞。真机验收这一批。
- **第二批（扑克本体）**：engine.ts + 单测（先测引擎再接消息层）→ holdem.ts → 注册 → 速查表。真机最小验收路径：两人桌走一局到摊牌，第三人旁观确认闲聊不搅局。

## 4.1 实施记录（2026-09-30，两批均已实施）

测试结果：引擎 18/18（test/holdem-engine.mts）、机器层 8/8（test/holdem-machine.mts），
typecheck 通过。实施中发现并修复的两个引擎 bug（都是单测逼出来的，值得记录）：

1. **advancePhase 提前跳摊牌导致 run-out 公牌发不全**：原实现在"无人可行动"
   （nextToAct === -1）时直接 `phase = "showdown"` 并 return——跳过了后续街的
   发牌。两人全下时公牌只发到 3 张就"摊牌"了。修复：不提前跳，队列留空，
   由 finishAction 的推进循环（needAct 空 → 继续 advancePhase）把牌发齐。
2. **短码全下被平跟后，长码玩家仍被要求逐街表态**：A 投 100、B 短码全下 80、
   A check 收口后，flop/turn/river 每街都还要 A 行动一次——因为 actionablePlayers
   只排除 allIn 玩家，A 未全下就进队列。规则上对手已 all-in 时后续街没有对抗性
   下注轮，应直接 run-out。修复：advancePhase 里可行动玩家 ≤1 时不再建队。

   两个 bug 同根：**"谁还能行动"（未弃牌未全下）和"还有没有下注轮"（可行动
   玩家 ≥2）是两个不同的问题**，第一版实现把它们混成了一个判断。

另：v1 实施时补的两个方案外细节——入座即私聊可达性探测（"加入"的 effects 里
带一条 dm，发不出去只记 warn 不拒入座；比方案 §5.1 倾向的"探测失败拒绝入座"
宽松，因为 runEffects 的失败路径拿不到机器状态做回滚，收紧留 v2）；run-out
中间态（摊牌前的连发公牌）逐街播报，玩家能看到牌逐张翻开。

## 5. 风险与开放问题（实现时留意）

1. **私聊不可达玩家**（拒收/未加好友，40054013/40054004）：effects 执行失败时标记 `player.unreachable`，群里提示"XX 的底牌发不出去，他可能没开私聊"；该玩家可正常玩（公牌信息在群里），只是看不到自己的牌——或开局时探测失败直接拒绝入座（倾向后者，规则更公平，实施时定）。
2. **被动回复 5 分钟窗口**：一局可能超过 5 分钟，行动播报若用 replyGroupMarkdown 会被窗口卡住（群 5 次/5 分钟上限也在）。方案：reply 只用于开局 30 秒内的响应，超窗播报走 effects 的 group-push（主动消息，4QPS/30QPM 级频控，一局几十条够用）。实施时统一封一个 `sayTable()` 帮助函数按时间选通道。
3. **行动指令的格式宽容度**：v1 只认精确指令（"跟注""加注 500"），不做自然语言（那是 Agent 的事，状态机保持确定性）。
4. **平分池的奇数筹码**：余数给最靠庄家左侧的赢家，写死规则即可。
5. **群粒度下单聊猜数字**：单聊 key 是 c2c:<openid>，单人游戏语义不变，无回归。
