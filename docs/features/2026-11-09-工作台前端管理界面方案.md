# 工作台前端管理界面方案（一期：浏览器文件管理 + Monaco 编辑器）

> 设计方案.md 的 bind-mount 目录）配一个网页端管理界面——文件树、代码/文本预览、
> 编辑保存。编辑器内核用 Monaco（VSCode 同源），体验对齐"网页版 VSCode 的编辑区"，
> 不做终端/插件（那是完整 code-server 的领地，多租户隔离成本不成比例）。
>
> **2026-11-09 架构改订**：初版方案为独立 UI 进程 + HMAC token，经与初版对比

> 2026-11-09-工作台UI单双进程与验签方案对比.md）后改订为**单进程**：UI 路由
> 挂在 bot 进程既有的 webhook HTTP server 上，认证回到与 kb 完全同款的
> "随机 token 存库、验签查库"。改订动机与代价分析全部记录在对比文档。

## 1. 背景：UI 面对的是宿主机目录，不是容器

工作台 runtime 是**任务级容器**：每任务起一次、预算到点自毁；真正持久的只有
宿主机 bind-mount（`workspaceRoot/sha256(tenantKey)/`，paths.ts 的
`workspaceDirFor`）。所以本界面本质是**对宿主机目录的文件管理器**——读写全程
不碰 Docker，容器生命周期与 UI 无关，UI 改完的文件下次任务自动可见。

这决定了两个工程结论：

- UI 与 runtime 升级（"真正能用的 coding agent"）**完全解耦**，先做 UI 无雷；
- UI 与 Agent 是同目录的两个独立写入者，并发用通用的 mtime 乐观锁解（§6），
  不需要感知对方的存在。

## 2. 架构总览：单进程，双域名，一个端口

```
QQ 群/单聊                     ECS
──────                    ──────────────────────────────────────
QQ 平台回调 ──────────────► nginx ──┐                         │
浏览器（ws 新域名）────────► nginx ──┤ 按 server_name 分流      │
                                  ▼ 同一端口                   │
                          bot 进程（webhook.ts 的 HTTP server） │
                           ├─ QQ 回调路由（平台验签，原有不动）  │
                           ├─ GET  /ws/<token>       UI 页面    │
                           ├─ GET  /ws/static/*      静态+Monaco│
                           └─ /ws/api/*              文件 API   │
                                 │（每请求查库验 token → scope） │
                                 ▼ 复用 paths.ts               │
                           workspaceRoot/<hash>/（bind-mount 根）│
```

要点：

- **不新增进程**：UI 是 bot 进程内的一组路由（独立模块
  `services/workspace-ui/http.ts`），webhook.ts 只加一处前缀挂载。pm2 应用数、
  端口数、.env 均不变。
- **新域名零代码**：nginx 新增一个 server block，`server_name ws.example.com`
  反代到同一端口。两个域名按 server_name 分流到同一进程——浏览器只见新域名，
  QQ 平台只见回调域名，互不相扰。
- **挂载纪律**：路由分发按前缀匹配，`/ws/` 前缀与 QQ 回调路径完全不相交；
  UI handler 独立模块、独立兜错（UI 路由的异常绝不冒进回调处理），把"动了
  最敏感文件"的接触面积压到最小——这也是将来若拆双进程的现成接缝
  （对比文档 §迁移路径）。

**单进程的已知代价**（对比文档详述，此处只列结论）：UI 发版 = bot 重启 =
在跑的长任务（深检/工作台任务）被杀。纪律：低峰期发版；若将来 UI 迭代
频率高到重启打扰任务，按对比文档的迁移路径拆出双进程。

## 3. 认证：与 kb 完全同款（随机 token 存库 + 查库验签）

签发方与验签方同在 bot 进程内——kb 的有状态方案原样适用，不引入任何密码学：

```
表 workspace_ui_tokens（挂在 data/memory.sqlite，进程内多连接已有先例
    images.ts；token 为主键）：
  token TEXT PK, scope TEXT, created_at INTEGER

签发：/工作台 命令内 randomBytes(24).toString("base64url") → INSERT
验证：每个 /ws/api 请求（及页面路由）查库反解 scope；查不到或超 TTL → 401
```

- **TTL 30 天**（`WORKSPACE_UI_TOKEN_TTL_DAYS`）：created_at 判定，过期 401；
  惰性清理（签发时顺带 DELETE 过期行）。kb 的 token 永不过期，这里有意加严。
- **可吊销**：有状态方案的独有优势——删行即失效（管理员外泄链接后可补救；
  HMAC 做不到这点，只能等自然过期）。
- **同 scope 重复签发**：与 kb 一致，已有有效 token 直接复用（同库同链），
  不堆积行。

命令入口 `/工作台`（新命令型 service，结构照抄 knowledge-base.ts，差异仅在
签发是本进程直接 INSERT，不经 MCP）：

| 语义 | 群聊 | 单聊 |
| --- | --- | --- |
| 闸①（bot 侧） | authorRole 非群主/管理员直接拒绝（fail-closed，null 同拒） | 天然本人 |
| 闸②（平台侧） | URL 只装进跳转按钮 action.data（permission type:1，成员点不动） | 按钮 type:2 |
| 降级红线 | 按钮发送失败→降级文案**不含 URL**（catch 就地兜，不落纯文本回退链） | 按钮失败→纯文本链接可发（通道私密） |

链接即凭证（同 kb）：拿到 URL 的任何人可看可改，管理员勿外传；群历史里的
旧按钮非管理员点不动。

## 4. API 设计（全部查库验 token，前缀 /ws/api）

| 方法与路径 | 语义 | 备注 |
| --- | --- | --- |
| GET `/api/list?dir=` | 列目录（惰性展开，非全量树） | 返回 entries：name/isDir/size/mtimeMs；dir 为空 = 根 |
| GET `/api/file?path=` | 读单个文件 | 超 `workspaceReadMaxBytes` → 413；返回 content + mtimeMs + size |
| PUT `/api/file` | 保存/新建文件 `{path, content, baseMtimeMs}` | mtime 乐观锁（§6）；配额前置（§7）；409=冲突，413=超限 |
| POST `/api/dir` `{path}` | 新建目录 | mkdir -p 语义 |
| POST `/api/rename` `{from, to}` | 重命名/移动 | to 走写路径校验 |
| DELETE `/api/file?path=` | 删除文件或目录（递归） | 永久删除，前端二次确认；回收站列为二期 |
| POST `/api/upload` | 上传（multipart） | **一期可选**，与 PUT 同配额链路 |

约定：

- 凭证形态同 kb 双轨：REST 用 `Authorization: Bearer <token>`（页面从
  `/ws/<token>` 路径取到后存 localStorage）；将来下载/`<img>` 场景用
  `/ws/<token>/api/...` 路径形式（浏览器原生标签带不了自定义头——kb 已趟
  过的路，接口层一开始就同时接受两种）。
- 业务错误统一 JSON `{ error: "可读中文" }` + 恰当状态码；PathError → 400。
- 二进制文件：一期只列出 + 尝试 UTF-8 解码预览（失败显示"二进制文件"），
  图片渲染按需后补。

## 5. 前端页面（无构建，原生 JS + Monaco）

单页 `index.html + app.js + style.css`，三栏布局：左文件树（惰性展开）｜
右编辑器｜顶部工具条（保存、新建、重命名、删除、上传）。

Monaco 集成（AMD loader，**不引入任何前端构建链**，与 kb 管理页同风格）：

```html
<script src="/ws/static/monaco/vs/loader.js"></script>
<script>
  require.config({ paths: { vs: "/ws/static/monaco/vs" } });
  require(["vs/editor/editor.main"], () => {
    monaco.editor.create(document.getElementById("editor"), {
      language: "python", theme: "vs-dark",
      minimap: { enabled: true }, automaticLayout: true,
    });
  });
</script>
```

- **Monaco 开源（MIT）**，微软官方维护，vendor 进仓库无许可问题。
- **版本钉住 0.44.0（经典 min/vs 布局）**：0.5x 起改为哈希平铺 + assets/ 的
  打包布局，editor.main 硬依赖各 worker 哈希文件，按目录裁剪会做出运行时才
  404 的残件（2026-11-09 实测 0.57 全量 17.9MB、裁剪面不可控）；经典布局的
  依赖边界是目录级的，裁剪可预测。
- **上服务器的方式**：本地一次性跑 `scripts/vendor-monaco.mjs`（从 npmmirror
  拉 tarball，解压用 npm tar 包——Windows Git-Bash 的外部 tar 对盘符路径有
  误判），裁剪规则：`vs/language/typescript` 整删（tsWorker 3.5MB 大头，JS/TS
  高亮由 basic-languages 的 Monarch 文法承担，只失去 TS 智能补全——工作台
  以 Python 为主，Python 本来就无 LSP）；json/css/html 三个小 LSP 保留
 （配置/样式文件有真校验）；basic-languages 只留 16 种常用语言；本地化 nls
  删。实测产物 **5.36MB**，git 提交进库——服务器 git pull 即部署，全程零
  联网、零 CDN（jsdelivr 国内可用性不稳，核心组件不冒这个险）。
- 语言按扩展名映射，未知扩展按纯文本。
- 保存流程：Ctrl+S / 按钮 → PUT（带打开时的 mtimeMs）→ 409 弹"文件已被修改
  （可能是任务容器写入）：重载 / 强制覆盖"。
- 脏状态标记（tab 标题 ●）、离开页面 beforeunload 提示。

预估代码量：页面 500~600 行；API 路由 ~300 行；token 表 ~60 行；命令 ~80 行。

## 6. 并发：mtime 乐观锁（统一覆盖所有写者组合）

UI 与 Agent（及群成员之间）互不感知，全部并发语义收敛到一条：

> 打开文件时记下 mtimeMs；保存时服务端比对当前 mtime——不一致即 409。

- 人对人、人对 Agent、Agent 对人**同一规则**，无需"UI 感知任务是否在跑"。
- last-write-wins + 冲突提示，这个规模够用；OT/CRDT 明确不做。
- 任务运行中用户改文件的"读到半成品"是共享目录模型的固有语义（等同两人
  同时编辑），不视为缺陷。

## 7. 路径安全与配额：复用 paths.ts（单一真相源）

paths.ts（services/workspace/paths.ts）已具备全部所需件，UI 路由直接
import，**不写第二份校验**：

| 复用件 | UI 用途 |
| --- | --- |
| `validateRelativePath` / `resolveReadPath` / `resolveWritePath` | 所有 API 的路径裁决（`..` 穿越 / 绝对路径 / NUL / symlink 逃逸全在既有三层滤网内） |
| `usageOf` + `workspaceMaxFileBytes` / `workspaceDiskQuotaBytes` / `workspaceMaxFiles` | PUT/upload 的前置配额（磁盘防线不因 UI 开口子） |
| `workspaceReadMaxBytes` | GET /api/file 读取上限 |

需要的一个小重构：`workspaceDirFor(event)` 从 BotEvent 推 key，UI 路由手里
只有 token 表反解出的 tenantKey 字符串——抽出 `workspaceDirForKey(key:
string)`，`workspaceDirFor` 改为它的 event 包装（六件套工具行为不变）。

属主问题已被 paths.ts 的 chmod 0o777 决议覆盖（2026-10-15 联调修正）；UI
路由与 Agent 工具跑在同一进程（同一用户），无新属主面。验证清单仍保留双向
实测项（§9），防部署环境差异。

## 8. 边界与已知语义

1. **UI 能力 ⊃ Agent 工具集**：删除/重命名/新建目录/上传是 UI 独有——绕过
   Agent 的写入前置检查，但配额仍在 UI API 层拦住；删除是永久删除。
2. **token 与 QQ 身份解耦**：链接不绑定 QQ openid，验的只是"持有有效凭证"
   （与 kb 同级安全性）；但 token 可由管理员侧吊销（删表行）。
3. **重启耦合（单进程的代价）**：UI 任何发版 = pm2 restart bot = 在跑的
   深检/工作台任务被杀。纪律：低峰发版。迭代频率升高后按对比文档拆双进程。
4. **事件循环共享**：UI 的文件操作与 QQ 消息处理同进程——大目录的 usageOf
   递归统计、multipart 解析会短暂占用事件循环。个人 bot 规模 + 各上限兜底
   下无碍，记录在案。
5. **不做的事**：终端、协同编辑、图片/二进制渲染、回收站、移动端优化、
   UI 内触发 Agent 任务（那是二期 runtime 深化的一部分）。

## 9. 验证清单

- typecheck 0；
- token：伪造（库里没有）/ 过期 / 吊销（删行）→ 401；正常通过；同 scope
  重复签发复用同一 token；
- 路径穿越矩阵：`../`、绝对路径、NUL、反斜杠、symlink 指外（读/写两方向都拒）；
- 配额：超单文件 / 超总量 / 超文件数 → 413；
- mtime 冲突：两次打开、先保存者赢、后者 409；
- 属主双向：UI 建文件 → 容器任务可写；容器写文件 → UI 可读可保存；
- kb 同款红线：群聊降级文案不含 URL；成员发 /工作台 得到拒绝文案；
- **QQ 回调回归（关键）**：挂载 /ws 路由后，回调验签/分发行为不变（动的是
  bot 的 HTTP 入口，此为单进程方案最需盯的回归面）；
- 实机：新域名打开页面、Monaco 高亮渲染、保存往返一致、Ctrl+S 生效。

## 附：初版双进程方案摘要（已改订，全文见对比文档）

初版（同日早稿）为独立 UI 进程：`npm run workspace-ui` 独立 pm2 应用、独立
端口，nginx 反代新域名；因签发方（bot）与验签方（UI）跨进程，token 采用
HMAC 无状态签名（payload 带 scope+exp，两进程共享 env secret，无共享存储）。
其动机是发版隔离（UI 重启不杀 bot 任务）与故障半径隔离；代价是 secret 管理
与两个进程的部署面。经对比权衡（对比文档），一期改订单进程，双进程留作
迭代频率升高后的升级路径。
