# 短期记忆两级化方案：热窗口 20 条自动注入 + 冷存储 300 条按需检索（recall_memory 工具）

> 状态：实现方案（未实现）
> 起因：20 条热窗口对"翻旧账"类请求（"我们之前聊过什么""上周你推荐的那个叫什么"）无能为力——旧消息其实还在库里，但模型永远看不到
> 日期：2026-09-05

## 0. 背景与用户诉求

现状：短期记忆 `short_term_messages` 表的读取口径是"最近 20 条"（`sqlite.ts` 的 `MAX_MESSAGES = 20`，`get()` 按 `ORDER BY id DESC LIMIT 20` 取）。20 条全量注入每次对话的 system 上下文。

两个痛点：

1. **容量不够**：活跃群里 20 条可能只是十几分钟的话题，用户问"之前聊的 XX"时早已滑出窗口，模型一无所知，只能瞎编或反问。
2. **扩容两难**：直接把注入量提到 300 条，token 成本 ×15、每次对话延迟显著增加、且大量历史与当前话题无关（稀释注意力）——不可取。

用户提出的解法（本方案的核心）：**两级记忆**。

- **热窗口**（最近 20 条）：照旧自动注入，日常对话的体验和成本完全不变；
- **冷存储**（最近 300 条）：不自动注入。当 Agent 判断当前上下文不足以解决问题时，主动调用 `recall_memory` 工具，由**模型自己挑关键词**从 300 条里检索，返回**命中条目前后 n 条**（n 暂定 10）的原文切片。

一句话：平时只带最近 20 条，需要翻旧账时模型自己去翻——检索成本只在真正需要时支付。

## 1. 方案评价与定位

这个设计就是记忆系统的标准两级形态——MemGPT/Letta 的"核心记忆 + 归档记忆"、Claude Code 的"compaction + 按需检索"都是同构设计。三个亮点：

1. **成本按需支付**：300 条只在触发工具的那次对话进上下文，平时零成本；
2. **关键词由模型挑**：它最清楚自己在找什么、当前缺口是什么——比代码侧预埋关键词灵活得多；
3. **"前后 n 条"切片语义**：对话的连贯性保住了（单条命中容易断章取义，前后文才有"当时聊到哪了"的语境）。

与长期记忆的关系是**互补而非重叠**：

| | 长期记忆（已有） | 冷存储（本方案） |
|---|---|---|
| 内容 | 提炼过的事实（"用户喜欢猫"） | 原始对话流水（逐字记录） |
| 注入方式 | RAG 自动召回 top-5 | 模型主动检索，不触发不进上下文 |
| 粒度 | 事实条目 | 对话切片（含说话人、含图片占位符） |
| 回答的问题 | "关于这个人我该知道什么" | "我们当时具体聊了什么" |

## 2. 关键可行性事实：一张表，两种读取

**扩容几乎免费**——`short_term_messages` 表本来就无限累积（没有任何清理逻辑），20 条只是 `get()` 的 LIMIT。数据已经在库里，300 条冷窗口 = 新增一条读取路径，**零迁移、零新表**。

改动本质：`sqlite.ts` 从"一个读取函数"变成"两个读取函数"——

```text
get(key)              → 最近 20 条（现状，热窗口，不变）
searchCold(key, kw)   → 最近 300 条内按关键词命中，返回命中处前后 n 条切片（新增）
```

300 的边界在检索侧强制：`ORDER BY id DESC LIMIT 300` 之后再做匹配。表无限增长不影响检索成本（300 条常量上限），也避免语义上"翻到一年前"。

## 3. 详细设计

### 3.1 冷窗口常量与联动

```ts
// sqlite.ts
const MAX_MESSAGES = 20;        // 热窗口（现状，不变）
const COLD_MESSAGES = 300;      // 冷窗口上限（新增）
const RECALL_CONTEXT = 10;      // 命中条目前后各取 n 条（暂定 10）
```

### 3.2 检索函数 `searchCold(key, keywords)`

读取最近 300 条到内存，应用层做匹配（300 条规模无需 SQL LIKE，毫秒级）：

- **匹配**：关键词对 `content` 做不区分大小写的包含匹配；多关键词**任一命中**（OR）——模型挑的词是同义候选（"猫/橘猫"），AND 会漏；
- **去重合并**：多个关键词命中相邻条目时切片重叠，按 id 合并成区间（[3..12] + [8..20] → [3..20]）；
- **切片**：每个合并区间最多 21 条（命中 ± 10），区间本身超长时保两头（保命中处附近，砍中间更远的部分）；
- **复用现有分词**：可选增强——用 `tokenizer.ts` 的 `tokenize()` 把 content 预分词做匹配，但一期先不做（包含匹配对"模型挑的关键词"已够用，分词匹配留作召回率不足时的升级位）；
- **返回格式**（给模型看的文本）：

```text
（在最近 300 条记忆中检索"量子纠缠"，命中 2 处）

── 第 1 处（约 47 条之前）──
小明：昨天看了个量子纠缠的科普
小红：我也想看，链接发我
...（前后共 21 条）

── 第 2 处（约 183 条之前）──
...
```

### 3.3 工具 `recall_memory`

```ts
{
  name: "recall_memory",
  description: "检索更早的对话记忆。当用户提到之前聊过的内容、当前上下文里没有"
    + "（如'我们之前说过什么''上次你推荐的''上周聊的那个话题'），或你判断回答"
    + "需要更早的对话信息时调用。关键词用当时对话里最可能出现的原词（可多个，"
    + "同义词一起传），不要用你自己的转述。",
  parameters: {
    type: "object",
    properties: {
      keywords: { type: "array", items: { type: "string" },
        description: "检索关键词，1~5 个，用对话里可能出现的原词" },
    },
    required: ["keywords"],
  },
}
```

实现要点：

- 无结果时返回明确文案："没找到相关记忆（最近 300 条内无『XX』相关内容）"——模型能据此诚实回答"我翻过了，没有记录"，不再瞎编；
- 参数校验：keywords 空数组/非字符串 → 参数错误提示（模型可修正重试）；
- **注册进全局注册表**（`agent.ts`），深检注册表不挂（深检有自己的任务上下文，不翻用户旧对话）。

### 3.4 落库豁免（本方案最必要的配套，不做会翻车）

**问题**：日常 /Agent 收尾时把这一轮全部 messages（含工具结果）append 进记忆（`runAgentTurn` 尾部）。recall 返回的 20 条切片一旦落库，下次热窗口就被旧对话的**复印件**占掉大半——而且复印件会被再次检索到，产生"记忆的记忆"复利膨胀。

**解法**：与深检的记忆策略同款精神（§3.5 只落结晶）——**声明式落库豁免**：

- Tool 契约（`agent/tool.ts`）加可选字段 `skipMemory?: boolean`：工具自己声明"我的 tool 结果不入库"，声明与实现同文件、进版本库。默认缺省 = 照常入库（既有工具行为不变）；
- `registry.ts` 提供 `memoryExemptToolNames(): Set<string>`——收集所有声明了 skipMemory 的工具名；
- `runAgentTurn` 落库前做**结构化身份判定**：扫这一轮 messages，把 assistant 消息里 `tool_calls[].id → 工具名` 存进 Map，tool 消息按自己的 `tool_call_id` 反查出工具名，命中豁免名单的整条剔除（assistant 的 tool_calls 消息保留——它是模型当时真实行为的一部分）；
- `recall_memory` 声明 `skipMemory: true`。日后 open_page（页面正文入库同样挤窗口）等工具要豁免，各自加一行声明即可，loop.ts 零改动。

为什么不按内容猜（如前缀匹配）：工具返回格式一改、或内容碰巧相似，过滤就静默失效——身份判定必须走 tool_call_id 这条模型协议自带的结构化关联。为什么不用数据库表配置："哪些工具豁免"是跟着工具实现走的静态知识（不是运行时数据），入库会造成两处真相，忘了同步就静默失效。

### 3.5 图片 prune 窗口联动

`images.ts` 的 `pruneImagesOutsideWindow` 用 `OFFSET 19`（写死 20 条窗口）决定图片删除边界。窗口语义变成"热 20 / 冷 300"后：

- **图片必须活满 300 条**：否则冷区的 `[图片:17]` 占位符全部 dangling，检索翻出来只剩 `[图片]`，冷存储的记忆价值大打折扣；
- 改动：`OFFSET 19` → `OFFSET 299`，并让 images.ts 和 sqlite.ts 共享冷窗口常量（导出 `COLD_MESSAGES`，images.ts 引用——消灭第二个写死 19/20 的位置）；
- 代价（知情接受）：磁盘图片存量变多（约 ×15），但识图仍是懒的——只有进入热窗口且触发 /Agent 才识图，vision API 成本不涨。

### 3.6 与 MAX_TOOL_TURNS=2 的配合

recall 是串行依赖型工具（翻完记忆 → 决定要不要再 search）。"recall → search"恰好用满 2 轮，没有余量。够用，但记录在案：若日后观察到"模型翻完记忆还想再翻/再调别的工具"被强制收尾，把 MAX_TOOL_TURNS 提到 3 即可（图结构不用动）。

### 3.7 提示词

- `agent_judge`（决策层）追加一句编排规则："用户提到之前聊过的内容而当前上下文没有时，先调 recall_memory 检索记忆（关键词用对话原词），再决定是否还需要联网搜索"；
- recall 工具 description 本身已含触发时机（3.3 节）；
- `daily` / `agent_finalize` 不动——它们不做调用决策。

## 6. 明确排除 / 后续扩展

- **不做向量检索**：300 条规模关键词包含匹配已够（毫秒级、零新依赖）；日后若冷窗口扩到千条级或召回率不足，再接 embedding.ts 的现成向量链路；
- **不做滚动摘要**：不引入"翻出窗口就摘要"的压缩层——那是长期记忆的职责，两系统保持正交；
- **不做跨会话检索**：冷检索按 memoryKey 隔离（群聊整群共享 300 条，单聊个人 300 条），与热窗口同口径；
- **后续扩展候选**：RECALL_CONTEXT 可配化（env）；命中条数上限（防一次翻出 10 处 × 21 条撑爆上下文——一期先靠"区间合并 + 最多 3 处"兜住，实现时定）；tokenizer 分词匹配增强；热窗口长度自适应（按 token 预算而非条数）。
