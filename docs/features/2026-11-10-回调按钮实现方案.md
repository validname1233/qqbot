# 回调按钮实现方案（INTERACTION_CREATE 通用按钮接口）

> 2026-11-10。目标：打通 QQ 回调按钮（action.type=1）的全链路，并落一个
> **通用的按钮回调接口**——任何业务发带按钮的消息、注册回调处理器，用户点击后
> 事件自动路由到该处理器。本轮只做按钮基础设施本身，不含任何具体业务消费方
>（审批等未来消费方另行成方案，挂在本接口之上）。
>
> 选型背景（2026-11-10 对话决议）：现有按钮能力只有跳转按钮（type=0，工作台/
> 知识库入口在用）——点击即打开链接，与 bot 零交互。回调按钮点击后平台推
> `INTERACTION_CREATE` 事件到 webhook、bot 3 秒内回应、按钮状态即时更新，
> 是"点击传达用户意图"的唯一载体。

## 0. 现状缺口

现有三种消息事件（C2C/GROUP_AT/GROUP_MESSAGE）的接收管道成熟：验签 →
parseEvent → dispatch → handler。**回调按钮的点击侧完全没有管道**：

- 平台未订阅 INTERACTION 意图（1<<26）——事件推不过来；
- events/registry.ts 无 `INTERACTION_CREATE` 定义；
- qq/api.ts 无 interactions 回应接口；
- keyboard.ts 只有 type=0 跳转按钮构造（jumpButton）；
- 没有统一的"按钮点击 → 业务处理器"路由机制（本方案的核心产出）。

## 1. 事件与接口契约（QQ 平台侧事实）

依据 docs/features/2026-09-05-QQ机器人消息按钮keyboard详解.md §4.2，
配合本仓库 webhook 信封格式（op=0 事件推送）：

```
外层（RawEvent 信封，与消息事件同构）：
  { op: 0, id: "<interaction_id>", t: "INTERACTION_CREATE", d: {...} }

d 的关键字段（详解文档记载）：
  type: 11                      —— 消息按钮回调的标识
  scene: "group" | "c2c" | "guild"
  chat_type: 1 | 2              —— 1=群 2=单聊
  group_openid / user_openid    —— 发生在哪个会话、谁点的
  data.resolved.button_data     —— 发送时填的 action.data（业务分发键）
  button_id                     —— 发送时填的按钮 id
```

回应契约（详解文档）：

- `PUT /interactions/{interaction_id}`，body `{"code": n}`；
- code：0 成功 / 1 失败 / 2 频繁 / 3 重复 / 4 无权限 / 5 仅管理员；
- **3 秒超时**——不回应则客户端按钮一直 loading；
- **同一 interaction_id 只能回应一次**（重推场景第二次会报错）。

若要点按钮后再发一条消息：发消息接口的 `event_id` 字段传本事件外层 id
（与 msg_id 二选一的被动回复锚点）——一期不用，记录在案。

## 2. 通用接口设计（本方案核心）

### 2.1 button_data 的路由约定

button_data 是发送时自由填写的字符串，点击后原样回到我们手里。约定
**命名空间路由格式**：

```
button_data = "<namespace>:<payload>"
例如 "approval:allow:a3f2c1b0"、"vote:opt2"
```

- `namespace` 是路由键（对应一个已注册的处理器）；
- `payload` 是该处理器自定义的剩余部分（可再含冒号，处理器自己解析）；
- 不带冒号或命名空间未注册 → handler 记 warn 并回应 code:1（失败），
  不炸管道——坏数据可见但不致命。

这个格式与现有命令体系的直觉一致（`/命令 参数`），但完全独立解析，不进
runCommand——按钮回调不是聊天消息。

### 2.2 处理器注册表（buttonRegistry）

新模块 `src/qq/button-registry.ts`，形态对照 registry.ts 的命令注册表：

```ts
export interface ButtonInteraction {
  interactionId: string;   // 外层 id（回应已由管道层完成，业务无需再回）
  namespace: string;
  payload: string;
  buttonId: string;
  userOpenid: string;      // 谁点的
  scene: "group" | "c2c" | "guild";
  chatType: 1 | 2;
  groupOpenid?: string;    // 群聊时有
}

export interface ButtonHandler {
  // 返回 true = 已正常处理；false/抛错 = 管道层回应 code:1
  handle(interaction: ButtonInteraction): Promise<boolean>;
}

export function registerButtonHandler(namespace: string, handler: ButtonHandler): void;
export function findButtonHandler(namespace: string): ButtonHandler | undefined;
```

**业务侧使用范式**（未来消费方的全部工作量）：

```ts
// 1. 发消息时：callbackButton("btn1", "允许", "approval:allow:a3f2", { type: 2 })
// 2. 注册处理器：
registerButtonHandler("approval", {
  async handle(interaction) { /* 校验 userOpenid、推进业务 */ return true; },
});
```

注册发生在模块加载/启动期（与命令注册同时），不随消息动态增删——
与 commands Map 同生命周期。

### 2.3 管道层职责边界

管道（事件定义 → handler → 回应）只做三件事，业务语义全部下沉到
ButtonHandler：

1. 3 秒内回应平台（成功与否不阻塞业务）；
2. 解析 button_data、查注册表、分发；
3. 处理器未注册/返回 false 时回应失败码。

处理器抛错：管道层 catch 记 error 日志 + 回应 code:1，不让单业务异常
影响事件管道（与 runCommand 的兜错纪律同源）。

## 4. key 设计决议

1. **先回应后业务**（§2.4）：3 秒窗口是硬约束，业务逻辑再快也不能赌——
   回应放第一行，失败不阻塞。
2. **interaction 不进 transcript**（§2.3）：按钮回调不是对话内容。这是
   dispatcher 首次为事件类型分流转录行为——确立"只有 chat 类事件才转录"
   的规则。
3. **命名空间路由 + 注册表**（§2.1/§2.2）：button_data 的格式约定与
   ButtonHandler 注册表构成本方案的"通用接口"——业务零管道知识接入，
   管道零业务知识分发。对照命令体系的 commands Map 同构。
4. **坏数据不炸管道**：button_data 缺冒号/命名空间未注册/处理器抛错，
   一律降级为 warn 日志 + 回应 code:1——单业务的坏数据不影响其它按钮。
5. **去重靠内存 Map + 惰性清理**：interaction 的重推去重没有库支撑，
   内存 Map 足够（单进程、事件量小）。

## 5. 数据流总览

```
任意业务（未来消费方：审批、投票、确认对话框……）
  ① 发消息带 callbackButton(id, label, "ns:payload", permission)
  ② registerButtonHandler("ns", handler)   ← 启动期注册
                    │
用户点击按钮        ▼
  QQ 平台 ── INTERACTION_CREATE ──► webhook（验签同现有）
  → dispatcher（跳过转录）→ INTERACTION_CREATE handler（管道层）
    ① respondInteraction(id, 0)    —— 3 秒内，fire-and-forget
    ② button_data 按 ":" 切 namespace → 查注册表
    ③ handler.handle(ButtonInteraction) —— 业务逻辑（验权、推进、回复消息）
       └ 处理器内可用 event_id 被动回复（§1），或主动 push
```

## 9. 回退路线：指令按钮（B 线）

若 7.1 平台实验失败（意图订阅不生效/按钮能力未开放）：

- 交互层降级为指令按钮（action.type=2）：点击后客户端发送
  `@bot btn:<ns>:<payload>` 普通消息，走现有消息管道；
- **本方案的注册表/命名空间格式原样保留**——降级只是把"事件进线"从
  INTERACTION_CREATE 换成普通消息里 `btn:` 前缀的文本解析，处理器接口
  （ButtonHandler）不变；
- 代价：群聊多一步手动发送（enter=true 仅单聊）、会话里多一条文本。

§2.2 的接口抽象保证了这个降级是纯进线替换。
