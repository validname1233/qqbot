# 记忆分层重构方案——上下文层 × 转录层

> 2026-10-27。核心提案（来自项目 owner）：把现在混在一张表里的"记忆"按用途切成两层——
> **第一层（上下文层）**：作为 message 数组直接拼接给模型看的工作记忆，内容是规范
> 的 user/assistant/tool 序列，群聊消息结构化处理后进入；**第二层（转录层）**：QQ
> 聊天窗口里出现过的全量对话记录，供工具（recall_memory）查询历史背景用，不含
> tool 结果和中间过程输出。两层经"第一层的 tool 查询第二层"产生联系。
>
> 本文对照代码验证这个划分的可行性与合理性，补足提案中欠考虑的部分，给出落地设计。
> 姊妹篇：`docs/problems/2026-10-27-上下文拼接重构分析报告与修改方案.md`（下称
> 〔拼接报告〕）——那里定义了上下文层的**装配机制**（token 预算读取、渲染层、摘要
> 槽、缓存），本文定义**分层与存储模型**，两者拼起来才是完整方案。

## 0. 结论先行

两层划分成立，而且正好击中现状的三个实证问题（§1）。但提案有五处需要修正/补充：

1. **第一层不能只是"给模型看的数组"**——它跨轮持续存在、且包含 tool 过程内容，
   无法从第二层派生，需要自己的持久化（或与第二层共存于一张按类型标记的表）；
2. **第二层的"全量"必须是双向的**：bot 说出口的话也"在群里出现过"，只记用户侧
   会让 recall 查历史时半盲。把不变量定为"**QQ 聊天窗口里实际出现过的一切**"，
>    写入点自然落在出站收口处（`qq/messages.ts`），顺带根治了覆盖缺口（§1.2）；
3. **第二层不需要任何"滑动窗口维护"**——存储无限累积，"窗口"只是查询深度参数
>    （现状本就如此，`sqlite.ts:5-9`），比提案设想的还简单；
4. **说话人 id 不该用 openid 原文进模型上下文**（长、对模型无意义、隐私面大）：
   结构化列存 openid，渲染层映射成短标签（u1/u2…+成员注册表），形态待〔拼接
   报告〕§3.3 的探针拍板；
5. **"打包给另一个大模型生成 user 内容"的路线否决**（提案本身也更倾向结构化）：
   有损重述用户原话、非确定性输出破坏前缀缓存（同一行历史两次渲染成不同文本）、
   增加时延与成本，四条都是硬伤。

## 1. 为什么要分：现状一张表混了两种职责

`short_term_messages`（`agent/memory/sqlite.ts`）同时承担两个角色：

- **热窗口**（20 条，`get()`）→ 拼进 /Agent 的 message 数组 = 提案的第一层职责；
- **冷档案**（300 条，`searchCold()`）→ recall_memory 工具检索 = 提案的第二层职责。

两种角色对"什么该进表"的要求**相互冲突**，混在一张表上就互相将就，已经付出三笔学费：

### 1.1 双写 bug（自动路由的消息入库两次）

三个 handler 都是 `Promise.all([runCommand, runObservers])`，观察者看到的是原始
ctx（`C2C_MESSAGE_CREATE.ts:25-28`），而自动路由在 `runCommand` 内部把
`{...ctx, command:"Agent", args}` 直接喂给 agentService（`registry.ts:152`）——
观察者不知道。单聊"你好"：memory-log 落一条（command===null 分支），
runAgentTurn 再落一条（`loop.ts:428`）。**根因：入库决策分散在 3 个文件，靠
注释约定对齐（`memory-log.ts:4-7` 的"天然不重叠"），自动路由上线后约定静默失效。**

### 1.2 覆盖缺口（bot 说过的很多话，档案里不存在）

除 /Agent、/深度检索外的一切命令交换（/help、/定时任务、未知命令提示、并发闸
拒绝文案）、定时提醒推送（`reminder.ts` 直推不落库）、状态机回复（扑克牌面快照、
结算报告）——全部不入库。冷档案号称"了解历史背景"，实际上 bot 侧只有两个命令
的输出存在。**根因：没有"bot 出站消息"的统一落库点。**

### 1.3 冷检索切片污染（现存缺陷，写本文时发现）

`searchCold` 的切片区间按行号切，区间内**所有**行都进结果，渲染时
`speaker = row.role === "user" ? author_name : "assistant"`（`sqlite.ts:156-158`）
——**tool 行被渲染成 "assistant：{工具原始输出}"**。模型检索到的"历史背景"里
混着被误标为 bot 发言的工具结果正文。**根因：表里混着 process 行，查询侧过滤
了匹配却没过滤切片。**

两层分离后：①②由"每类事件单一写入者"根治（§4），③由"第二层根本不存 process
行"根治（结构性的，不靠查询纪律）。

## 2. 两层模型定义

| | 第一层：上下文层 | 第二层：转录层 |
|---|---|---|
| 本质 | 模型的**工作记忆**（它"经历过"的对话） | 聊天窗口的**地面真相**（实际发生过什么） |
| 内容 | 结构化 chat 消息（user/assistant）+ agent 过程（tool_calls/tool，写入时塑形）+ 压缩摘要 | 双向 chat 消息：所有用户消息 + 所有 bot 用户可见回复，**不论出自哪个子系统** |
| 不含 | —（tool 结果属于本层） | tool 结果、中间节点输出、压缩摘要、瞬时提示（进度推送） |
| 消费方式 | 每轮装配成 message 数组直接进模型 | 偶尔查询：关键词切片（现 searchCold）、未来可按说话人/时间 |
| 体积控制 | token 预算 + 压缩（摘要槽）+ 写入时塑形 | 不控制——无限累积，读取带界 |
| 说话人 | 渲染层标签（u1·张三 / name 字段，待探针） | 结构化列（author_openid/author_name），渲染时才决定模型看到什么 |

**层间联系**：`recall_memory` 工具查询转录层，结果以 `role:"tool"` 消息落入
上下文层——成为模型"经历过"的一部分，后续轮次直接可见，压缩时被摘要吸收。
recall 的输出形态（v4 定案，详见 §5.2）：**固定深度回看 + LLM 检索式摘要**——
工具从 L2 取最近 N 条 chat 行（带说话人标签渲染成文本包），过一次 flash 模型，
提示词带一锚（用户当前问题），产出 ≤200 字的问题感知摘要 + 由摘要模型自己
挑出的 ≤5 条最相关原文行（逐字，作为保真地板——"挑相关行"这个动作从 SQL
关键词匹配移交给了 LLM，语义级检索天然免疫改述/同义词）。**零参数工具**：
不暴露 keywords/n 给判断模型（挑关键词正是旧设计最大的失败面，零参数 = 最
可正确调用）。小包不过 LLM（不足阈值直接原文返回），摘要调用失败返回固定的
"记忆检索暂时失败"短语——绝不把整个文本包倾泻进上下文。

**独立于两层的既有机制**（提案"其余层级以后再讨论"，明确归档）：
长期记忆 `long_term_memories`（RAG 事实库，add_memory/recall 注入，保持现状）、
图片库 `message_images`（懒加载识图资产，两层共享：转录层存 `[图片:id]` 占位符，
上下文层读取时展开成 `[图片]{描述}`，〔拼接报告〕§6.4 的确定性规则不变）。

## 3. 存储设计：一张表，两种投影（推荐）

### 3.1 为什么不是两张表

直觉做法是两层各一张表，但入站消息要同时写两张（上下文层要结构化版、转录层要
原文版），双写一致性问题和 §1.1 的多写点问题是同一类病。而两层的内容高度重叠
（chat 消息两层都要），差异只在 process/summary 行——这是"同一份日志、两种视图"
的形状，正是 dsh 的 log-as-truth 模式（SessionEvent 日志为真相，messages 是
`deriveMessages()` 派生的冻结投影）。

### 3.2 表结构（新表 `conversation_events`，旧表直接废弃）

```sql
CREATE TABLE conversation_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  key TEXT NOT NULL,                     -- 租户键（group:<gid> / c2c:<openid>），同现状
  kind TEXT NOT NULL CHECK(kind IN
    ('chat_user', 'chat_bot', 'process', 'reset', 'summary')),
                                         -- reset=上下文窗口清空标记（v5：压缩延迟，
                                         --   phase1 预算溢出即全量清空，投影从最新 reset 之后开始）
                                         -- summary=预留（摘要槽，v5 延迟实现，phase1 不写入）
  author_openid TEXT,                    -- chat_user 必填；chat_bot 为 NULL
  author_name TEXT,                      -- 同上
  role TEXT NOT NULL,                    -- 投影到 ChatMessage 的 role：
                                         --   chat_user→user, chat_bot→assistant,
                                         --   process→assistant(tool_calls)/tool, summary→user
  content TEXT,
  tool_calls TEXT,                       -- process 行专用（JSON）
  tool_call_id TEXT,                     -- process 行专用
  qq_msg_id TEXT,                        -- chat_user 行必填，UNIQUE 去重（QQ 会重推事件——
                                         --   images.ts:51 已为此吃过亏，旧表没有这层防护）
  origin TEXT,                           -- 来源标记（agent/deep-search/poker/reminder/help/
                                         --   unknown-command/…），排查与未来按来源过滤用
  created_at INTEGER NOT NULL,
  UNIQUE(key, qq_msg_id)                 -- chat_user 去重；process 行 qq_msg_id 为 NULL 不受约束
);
```

两种投影就是两种读取口径：

- **上下文层读取** = `[summary 行（最新 1~2 条，置顶）] + [chat_user/chat_bot/process 行，token 预算内]`，经渲染层变成 `ChatMessage[]`（〔拼接报告〕§3.2/3.3）；
- **转录层读取** = `WHERE kind IN ('chat_user','chat_bot')`，关键词/说话人/时间查询。

### 3.3 备选：两张物理表

若担心单表列太宽（process 列对 chat 行是死列），可以拆成 `chat_events` +
`context_events` 两张表，用同一个全局序（或同租户 seq）维持交错顺序。语义等价，
代价是写入扇出和两表一致性。**推荐先单表**——列宽的成本是静态的、可见的；
双写的成本是动态的、会再犯 §1.1 的病。

## 4. 写入点重排：每类事件一个写入者

这是本方案对现状最大的行为修正，也是 §1.1/§1.2 的根治点。原则：**写入跟着
"事件发生的地方"走，不跟着"恰好想读的 service"走**。

| 事件 | 写入者 | 写什么 |
|---|---|---|
| 任何入站消息 | **dispatcher 层**（或 memory-log 观察者改造后担任，见 §4.1） | 一行 `chat_user`（含先持久化图片拿占位符）；UNIQUE(qk_msg_id) 天然吸收 QQ 重推 |
| 任何出站消息发送成功 | **`qq/messages.ts` 收口**（8 个函数在 `traceOut` 处同步写） | 一行 `chat_bot`；markdown 回退链只记成功那次；**ephemeral 发送显式跳过**（进度推送） |
| agent 一轮的过程 | **图节点就地写入**（v2 修订，见下）：`llmCall` 每产出一条 assistant（含判断碎念与 tool_calls）、`toolsNode` 每产出一条 tool 结果，就在该节点内**原文全文**写 `process` 行；`plainReply`/`finalize` 什么都不写——最终回复由出站收口记唯一的 `chat_bot` 行，轮次天然闭合 |
| 上下文预算溢出（装配时判定） | 装配层（v5，见 §4.3） | 一行 `reset`（窗口清空标记；`summary` 行延迟实现，phase1 不写入） |

对比现状的三个写入点：memory-log（上移为 dispatcher 级 chat_user 记录员）、
`loop.ts:428` 的批量收尾（**整段退役**，见下）、`deep-search.ts:527`（**整个
删除**——问题行由 dispatcher 记 chat_user，报告行由出站收口记 chat_bot，手拼的
`${authorName}：/深度检索 …` 前缀格式也随之消亡）。

**v2 修订（2026-10-27 讨论）：agent 过程改为节点就地入库，替代"invoke 之后
统一切片落库"。**收益有三：① `loop.ts:388-433` 那段约 45 行的切片重建逻辑
（`slice(1 + history.length)` 反推新消息、占位符版重拼 storedUserMessage、
tool_call_id 反查豁免名单）**整个删除**——它的全部存在理由就是"跑完再批量落库
需要反推哪些是新的"，就地入库后每个节点只写自己刚产出的消息，无需反推；
② 残缺轮次（/stop、崩溃）不再整轮丢失——写到哪算哪；③ 库里是未经塑形的全量真相，体积控制全部移到装配侧（§4.3，v3 起压缩是唯一
机制），可逆可调。代价是一条新纪律：
中断轮会留下没有 chat_bot 闭合的半截 process 行（甚至悬空的
assistant(tool_calls)），由 §4.3 的闭合投影规则兜住。

### 4.1 入站写入的位置选择

两个候选：**a) dispatcher/handler 层**（`buildContext` 附近，命令/观察者分叉之前）
或 **b) memory-log 观察者扩展为"全量 chat 记录员"**（去掉 `command === null`
过滤）。推荐 a：观察者模型里"命令消息也记"违反 memory-log 头注释的自我描述，
而 dispatcher 层天然在所有分叉之前，一处覆盖全部入站。图片持久化
（`persistEventImages`）随之搬家——它必须先于 chat_user 写入（占位符要进 content），
dispatcher 层顺序清晰。

### 4.2 出站写入的细节

- `traceOut` 已在每个函数的成功路径上（`messages.ts:13-15`），转录写入挂同处，
  记 `(key, kind=chat_bot, role=assistant, content, origin)`；markdown 与纯文本
  都记最终内容（回退链重发时第一次失败未发出，不记）。
- **ephemeral 排除**：进度推送走 `pushGroupMessage/pushC2CMessage`
  （`progress-bus.ts:31-33`），"正在搜索…"这类瞬时提示进转录层纯属噪声，也灌进
  上下文层。给两个 push 函数加可选参 `opts?: { record?: boolean }`，progress-bus
  传 `record:false`；其余调用方默认记。
- 私聊 DM（扑克发牌等 effect）会写入**该玩家自己的 c2c 租户键**——符合"窗口里
  出现过"不变量（那确实是 bot 对他说的话），且未来该玩家问"我上次什么牌"时
  recall 可查。游戏保密性不受影响（跨租户本就隔离）。
- 主动推送失败（频控/拒收）会抛错，不写转录——没发出的消息不存在，语义自洽。

### 4.3 装配侧：零策略投影 + 压缩作为唯一体积机制（v3）

v1/v2 曾在装配侧设两道闸（prune 头尾截断、skipMemory 占位替换）。v3 全部退役，
理由：两者与压缩管线职责重复，且盲切（保头尾字符）的信息保真劣于语义折叠
（摘要保"对话实际用到的事实"）。分层纪律收敛为三条：

- **工具层**：每个工具自己决定返回什么形态（recall 内部摘要、open_page 正文
  抽取、search 结果列表）——这是工具的输出契约，记忆层不认识任何工具名；
- **记忆层**：零策略。L1 存什么、投影什么，忠实于"发生过什么"，全量原文；
- **装配层**：phase1（v5）体积控制 = **预算溢出即全量清空**——装配时估算超限，
  追加一行 `reset` 标记，投影从最新 reset 之后从零积累。摘要式压缩与摘要槽
  整体延迟：当前场景历史价值衰减快、流量低，全量清空的损失可接受，实现成本
  近乎为零。reset 边界天然落在轮与轮之间（装配时写入，不在消息流中间），
  切割不会落进 tool 配对——`dropOrphanToolHead` 要处理的孤儿形态结构性消失，
  该函数随之退役。

具体规则：

- **闭合投影规则**（不变）：L1 只投影"被 chat_bot 行闭合的 process 段"——读到
  chat_bot（本轮最终回复，天然是轮次终点）即认为其之前的 process 段完整；末尾
  未被闭合的尾巴（中断轮）整段不进 L1，但留在库里作为真相。悬空配对
  （assistant(tool_calls) 写了、tool 没跑完）与残缺轮问题被同一条规则解决，
  不需要 turn_id 列。
- **预算取宽**（建议 24k~32k token 起步）：append-only 期间全部命中缓存，
  reset 一次 = 一次全量前缀 miss，攒得越久均摊越好；
- **观测兜底**（随日志设计一并延迟，v5 日志置空）：若日后 usage 数据显示
  reset 过频（缓存命中趋零），先调宽预算，再考虑实现摘要式压缩。

轮内例外：agent 图循环内不回读库，state.messages 即真相的内存副本（节点就地
入库是"顺手写一份"，逻辑走内存）；跨轮装配（prepareContext）与压缩器才从库里
取行做投影。轮内模型看到的 tool 结果本就只能是全文（function-calling 协议要求，
v2 的投影时 prune 也从未作用于轮内）——v3 的统一只是把轮外的盲切也去掉了，
当轮回答质量无回归。

轮内例外：agent 图循环内不回读库，state.messages 即真相的内存副本（节点就地
入库是"顺手写一份"，逻辑走内存）；跨轮装配（prepareContext）与压缩器才从库里

## 5. 读取路径

### 5.1 上下文层（每轮 /Agent）

```
[system] [最新 reset 之后的 chat 行（v7：process 不跨轮投影），token 预算内，渲染层标注说话人] [u_now]
```

phase1（v5）无摘要槽、无长期记忆注入位（两者均延迟/置空）。装配机制在
〔拼接报告〕§3 与总方案（`2026-10-28-记忆与上下文重构总方案.md` 模块二）：
预算读取替代 20 条窗口、u 标签/name 探针、渲染确定性。与现状的衔接点只有
一个：`get()`（`sqlite.ts:164-179`）换成新表的投影读取。v7 后 process 行
不进投影——残缺轮/悬空配对/孤儿问题结构性消失，无需闭合过滤，
`dropOrphanToolHead` 的退役理由更彻底。

### 5.2 转录层（recall_memory 工具，v4：固定深度回看 + LLM 检索式摘要）

旧 `searchCold` 的三段逻辑——判断模型挑关键词、SQL OR 匹配、区间合并取最新
3 切片——**整体退役**。新读取路径只有一步取数：

```
取最近 N 条 chat 行（kind IN chat_user, chat_bot，正序）
  → 渲染成带说话人标签的文本包（"张三：…" / "bot：…"；[图片:id] 占位符
    作为字面文本保留——摘要模型只需知道"发过图片"，不触发识图）
  → flash 模型：给定当前问题，产出摘要 ≤200 字 + 自选最相关原文行 ≤5 条
```

- **N 是 config 常量**（建议 300，等于旧冷窗口深度；chatty 群约 15k~40k 字符，
  flash 输入成本每次不足一分钱，时延秒级——可接受）；
- 保真地板从"SQL 命中行"变成"摘要模型自选行"：改述/同义词不再漏检
  （"那个毛茸茸的"旧关键词匹配必漏，LLM 语义检索能中）；
- 实现时同步删 `agent_judge` 提示词里"（关键词用对话里可能出现的原词）"
  的指引（`functional.ts:64`）与工具 schema 的 keywords 参数；
- 连带影响：`COLD_MESSAGES` 常量死后，images.ts 的 prune 锚点（§3.5 旧方案）
  改挂到同一 N（图片只保留最近 N 条 chat 行内被引用的，语义不变）。

按说话人/时间过滤的"升级"不再需要预做——摘要模型在文本包上天然能做
（"我和张三聊过什么"由提示词锚直接回答），L2 保持哑存储。

### 5.3 压缩摘要与两层的边界

摘要行（`kind=summary`）只在上下文层投影出现，转录层永远看不到——**转录层不做
压缩**，它是档案不是工作集。这是两层最重要的纪律：体积问题全部关在上下文层内
解决（预算、塑形、摘要），永远不反向污染档案。

## 7. 迁移（2026-10-28 定案：无兼容负担）

测试环境、旧数据无保留价值——**不做双读过渡、不做存量回填、不保留旧表**：

- 部署新代码前在服务器上 `DROP TABLE short_term_messages`（或连同新表一起由
  启动时的 `CREATE TABLE IF NOT EXISTS` 自动创建，现状模式 `sqlite.ts:46`），
  新表从零开始积累；
- 注意 `data/memory.sqlite` 里还有 `long_term_memories` 和 `message_images`
  两张表（长期记忆与图片资产，独立于本次重构的两个层级）——"清空旧历史"指的
  只是 `short_term_messages` 这一张；若测试数据一并不要，删整个文件也行，但
  要知道顺手清掉的是三个模块的数据，长期记忆和图片描述缓存会一起归零。

## 8. 分阶段实施（与〔拼接报告〕的阶段对齐）

- **M0 观测与探针**＝拼接报告 Phase 0（usage 日志、name 字段探针）——两方案共用；
- **M1 分层落地（本方案主体）**：新表 + 四个写入点重排 + 双写/覆盖缺口修复 +
  recall 迁移。**行为收益立即可验**：同一条自动路由消息在新表恰好一行；
  /help 回复、提醒推送、扑克快照在转录层可查；
- **M2 上下文层装配**＝拼接报告 Phase 1+2（尾部化、finalize 结构化、预算读取、
  渲染层、缓存命中验证）——依赖 M1 的新表；
- **M3 压缩管线**＝拼接报告 Phase 3（摘要行写入本表 kind=summary）。

每阶段验收：M1 后 `SELECT kind, COUNT(*) FROM conversation_events GROUP BY kind`
的分布与真实聊天记录人工比对；自动路由消息单行验证；typecheck + 现有测试。

## 9. 开放问题

1. 说话人标注形态：name 字段 / u-registry / 全角标注（拼接报告 §3.3 探针拍板，

   L1（现状方案默认进——保持"模型经历过=窗口出现过"的简单不变量；若噪声明显
   再加 visibility 细分，避免过早设计）；
