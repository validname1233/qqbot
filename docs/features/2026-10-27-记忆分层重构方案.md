# 记忆分层方案——L1 上下文层 × L2 转录层

> 2026-10-27 初稿，**2026-10-30 按终版架构整体重写**（初稿写作时 v7~v10 决议
> 尚未发生，内容已过时，不保留）。本文是记忆分层的**概念定义文档**：两层
> 是什么、什么关系、为什么这样分、未来往哪去。工程实现（表结构、写入点、
> 装配管线、提示词模块）见《2026-10-28-记忆与上下文重构总方案.md》与
> 《2026-10-29-系统提示词模块化重构方案.md》，本文不重复。

## 1. 一句话版本

两层不是两份存储，而是**同一张总表（`conversation_events`）的两种投影**：
L2 是全量视图（QQ 窗口里出现过的一切对话），L1 是压缩视图（按规则截取、
拼装成 prompt 注入给模型的部分）。

## 2. L2：转录层（档案层）

**定义**：QQ 聊天窗口里实际出现过的一切对话记录（文本维度）——所有用户
发言（`chat_user` 行）+ bot 实际发出的所有回复（`chat_bot` 行），不论出自
哪个子系统（Agent、/help、提醒推送、扑克快照……）。不变量一句话：
**"窗口里出现过 = L2 里有一行"**。

**为什么必须自建**：QQ 官方没有历史消息 API——窗口里的过去，平台不提供
回查，只能自己记。这是 L2 存在的根本理由：它是我们自建的聊天记录地面真相
（bot 视角下平台欠我们的一份 API）。

**职责**：
- 历史回查：`recall_memory` 工具从 L2 取最近 N 条 chat 行做检索式摘要
  （模型在 L1 里发现需要已滑出窗口的更早历史时的查询通道）；
- 长期记忆的素材源（未来，§7）；
- 审计排查：`origin` 列标记每条消息来自哪个子系统。

**纪律**：
- append-only，永不压缩、永不改写——档案不做体积控制，读取带界（N 条深度）；
- 不含 tool 结果与中间输出（那些没出现在 QQ 窗口里，见 §4 的 process）；
- 图片以 `attachment_ids` 引用列关联 `message_images` 附表（描述缓存在此），
  L2 的行本身只存文本原文——"文本维度"指这个。

## 3. L1：上下文层（prompt 层）

**定义**：每次模型调用实际注入的完整 prompt——模型"此刻看得到"的一切。
由四段组成，**生命周期不同**（这是理解 L1 的关键，它不是一块同质的东西）：

| 段 | 内容 | 来源 | 生命周期 |
|---|---|---|---|
| ① system | 身份与输入格式 + 工具规则 + 人格 + 输出格式（提示词 v2 的 M1+M2+人格槽+M3） | functional.ts/builder 装配 | 按租户恒定（缓存锚点） |
| ② 历史投影 | chat 行视图：用户发言打包成 blob 批（`{"speaker":…,"content":…}` 逐行）+ bot 回复作裸 assistant 隔断 | **总表投影**（v10 压缩规则过滤） | 每轮现算；行字节跨轮稳定（缓存契约） |
| ③ u_now | 当前这条用户消息——独立成条、恒在末位（"末位 = 当前诉求"的构造性保证） | ctx 构造（不经库行；图片按 msgId 反查展开） | 单轮 |
| ④ 轮内过程段 | 本轮的 assistant 中间输出（含 tool_calls）+ tool 结果，原文全量 | 内存 state（同步落库为 process 档案行） | **轮内易失**——轮末蒸发 |

三条关键性质：

- **②不含过程内容**（v7）：跨轮只见成品（用户说了什么、bot 答了什么），
  不见过程（怎么查到的）。理由见 §6.3；
- **④只活一轮**：过程对是模型的"工作台"，不是记忆——轮一结束就从 L1
  消失；库里对应的 process 行属于审计档案（§4），**永不回投影**。所以
  "所有工具结果都进上下文"这条决议的适用范围是**轮内**，轮内一点不打折；
- 降级分支（forcedFinalize，轮次触顶时）会额外注入一条恒定的终止信号
  user 消息——属控制指令不属记忆，同样轮末蒸发。

**压缩规则（v10）——②的截取依据，只有两条**：

1. 条数截断：候选 chat 行超过 `CONTEXT_MAX_MESSAGES`（初定 200）→ 只保留
   最近 200 行（尾部对齐）。未来可换成 token 驱动判定（上限刻意设低——
   上下文逼近模型上限时能力会下降，预计设为一半左右再截）；
2. 时间窗：行的 `created_at` 距装配时刻超过 `SESSION_WINDOW_HOURS`
   （默认 2h）→ 离开投影。窗口是**滑动的**：会话持续活跃时窗口跟着
   "现在"前滚，静置超时后旧消息在下一次触发时整块滑出。

两条都是**纯投影过滤**：不往流里写任何标记行，库永远全量。除此之外——
**没有意外就全量注入**。

## 4. 投影源：conversation_events 总表

单一真相源。L1 和 L2 都是它的查询视图：

| kind | 内容 | 进 L1？ | 进 L2？ |
|---|---|---|---|
| `chat_user` | 用户发言原文（+ attachment_ids 图片引用） | ②的来源 | ✓ |
| `chat_bot` | bot 发出的成品回复原文 | ②的来源（裸 assistant） | ✓ |
| `process` | agent 轮内过程全文（assistant 含 tool_calls / tool 结果，零塑形） | ✗（v7）——轮内走内存 ④ | ✗（QQ 窗口里不存在） |
| `reset` | 历史遗留 kind（v10 废除语义：不写入、不读取，仅为旧库兼容保留） | ✗ | ✗ |
| `summary` | 已取消（v10），永不写入 | ✗ | ✗ |

**process 行的地位值得单独说清**：它是审计档案，**不属于任何一层的投影**。
它记录的是模型的工作过程——当轮在内存 ④ 里用过、用完即弃。既不在 QQ
窗口（非 L2 的"出现过"），也不跨轮注入（非 L1 的投影口径）。留它的理由
只有排查回放（当时模型看到/做了什么）与未来可能的训练素材价值。

图片附表 `message_images` 与总表同库共存：chat_user 行的 attachment_ids
指向它；L1 投影渲染时展开成 `[图片]{描述}`（描述写后不重写——同一行恒
渲染同一字符串，缓存红线）。

## 5. 两层的关系

- **内容上**：L1 的历史段 ② ⊆ L2——同一个 chat 行池，L1 只是多套了压缩
  过滤。注意方向：**不是"L1 从 L2 读取"，而是两者各自查总表**——L2 是
  全量口径，L1 是压缩口径。分层是读取口径的分层，不是存储的分层；
- **生命周期上**：L2 单调累积、永不遗忘；L1 每轮从零现算、窗口随时间与
  条数上限滑动；
- **层间联系（唯一的运行时交汇点）**：`recall_memory`——模型在 L1 里
  发现自己需要更早的历史（已滑出 ② 的窗口），调用工具查 L2，结果以
  tool 消息进入 ④（当轮可见、轮末蒸发）。"短期不够查长期"的单行道；
- **一句话**：L2 负责"发生过什么"（真相），L1 负责"此刻该想起什么"（视图）。

## 6. 设计动机

1. **L2 必须自建**：QQ 无历史消息 API，窗口的过去平台不还——不自建，
   bot 就没有任何跨轮记忆可言；
2. **L1 必须是视图而不是第二份存储**：旧架构把"热窗口"和"冷档案"混在
   一张 `short_term_messages` 表里，两种职责对写入的要求互相冲突，付出过
   双写 bug（自动路由消息入库两次）与覆盖缺口（bot 大部分出站不入库）
   的学费。修复方向不是"拆成两张表"（那会引入双写一致性的同类病），
   而是**一个真相 + 两种视图**：写入只写一遍（每类事件恰好一个写入者），
   读取口径各自演化。v10 把 reset 标记语义换成纯投影过滤、零迁移成本
   完成，就是这份红利的直接兑现；
3. **process 不跨轮投影（v7）**：QQ 闲聊场景里，上一轮的工具过程对下一轮
   没有延续价值——用户真正需要 bot 记得的是"说过什么、答过什么"，成品
   回复已是当轮信息的蒸馏，细节缺失重查一次工具即可。跨轮保留反而带来
   两个实害：中断轮的孤儿配对会让 DeepSeek 直接 400（协议硬校验），以及
   几十 KB 的过程废料常驻窗口挤占预算。编码型 agent 的工具结果（文件
   内容、grep 输出）是工作材料本身、必须跨轮——**场景不同，取舍不同**；
4. **压缩是纯过滤而非标记行（v10）**：标记行方案（reset）把"截断到哪"
   持久化进流里——历史被永久丢弃，且规则一改就不可恢复。纯过滤让截断点
   成为每次装配的现算值：库永远全量、规则可逆可调可实验，语义简单一个
   数量级。代价是截断点前的缓存前缀作废（缓存不友好方向），但都是低频
   事件，接受。

## 7. 未来规划：长期记忆注入（M4 插槽）

L1/L2 覆盖的是"会话窗口内"的记忆。跨会话的用户画像、事实、偏好（"我对
花生过敏""这个群爱聊足球"）是第三种记忆——**长期记忆**，既不该塞进 L1
的滚动窗口（每次装配都要重新挑选），也不止是 L2 的被动回查（该常驻而非
等模型想起去查）。规划方向：**skill 式 system 注入**（提示词 v2 方案为
其预留的 M4 插槽）：

- **注入位置**：system 尾部（M3 之后）——M1~M3 的公共前缀字节不受影响，
  记忆更新只付该租户一次前缀 miss；
- **更新频率**：低频（用户显式记忆/遗忘时），人格级频率而非逐轮变化
  （逐轮变化的内容入 system 是缓存家族的红线）；
- **体积上限**：设预算，超限走压缩/裁剪而非直注（防 system 无界膨胀）；
- **素材源**：L2（转录层是天然的事实矿）+ 显式记忆操作；
- **实现另立方案**，本文件只锁定位置与纪律。
