# 租户 Python 工作台设计方案：子 Agent + 短生命周期容器，每群/每人一个持久 workspace

> 状态：设计定稿（未实现）
> 起因：想给每个租户（群聊/单聊）开一个 workspace，让 Agent 在里面写 Python、运行简单的命令和代码。服务器只有 2G 内存，担心撑不起 Python，且担心代码执行带来安全隐患。
> 日期：2026-10-10（调研与方案讨论凝结；文中行号以当日代码为准）
>
> 讨论中逐步收敛的关键结论：
> 1. Python 解释器本身不是 2G 内存的主要威胁，真正的压力点是**并发任务数、Chromium、以及代码能触达的文件与网络**；
> 2. 执行环境用 **Docker 任务级容器**（一次 /代码 任务创建一次、销毁一次，loop 多轮命令经 `docker exec` 共用同一容器），而不是给 Node 子进程设个 cwd；
> 3. Python 库白名单（numpy/pandas 可，torch/爬虫库不可）**用镜像内容实现**，不做安装拦截——`--network=none` 下 pip 天然失效；
> 4. 不给日常 Agent 加 workspace 工具，而是做一个**子 Agent**（独立命令入口 + 独立图 + 独立工具表），只有它能操作 workspace；
> 5. workspace 路径**由服务端从 ctx.event 推导**，模型唯一能决定的是 bash 命令字符串；
> 6. 镜像在 GitHub Actions 构建、经 GHCR 分发、服务器只 `docker pull`，2G 机器不干 build 重活。

---

## 0. 一句话方案

```text
/代码 <任务描述>
  → 子 Agent（宿主机 Node 进程内的独立 LangGraph 图）
      任务开始：docker run -d [全套资源与安全限制] -v 本租户workspace:/workspace 白名单镜像 sleep <任务预算秒数>
               └ 容器与任务同生命周期；主进程 sleep = 自毁定时器（无人回收也最多吊到预算上限）
      循环{ 调云端 LLM → 得到一条 bash 命令或一次写文件 → 执行 → 结果回流 }
          → 执行命令 = docker exec <容器> timeout 60 bash -lc '<命令>'（超时由容器内 timeout 自杀）
          → 写文件 = Node fs 直写 workspace（不经容器）
      任务结束/中止/预算耗尽：docker kill + 确认退出 → 容器销毁
      文件留在宿主机 workspace 目录，跨轮次/跨任务持久；容器内状态（cd/临时文件）任务内连续、任务结束即焚
  → 整理最终回复 → 发回 QQ
```

## 1. 背景调研结论

### 1.1 与本方案相关的项目现状

| 事实 | 位置 | 对本方案的意义 |
|---|---|---|
| 单进程 TS，QQ Webhook → 分发 → 命令/Agent，模型走云 API | `src/webhook.ts`、`src/registry.ts` | 执行器只是给 Node 加 `spawn("docker", ...)`，无新常驻服务 |
| 深度检索已是"独立命令 + 独立图 + 独立工具表"的先例 | `src/services/deep-search.ts:1-20`、`src/agent/deep-search.ts`、`src/agent/deep-search/registry.ts` | 子 Agent 不是新范式，照抄深检的组织方式 |
| 三种会话键语义分离是代码库惯例（sessionKey 人粒度 / conversationKey 群粒度 / memoryKey） | `src/session/key.ts:14-34` | workspaceKey 作为第四种独立 key 加入，群一群一个、单聊一人一个 |
| Agent 工具参数注入机制已存在（schema 隐藏 + 分发时无条件覆盖） | `src/agent/tools/arg-injectors.ts`、`src/agent/registry.ts:27,64` | 身份字段不信任模型的机制有先例；本方案更进一步——workspace 干脆不做成参数，工具内从 ctx 推导 |
| 日常 Agent `MAX_TOOL_TURNS = 2`，工具并发 `Promise.all` | `src/agent/loop.ts:48`、`src/agent/loop.ts:265-278` | 写代码任务典型要 4-6 轮"写→跑→看报错→改→再跑"，日常 Agent 装不下 → 独立图的又一理由 |
| /stop 流程锁：abort 后立即删条目，异步生效 | `src/session/interrupt.ts:31-35` | 容器执行不能沿用"先解锁后回收"，必须杀完容器才放行下一个任务 |
| 部署：push main → Actions 类型检查 → SSH 到 `~/workspace/qqbot` → npm install → pm2 | `.github/workflows/deploy.yml` | 镜像构建 job 挂进同一条流水线；注意 `~/workspace/qqbot` 是部署目录，别与租户 workspace 混淆 |
| 日志全量落盘（模型输入输出、工具参数与结果全文） | `src/services/model.ts:114-125`、`src/agent/registry.ts:75` | 执行类工具需要摘要日志策略，避免代码/stdout 全文进日志 |

### 1.2 现有隔离边界与先修缺口

现有租户隔离是**应用层键隔离**（数据库/内存按 key 分桶），不是进程、目录、用户级隔离。项目目前没有用户 workspace、shell 执行、代码运行能力。与本方案直接相关、建议先修的问题：

1. **图片 ID 跨租户引用（IDOR）**：`src/agent/memory/images.ts:187-205` 按 `[图片:<id>]` 查库只有 `WHERE id = ?`，无租户过滤。用户可构造他人图片 ID，使其描述进入自己的对话。未来 workspace 的文件引用必须做租户归属校验，这个现有洞先补上。
2. **无全局长流程并发配额**：不同用户可同时跑 Agent/深检；工具调用还是 `Promise.all` 并发。2G 机器上叠加 Chromium 后，多任务并发是 OOM 主因。
3. **浏览器跨请求共享 + 动态浏览无 SSRF 守卫**：page 是模块级单例（`src/services/browse/browser.ts:25-43`）；`interact_page` 的 `page.goto` 未复用静态抓取的私网校验（`src/agent/tools/interact-page.ts:102-108`）。workspace 容器禁网后风险不互通，但整体面值得后续收。

### 1.3 2G 内存的资源账

- **Python 本体**：解释器空闲占用很小；`venv` 是包目录隔离不是虚拟机，也不常驻内存。装 Python、建 venv 都不是瓶颈。
- **真正的内存竞争者**：Node 主进程 + Playwright/Chromium + 并发云请求 + 未来并发的容器 + 可能残留的子进程。
- **容器资源**（单任务）：`--memory=256m` 已足够 numpy/pandas 级分析（`import pandas` 约 100-150MB）。
- **磁盘**（非内存）：镜像约 300-400MB（python:3.12-slim ~150MB + 库），全局只存一份；每 workspace 是普通目录（配额 50-100MB）。
- **Docker daemon 常驻**：数十到一百多 MB。若这笔账心疼，备选 podman（无 daemon），但第一版先用服务器上已装好的那个。

结论：**2G 可以做，但只能按"低并发实验环境"定位**——全局同时 1 个执行任务起步，实测后再调。

## 2. 核心决策（含理由与已否决项）

### 决策一：子 Agent 独立入口，不给日常 Agent 加工具

`/代码` 作为与 `/Agent`、`/深度检索` 平行的命令入口，拥有自己的图、工具表、轮次与预算。

| 收益 | 说明 |
|---|---|
| 工具面隔离 | 日常 Agent 的工具表里完全没有 read/write/bash，群聊历史/网页/图片 OCR 里的注入指令无法让它碰 workspace。攻击面从"所有 Agent 工具"缩到"用户显式发起 /代码 时才存在" |
| 绕开轮次硬伤 | `MAX_TOOL_TURNS=2` 装不下写代码循环；子 Agent 自定 6-8 轮、总预算分钟级 |
| 串行与锁好做 | 入口唯一，"全局同时 1 个"、"每 workspace 同时 1 个"都挂在这一个入口，不用改日常 Agent 的并发逻辑 |
| 权限模型干净 | 群主开关、定时任务默认拒绝等策略只作用于此入口 |

限定：**子 Agent 是架构选择不是安全边界**——真正拦恶意代码的是容器；且任务描述仍是不可信输入，但爆炸半径已被限制在"本租户 workspace + 容器配额"内。

### 决策二：Docker 任务级容器——一次 /代码 任务创建一次、销毁一次

**形态**：任务开始时 `docker run -d` 启动容器（主进程 `sleep <任务预算秒数>`），loop 多轮命令经 `docker exec` 发进同一容器执行；任务结束/中止/预算耗尽时 `docker kill` 销毁。任务的连续性有两层：**文件层靠 workspace 目录**（跨任务持久），**会话层靠容器**（cd/环境变量/临时文件任务内连续、任务结束即焚）。

**采纳理由**：

1. 启动开销只付一次：每任务 5-15 条命令，省 5-15 秒的累计容器创建；
2. 命令间状态连续（cd、export、上一条的临时文件对下一条可见），更接近"真人坐在终端前写代码"的工作流，对写→跑→改循环体验正向——每命令一容器模式下模型必须每条命令写全路径，偶尔会忘；
3. `--memory=256m` 变成"整个任务的预算池"而非"单条命令的预算池"，语义更贴切，pandas 大对象可跨命令存活。

**最初否决过它，后来发现顾虑在本项目条件下都有解**（记录取舍过程备查）：

| 当时的顾虑 | 解法 |
|---|---|
| 忘了杀就泄漏一个吃内存的容器 | ① 主进程用 `sleep <任务预算>` 代替业务进程——**自毁定时器**，就算 bot 崩了没人来杀，容器最多吊到预算上限自然死亡；② 容器名带 runId（`qqbot-exec-<runId>`），bot 启动时 prune 该前缀的孤儿——全局并发 1 保证这些一定是死任务遗留 |
| docker exec 没有单独的 kill API，每命令超时强杀难 | 容器内自杀：每条命令统一包 `timeout 60 bash -lc '<命令>'`，超时由容器内的 timeout 掐；宿主侧只需处理整个任务的 abort（kill 整个容器，反而更简单） |
| 状态残留（后台进程、环境变量跨命令） | 禁网 + 白名单镜像 + pids-limit 下，残留出不了安全边界；任务内残留恰是收益 2；任务结束容器销毁，残留不跨任务 |

**剩余的已接受缺点**：任务中途 bot 部署重启（pm2 restart 是现有部署流程一部分）会中断 run，容器靠自毁定时器兜底——执行中遇部署是小概率事件，可接受；吊着的容器持续占 256m 的**额度**（非实际内存，空 sleep 几乎不占），全局并发 1 下无所谓。

**其他已否决的备选**：
- *Node 直接 spawn python + cwd*：同用户环境继承，`.env` 凭证、数据库、其他租户目录全可达，不可接受。
- *命令级白名单/黑名单解析*：bash 语法千变万化必漏；边界在容器，不在命令解析。
- *每命令一容器（`docker run --rm`）*：零残留最彻底，但白付每条 0.5-1s 的启动开销且无会话连续性——若任务级容器在实践中暴露问题，可退回此模式（对模型无感）。

### 决策三：库白名单 = 镜像内容，配 `--network=none`

- 不做 pip 安装拦截：禁网后 `pip install`/`apt install` 天然失败，无绕法（改名包、纯手写 `urllib` 爬虫也被禁网堵死——只禁爬虫库是堵不住 stdlib 的）。
- 镜像里有什么就只有什么：第一版 = python:3.12-slim + numpy + pandas + matplotlib。
- 清醒认识：**库白名单不是安全边界**（numpy 一样能死循环/fork），它定位的是"资源预算 + 数据分析工作台的功能边界"；兜底的仍是容器限额。

### 决策四：workspace 由服务端推导，模型只产出命令

- `exec` 工具暴露给模型的 schema 只有一个 `command` 字段。
- workspace 路径在工具 `run(args, ctx)` 内部从 `ctx.event` 推导（字段不存在就不存在"被模型填"的问题）；另照 kb_search 模式注册一条 arg-injector 作为文档化声明（对原生工具是双保险）。
- 镜像名、资源限额、网络开关等根本不是参数，是执行器内的固定常量。

| 参数 | 谁决定 | 模型可触达 |
|---|---|---|
| `command`（bash 命令字符串） | 模型 | ✅ 唯一自由度 |
| workspace 目录 | 服务端从 ctx.event 推导 | ❌ |
| 镜像/内存/CPU/PID/网络/用户 | 执行器常量 | ❌ 模型不知道它们存在 |

### 决策五：镜像 Actions 构建、GHCR 分发、服务器只 pull

- build 是重活（拉基础镜像、pip 装包、叠层，内存/磁盘峰值高），交给 Actions 的免费临时机（用完即扔）；产物必须有个中转仓库 → GHCR（复用 GitHub 账号与 Actions 自带 `GITHUB_TOKEN`，私有配额对"一台服务器偶尔拉几次"绰绰有余；镜像不含任何秘密，设 public 亦可）。
- 服务器只做 `docker pull`（轻活：下载压缩层 + 解压，有分层缓存只传变化层）。
- 已否决：服务器现场 build（2G 撞 OOM）；`docker save`+scp 搬 tar（无版本无回滚）。
- **国内连通性**：2026-10-10 本机实测 ghcr.io 可达（`/v2/` 401=正常未认证响应 1.7s；token 接口 200 0.97s；对照 Docker Hub 超时=被墙）。**服务器侧连通性待测**（pull 由服务器发起，服务器结论才算数）：
  ```bash
  curl -4 -sS -o /dev/null --connect-timeout 8 --max-time 25 \
    -w 'ghcr /v2/: HTTP %{http_code}, 总耗时 %{time_total}s\n' https://ghcr.io/v2/
  timeout 60 docker pull ghcr.io/stargz-containers/alpine:latest && echo 拉取成功
  ```
  不通的退路：阿里云 ACR 个人版（免费、国内节点、Actions 可 push），架构不变只换中转站。
- tag 策略：`latest` 供服务器追踪 + 日期/短 SHA 不可变 tag 供精确回滚（镜像行为变更跑崩脚本时，改 pull 旧 tag 即回滚）。

## 3. 运行时设计

### 3.1 一次任务的完整生命周期

```text
用户: /代码 分析这份成绩数据的分布
  ↓
宿主机 Node（qq-bot 进程）
  ├─ /代码 service 壳：参数校验、功能开关、并发闸（全局 1 + 本 workspace 1）
  ├─ 订阅进度 bus（复用 progress-bus）→ 中途推送"正在写脚本/第 2 轮修改…"
  ├─ 任务开始：docker run -d --name qqbot-exec-<runId> [全套限制] <镜像> sleep 300
  │            └ sleep = 自毁定时器；容器与本任务同生命周期，多轮共用
  └─ 子 Agent 图循环（6-8 轮，总预算分钟级）：
       轮 1  LLM → write_file(main.py)      [Node fs 直写 workspace，路径校验]
       轮 2  LLM → exec("python main.py")   [docker exec 容器 → stderr 回流]
       轮 3  LLM → write_file(main.py)      [改文件；容器还在，cd/环境保持]
       轮 4  LLM → exec("python main.py")   [同一容器 → 成功，输出分析结果]
  ↓
docker kill qqbot-exec-<runId> + 确认退出（容器销毁；workspace 文件留存）
  ↓
整理最终回复（消息级截断）→ 发回 QQ → 释放并发闸
```

### 3.2 workspace 身份与目录布局

- 新增第四种会话键 `workspaceKey(event)`（放 `src/session/key.ts`，遵循"key 语义分离"惯例）：群聊 `group:<group_openid>` 一群一个共享；单聊 `c2c:<user_openid>` 一人一个。
- 目录名**不使用**原始 openid 拼接，用 `sha256(workspaceKey)` 十六进制前 32 字符：
  ```text
  /var/lib/qqbot-workspaces/     ← 独立根目录，绝不放进 ~/workspace/qqbot（部署目录）或 data/（含跨租户库）
    ├── a3f0…/  (群甲)
    │     ├── main.py
    │     └── data.csv
    └── 9c2b…/  (用户乙)
  ```
- 目录惰性创建（首次执行时 mkdir）；保留映射表（key hash ↔ 最近活跃时间 ↔ 显示名）供后续 /工作台 files 与清理策略使用。
- 群内 A、B 共享同一目录 → 写冲突由"每 workspace 同时 1 个任务"的闸解决；每次执行的发起人记入审计摘要。

### 3.3 子 Agent 图结构（`src/agent/code-workspace.ts`）

照深检骨架裁剪：`prepareContext → llmCall → tools → llmCall → … → finalize`，要点：

- **独立工具表**（`src/agent/code-workspace/registry.ts`）：只有 `write_file`、`exec`，不进全局注册表——这就是工具面隔离的落点。
- 轮次上限 6-8（可配），**总墙钟预算**（默认 5 分钟，节点边界检查 + 工具级硬超时双保险）。
- 工具**串行**执行（本图内不 `Promise.all`）：写→跑的顺序依赖天然成立。
- AbortSignal 贯穿：图的每个节点入口检查；`exec` 收到 signal 即 `docker kill` **任务容器**并等待容器退出后才 resolve——**杀完才解锁**，修正 interrupt.ts "先删条目异步生效"的时序（不复用/stop 旧语义，新闸自管生命周期，但仍登记进 controlledFlow 让 /stop 可触发 abort）。
- 上下文精简：不带聊天记忆/长期记忆（任务描述 + 本任务内的工具轨迹足够），降低注入面与 token 成本。

### 3.4 工具一：`write_file`（Node fs 直写，不经容器）

写文件用容器跑 heredoc 引号地狱多、且无必要——直接 Node 写：

```ts
// 参数 schema（模型可见的全部）：
//   { path: string; content: string }
// 服务端强制：
//   - path 必须相对、禁 ".."、禁绝对路径、禁 NUL、无符号链接段
//   - realpath 解析后必须仍在 workspace 根内（前缀比较基于 realpath，非字符串拼接）
//   - 单文件 ≤ 1MB；workspace 文件数/总容量配额（见 3.6）
//   - 原子写：临时文件 + rename
//   - 拒绝写入已存在的符号链接（防链接逃逸：先 lstat）
```

### 3.5 工具二：`exec`（执行器与容器参数全集）

**任务容器创建**（任务开始时一次）：

```bash
docker run -d \
  --name qqbot-exec-<runId> \
  --network=none \                # 禁网：pip/爬虫/内网探测/外传全部失效
  --memory=256m --memory-swap=256m \   # 硬内存上限=整个任务的预算池，无 swap 余地
  --cpus=1 \                      # CPU 上限（非预留）
  --pids-limit=64 \               # fork 炸弹兜底（含 exec 进来的进程）
  --user 1000:1000 \              # 非 root
  --read-only \                   # rootfs 只读
  --tmpfs /tmp:rw,size=16m,noexec \    # 唯一可写区（noexec 防落地再执行）
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --log-driver=none \             # 不落盘 Docker json 日志（宿主侧流式收集已是主通道，避免双写）
  -v /var/lib/qqbot-workspaces/<hash>:/workspace \   # 唯一挂载：本租户目录
  -w /workspace \
  ghcr.io/<user>/qqbot-python:<tag> \
  sleep <任务预算秒数>            # 主进程=自毁定时器：无人回收也最多吊到预算上限自然死亡
```

**每条命令执行**（loop 各轮）：

```bash
docker exec qqbot-exec-<runId> timeout <单命令超时> bash -lc '<模型给的命令>'
```

Node 侧要点（`src/services/workspace/executor.ts`）：

- 全部 `spawn("docker", [argv 数组])`，**不经宿主 shell**（命令字符串是容器内 bash 的输入，不是宿主的）。
- 容器 env 天然干净：`docker run` 默认不透传宿主环境变量（Node 的 env 只到 docker CLI，不进容器），只要不传 `-e/--env-file`——bot 的 `.env` 凭证与容器无关。`stdin` 关闭，不分配 tty（输出纯管道）。
- 流式收集每次 exec 的 stdout/stderr，**各截断 64KB** 并置截断标记（不是先攒完再切）；返回 `{ exitCode, stdout, stderr(truncated), durationMs }`。
- **两级超时**：单命令级由容器内 `timeout` 自杀（docker exec 无单独 kill API，这是标准解法）；任务级由图层预算检查触发 `docker kill qqbot-exec-<runId>`。
- 任务结束路径（正常完成 / abort / 预算耗尽）统一：`docker kill` → **等待容器退出确认** → 才向 scheduler 报告完成、释放闸。
- **孤儿兜底**：bot 启动时 `docker rm -f` 所有 `qqbot-exec-` 前缀容器（全局并发 1 保证在跑任务不可能是合法的——若启动时确有任务在跑，它随旧进程一起死了， prune 是正确语义）。
- 每次任务开始前置检查：workspace 磁盘配额（目录递归统计）、docker 可用性（daemon 存活、镜像在位）；失败直接拒绝任务并给用户可理解的提示。

### 3.6 并发与配额总表（首版默认值，全部进配置）

| 维度 | 默认 | 说明 |
|---|---|---|
| 全局同时执行任务数 | 1 | 2G 起步值；实测 Node+Chromium 余量后调整 |
| 每 workspace 同时任务数 | 1 | 群内 A/B 互斥；不排队，直接拒绝提示稍后再试（短队列是阶段 2 选项） |
| 单容器内存 | 256m（swap 同值=禁 swap） | 任务级预算池（容器与任务同生命周期）；pandas 级分析够用 |
| 单容器 CPU | 1 核 | 上限非预留 |
| 单容器 PID | 64 | fork 炸弹兜底（覆盖 exec 进来的所有进程） |
| 单命令墙钟 | 60s | 容器内 `timeout` 自杀（docker exec 无单独 kill API） |
| 任务容器自毁上限 | = 任务预算（sleep 秒数） | 无人回收时兜底，不超预算上限 |
| 单任务轮次 / 总预算 | 8 轮 / 5 分钟 | 图层控制 |
| stdout+stderr | 各 64KB 截断 | 容器级；QQ 回复另有消息级截断 |
| 单文件 / workspace 总量 | 1MB / 100MB | write_file 与 exec 前置检查 |
| workspace 文件数 | 200 | 同上 |

磁盘配额说明：`--memory` 管不了磁盘，需 Node 侧在启动容器前统计目录（或维护增量计数），超额拒绝执行——内存限制解决不了磁盘被写满的问题。

## 4. 安全边界总结

**允许**：workspace 内读写自己的文件；跑白名单镜像里的 Python/标准工具；受控 bash 命令（ls/cat/python 等，无命令白名单——边界在容器）。

**禁止（由容器与执行器硬性保证，非提示词）**：

| 威胁 | 防线 |
|---|---|
| 读 bot 凭证（.env/API key） | 容器默认不继承宿主 env；不挂载 bot 目录/宿主根 |
| 跨租户读写 | 唯一挂载是本租户目录；路径校验 realpath 前缀 |
| 联网（外传/内网/云 metadata/爬虫） | `--network=none` |
| 装包（pip/apt/torch） | 禁网 + 镜像内容即白名单 |
| fork 炸弹 / 死循环 | `--pids-limit=64` + 单命令 timeout + 任务预算强杀 + CPU 上限 |
| 内存耗尽拖垮宿主 | `--memory=256m` + 全局并发 1 + 自毁定时器兜底 |
| 写系统文件/留后门 | `--read-only` + 任务结束容器销毁 + tmpfs noexec |
| 提权 | `--user 1000:1000` + `--cap-drop=ALL` + `no-new-privileges` |
| 写满磁盘 | Node 侧配额前置检查 |
| 输出洪泛 | 流式 64KB 截断 + 消息级截断 |
| 注入指令让日常 Agent 越权 | 日常 Agent 无此类工具；只有显式 /代码 入口存在执行面 |
| /stop 或崩溃后容器泄漏/继续产生副作用 | abort → docker kill → 等待退出 → 才释放闸；主进程 sleep 自毁定时器 + bot 启动 prune 孤儿 |

**已知接受的残余风险**：容器逃逸类 0day（普通容器非绝对沙箱，面向不完全信任用户需 gVisor/microVM——阶段 3 选项）；同 workspace 群友互删文件（共享语义，靠群社交约束 + reset 确认）；提示注入影响子 Agent 在自己 workspace 内的行为（爆炸半径已限于配额内）。

## 6. 分阶段实现计划

### 阶段 0：先修与地基（不含 workspace 功能本身）

1. 修复 `images.ts` IDOR（查询加 key 过滤）；
2. 全局长流程并发上限（现有 Agent/深检就受益，2G 稳定性先改善）；

4. （可选）webhook body 大小上限。

验收：IDOR 用例（构造他人图片 ID 不再展开）；并发上限触发拒绝文案；服务器盘点结论记录进本文档附录。

### 阶段 1：最小可用（MVP）

范围：Dockerfile → Actions 构建分发 → executor → workspace 三个工具件（paths/scheduler/exec+write_file）→ 子 Agent 图 → `/代码` 命令 → 进度推送 → 摘要日志 → 配置项全套。

明确不做：pip/任意装包、网络、定时任务触发、命令白名单、磁盘清理、群管理命令、队列。

验收（负面测试清单，逐条通过才算完成）：
- 死循环 60s 被 `timeout` 自杀（exit code 124），下一条命令照常可执行；
- `os.fork()` 循环被 pids-limit 掐灭，宿主无恙；
- 打印洪泛只回 64KB 截断块，QQ 消息不超长；
- 写 200MB 大文件被配额拒绝且给出可理解的失败信息；
- `pip install requests` 失败（禁网）；`urllib` 请求超时（禁网）；
- 容器内 `cat /proc/1/environ`、读挂载外路径、`ls ../` 均不可达 bot 数据；
- A 群任务运行中 B 群发 /代码 收到"忙"拒绝；同群第二人同样拒绝；
- /stop 后 `docker ps` 无残留容器，workspace 无 stop 后新写入，闸已释放；
- 任务中途 kill bot 进程模拟崩溃 → 重启后启动 prune 清掉孤儿容器；
- 同一任务内两条命令间 cd/环境变量连续性成立（任务级容器行为验证）；
- 正向用例：贴一段成绩数据 → 子 Agent 写 pandas 脚本 → 首跑报错 → 自行修复 → 输出中位数/标准差，全程 ≤5 分钟、≤8 轮。

### 阶段 2：体验与治理

- `/工作台 status|files|enable|reset`（群主/管理员校验、reset 二次确认）；
- 磁盘配额增量计数与 LRU 清理策略（超 30 天不活跃的 workspace 提醒/归档）；
- 拒绝转短队列（全局等待位 1-2 个，带排队提示）；
- 执行指标：次数/时长/P95/失败率/资源峰值的摘要报表（/工作台 status 展示）；
- 审计完善（docker stats 采样、发起人记录）。

### 阶段 3（可选，按需启动）

- 更强隔离：gVisor（runsc runtime）替换默认 runtime——面向不完全信任用户群时的升级路径，executor 只换 runtime 参数；
- podman 替换 docker（省 daemon 常驻内存，参数几乎兼容）；
- 受控网络出口（如仅允许特定域名的代理）——复杂度高，除非有明确需求不做；
- 预装库扩编流程化（改 Dockerfile 走 PR 评审 + 镜像双 tag 回滚演练）；
- 独立执行机：executor 抽成远程服务（RPC/SSH），2G 主机彻底不跑代码——接口已在 executor 边界预留；
- 定时任务独立授权模型（预批准任务清单）。

## 8. 附录：讨论中已否决/搁置的选项（备查）

| 选项 | 否决原因 | 何时可重启 |
|---|---|---|
| Node spawn python + cwd | 同用户凭证/数据全可达，无隔离 | 永不 |
| venv 作为隔离手段 | 仅包隔离，非安全沙箱（官方文档口径） | 不适用（镜像内可用 venv 做包管理，但非安全边界） |
| pip 安装时黑/白名单拦截 | 黑名单永远漏；白名单可被改名/离线包绕过 | 已被"镜像内容+禁网"替代 |
| 命令级白名单解析 | bash 语法复杂必漏；容器已兜底 | 永不 |
| 每命令一容器（docker run --rm） | 每条命令 0.5-1s 启动开销；无会话连续性（cd/环境不保持） | 已被任务级容器替代（2026-10-11 讨论采纳后者）；任务级容器若实践暴露问题可退回，对模型无感 |
| 服务器现场 build | 内存/磁盘峰值撞 OOM | 服务器扩容后也不建议 |
| Docker Hub 托管 | 国内不通（本机实测超时） | 永不 |
| MCP 形态的 runner | 现有 MCP 客户端"失败自动重试一次"与非幂等执行冲突；需先做幂等 runId/取消 RPC | executor 服务化时一并考虑 |
| 给日常 Agent 加 read/write/bash 工具 | MAX_TOOL_TURNS=2 装不下；注入面暴露给所有日常输入 | 永不（子 Agent 已覆盖） |
