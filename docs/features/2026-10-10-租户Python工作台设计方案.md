# 租户 Python 工作台设计方案：子 Agent + 短生命周期容器，每群/每人一个持久 workspace

> 状态：设计定稿（未实现）
> 起因：想给每个租户（群聊/单聊）开一个 workspace，让 Agent 在里面写 Python、运行简单的命令和代码。服务器只有 2G 内存，担心撑不起 Python，且担心代码执行带来安全隐患。
> 日期：2026-10-10（调研与方案讨论凝结；文中行号以当日代码为准）；2026-10-11 执行模型改为任务级容器；2026-10-14 工具面扩为六件套并写死持久化语义
>
> 讨论中逐步收敛的关键结论：
> 1. Python 解释器本身不是 2G 内存的主要威胁，真正的压力点是**并发任务数、Chromium、以及代码能触达的文件与网络**；
> 2. 执行环境用 **Docker 任务级容器**（一次 /代码 任务创建一次、销毁一次，loop 多轮命令经 `docker exec` 共用同一容器），而不是给 Node 子进程设个 cwd；
> 3. Python 库白名单（numpy/pandas 可，torch/爬虫库不可）**用镜像内容实现**，不做安装拦截——`--network=none` 下 pip 天然失效；
> 4. 不给日常 Agent 加 workspace 工具，而是做一个**子 Agent**（独立命令入口 + 独立图 + 独立工具表），只有它能操作 workspace；
> 5. workspace 路径**由服务端从 ctx.event 推导**，模型能决定的只有工具参数本身（命令字符串/文件路径与内容），一切身份与边界由服务端强制；
> 6. 镜像在 GitHub Actions 构建、经 GHCR 分发、服务器只 `docker pull`，2G 机器不干 build 重活；
> 7. 工具面对标 Claude Code：read/write/edit/grep/glob/exec 六件套——文件五件套是 Node fs 薄封装（共用同一套路径校验），只有 exec 走容器，不新增安全面；
> 8. workspace 持久化是默认语义：任务结束只销毁容器，目录永不清空；"清空"只有显式 reset（LRU 清理默认关闭），磁盘兜底靠配额不靠清理；
> 9. 子 Agent 以**委派模式**并入主 Agent（workspace_task 工具，主模型填的 task 参数即规格书，状态完全隔离），/代码 降为兜底命令；两种入口收敛到同一服务函数，仅闸获取方式不同（继承父 signal vs 自己登记）。

## 0. 一句话方案

```text
/代码 <任务描述>
  → 子 Agent（宿主机 Node 进程内的独立 LangGraph 图）
      任务开始：docker run -d [全套资源与安全限制] -v 本租户workspace:/workspace 白名单镜像 sleep <任务预算秒数>
               └ 容器与任务同生命周期；主进程 sleep = 自毁定时器（无人回收也最多吊到预算上限）
      循环{ 调云端 LLM → 得到一次工具调用（read/write/edit/grep/glob/exec）→ 执行 → 结果回流 }
          → 文件五件套（read/write/edit/grep/glob）= Node fs 直读直写 workspace（不经容器，统一路径校验）
          → exec = docker exec <容器> timeout 60 bash -lc '<命令>'（超时由容器内 timeout 自杀）
      任务结束/中止/预算耗尽：docker kill + 确认退出 → 容器销毁
      文件留在宿主机 workspace 目录，跨轮次/跨任务持久；容器内状态（cd/临时文件）任务内连续、任务结束即焚
  → 整理最终回复 → 发回 QQ
```

## 1. 背景调研结论

### 1.1 与本方案相关的项目现状

| 事实 | 位置 | 对本方案的意义 |
|---|---|---|
| 单进程 TS，QQ Webhook → 分发 → 命令/Agent，模型走云 API | `src/webhook.ts`、`src/registry.ts` | 执行器只是给 Node 加 `spawn("docker", ...)`，无新常驻服务 |
| 深度检索已是"独立命令 + 独立图 + 独立工具表"的先例 | `src/services/deep-search.ts:1-20`、`src/agent/deep-search.ts`、`src/agent/deep-search/registry.ts` | 子 Agent 不是新范式，照抄深检的组织方式 |
| ~~三种会话键语义分离~~ **已统一为单一 tenantKey（2026-10-14）**：原 sessionKey（人粒度）/conversationKey/memoryKey/kbScope 四种收敛为 `src/session/key.ts` 的 `tenantKey()`（群一群/单聊一人，群粒度语义：同群同时一个长流程、任何群员可 /stop 本群任务）；workspace 直接复用 | `src/session/key.ts` | 工作台目录 = `sha256(tenantKey(event))`，不再需要独立的 workspaceKey |
| Agent 工具参数注入机制已存在（schema 隐藏 + 分发时无条件覆盖） | `src/agent/tools/arg-injectors.ts`、`src/agent/registry.ts:27,64` | 身份字段不信任模型的机制有先例；本方案更进一步——workspace 干脆不做成参数，工具内从 ctx 推导 |
| 日常 Agent `MAX_TOOL_TURNS = 2`，工具并发 `Promise.all` | `src/agent/loop.ts:48`、`src/agent/loop.ts:265-278` | 写代码任务典型要 4-6 轮"写→跑→看报错→改→再跑"，日常 Agent 装不下 → 独立图的又一理由 |
| /stop 流程锁：abort 后立即删条目，异步生效 | `src/session/interrupt.ts:31-35` | 容器执行不能沿用"先解锁后回收"，必须杀完容器才放行下一个任务 |
| 部署：push main → Actions 类型检查 → SSH 到 `~/workspace/qqbot` → npm install → pm2 | `.github/workflows/deploy.yml` | 镜像构建 job 挂进同一条流水线；注意 `~/workspace/qqbot` 是部署目录，别与租户 workspace 混淆 |
| 日志全量落盘（模型输入输出、工具参数与结果全文） | `src/services/model.ts:114-125`、`src/agent/registry.ts:75` | 执行类工具需要摘要日志策略，避免代码/stdout 全文进日志 |

### 1.2 现有隔离边界与先修缺口

现有租户隔离是**应用层键隔离**（数据库/内存按 key 分桶），不是进程、目录、用户级隔离。项目目前没有用户 workspace、shell 执行、代码运行能力。与本方案直接相关、建议先修的问题：

1. **图片 ID 跨租户引用（IDOR）**：`src/agent/memory/images.ts:187-205` 按 `[图片:<id>]` 查库只有 `WHERE id = ?`，无租户过滤。用户可构造他人图片 ID，使其描述进入自己的对话。未来 workspace 的文件引用必须做租户归属校验，这个现有洞先补上。
2. **无全局长流程并发配额**：不同用户可同时跑 Agent/深检；工具调用还是 `Promise.all` 并发。2G 机器上叠加 Chromium 后，多任务并发是 OOM 主因。
3. **浏览器跨请求共享 + 动态浏览无 SSRF 守卫**：page 是模块级单例（`src/services/browse/browser.ts:25-43`）；`interact_page` 的 `page.goto` 未复用静态抓取的私网校验（`src/agent/tools/interact-page.ts:102-108`）。workspace 容器禁网后风险不互通，但整体面值得后续收。

### 1.3 2G 内存的资源账

- **Python 本体**：解释器空闲占用很小；`venv` 是包目录隔离不是虚拟机，也不常驻内存。装 Python、建 venv 都不是瓶颈。
- **真正的内存竞争者**：Node 主进程 + Playwright/Chromium + 并发云请求 + 未来并发的容器 + 可能残留的子进程。
- **容器资源**（单任务）：`--memory=256m` 已足够 numpy/pandas 级分析（`import pandas` 约 100-150MB）。
- **磁盘**（非内存）：镜像约 300-400MB（python:3.12-slim ~150MB + 库），全局只存一份；每 workspace 是普通目录（配额 50-100MB）。
- **Docker daemon 常驻**：数十到一百多 MB。若这笔账心疼，备选 podman（无 daemon），但第一版先用服务器上已装好的那个。

结论：**2G 可以做，但只能按"低并发实验环境"定位**——全局同时 1 个执行任务起步，实测后再调。

## 2. 核心决策（含理由与已否决项）

### 决策一：独立子 Agent（自己的图、工具表、轮次与预算），主 Agent 以委派模式触达（2026-10-15 修订）

初版设计为 `/代码` 独立命令入口；决策八将其演进为**委派为主、命令兜底**——但"独立子 Agent"这个核心不变：子 Agent 拥有自己的图、工具表、轮次与预算，日常主 Agent 的工具表里没有 read/write/bash，只有一个"委派"动作（workspace_task）。

| 收益 | 说明 |
|---|---|
| 工具面隔离 | 日常 Agent 的工具表里没有 read/write/bash——注入指令最多诱导它**委派一个任务**（在受限容器里跑），无法直接碰 workspace 文件；真正的执行工具只存在于子图中 |
| 绕开轮次硬伤 | `MAX_TOOL_TURNS=2` 装不下写代码循环；子 Agent 自定 10-12 轮、总预算分钟级 |
| 串行与锁好做 | 全局执行闸 + 双模式租户闸（决策七/八）挂在工作台服务层，不用改日常 Agent 的并发逻辑 |
| 权限模型干净 | 群主开关、（将来的）定时任务策略只作用于工作台服务这一个点 |

限定：**子 Agent 是架构选择不是安全边界**——真正拦恶意代码的是容器；且任务描述仍是不可信输入，但爆炸半径已被限制在"本租户 workspace + 容器配额"内。

### 决策二：Docker 任务级容器——一次 /代码 任务创建一次、销毁一次

**形态**：任务开始时 `docker run -d` 启动容器（主进程 `sleep <任务预算秒数>`），loop 多轮命令经 `docker exec` 发进同一容器执行；任务结束/中止/预算耗尽时 `docker kill` 销毁。任务的连续性有两层：**文件层靠 workspace 目录**（跨任务持久），**会话层靠容器**（cd/环境变量/临时文件任务内连续、任务结束即焚）。

**采纳理由**：

1. 启动开销只付一次：每任务 5-15 条命令，省 5-15 秒的累计容器创建；
2. 命令间状态连续（cd、export、上一条的临时文件对下一条可见），更接近"真人坐在终端前写代码"的工作流，对写→跑→改循环体验正向——每命令一容器模式下模型必须每条命令写全路径，偶尔会忘；
3. `--memory=256m` 变成"整个任务的预算池"而非"单条命令的预算池"，语义更贴切，pandas 大对象可跨命令存活。

**最初否决过它，后来发现顾虑在本项目条件下都有解**（记录取舍过程备查）：

| 当时的顾虑 | 解法 |
|---|---|
| 忘了杀就泄漏一个吃内存的容器 | ① 主进程用 `sleep <任务预算>` 代替业务进程——**自毁定时器**，就算 bot 崩了没人来杀，容器最多吊到预算上限自然死亡；② 容器名带 runId（`qqbot-exec-<runId>`），bot 启动时 prune 该前缀的孤儿——全局并发 1 保证这些一定是死任务遗留 |
| docker exec 没有单独的 kill API，每命令超时强杀难 | 容器内自杀：每条命令统一包 `timeout 60 bash -lc '<命令>'`，超时由容器内的 timeout 掐；宿主侧只需处理整个任务的 abort（kill 整个容器，反而更简单） |
| 状态残留（后台进程、环境变量跨命令） | 禁网 + 白名单镜像 + pids-limit 下，残留出不了安全边界；任务内残留恰是收益 2；任务结束容器销毁，残留不跨任务 |

**剩余的已接受缺点**：任务中途 bot 部署重启（pm2 restart 是现有部署流程一部分）会中断 run，容器靠自毁定时器兜底——执行中遇部署是小概率事件，可接受；吊着的容器持续占 256m 的**额度**（非实际内存，空 sleep 几乎不占），全局并发 1 下无所谓。

**其他已否决的备选**：
- *Node 直接 spawn python + cwd*：同用户环境继承，`.env` 凭证、数据库、其他租户目录全可达，不可接受。
- *命令级白名单/黑名单解析*：bash 语法千变万化必漏；边界在容器，不在命令解析。
- *每命令一容器（`docker run --rm`）*：零残留最彻底，但白付每条 0.5-1s 的启动开销且无会话连续性——若任务级容器在实践中暴露问题，可退回此模式（对模型无感）。

### 决策三：库白名单 = 镜像内容，配 `--network=none`

- 不做 pip 安装拦截：禁网后 `pip install`/`apt install` 天然失败，无绕法（改名包、纯手写 `urllib` 爬虫也被禁网堵死——只禁爬虫库是堵不住 stdlib 的）。
- 镜像里有什么就只有什么：第一版 = python:3.12-slim + numpy + pandas + matplotlib。
- 清醒认识：**库白名单不是安全边界**（numpy 一样能死循环/fork），它定位的是"资源预算 + 数据分析工作台的功能边界"；兜底的仍是容器限额。

### 决策四：workspace 由服务端推导，模型只产出命令

- `exec` 工具暴露给模型的 schema 只有一个 `command` 字段。
- workspace 路径在工具 `run(args, ctx)` 内部从 `ctx.event` 推导（字段不存在就不存在"被模型填"的问题）；另照 kb_search 模式注册一条 arg-injector 作为文档化声明（对原生工具是双保险）。
- 镜像名、资源限额、网络开关等根本不是参数，是执行器内的固定常量。

| 参数 | 谁决定 | 模型可触达 |
|---|---|---|
| `command`（bash 命令字符串） | 模型 | ✅ 唯一自由度 |
| workspace 目录 | 服务端从 ctx.event 推导 | ❌ |
| 镜像/内存/CPU/PID/网络/用户 | 执行器常量 | ❌ 模型不知道它们存在 |

### 决策五：镜像 Actions 构建、GHCR 分发、服务器只 pull

- build 是重活（拉基础镜像、pip 装包、叠层，内存/磁盘峰值高），交给 Actions 的免费临时机（用完即扔）；产物必须有个中转仓库 → GHCR（复用 GitHub 账号与 Actions 自带 `GITHUB_TOKEN`，私有配额对"一台服务器偶尔拉几次"绰绰有余；镜像不含任何秘密，设 public 亦可）。
- 服务器只做 `docker pull`（轻活：下载压缩层 + 解压，有分层缓存只传变化层）。
- 已否决：服务器现场 build（2G 撞 OOM）；`docker save`+scp 搬 tar（无版本无回滚）。
- **国内连通性（已验证，2026-10-14）**：本机与服务器均实测可达。服务器：`/v2/` 401（总耗时 0.53s）、匿名 token 接口 200 发放真 token、`docker pull ghcr.io/kyverno/kyverno:latest` **端到端拉取成功**（manifest + blob CDN 层下载全通）。服务器 Docker 可用、cgroup v2 已确认。测试镜像选型备注：`stargz-containers/alpine` 已不存在（not found）、`fluent/fluentd` 在 GHCR 非公开（denied）——都是 registry 应用层正常响应，恰可证明链路通；跨过这两个坑后用 kyverno 完成验证。
- tag 策略：`latest` 供服务器追踪 + 日期/短 SHA 不可变 tag 供精确回滚（镜像行为变更跑崩脚本时，改 pull 旧 tag 即回滚）。

### 决策六：工具面对标 Claude Code 六件套；workspace 持久化是默认语义（2026-10-14 增补）

**工具集映射**：

| Claude Code | 本方案 | 实现路径 |
|---|---|---|
| Read | read_file | Node fs（行号、offset/limit、双上限截断） |
| Write | write_file | Node fs（原子写） |
| Edit | edit_file | Node fs（old/new 逐字节匹配 + 唯一性检查） |
| Grep | grep | Node fs（正则 + glob 过滤 + 匹配上限） |
| Glob | glob | Node fs（模式匹配 + 上限 + mtime 排序） |
| Bash | exec | 容器（见 3.5） |
| LS | 不单独做 | glob + `exec ls` 已覆盖 |

- **不新增安全面**：文件五件套全是 Node 对 workspace 目录的薄封装，走 paths.ts 同一套 realpath 前缀校验；安全边界仍然只有"容器 + 路径校验"两道，工具数量不改变边界。
- **实现无架构困难，难点在打磨**：上下文预算管理（read 的默认上限/截断标记/续读提示要写进工具描述——模型省不省上下文一半取决于此）；edit 精确匹配失败（返回匹配数 + 附近片段让模型下轮自纠）。每个工具约 100-150 行。
- **grep/glob 走 Node 不走容器**：输出格式完全可控、不依赖容器存活、与文件工具对称——容器只负责"跑代码"，文件操作全在 Node 侧。
- **命名贴主流惯例**（read_file/grep/glob、`file:line: content`）：吃强模型的训练先验，不自创命名。

**workspace 持久化语义**（写死，防实现时误加"任务后清理"）：

- 任务结束 `docker kill` 销毁的只是容器；workspace 目录跨任务/跨天持久，上次留下的脚本下次任务直接可见——"改一下上次那个脚本"天然成立。
- "清空"只有两条显式路径：`/工作台 reset`（用户主动 + 二次确认）；LRU 清理（阶段 2，**默认关闭**）。
- 磁盘安全的兜底是每 workspace 配额前置检查（§3.6），不依赖任何清理策略。

### 决策七：并发闸直接复用统一租户键的流程闸（2026-10-14 键统一红利）

键统一（全项目收敛为 `tenantKey`，群粒度）后，原设计"scheduler.ts 自管两层闸"简化为一层：

- **"每 workspace 同时 1 个任务"的闸被继承**：工作台任务经 `beginControlledFlow(tenantKey(event))` 登记进现有 /stop 注册表即得，键天然相同。附带**跨类型互斥**：同群有人跑 `/Agent`/`/深度检索` 时 `/代码` 被拒（反之亦然）——2G 上避免 Chromium 与执行容器同群叠加，是收益不是缺陷。
- **`/stop` 对工作台任务开箱即用**：同键拉闸 → AbortSignal 传导至 `exec` 工具 → `docker kill`（§3.3 已有此链路）；abort 发起人审计日志（stop.ts）同样覆盖。
- **interrupt.ts"abort 后先删条目"的时序漏洞被全局闸兜住**：/stop 后租户条目虽已删、新 /代码 能过租户闸，但全局执行闸（并发 1）在旧任务 docker kill + 容器退出确认前不释放——新任务仍被拒。**"杀完才放行"由全局闸保证，v1 无需改 interrupt.ts**。
- 已知代价（接受）：一个长 /代码 任务期间该群不能用 /Agent。注意：**将来全局并发放宽到 >1 时此兜底失效**，需给 interrupt.ts 加 aborting 状态（删条目延迟到 endControlledFlow）——记为阶段 2 前置条件。
- scheduler.ts 职责随之瘦身：仅全局执行信号量 + "docker kill 确认退出后才释放全局闸"的生命周期。

### 决策八：委派模式——workspace_task 作为主 Agent 工具，/代码 降为兜底命令（2026-10-15）

主 Agent 判断用户需要工作台时，自动编写任务规格书并委派给子 Agent（agent-as-tool / delegation 模式，同 Claude Code 的 Task 工具）：

- **提示词编写不需要额外 node**：主模型调用 `workspace_task` 工具时填写的 `task` 参数**就是**那份提示词——schema 描述明确要求"完整任务规格书：目标、数据位置、期望输出、背景约束；子执行者只看到这段文字，把任务需要的一切写进去"。模型填参数的过程天然完成上下文蒸馏（它看得见群聊历史/长期记忆，压缩进 task 字符串）。若实测 task 太简略，再在子图前加"任务补全"节点（阶段 2 升级项）。
- **状态隔离是结构性的**：子 Agent 的上下文 = 子系统提示 + task + 本任务工具轨迹，不含主 Agent 的历史/人格/其他工具轨迹——"完全只依靠详细需求规划行动"在 schema 层面成立。
- **基础设施复用**：ctx.event 相同 → tenantKey 相同 → 进度推送（progress-bus）自动把子任务的"正在编写脚本…"推给用户；全局执行闸照旧在容器启动前检查。
- **结果回流**：子 Agent 的最终报告作为 tool 结果回到主 Agent messages，第 2 轮收尾（finalize，套人设转述）。报告自带"关键结果块"，收尾提示词要求精确数字原样保留，防转述损耗。
- **`/代码` 保留为兜底命令**：模型漏路由时用户强制直达，调试时需要确定入口。两个入口共用同一个 `runWorkspaceTask` 服务。

**闸的两种获取方式**（唯一的双模式点，实现收敛为一个服务函数）：

```text
runWorkspaceTask(task, ctx, opts?: { signal?: AbortSignal })
  ├─ 委派模式（主 Agent 工具调用）：主流程已持闸（runAgentTurn 开头的
  │   beginControlledFlow）→ 子任务【不登记】（同 key 嵌套登记会返回 null
  │   把自己拒了——键统一后全项目单键，流程套流程必撞此语义），
  │   继承父 controller.signal 响应 /stop
  └─ 独立模式（/代码 命令）：自己 beginControlledFlow(tenantKey)（与
      /Agent、深检入口同款），finally 里 end——不走主 Agent 的 abort
两条路汇入同一个子图执行器；全局执行闸（并发 1）两种模式下统一生效
```

**主 Agent 轮次算术**（`MAX_TOOL_TURNS=2` 下）：第 1 轮或第 2 轮调 `workspace_task` 均可行——第 2 轮调时工具结果直接进 finalize 收尾（设计行为）；真正调不到的只有"两轮都被其他工具占满"（这种任务本不该走工作台）。用户计划将来扩展 loop 轮数规避此类问题；工具路由提示词（"数据分析/写代码任务直接调 workspace_task，不要绕路"）记为后续优化项，暂不加。

**cron 触达（2026-10-15 用户决策：暂不设防）**：workspace_task 进入主 Agent 工具表后，cron 定时任务（fake author，无真实发起者）理论上可触达代码执行。完整风险链（任务 prompt 可被群成员注入 + 深夜无人值守 + 最高破坏力）与正规解法（`source: "real" | "cron"` 标记 + 拒绝）已知——**测试环境优先验证功能，不加防线**；上线对外前必须补，已在阶段 1 验收清单外单列提醒。

**注入面扩大的接受论证**：委派模式下群聊历史/网页内容理论上可诱导**主 Agent** 调 workspace_task——但能被注入出的只有"在本租户 workspace 跑一个任务"（真正的 read/write/bash 在子图里，注入文本够不到），爆炸半径仍是"本租户 + 容器配额 + 无网"，最坏后果是白跑一个任务（LLM 费 + 一次容器执行），全局并发 1 与 5 分钟预算兜底。可选加固（阶段 2）：执行前把任务描述发回群里让用户确认。

## 3. 运行时设计

### 3.1 一次任务的完整生命周期

主路径是**委派模式**（决策八）：用户闲聊"帮我算算这组数的平均值"→ 主 Agent 识别出工作台需求 → 调 `workspace_task` 工具（task 参数 = 模型蒸馏的任务规格书）→ 子 Agent 常规 pipeline。`/代码 <描述>` 是兜底直通入口，跳过主 Agent 直达同一个服务。

```text
用户: 帮我算算这组数的平均值（或 /代码 分析成绩数据——兜底入口）
  ↓
主 Agent（runAgentTurn，已持流程闸 beginControlledFlow(tenantKey)）
  └─ llmCall 识别工作台需求 → workspace_task(task="...规格书...")
       │  委派模式不重复登记（同 key 嵌套会自拒），继承父 AbortSignal
       ↓
runWorkspaceTask 服务（两种入口收敛于此）
  ├─ 全局执行闸检查（并发 1）+ workspace 配额前置检查
  ├─ 订阅进度 bus → 中途推送"正在写脚本/第 2 轮修改…"
  ├─ 任务开始：docker run -d --name qqbot-exec-<runId> [全套限制] <镜像> sleep 300
  │            └ sleep = 自毁定时器；容器与本任务同生命周期，多轮共用
  └─ 子 Agent 图循环（10-12 轮，总预算分钟级）：
       轮 1  LLM → write_file(main.py)      [Node fs 直写 workspace，路径校验]
       轮 2  LLM → exec("python main.py")   [docker exec 容器 → stderr 回流]
       轮 3  LLM → write_file(main.py)      [改文件；容器还在，cd/环境保持]
       轮 4  LLM → exec("python main.py")   [同一容器 → 成功，输出分析结果]
  ↓
docker kill qqbot-exec-<runId> + 确认退出（容器销毁；workspace 文件留存）
  ↓
子 Agent 最终报告（含关键结果块）
  ↓ 委派模式：作为 tool 结果回主 Agent → finalize 套人设转述发回 QQ
  ↓ 独立模式（/代码）：直接整理回复（消息级截断）发回 QQ，finally 释放自己的闸
```

### 3.2 workspace 身份与目录布局

- 租户身份直接复用 `tenantKey(event)`（`src/session/key.ts`，2026-10-14 键统一后全项目唯一键函数）：群聊 `group:<group_openid>` 一群一个共享；单聊 `c2c:<user_openid>` 一人一个——与并发闸、记忆、人格、任务、知识库 scope 同键，天然同粒度。
- 目录名**不使用**原始 openid 拼接，用 `sha256(tenantKey(event))` 十六进制前 32 字符：
  ```text
  /var/lib/qqbot-workspaces/     ← 独立根目录，绝不放进 ~/workspace/qqbot（部署目录）或 data/（含跨租户库）
    ├── a3f0…/  (群甲)
    │     ├── main.py
    │     └── data.csv
    └── 9c2b…/  (用户乙)
  ```
- 目录惰性创建（首次执行时 mkdir）；保留映射表（key hash ↔ 最近活跃时间 ↔ 显示名）供后续 /工作台 files 与清理策略使用。
- 群内 A、B 共享同一目录 → 写冲突由并发闸解决：本租户互斥继承自统一键的既有流程闸（决策七），同群第二人在跑长流程时 /代码 直接被拒；每次执行的发起人记入审计摘要。
- **持久化语义**（决策六）：任务结束只销毁容器，目录永不清空；"清空"仅显式 reset 与默认关闭的 LRU 两条路径，磁盘兜底靠配额前置检查。

### 3.3 子 Agent 图结构（`src/agent/code-workspace.ts`）

照深检骨架裁剪：`prepareContext → llmCall → tools → llmCall → … → finalize`，要点：

- **独立工具表**（`src/agent/code-workspace/registry.ts`）：六件套 `read_file` / `write_file` / `edit_file` / `glob` / `grep` / `exec`（规格见 3.4/3.5），不进全局注册表——这就是工具面隔离的落点。
- 轮次上限 10-12（可配）——探索式工作流一轮任务常是 read×3 → grep → edit → run → edit → run 的十几步，6-8 轮不够；图内串行执行 + 每轮可多个 tool call，实际比轮次数字更耐用，真正的约束是**总墙钟预算**（默认 5 分钟，节点边界检查 + 工具级硬超时双保险）与 256m 内存池。
- 工具**串行**执行（本图内不 `Promise.all`）：写→跑的顺序依赖天然成立。
- AbortSignal 贯穿：图的每个节点入口检查；`exec` 收到 signal 即 `docker kill` **任务容器**并等待容器退出后才 resolve——**杀完才解锁**。signal 来源按入口分两种（决策八）：委派模式继承主流程 controller.signal（同 key 嵌套登记会自拒，不登记）；`/代码` 独立模式自己 `beginControlledFlow(tenantKey)`（与 /Agent、深检同款）。"abort 先删条目"的窗口由全局执行闸兜底（见决策七）。
- 上下文精简：不带聊天记忆/长期记忆（任务描述 + 本任务内的工具轨迹足够），降低注入面与 token 成本。

### 3.4 文件工具五件套（Node fs 直读直写，不经容器）

五件套共用一套服务端强制约束（集中实现在 paths.ts，工具自身不重复实现）：

```ts
// 对每个 path 参数：
//   - 必须相对、禁 ".."、禁绝对路径、禁 NUL、无符号链接段
//   - realpath 解析后必须仍在 workspace 根内（前缀比较基于 realpath，非字符串拼接）
// 写路径（write_file / edit_file）额外：
//   - 拒绝写入已存在的符号链接（防链接逃逸：先 lstat）
//   - 原子写：临时文件 + rename
//   - 单文件 ≤ 1MB；workspace 文件数/总容量配额（见 3.6）
```

各工具规格（模型可见的参数 schema 与关键上限）：

| 工具 | 参数 schema | 关键行为与上限 |
|---|---|---|
| read_file | { path, offset?, limit? } | 输出带行号（cat -n 风格）；行数/字节双上限（默认 500 行 / 32KB，先到为准），超限截断并附"用 offset 续读"提示；二进制文件不回显内容仅标记 |
| write_file | { path, content } | 覆盖语义；返回写入字节数与最终路径 |
| edit_file | { path, old_string, new_string, replace_all? } | old_string 逐字节匹配；匹配 0 次或多次（未开 replace_all）即失败，错误信息附匹配数与附近内容片段，让模型下一轮自纠 |
| glob | { pattern } | `**/*.py` 风格模式；结果数上限（默认 200），按 mtime 降序（最近改动的在前） |
| grep | { pattern, glob? } | 正则（编译失败返回明确错误）；单文件超 5MB 跳过并标记；匹配条数上限（默认 50），每条截断；输出 `file:line: content` 格式 |

设计要点：

- **上下文预算纪律写进工具描述**：read 的默认上限、截断标记、"想看后面用 offset"——模型省不省上下文，一半取决于工具描述写得好不好（Claude Code 的 Read 带行号/默认截断/offset+limit 正是这个用途，本方案照此办理）。
- **命名与输出格式贴主流 agent 框架惯例**（read_file/grep/glob、`file:line: content`）：强模型对这套约定有训练先验，调用成功率高——不自创命名。
- **grep/glob 走 Node 不走容器**：输出格式完全可控（结构化行号 + 确定性截断，不赌 64KB 截断点）、不依赖容器存活、与 write_file 对称（文件操作全在 Node 侧，容器只负责跑代码）；最坏情况 200 文件 × 100MB 配额的遍历也是毫秒级。
- 上限值全部进配置（§3.6），首版从紧，实测再放。

**为什么每条路径校验都是必须的——具体攻击链**（2026-10-15 评审补记，symlink 跨视角逃逸）：

> 用户代码在容器内执行 `ln -s /etc/passwd /workspace/leak`（容器内 `/etc` 是镜像的，这一步本身无害），随后诱导模型调用 `read_file("leak")`——Node 侧的 realpath 在**宿主机视角**解析这个 symlink，得到的将是**宿主的** `/etc/passwd`。

防线逐层对应：realpath 前缀检查（解析结果不在 workspace 根内 → 拒绝）挡住读取；写入侧 lstat 拒绝已存在的符号链接挡住"写穿"变体（`ln -s /宿主路径 /workspace/poison` 后 `write_file("poison", ...)`）。**因此路径校验必须基于 realpath 而非字符串前缀比较，且 read/grep/glob 与 write_file 同样全程受校验**——不是只有写路径才需要。实现时的 TOCTOU 注意项：realpath 检查与实际 open 之间存在竞态窗口（校验后 symlink 被换掉），打开时带 `O_NOFOLLOW` 语义或打开后 fstat 复核目录归属；同租户单任务串行使窗口极小，但按纵深防御实现。

**双路径隔离强度对比**（诚实记录，防将来误判）：

| 路径 | 防线层级 | 突破含义 | 为何可接受 |
|---|---|---|---|
| exec（容器） | 内核级（mount namespace + cgroup + caps） | 容器逃逸，需内核漏洞 | 这是任意代码唯一运行的地方，用最强防线 |
| 五件套（Node fs） | 应用层（paths.ts 校验） | 校验 bug（symlink/TOCTOU/解析漏洞） | 调用者是模型不是任意代码——它只能传 path 参数，过校验即到不了外部；任意代码（python/shell）只存在于容器内 |

推论：**不要往五件套里加"运行代码"语义的工具**（如 `eval_python` 走 Node 执行）——那会把应用层防线暴露给任意代码，破坏上表的分工。

### 3.5 `exec`（唯一走容器的工具；执行器与容器参数全集）

**任务容器创建**（任务开始时一次）：

```bash
docker run -d \
  --name qqbot-exec-<runId> \
  --network=none \                # 禁网：pip/爬虫/内网探测/外传全部失效
  --memory=256m --memory-swap=256m \   # 硬内存上限=整个任务的预算池，无 swap 余地
  --cpus=1 \                      # CPU 上限（非预留）
  --pids-limit=64 \               # fork 炸弹兜底（含 exec 进来的进程）
  --user 1000:1000 \              # 非 root
  --read-only \                   # rootfs 只读
  --tmpfs /tmp:rw,size=16m,noexec \    # 唯一可写区（noexec 防落地再执行）
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --log-driver=none \             # 不落盘 Docker json 日志（宿主侧流式收集已是主通道，避免双写）
  -v /var/lib/qqbot-workspaces/<hash>:/workspace \   # 唯一挂载：本租户目录
  -w /workspace \
  ghcr.io/<user>/qqbot-python:<tag> \
  sleep <任务预算秒数>            # 主进程=自毁定时器：无人回收也最多吊到预算上限自然死亡
```

**每条命令执行**（loop 各轮）：

```bash
docker exec qqbot-exec-<runId> timeout <单命令超时> bash -lc '<模型给的命令>'
```

Node 侧要点（`src/services/workspace/executor.ts`）：

- 全部 `spawn("docker", [argv 数组])`，**不经宿主 shell**（命令字符串是容器内 bash 的输入，不是宿主的）。
- 容器 env 天然干净：`docker run` 默认不透传宿主环境变量（Node 的 env 只到 docker CLI，不进容器），只要不传 `-e/--env-file`——bot 的 `.env` 凭证与容器无关。`stdin` 关闭，不分配 tty（输出纯管道）。
- 流式收集每次 exec 的 stdout/stderr，**各截断 64KB** 并置截断标记（不是先攒完再切）；返回 `{ exitCode, stdout, stderr(truncated), durationMs }`。
- **两级超时**：单命令级由容器内 `timeout` 自杀（docker exec 无单独 kill API，这是标准解法）；任务级由图层预算检查触发 `docker kill qqbot-exec-<runId>`。
- 任务结束路径（正常完成 / abort / 预算耗尽）统一：`docker kill` → **等待容器退出确认** → 才向 scheduler 报告完成、释放闸。
- **孤儿兜底**：bot 启动时 `docker rm -f` 所有 `qqbot-exec-` 前缀容器（全局并发 1 保证在跑任务不可能是合法的——若启动时确有任务在跑，它随旧进程一起死了， prune 是正确语义）。
- 每次任务开始前置检查：workspace 磁盘配额（目录递归统计）、docker 可用性（daemon 存活、镜像在位）；失败直接拒绝任务并给用户可理解的提示。

### 3.6 并发与配额总表（首版默认值，全部进配置）

| 维度 | 默认 | 说明 |
|---|---|---|
| 全局同时执行任务数 | 1 | 2G 起步值；实测 Node+Chromium 余量后调整 |
| 每 workspace 同时任务数 | 1（继承） | 统一键的既有流程闸免费提供（决策七）；同群跑着 /Agent 时 /代码 同样被拒（跨类型互斥）；不排队，短队列是阶段 2 选项 |
| 单容器内存 | 256m（swap 同值=禁 swap） | 任务级预算池（容器与任务同生命周期）；pandas 级分析够用 |
| 单容器 CPU | 1 核 | 上限非预留 |
| 单容器 PID | 64 | fork 炸弹兜底（覆盖 exec 进来的所有进程） |
| 单命令墙钟 | 60s | 容器内 `timeout` 自杀（docker exec 无单独 kill API） |
| 任务容器自毁上限 | = 任务预算（sleep 秒数） | 无人回收时兜底，不超预算上限 |
| 单任务轮次 / 总预算 | 10-12 轮 / 5 分钟 | 探索式流程一轮常十几步工具调用；真正约束是预算与内存池 |
| stdout+stderr | 各 64KB 截断 | 容器级；QQ 回复另有消息级截断 |
| read_file 单次输出 | 500 行 / 32KB 双上限（先到为准） | 上下文预算纪律；超限附 offset 续读提示 |
| grep / glob 结果上限 | 50 条匹配 / 200 条文件 | 每条截断、超限置截断标记 |
| 单文件 / workspace 总量 | 1MB / 100MB | write_file 与 exec 前置检查 |
| workspace 文件数 | 200 | 同上 |

磁盘配额说明：`--memory` 管不了磁盘，需 Node 侧在启动容器前统计目录（或维护增量计数），超额拒绝执行——内存限制解决不了磁盘被写满的问题。

## 4. 安全边界总结

**允许**：workspace 内读写自己的文件；跑白名单镜像里的 Python/标准工具；受控 bash 命令（ls/cat/python 等，无命令白名单——边界在容器）。

**禁止（由容器与执行器硬性保证，非提示词）**：

| 威胁 | 防线 |
|---|---|
| 读 bot 凭证（.env/API key） | 容器默认不继承宿主 env；不挂载 bot 目录/宿主根 |
| 跨租户读写 | 双路径：exec 由容器挂载边界（内核级）；五件套由 paths.ts realpath 前缀校验（应用层，含 symlink 逃逸防线，见 §3.4 攻击链） |
| 联网（外传/内网/云 metadata/爬虫） | `--network=none` |
| 装包（pip/apt/torch） | 禁网 + 镜像内容即白名单 |
| fork 炸弹 / 死循环 | `--pids-limit=64` + 单命令 timeout + 任务预算强杀 + CPU 上限 |
| 内存耗尽拖垮宿主 | `--memory=256m` + 全局并发 1 + 自毁定时器兜底 |
| 写系统文件/留后门 | `--read-only` + 任务结束容器销毁 + tmpfs noexec |
| 提权 | `--user 1000:1000` + `--cap-drop=ALL` + `no-new-privileges` |
| 写满磁盘 | Node 侧配额前置检查 |
| 输出洪泛 | 流式 64KB 截断 + 消息级截断 |
| 注入指令让日常 Agent 越权 | 日常 Agent 无 read/write/bash，只有委派动作（决策八注入面论证：最坏=白跑一个受控任务）；执行工具只存在于子图 |
| /stop 或崩溃后容器泄漏/继续产生副作用 | abort → docker kill → 等待退出 → 才释放闸；主进程 sleep 自毁定时器 + bot 启动 prune 孤儿 |

**已知接受的残余风险**：容器逃逸类 0day（普通容器非绝对沙箱，面向不完全信任用户需 gVisor/microVM——阶段 3 选项）；同 workspace 群友互删文件（共享语义，靠群社交约束 + reset 确认）；提示注入影响子 Agent 在自己 workspace 内的行为（爆炸半径已限于配额内）。

- 死循环 60s 被 `timeout` 自杀（exit code 124），下一条命令照常可执行；

- 打印洪泛只回 64KB 截断块，QQ 消息不超长；

## 8. 附录：讨论中已否决/搁置的选项（备查）

| 选项 | 否决原因 | 何时可重启 |
|---|---|---|
| Node spawn python + cwd | 同用户凭证/数据全可达，无隔离 | 永不 |
| venv 作为隔离手段 | 仅包隔离，非安全沙箱（官方文档口径） | 不适用（镜像内可用 venv 做包管理，但非安全边界） |
| pip 安装时黑/白名单拦截 | 黑名单永远漏；白名单可被改名/离线包绕过 | 已被"镜像内容+禁网"替代 |
| 命令级白名单解析 | bash 语法复杂必漏；容器已兜底 | 永不 |
| 每命令一容器（docker run --rm） | 每条命令 0.5-1s 启动开销；无会话连续性（cd/环境不保持） | 已被任务级容器替代（2026-10-11 讨论采纳后者）；任务级容器若实践暴露问题可退回，对模型无感 |
