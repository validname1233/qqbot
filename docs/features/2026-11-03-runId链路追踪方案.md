# runId 链路追踪方案（一期：日志关联）

> 2026-11-03。目标：给每一次「运行」一个贯穿全程的短 id（runId），该运行沿途
> 产生的所有日志自动携带它——并发多群时 `grep runId` 即可抽出一次运行的完整
> 轨迹，不再靠时间戳 + 模块名人肉对时间线。
>
> 定位：可观测性从「结构化日志」到「关联日志」的第一步（差距分析 02 报告
> 深挖点 #10），也是后续 usage 按运行聚合的前置。方案依据：本文件 §3 的
> 选型对比 + `docs/problems/2026-09-18-租户参数透传问题复盘.md` §4.3 为
> AsyncLocalStorage 预留的演进路径（触发条件 B：「深层调用也需要上下文」
> ——日志先行兑现，租户身份口径统一仍是该机制将来的第二个消费者）。
>
> **2026-11-03 已实施（一期）**，实施时并入两处评审修订：入口「run 开始」
> 锚点日志（§4.3 表后说明）、按位置解析日志行的兼容性备注（§4.2/§5.6）。

## 1. 问题

当前 logger（services/logger.ts）双维度内核成熟，但 LogEvent 只有
module + ts + message：**日志有形状，没有关联**。bot 同时服务多群时，
A 群的深检、B 群的 /Agent、C 群的闲聊在日志文件里交错：

```
[agent] llmCall 返回 tool_calls=search(...)
[browse] 第2页抓取完成 (+1200ms)
[agent] llmCall 返回 content="..."
```

哪行属于哪次运行，只能靠时间戳 + 模块名猜。具体排障场景：一次 /Agent
失败要复盘「prepareContext 装配了什么 → 模型每轮说了什么 → 工具返回了
什么 → usage 花了多少」——这些行都在（detail 通道很全），但交织在其他
群的运行里，抽不出来。

## 2. 目标与非目标

**目标（一期）**：
- 一次运行的**所有**日志行（trace + detail，console + file）自动带同一 runId；
- runId 在日志里可 grep、肉眼可比对（短、定长）；
- 主图 / 深检子图 / workspace 子图 / 工具层 / progress-bus 的 warn——
  委派链路沿途全覆盖，**不要求任何调用方改签名**。

**非目标（一期不做，二期再议）**：
- runId 落库（conversation_events 加列，按运行回放 process 行）；
- usage 四元组按 runId 聚合的报表；
- span 层级 / 耗时分解（OTel 式 trace→span 树）——单进程场景收益低于
  成本，greppable runId 够用；
- 跨进程传播（MCP kb server 是另一进程，runId 止步于 bot 侧的调用日志）。

## 3. 选型：为什么是 AsyncLocalStorage

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| 显式传参 | runId 塞进 MessageContext，逐层透传 | 侵入所有签名：runTool、callModel、appendEvent、子图 state、工具实现……改动面 = 全项目；且新工具作者必然忘传 |
| LangGraph state 字段 | state 加 runId，节点读 state | 只覆盖图内——registry.runTool、progress-bus、transcript 等图外日志拿不到；深检子图还得跨图传 |
| progress-bus 搭车 | bus 里挂 runId | 语义错位（bus 是用户侧进度通道）；且 emit 点本就在异步链上，没必要 |
| **AsyncLocalStorage**（选） | 入口 `startRun()` 建上下文，logger 的 emit 里 `getStore()` 读 | 零签名侵入；Node 内置；异步链自动传播。代价：store 读一次的开销（可忽略）与 §5 的边界语义 |

传播路径验证（为什么「零穿透」成立）：dispatcher 的 `startRun` 内
`await handler(event)` → runAgentTurn → `agentGraph.invoke`（LangGraph
的节点执行就是 async 函数调用，无线程池/队列转移）→ toolsNode 的
`Promise.all`（每个分支继承建立时的 store）→ `runTool` → 委派的
`runDeepSearch`（ownFlow:false，同一条 await 链）→ 子图节点 → browse/fetch。
沿途任何 logger 调用都在同一条异步链上，store 可见。**唯一传不出去的是
进程边界**（MCP server、docker 容器内），那本来就是二期的显式参数话题。

## 4. 设计

### 4.1 新模块 `src/services/trace.ts`（~40 行）

```ts
import { AsyncLocalStorage } from "node:async_hooks";
import { randomBytes } from "node:crypto";

const runALS = new AsyncLocalStorage<{ runId: string }>();

// 生成 4 字节 hex（8 字符）：同屏两群冲突概率可忽略，真撞了 grep 出两条
// 轨迹也只是混淆不致错——不做全局唯一承诺，日志够用。
const newRunId = (): string => randomBytes(4).toString("hex");

// 入口包装：fn 整条异步链内 getRunId() 可见。
export function startRun<T>(fn: () => Promise<T>): Promise<T> {
  const runId = newRunId();
  return runALS.run({ runId }, fn);
}

// logger.emit / 需要显式拿 id 的点调用；链外（理论不可达）返回 null。
export function getRunId(): string | null {
  return runALS.getStore()?.runId ?? null;
}
```

### 4.2 logger 改动（~10 行）

- `LogEvent` 加可选字段 `runId: string | null`；`emit()` 里 `getRunId()` 填充；
- 两个 sink 的行渲染加段：有 runId 时 `[runId]` 插在 `[module]` 前
  （`[a3f2c1b0]`），无 runId（启动期、定时器裸回调等链外日志）原样输出；
- console 格式变化对 pm2 无影响（人读为主），file 格式向后兼容
  （新字段是插入不是替换，旧行解析不受影响）。但**按括号位置**解析日志行
  的脚本（"第 2 个方括号是 module"式）会因 `[runId]` 段插入而错位——
  一期无已知解析脚本；若将来有，须按字段内容而非位置解析（§5.6）；

### 4.3 入口埋点（每处 ~3 行，共三处）

| 入口 | 位置 | 说明 |
| --- | --- | --- |
| 消息事件 | `events/dispatcher.ts` dispatch() | `recordInbound` 之后包 `handler(event)`——重推短路的不算运行。**同一条事件的 runCommand 与 runObservers（handler 内 Promise.all 两分支）共享同一 runId**：它们同属「处理这条消息」这一次运行，语义正确 |
| 定时任务 | `services/scheduler/cron.ts` 触发处 | cron 起的流程没有入站事件，自己 `startRun`——与用户触发的运行天然区分 |
| 提醒触发 | `services/reminder.ts` setTimeout 回调 | 见 §5 边界第 3 条——必须在**触发时**重挂，不能依赖创建时继承 |

/stop 也是入站事件，经 dispatcher 自动获得自己的 runId（与被停的运行
不同 id）——「谁停了哪次运行」在日志里可关联：停人日志引用被停运行的
key，被停运行的中断静默日志在自己的 runId 下，两次运行各自成线。

## 5. 边界与已知语义（诚实记录）

1. **MCP 跨进程**：runId 止于 bot 侧 `mcp/client.ts` 的调用/返回日志；
   kb server 进程内无此 id（要传就得进 MCP 参数 + server 侧落日志，
   二期与「子 Agent 过程归档」一起议）。
2. **workspace 容器内**：docker exec 的执行日志在容器 stdout，本就另有
   归档（2026-10-23 workspace 细节日志持久化），runId 不进入容器。
3. **长定时器的上下文继承陷阱**：AsyncLocalStorage 沿创建时的上下文进
   setTimeout 回调——reminder 的 setTimeout 若在运行 A 内创建、两小时后
   触发，回调里 getRunId() 会拿到**早已结束的 A**。所以提醒触发必须
   `startRun` 重挂（§4.3 第三行），这也解释了为什么「入口清单」要显式
   枚举而不是「建立了就永远对」。
4. **state 字段不加**：LangGraph state 不存 runId——加了就会出现「state
   里的 id 与 ALS 里的 id 谁是真相」的双源问题；ALS 是唯一来源。
5. **runId 不进 conversation_events（一期）**：process 行已有 origin 区分
   归属（agent/deep-search/workspace），加 runId 列是 schema 变更，收益
   （按运行回放）属二期话题。一期的 runId 只活在日志层。

## 6. 验证清单

- typecheck 0；
- 冒烟断言（test/context-rebuild-smoke.mts 追加）：同一 `startRun` 内
  两次 logger 调用捕获同一 runId；链外 `getRunId()` 为 null；嵌套
  `startRun`（模拟委派）内层拿到新 id、退出后外层 id 恢复；
- 实机抽验：两个群近乎同时各发一条 /Agent，file 日志里两段轨迹的
  runId 互不串线、`grep <runId>` 各自完整（从 webhook 行到 usage 行）；
- 回归：无 runId 的启动期日志格式不变（旧解析脚本兼容）。

## 7. 分期与不做的事

- **一期（本方案）**：日志关联。改动 = trace.ts 新建 + logger 两处渲染 +
  三个入口包装，预计 <100 行，无 schema 变更、无签名变更。
- **二期候选（不承诺）**：runId 进 conversation_events（按运行回放
  process 行）；usage 四元组按 runId/tenantKey 聚合（成本报表）；
  MCP 参数透传（跨进程关联）。
- **不做**：OTel/span 层级（单进程杀鸡牛刀）；runId 进用户可见消息或
  进度推送（对用户无意义，徒增噪声）；全局唯一 id 生成（日志场景
  8 hex 字符足够，冲突可容忍且可检测）。
