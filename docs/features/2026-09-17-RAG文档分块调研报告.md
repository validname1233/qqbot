# RAG 文档处理与分块调研报告：PDF / Markdown / CSV

> 日期：2026-09-17
> 背景知识库：`2026-09-04-知识库RAG-MCP方案.md`（omen6 端侧 MCP_RAG）
> 方法：三路并行调研（解析工具链 / Markdown 结构分块 / 表格数据），来源以官方文档、arXiv 论文、框架源码实测为主；"业界共识"与"单家之言"已分开标注。调研环境部分搜索引擎超时，个别结论已注明未能二次核验。

## 0. 结论速览

| 主题 | 业界共识 | 对 MCP_RAG 的启示 |
|---|---|---|
| 分块策略 | **结构感知**（按标题/章节/元素切）优于固定窗口；表格永远单独成块 | 我们已按标题切 Markdown ✓；PDF 暂只有文本层 |
| 语义保留三板斧 | 面包屑前缀、parent-child（小块检索大块喂模型）、contextual retrieval（LLM 生成块上下文，检索失败率 −49%~−67%） | 面包屑部分已有；后两个是低成本高收益升级项 |
| chunk 参数 | 512–1024 token、overlap 10–25%；**结构感知 + 面包屑后 overlap 可趋零** | 我们的 500–900 字 ≈ 510–920 token，**恰在共识区间** ✓ |
| 中文要点 | 1 汉字 ≈ 1 token（cl100k 实测 1.02）；分隔符须含中文标点 | 我们按字符计量、句边界含中文标点 ✓ |
| 表格 | 能翻译成 SQL 的问题不该走 embedding；语义查找才线性化；**表头必须随行** | CSV 目前当纯文本（表头丢失）→ 值得写专门解析器 |
| 规模红线 | 知识库 < 20 万 token（约 500 页）时，整篇进 prompt 可能优于任何分块 | 家用群聊库大概率在红线内，RAG 仍值得做（跨文档+持续增长），但不必过度工程 |

## 1. PDF

### 1.1 解析工具分三层

| 层 | 代表 | 能力 | 适用 |
|---|---|---|---|
| L1 轻量文本提取 | **pdf-parse / pdfjs**（我们在用）、pdfminer | 只读文本层，快、零模型 | 数字版、简单排版 |
| L2 结构感知解析 | **Docling**（MIT）、**MinerU**（4.0，ONNX 小模型 2GB 内存可跑）、Unstructured hi_res、Marker | 布局模型识别标题/段落/表格/阅读顺序；扫描件 OCR | 复杂排版、双栏、表格密集、扫描件 |
| L3 托管 API / VLM | **LlamaParse**、Azure Document Intelligence | 多栏/合并单元格/图表结构化，输出 Markdown | 不想维护模型、量不大 |

关键事实：
- L1 的硬伤是**丢失阅读顺序**（双栏左右串行）和**表格结构**——Unstructured 官方明确其 fast 策略（同层）是 PDF 表格提取唯一不可用的档位。
- 第三方基准（Marker README 引 olmocr-bench，**单家之言**）：Marker 76.0%、MinerU 72.7%、Gemini Flash 76.4%、Docling 50.3%——量级参考，Docling 输在纯解析精度但许可最干净。
- 我们现有 pdf-parse（L1）对"数字版简单文档"就是正确选择，不是妥协。

### 1.2 分块与语义保留

- **按页切**最简单但一页多主题、跨页段落被腰斩——不推荐为主策略。
- **结构感知分块**（共识方向）：建立在解析产出的语义元素上。Unstructured `by_title`：遇 Title 元素即关块，**单个 chunk 绝不跨章节**；表格元素**总是单独成块**。
- **面包屑注入**（共识）：`文档名 > 章 > 节` 前缀进每个 chunk 再 embedding（Azure 官方建议、LlamaIndex metadata 继承机制）。
- **Parent-child / small-to-big**（LlamaIndex 标准件）：`[2048, 512, 128]` 三级分块 + AutoMergingRetriever——小块做向量检索，命中后自动升级为大块喂 LLM。
- **Contextual Retrieval**（Anthropic，单家但数据扎实）：入库前用便宜 LLM 给每块生成 50–100 token 的"本块在全文中的位置说明"前置；配 prompt caching 约 $1.02/百万文档 token。检索失败率：基线 5.7% → 上下文 embedding 3.7%（−35%）→ +BM25 2.9%（−49%）→ +rerank 1.9%（−67%）。
- **Late Chunking**（Jina，arXiv:2409.04701）：长上下文 embedding 先编码全文、池化前才切块，块向量天然带全文上下文；nDCG@10 约 +3.5%，且实验中 overlap 无明确收益——前沿方向，依赖特定 embedding 模型。

### 1.3 PDF 内表格

通行做法（多家交叉印证）：单独成块；默认**转 Markdown**（MinerU/Marker/LlamaParse 默认输出格式）；要 LLM 阅读理解优先 HTML；要精确单元格检索做**行展开**（每行拼表头）；表题与表格同块。

### 1.4 我们的现状与差距

| 项 | 现状 | 差距 |
|---|---|---|
| 解析 | pdf-parse v2，魔数校验+加密识别+空文本交回退链 | L1 定位正确；扫描件等 MinerU（已在路线图） |
| 阅读顺序 | 无感知（双栏会串） | 家用文档多为单栏，暂可接受 |
| 分块 | PDF 文本进通用 chunker，无标题结构 | pdf-parse 拿不到标题层级——L1 天花板，不值得在 L1 上硬补 |
| 表格 | 当正文文本切 | 同上，等 L2/L3 解析器 |

**结论：PDF 侧现状合格，不欠账。** 升级路径就是既定的 MinerU（阶段三）——它同时解决扫描件、阅读顺序、表格结构三个问题，输出 Markdown 后下游（结构分块、表格单独成块）全部自动受益。

## 2. Markdown

### 2.1 业界机制（两大框架源码级一致）

- **标题栈 + 弹栈**（LangChain `MarkdownHeaderTextSplitter`、LlamaIndex `MarkdownNodeParser` 同款）：逐行扫，维护标题栈；遇新标题弹出所有 ≥ 当前置的旧标题（支持 H1 直接跳 H3）。LlamaIndex 存 `metadata["header_path"] = "/H1/H2/"`（只含祖先、不含自身）。
- **面包屑进正文**：LlamaIndex `MarkdownReader` 直接 `f"\n\n{header}\n{text}"` 拼接。
- **代码块保护**（两家默认）：跟踪 ``` / ~~~ 围栏开关，**块内不切分、`#` 注释行不误判标题**。
- 回退链分隔符优先级（LangChain MarkdownTextSplitter 实测）：`\n#{1,6} ` > 代码围栏 > `\n---+\n`（水平线）> `\n\n` > `\n` > 空格。

### 2.2 参数经验值

| 来源 | chunk / overlap | 单位 |
|---|---|---|
| LangChain RecursiveCharacterTextSplitter | 4000 / 200 | 字符 |
| LlamaIndex 全局默认 | 1024 / 20 | token |
| Anthropic 示例 | 800 / 上下文 50–100 | token |
| unstructured 起点 | ~250 token | token |

- 共识区间 **300–800 token**；**结构感知 + 面包屑下 overlap 可为 0–50**（Jina 实验支持，我们现在的 80 字偏保守但无害）。
- 中文 tiktoken 实测：cl100k 下 1.02 token/字——**"1 字 ≈ 1 token"近似成立**；我们 500–900 字块即 ~510–920 token，在共识区间内。
- 两个中文陷阱：两家标题正则都要求 `#` 后有空格（`##标题` 无空格不识别——这符合 CommonMark，但中文用户常写无空格标题，自研可放宽）；Setext 式标题（`===`/`---` 下划线）不被识别。

### 2.3 我们的现状与差距

| 项 | 现状（src/chunker.ts） | 差距 | 优先级 |
|---|---|---|---|
| 标题边界 + 前缀 | ✓ 单级标题进 heading/prefix | **只有当前标题，无祖先路径**（`文档 > 章 > 节` 面包屑） | 高（性价比最高的一项） |
| 代码块保护 | **无**——代码块内 `#` 注释行会被误判为标题、按空行切断代码 | 需加围栏跟踪 | 高 |
| 水平线 `---` | 未当边界 | 低成本补 | 低 |
| 无空格标题 | 要求 `\s+`（与两家一致） | 可放宽为 `\s*` | 低 |
| prev/next 关系 | 无（LlamaIndex 默认存相邻 chunk id，召回后可拼接上下文） | kb_search 时再补 | 中 |
| 尺寸/overlap | 500–900 字 / 80 字 | **已在合理区间，不动** | — |

**Markdown 是我们欠账最多的格式**（因为它是"主力格式 + 我们已经有结构感知的底子，离满分最近"）：加**标题栈面包屑**和**代码块围栏保护**两项，就能对齐两大框架的默认行为。

## 3. CSV / 表格

### 3.1 根本问题：先问"该不该 embedding"

**共识：按问题类型分流，不能一刀切。**

- **精确问题**（"Q3 总支出"、"按地区分组"）→ Text-to-SQL / SQL 引擎（Vanna、DuckDB）。凡能翻译成 SQL 的，直接 SQL——毫秒级且精确，**不应 embedding**。
- **语义查找**（"跟某某相关的记录"、"提到退款的那几条"）→ 线性化 + embedding。
- **学术前沿**（NeurIPS 2024 TableRAG）：schema 检索（找相关列）+ cell 检索（找相关值）分层，解决百万 token 长表。

证据底座：Microsoft《Table Meets LLM》（WSDM 2024）证明 LLM 对表格的理解**高度敏感于输入格式与顺序**；TEM（arXiv:2405.01585）指出通用 embedding 模型在数值密集表格上表现弱。

### 3.2 线性化格式研究结论

- 《Table Meets LLM》实验（GPT-3.5/4 时代，**单家之言但影响大**）：HTML 综合最优（比朴素分隔符 +6.76%），Markdown 次之（合并单元格检测最好）；**外部信息（问题/说明）应放在表格之前**，放后面平均掉 6.81%。
- 工程通行分工（**共识**）：**存储用"列名: 值"逐行拼接**（行自包含语义）、**展示回填用 Markdown 表格**（省 token、模型友好）、交换用 JSON。

### 3.3 行级分块

- **表头必须随行**（所有方案的隐含前提）——这正是我们现状最大的洞：CSV 按纯文本切块，第二块起表头就丢了。
- 一行一条 vs 攒批（5–20 行）：内容型清单选**一行一条**（检索精度高、支持行级元数据）；同质流水可攒批。工程经验，无权威定论。
- 数值列不指望 embedding：数值向量语义极弱，通行做法是进 **metadata 做精确/范围过滤**，或离散化（"高消费"、"2024-Q3"）。
- 每表生成一条 **profile chunk**（行数、列含义、数值统计、类别 top 值）——回答"这表有什么"并辅助路由。

### 3.4 我们的现状与差距

现状：CSV 走 plain 解析器当纯文本读。对"值语义为主"的小型内容型 CSV **勉强能用**（值本身的语义 embedding 能捕捉），但三个确定性的洞：表头第二块起丢失；超长单行会被句边界二分切碎；数值列裸奔。

**建议（已在 §3.5 行动清单）**：写专门 csv 解析器注册到链前排——逐行解析成 `列名: 值` 序列化 + 表名/文件名前缀 + 表 profile 块，plain 自动退为兜底。精确统计类问题**不做**（DuckDB 旁路是好方向但家用群聊收益低，等真有需求）。

## 4. 统一行动清单（按投入产出排序，对照 MCP_RAG 架构）

| # | 行动 | 改动位置 | 规模 | 依据 |
|---|---|---|---|---|
| 1 | **chunker 加标题栈 + 面包屑**：heading 从"当前标题"升级为"祖先路径"，前缀 `文档名 > 章 > 节` | chunker.ts | ~20 行 | Markdown §2.1，两大框架默认行为 |
| 2 | **chunker 加代码块围栏保护**：跟踪 ```/~~~ 状态，块内不切分、不识别标题；超长代码块按行切并复制语言标记 | chunker.ts | ~30 行 | Markdown §2.1 |
| 3 | **专门 csv 解析器**：`列名: 值` 行序列化 + 文件名前缀 + 每表一条 profile chunk；plain 退为链尾兜底 | parsers/csv.ts + 注册一行 | ~60 行 | CSV §3.3/§3.4 |
| 4 | **parent-child 简化版**：embedding 用小 chunk，同 row 存所属 section 全文，kb_search 命中后回填 section（截断 ~3000 字） | vector-store + kb_search | ~100 行 | PDF §1.2，几百行复现 small-to-big |
| 5 | **轻量 contextual retrieval**：入库时用便宜 LLM 给每个 section 生成 1–2 句摘要前置（单独此步即 −35% 检索失败率） | worker 流水线 | ~80 行 | PDF §1.2 / Markdown §2.3 |
| 6 | **prev/next chunk id** 存 metadata，召回后可拼接相邻块 | db schema + chunker | ~20 行 | LlamaIndex 默认做法 |
| 7 | MinerU 外部解析器（扫描件/阅读顺序/表格结构一次解决，输出 Markdown 自动吃 #1 的收益） | parsers + Docker | 阶段三 | PDF §1.1 |
| 8 | rerank（bge-reranker 或智谱同族）接进 kb_search | 检索侧 | 阶段二尾 | 方案文档既定 + Anthropic 数据（−67% 的最后一环） |

**明确不做**（本调研支撑的"不做什么"同样重要）：
- 不做 Text-to-SQL / PandasAI 式动态执行（家用数据杂、无 schema 治理、eval/注入风险 > 收益）
- 不在 pdf-parse（L1）上硬补标题层级/表格识别（L1 天花板，等 MinerU）
- 不追 late chunking（依赖特定长上下文 embedding 模型，换模型成本 > 收益）
- 知识库总量 < 20 万 token 期间不过度工程（分块参数已在共识区间，无需再调）
