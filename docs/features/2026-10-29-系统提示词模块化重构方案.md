> 状态：设计定稿（模块规划阶段）——**本方案只界定模块结构与各模块职能，不产出提示词正文**。
> 正文编写是后续独立工作，按 §7 分期逐模块推进。
>
> 上游：《2026-10-28-记忆与上下文重构总方案》v9 直通架构 + 提示词殿后决议
> （"提示词最好在所有架构都更新完之后再编写"——架构已落地并验证，本方案即
> 殿后工作的第一步）。
>
> 范围：**仅重构 Agent 主链路（agent_unified 场景）的系统提示词**。
> reminder / deep_plan / deep_browse / deep_research / deep_report / daily
> 等场景不动（它们引用的共享常量去留见 §5 迁移映射）。
>
> 方法论：仿 Claude Code 的提示词组织——整体由几个大模块构成，各模块独立

## 0. 现状与动机

当前 system = `人格 + "\n\n" + agent_unified`（builder.ts:38 拼接），约 1400 字。
v9 合并三场景时把原 judge/plain/finalize 的规则揉进了 agent_unified 单场景，
已知欠账：

- **结构无层次**：工具规则、输入格式、收尾规则、输出格式混在一段功能文本里，
  修改任一处都要通读全文，没有"改哪块只看哪块"的边界；
- **语义重复**：人格行为准则第 6 条（只回应最后一条消息）与 SPEAKER_NOTE
  末句（末位单独成条 = 当前请求）重叠；
- **双源文本**：forcedFinalize 降级指令在 loop.ts:152 硬编码，functional.ts
> 的 agent_finalize 场景存着同一字符串（此前已记"待收口为单一 import"）；
- **过渡措辞**：SPEAKER_NOTE 自标注 v2 过渡版（"完整版待真机样本后定稿"）。

动机：把 system 从"两段拼接"升级为"模块化装配"——每个模块有明确的职能、
变异性（恒定 / 按租户 / 低频更新）和字节位置，为后续工具细则扩充、长期记忆
注入（CLAUDE.md 式）、技能注入（SKILL.md 式）预留结构性插槽。

## 1. 设计原则

1. **总纲继承**：System 管"怎么读、怎么答"，user 侧 100% 是数据（2026-10-28
   总方案定稿）。模块化是 system 内部的结构化，不动摇总纲。
2. **恒定性纪律**：system 按"租户 × 场景"恒定。任何逐轮变化的内容（时间戳、
   消息数、召回结果）依旧禁止入 system——这是缓存家族的锚，模块化不豁免。
   M4 的"动态"指**低频更新**（人格级频率），不是逐轮变化。
3. **模块序 = 字节序**：拼装顺序就是请求字节顺序。模块位置的调整是一次性
   全量 miss（部署日），此后按新字节稳定。模块一旦定序，不轻易对调。
4. **变异性分区**：全局恒定模块（M1/M2）在前、按租户可变模块（M3 人格槽）
   居中、低频可变模块（M4）在尾——公共前缀最大化（量化分析见 §4）。
5. **单一真相源**：代码常量与提示词引述处必须同源。降级信号文本 = 一处
   export；M1.2 的 blob 示例必须与 `renderBlobLine` 实际输出同构（测试锚定，
   防代码改格式后提示词漂移成"说明与实况不符"）。
6. **模块自治**：每个子模块有"写什么 / 不写什么"的边界声明。可独立修改而
   不牵连其他模块——这是"先框架后细节"得以成立的前提：二期往 M2.2 加工具
   细则时，M1/M3 一字不动。

## 2. 模块总览

```
system = [ M1 核心身份与输入格式 ]   ← 全局恒定
        + [ M2 工具判断与规则     ]   ← 全局恒定
        + [ M3 回复要求           ]   ← 人格槽按租户可变，其余恒定
        + [ M4 动态上下文注入     ]   ← 低频可变（预留，一期为空）
```

| 模块 | 变异性 | 职能一句话 | 吸收自 |
|---|---|---|---|
| M1 核心身份与输入格式 | 全局恒定 | 我是谁、输入长什么样、怎么读 | agent_unified 定位句、SPEAKER_NOTE、IMAGE_NOTE |
| M2 工具判断与规则 | 全局恒定 | 何时调工具、调哪个、何时必须停、不调时怎么走 | agent_unified 工具规则段、agent_finalize 信号语义 |
| M3 回复要求 | 人格槽按租户可变 | 以什么身份、什么格式作答 | DEFAULT_PERSONALITY、OUTPUT_FORMAT_RULE |
| M4 动态上下文与系统注入 | 低频可变（预留） | 记在骨子里的记忆、可扩展技能 | 无（新设，三期实现） |

与 Claude Code 的粗略对照（方法论参照，非逐项对应）：CC 的身份/环境说明 ≈
M1，工具使用规范 ≈ M2，语气与输出约定 ≈ M3，CLAUDE.md / SKILL.md 机制 ≈ M4。

## 3. 模块细则

### M1 核心身份与输入格式

职能：让模型知道"自己是什么、看到的是什么"。这是全部后续规则的读法基础——
M2 的意图识别、M3 的针对对象，都建立在对输入格式的正确理解上。

#### M1.1 身份与使命

- 职能：声明"运行在 QQ 群聊/私聊中的智能体"身份；声明工作模式——**从聊天
  记录推断用户意图，完成（最后一位发言人的）任务**。
- 边界：不含人设（M3）、不提工具（M2）、不写输出要求（M3）。
- 来源：agent_unified 定位句重写（"运行在 QQ 群聊/私聊中的智能助手"扩展为
  含使命表述的完整身份句）。

#### M1.2 输入格式契约（blob）

- 职能：定义输入的形态契约，**附真实格式的消息示例**。
- 内容要点：
  - blob 行定义：`{"speaker":"…","content":"…"}`，speaker = 发言人昵称、
    content = 发言原文；
  - 打包说明：历史消息以批（多条打包成一条 user 消息、逐行排列）给出；
  - 当前请求说明：**最后一位发言人的消息独立于 blob、单独成条位于末位**，
    即当前要完成的任务；
  - 真实示例：至少覆盖一条纯文本行 + 一条带图片行（图片内嵌形态见 M1.3）。
- 工程锚点：示例行由 `renderBlobLine` 逻辑生成或以冒烟测试断言同构——
  禁止手写字面量与代码格式各自漂移。
- 边界：只描述"格式是什么"，不规定"怎么回应"（那是 M1.4）。
- 来源：SPEAKER_NOTE 的格式说明部分（v2 过渡版措辞在此定稿）。

#### M1.3 图片转写说明

- 职能：解释 content 中的 `[图片]{图片描述}`——图片已预先解析成文字，花括号
  内即图片内容（含图中文字转写），可直接基于描述讨论图片。
- 决议：**降级形态（视觉开关关闭时的裸 `[图片]`）不写入提示词**——说明文字
  按完整形态恒定书写（system 不随部署配置分叉），裸标记语义自明，无需专门
  解释。
- 边界：只讲"怎么读图"，不讲"收到图该做什么"（动作属意图判断，M2）。
- 来源：IMAGE_NOTE 原文迁移。

#### M1.4 消息焦点与工作流

- 职能：规定注意力的分配与工作顺序。
- 内容要点：
  - 焦点规则：末位单独成条的消息 = 当前请求，重点回应；历史批 = 背景与
    信息补充，不逐条回应、不重新回答旧消息；
  - 多说话人规则：按 speaker 分别理解各自的话，谁在向你提问就回应谁，
    不把不同人的话混为一谈；
  - 工作流：背景推断（结合历史理解现状）→ 意图识别（确认最后一位发言人
    要什么）→ 执行（完成任务并作答）。
- 来源：SPEAKER_NOTE 焦点部分 + 人格行为准则第 6 条（人格模板同步瘦身，
  见 §5；已存库的自定义人格不迁移——重叠无害，容忍）。

### M2 工具判断与规则

职能：全部"动作决策"知识——调不调、调哪个、参数怎么来、何时被禁止。
本模块只会膨胀（二期逐工具加细则），结构上必须给膨胀留好插槽。

#### M2.1 通用工具准则

- 职能：与具体工具无关的判断纪律。
- 内容要点：判断果断——需要工具就调用、确认不需要（闲聊、知识问答等）
  就一个不调；严格按 tool schema 做意图与参数识别，参数从用户原话准确
  提取；可同一次输出多个调用；已调结果不足以完成时可继续调用；绝不编造
  工具列表之外的工具、绝不强行调用与请求无关的工具。
- 分工声明：工具的名称/参数定义住在请求的 tools 字段，本模块只写**判断
  纪律**，不复述 schema——两处各司其职，避免双源漂移。
- 来源：agent_unified 工具规则段（原 judge 措辞重写版）。

#### M2.2 原生工具使用细则（逐工具）

- 职能：每个工具一组"何时必须 / 优先调用"的触发准则。**槽位先立，正文
  二期逐个充实**（一期可只收两三条最刚性的）。
- 槽位表（收录四个工具；`set_reminder` / `workspace_task` **不写专属细则**
  ——触发判断完全交给其 tool schema 自描述。细则表不是完备清单，只收录
  需要强触发提示的工具）：

| 工具 | 细则方向（待充实，示例） |
|---|---|
| `get_time` | 用户要求"最近 / 前几天 / 今天"等**相对时间**相关信息时，必须先取当前时间，再作答或续调 |
| `search` | 用户要求联网查询、时效性信息，或明确说"搜一下"时，必须调用搜索 |
| `open_page` | 用户消息里直接给了 URL 时，打开阅读后再回应 |
| `recall_memory` | 用户提"之前说过 / 上次 / 你还记得吗"等回溯意图时，回看历史 |

- 边界：细则写"何时用"，不写"怎么执行"（执行在工具实现里）、不贴参数表
  （在 tools 字段里）。
- 来源：新设（用户框架第 2 点："这部分可以慢慢添加"）。

#### M2.3 循环终止信号

- 职能：让模型识别轮次触顶的降级消息（"工具调用的轮次已经用完……"）并
  正确反应：**禁止再发起任何工具调用，立即基于已获得的工具结果总结作答**，
  严格遵照 M3 的回复要求。
- 单一真相源：降级信号文本 = functional.ts 一处 export 常量，loop.ts
  import 注入（消除现有硬编码重复）；本模块提示词引述同源常量的措辞
  （提示词为编译期文本、常量为运行期注入，两者以测试锚定一致）。
- 与协议双保险的关系：forcedFinalize 不传 tools 字段是硬约束（物理上无工具
  可调），本条是行为强化——即便未来降级路径变化（如仍带 tools），模型也
  知道该停。
- 来源：新设（用户框架第 2 点"重点 2"）。

#### M2.4 无工具直出衔接

- 职能：声明不需要工具时的出口——直接按 M3 的回复要求作答，零工具调用。
- 措辞注意：M2 在 M3 之前（模块序 = 字节序），"遵照下面的回复要求"这类
  前指引代天然成立，不产生悬空引用。
- 来源：新设（用户框架第 2 点"重点 1"），吸收 agent_unified 中"确认不需要
  就直接回答"一句的衔接语义。

### M3 回复要求

职能："表达层"知识——以什么人格身份、按什么排版格式作答。人格槽在此，
即 system 的"按租户可变"从本模块开始。

#### M3.1 人格注入槽

- 职能：builder 注入点——自定义人格（/set_personality，按租户存库）优先，
  DEFAULT_PERSONALITY 兜底。整块替换，语义与现在一致。
- 人格模板瘦身决议：默认模板删除行为准则第 6 条（焦点职责已归 M1.4）；
  其余保留（身份、行为分寸、语气示例）。
- 顺序决议：人格槽在 M3 首位——M3.2 的措辞可以自然指代
  "设定好的人设"，先行物明确。

#### M3.2 输出格式

- 职能：OUTPUT_FORMAT_RULE 迁入——Markdown 子集（标题/粗体/无序列表/代码
  块/表格），禁数字编号列表与引用块，正常换行分段。
- 共享决议：daily / reminder 等场景继续**引用同一常量**（import 共享，不是
  复制一份文本），单一真相源。

### M4 动态上下文与系统注入（预留，三期）

职能：CC 的 CLAUDE.md / SKILL.md 对应物——需要模型"记在骨子里"的跨会话
知识与可扩展能力说明。一期不实现、不注入（system 止于 M3），本模块只立
插槽与纪律，防止将来注入时破坏 §1 原则。

#### M4.1 长期记忆槽（CLAUDE.md 式）

- 职能：跨会话事实与偏好的常驻注入（用户画像、既定事实、约定）。
- 形态：system 尾部追加一个记忆块；更新低频（用户显式记忆/遗忘时）。
- 实现另立方案（总方案二期清单已有"长期记忆 skill 式 system 注入"条目，
  本模块为其预留字节位置）。

#### M4.2 技能槽（SKILL.md 式）

- 职能：按需扩展的能力说明包（如"会用某工具完成某类任务的专门教程"）。
- 形态：触发式加载（按会话/按需注入），架构三期设计。

#### M4.3 注入纪律（将来实现的硬约束）

- **位置**：恒在 system 最尾（M3 之后）——任何注入不得插到 M1-M3 中间，
  否则全租户前缀失效；
- **频率**：低频更新（人格级）；每次更新 = 该租户一次性前缀 miss，接受；
- **体积**：设预算上限，超限走压缩/裁剪而非直注（防 system 无界膨胀）。

## 4. 缓存影响分析

- **部署日一次性全量 miss**：模块重排 + 文本重写 → 所有租户 system 字节全变
  → 全量前缀 miss 一次，此后按新字节稳定。提示词重构的固有成本，接受。
- **跨租户共享部分挽回**：人格从 system 头部移到 M3 中段后，M1+M2 成为
  全部租户请求的公共前缀字节（DeepSeek 有跨请求公共前缀的缓存单元固化
  机制，可命中）。v9 决议曾记录"unified 家族失去跨租户共享（按租户各建
  缓存）"——本排序把它部分挽回。幅度有限（单租户自身流量主导缓存命运），
  但零成本白得。
- **租户内家族不分裂**：人格位置移动对单个租户无影响——system 仍是单条
  恒定字符串，租户内所有轮次（llmCall 各轮 + forcedFinalize）字节一致。
- **M4 的缓存含义**：记忆/技能更新只影响该租户（M1-M3 前缀仍命中），miss
  一次性。这是 §3 M4.3"恒在尾部"纪律的缓存理由。
- **tools 字段不受影响**：工具定义在请求体内、与 system 分离，本重构不动
  它。M2.2 细则膨胀会增大 system 体积（每轮请求都携带），但命中价约 1/10，
  可接受；仍建议每模块设软性字数上限，膨胀有度。

## 6. 代码组织（一期实现时的落点）

- **functional.ts**：场景定义从单模板字符串演进为模块化装配——M1/M2 各
  子块为命名常量，M3 尾段（语气/过程/格式）为常量，人格槽由 builder 注入；
  `agent_unified` 的产出改为拼装函数。新增降级信号导出常量。
- **builder.ts**：`getSystemPrompt` 对 agent_unified 的拼装从"人格 + 功能"
  改为"M1 + M2 + 人格 + M3 尾"（人格从头部移到中段——builder 获得中段
  注入能力，函数签名不变）。PURE_FUNCTIONAL_SCENES 路径不变。
- **loop.ts**：仅一处改动——降级指令从硬编码改为 import 常量。节点结构、
  消息拼装零改动。
- **assembly.ts**：零改动。blob 示例的"同构锚定"放在测试侧（冒烟测试渲染
  `renderBlobLine` 输出与提示词示例比对），不做 services → agent 的运行期
  import（保持分层方向）。

## 7. 工程分期

- **一期（骨架落地）**：M1-M3 立模块，内容以现有文本重组 + 去重为主、措辞
  最小改动；builder 中段注入；降级信号常量收口；blob 示例测试锚定；M2.2
  仅收 2~3 条最刚性细则。验收 = §8 全绿。
- **二期（细则充实，逐项独立排期）**：M2.2 按真机误判样本逐工具补细则；
  M1.2 示例按真机 blob 微调；M1.4 措辞按真机表现打磨。
- **三期（M4，另立方案）**：长期记忆注入与技能注入的架构设计（本方案只
  留了插槽与纪律）。
