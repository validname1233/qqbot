# Agent 工具调用与参数准确率测试方案

## 1. 目标与交付范围

评估真实模型在 qq-bot **现有 Agent Runtime 链路**中的工具选择准确率和生成参数准确率，而不是另写一个简化 Agent 或只检查最终回复。

本阶段交付本方案。后续按以下顺序实施：

1. **生成测试用例**：定义覆盖矩阵、金标和参数断言，人工审核。
2. **生成端到端测试脚本**：复用生产 Runtime，采集原始模型调用和实际执行参数，实现评分与隔离。
3. **开始测试**：离线自检、真实模型冒烟、完整重复评测。
4. **汇总结果与回归验证**：分析失败样例，固定基线，后续修改后用相同数据重测。

当前尚未生成用例集和脚本，也未执行模型评测。本文不预设准确率或达标结论。

## 2. 项目与原始链路

项目使用 TypeScript ESM、tsx、LangGraph 和 SQLite。现有测试以独立脚本为主，并非统一 Jest/Vitest 测试套件。参考 `test/recall/方案.md`、`test/recall/eval.ts` 和 `test/deep_research/方案.md`。

关键生产入口：

| 位置 | 职责 |
| --- | --- |
| `src/services/agent.ts` | `/Agent` 服务入口与原生工具注册 |
| `src/agent/loop.ts:340` | `runAgentTurn`，会话控制、历史读取、图执行和记忆持久化 |
| `src/agent/loop.ts:81` | `prepareContext`，历史、图片和长期记忆上下文准备 |
| `src/agent/loop.ts:216` | `llmCall`，携带生产 `toolSchemas()` 请求模型 |
| `src/agent/loop.ts:261` | `toolsNode`，解析模型参数并调用 `runTool` |
| `src/agent/registry.ts` | 工具 schema、参数注入及统一执行 |
| `src/services/model.ts` | 模型 HTTP 请求、原始响应解析与日志 |
| `src/agent/tools/arg-injectors.ts` | 隐藏字段剥除与上下文参数注入 |

原始链路：

```text
agentService.handle / runAgentTurn
  → prepareContext
  → llmCall（生产提示词、历史、工具 schema）
  → 无工具：plainReply → END
  → 有工具：toolsNode → runTool → Tool.run
      → 第一轮后：llmCall
          → 不再调用工具：finalize → END
          → 第二轮工具执行：finalize → END
  → 持久化本轮消息，清理会话和进度订阅
```

`MAX_TOOL_TURNS = 2`（`loop.ts:48`）。同轮多个调用通过 `Promise.all` 并发执行，不能用完成先后顺序判定工具顺序。参数在 `loop.ts:269` 做 `JSON.parse`，失败时回退 `{}`；当前没有统一的运行时 JSON Schema 校验。模型参数在执行前还可能被注入器覆盖。

因此必须区分：**模型原始 arguments → 解析参数 → 注入后的执行参数 → 工具结果**。不能把系统补救后的执行成功算作模型参数生成正确。

## 3. 测试边界和模式

### 3.1 Runtime 端到端

测试脚本使用模拟 `MessageContext`，初始化与 `/Agent` 一致的生产工具集合，通过服务入口或 `runAgentTurn` 跑原始图。无图片用例优先使用已完成相同注册的 `runAgentTurn`；服务入口覆盖单独验证。不复制提示词、schema、路由或工具循环。

本测试不经过 QQ Webhook、验签或 QQ 消息发送，所以是 **Agent Runtime 端到端**，不是 QQ 平台全链路测试。

### 3.2 真实模型 + 受控工具执行（主要准确率评测）

- 保留生产工具名称、描述、参数 schema、提示词和完整工具选择空间。
- 在独立测试进程内替换有副作用或不稳定外部依赖的 `Tool.run`，返回每条用例定义的稳定结果，并记录执行参数。
- 不真实发送提醒，不删除生产记忆，不访问未经批准的 MCP 写操作，不向 QQ 推送进度。
- 工具替身用于控制环境，不用于预先替模型选择工具；模型必须自己生成真实 `tool_calls`。
- 报告明确注明：该模式评估 Runtime 下的模型决策，不代表真实外部工具服务的集成成功率。

### 3.3 固定模型响应（仅脚本自检）

使用固定 OpenAI-compatible 响应，验证捕获、图路由、两轮依赖、并发匹配和评分器。它只证明测试设施能正确工作，**不计入真实模型准确率**。

真实工具集成属于可选后续层，需要单独批准副作用范围与服务成本，结果单独报告。

## 4. 第一步：生成测试用例

### 4.1 覆盖矩阵

首批以实际注册的原生工具为主，建议 40–60 条，经审核后确定数量；不是先固定数量再凑题。每类都含正常例、边界例和容易混淆的对照例。

| 类别 | 覆盖内容 |
| --- | --- |
| 不调用工具 | 闲聊、无需外部事实的回答、缺失信息需要澄清 |
| 单工具选择 | `get_time`、`search`、`open_page`、`set_reminder`、记忆新增/召回/删除 |
| 参数抽取 | 必填字段、类型、枚举、数字、URL、中文文本、可选字段省略 |
| 相近意图 | 查询与保存记忆、搜索网页与打开已知 URL、当前时间与一般时间知识 |
| 多工具 | 同轮独立调用、漏调、多调、重复调用 |
| 两轮依赖 | 第一轮获取信息，第二轮参数依赖第一轮结果，例如时间与带日期的搜索 |
| 上下文 | 单聊/群聊、明确指代、带历史与无历史的对照 |
| 安全与隐藏参数 | 模型不应生成上下文注入字段，注入后的租户身份保持正确 |

MCP 为可选扩展，只在测试环境明确启用时使用其真实 schema，不把不可用工具写入默认金标。图片识别、真实网页交互可作为后续扩展，不混入首批文本决策基线。

### 4.2 数据字段

后续 `cases.json` 每条包含：

- `id`、`category`、`description`：标识与覆盖目标。
- `input`：用户自然语言请求，不要求直接写工具名称。
- `context`、`historySeed`：单聊/群聊及历史种子；默认空历史。
- `expected`：是否应调用工具、允许的调用路径、可接受等价工具集合、每轮数量约束。
- `argumentRules`：必填/禁止字段、类型、精确值、范围、正则或明确语义匹配规则。
- `toolResults`：按调用返回的稳定结果，供下一轮推理使用。
- `notes`：歧义、可接受行为及审核依据。

金标以真实工具契约和用户意图为依据，人工审核。不得让被测模型独自生成金标并给自己评分。

### 4.3 匹配规则

- 调用路径按轮次判断，同轮调用按无序集合匹配；重复调用不得被集合去重隐藏。
- 精确字段用精确比较；空白等规范化必须在规则中声明。
- 搜索 query、提醒文本等有等价表达时使用明确的语义条件或人工复核，不能全部逐字匹配，也不能用宽松“包含关键词”掩盖关键信息缺失。
- 歧义请求允许澄清或不调用工具时，提前写进金标，而不是看到输出后改答案。
- 第二轮参数可引用固定第一轮工具结果；时间相关用例使用固定时间结果，不随运行日期漂移。

## 5. 第二步：生成端到端测试脚本

### 5.1 计划目录

```text
test/agent_tool_accuracy/
  方案.md                  # 本次交付
  README.md                # 后续：运行说明
  cases.json               # 后续：审核后的用例
  e2e.ts                   # 后续：生产 Runtime 驱动与观测
  score.ts                 # 后续：匹配与指标计算
  reports/                 # 后续：脱敏轨迹和汇总
```

这些后续文件当前不创建占位内容。沿用项目 `.js` 本地导入路径和 tsx 独立脚本模式，非必要不增加新的测试框架。

### 5.2 隔离与初始化

1. 在动态导入生产模块前设定测试存储配置，确认所有可能访问的记忆/图片/定时任务存储均与生产隔离。
2. 为每个用例和每次重复运行使用独立会话身份，避免热窗口污染；多轮历史测试只使用指定种子。
3. 初始化生产工具注册，使用同名注册替换执行体时先确认 registry 的覆盖语义，保留描述和 schema。
4. 禁止 QQ 消息发送和意外网络调用。若无法在测试进程内安全隔离，停止真实评测，不通过改生产链路绕过。
5. 清理只针对本次创建的临时资源，不删除现有用户数据或覆写 `.env`、MCP 配置。

### 5.3 观测点

在模型 HTTP 边界捕获生产 `callModel` 的请求与响应。真实模式透传原请求和响应，不能增删提示词、过滤干扰工具或修正参数。其他网络请求单独处理，不把它们误当模型调用。

每条轨迹保存：

- 用例 ID、重复序号、模型配置与耗时。
- 实际发送的工具 schema 和消息快照/指纹。
- 每轮模型原始 `tool_calls`，包含调用 ID、名称、arguments 字符串。
- JSON 解析状态、schema 校验结果、业务参数断言结果。
- 工具替身收到的最终执行参数、返回结果和错误。
- 最终回复及 Runtime 是否正常完成。

必须记录“生成但未执行”的调用，不能只依据工具执行日志算工具选择正确率。JSON 非法即记为生成失败，即使 Runtime 回退 `{}` 后执行成功也不改判。

使用独立的测试侧 schema 校验器检查当前生产 schema；不在生产流程新增校验节点。工具描述中的业务约束（例如二选一）另外断言。未知工具和超出范围的字段要保留证据。

### 5.4 离线自检

固定模型响应至少验证：不调用工具、单工具、同轮并发、两轮依赖、非法 JSON、错误字段类型、未知工具、工具异常、注入参数覆盖和工具后进入 finalize。评分器应对“错调工具但参数形式正确”和“系统注入修正错误参数”给出预期失败结果。

## 6. 第三步：开始测试

以下命令为后续脚本的计划接口，**目前尚不可执行**：

```bash
# 在项目根目录执行
npm run typecheck
npx tsx test/agent_tool_accuracy/e2e.ts --mode mock
npx tsx --env-file=.env test/agent_tool_accuracy/e2e.ts --mode live --limit 5 --repeat 1
npx tsx --env-file=.env test/agent_tool_accuracy/e2e.ts --mode live --repeat 3
```

运行顺序：

1. 类型检查与离线自检，确保评分器和隔离有效。
2. 5 条以内真实模型冒烟，检查 schema、轨迹、费用和时间。
3. 完整测试，首轮建议每例重复 3 次；按用例 ID/类别可筛选。
4. 保存结果，复核失败样例与存在语义争议的参数。

脚本提供请求预算、每例超时和总预算。预算应按用例、重复次数和 Runtime 的实际多次模型请求估算，不能把一条用例当成一次请求。超时/限流/网络错误独立统计，不自动重试后丢弃首次失败；重跑保留原尝试并注明策略。

## 7. 指标与评分口径

所有报告同时显示分子、分母和有效样本数量；准确率按每次用例运行计算，重复运行不偷偷挑最好的一次。

| 指标 | 定义 |
| --- | --- |
| 工具选择准确率 | 实际生成的调用路径符合金标的有效运行数 / 有效运行总数，包含正确不调用工具 |
| 调用 precision | 正确匹配的生成调用数 / 生成调用总数 |
| 调用 recall | 正确匹配的期望调用数 / 应生成调用总数 |
| 误调用率 | 不应调用工具但生成调用的运行数 / 不应调用工具的运行数 |
| 原始 JSON 合法率 | arguments 可解析为参数对象的调用数 / 生成调用总数 |
| schema 合规率 | 原始参数满足对应生产 schema 的调用数 / 生成调用总数；未知工具不合规 |
| 参数字段准确率 | 正确匹配工具调用中通过的字段断言数 / 这些调用的字段断言总数 |
| 整调用参数准确率 | 所有参数断言通过的正确匹配调用数 / 正确匹配调用总数 |
| 联合成功率 | 工具路径和参数规则均满足的运行数 / 有效运行总数 |
| 执行参数一致性 | 注入后满足上下文身份/业务约束的执行调用数 / 相关执行调用总数 |

条件参数指标必须与联合成功率一起展示，避免只在选对工具的少数样本中算参数准确率。对于多个允许金标，先选择一个完整匹配路径再评分，不拼凑多个路径的局部正确结果。分母为零时显示 N/A，而非 100%。

基础设施失败不混同模型决策错误，但同时报告：总尝试数、有效运行数、基础设施失败数和端到端完成率，不能只展示过滤后的高准确率。

失败分类：漏调、错调、多调、重复调用、轮次/依赖错误、非法 JSON、缺字段、错误类型/枚举/值、业务语义错误、隐藏字段生成、上下文注入错误、Runtime/网络错误。

最终回复主要检查是否有结果、是否正常结束；内容质量与事实正确性属于额外维度，不用它代替工具/参数评分。

## 8. 报告、可复现性与验收

每次运行保存脱敏 JSON/JSONL 轨迹和 Markdown 汇总，按工具、类别、重复次数分组，列出失败用例的期望、原始生成参数和实际执行参数。

记录运行时间、实际模型配置、生产提示词/schema 指纹、用例版本和可获取的代码版本。不得保存 API key、Authorization、真实 QQ 身份或生产记忆内容；报告输出应留在本地。

后续测试设施验收标准：

- 确实调用原始 Runtime，没有独立简化链路。
- 默认评测不修改生产数据，不发送真实提醒/QQ 消息。
- mock 自检验证评分器能够识别预设错误。
- 真实模型原始参数和注入后参数分别留证。
- 可复现同一用例并生成带明确分母的报告。
- 网络失败、未执行调用和有歧义样本均可追踪。

模型是否达标应在第一次真实基线完成后，再按业务风险制定阈值；本方案不凭空规定项目当前准确率。
