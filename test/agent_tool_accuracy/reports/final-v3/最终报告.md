- 时间：2026-10-13
- 模型：deepseek-v4-flash（`AGENT_MODEL` 由 pro 临时降为 flash，仅本次评测）
- 样本：104 条用例 × 3 次重复 = 312 次运行，基础设施失败 0
- 链路：生产 `runAgentTurn` 原始链路（prompt/路由/参数注入不变），工具执行体为固定替身
- 评分口径：v3 覆盖式匹配——金标要求的工具按发生顺序全部被覆盖即通过；多出的调用（`get_time`、重复 search、拆多次记忆）与轮次先后不判错；**漏调、调错工具仍判错**
- 严格口径基线报告：`final-merged/summary.md`；中间口径：`final-relaxed/summary.md`

## 指标总览

| 指标 | 数值 | 计算口径 |
| --- | --- | --- |
| 工具选择准确率 | **93.9%**（293/312） | 调用序列命中金标（含覆盖式放行）的运行次数 / 有效运行总次数；「正确地不调用工具」也计入分子 |
| 调用 precision | 82.4%（286/347） | 与金标配对成功的生成调用数 / 模型生成的调用总数。多余调用（过度 get_time、双搜索）不判选择错误，但在此指标中如实扣分——该指标反映调用成本效率，非正确性 |
| 调用 recall | 94.4%（286/303） | 与金标配对成功的期望调用数 / 金标要求的调用总数。分母低说明存在漏调（如 multi-tool-003 一次 search 都没发） |
| 原始 JSON 合法率 | **100%**（347/347） | `tool_calls.function.arguments` 可被 `JSON.parse` 的生成调用数 / 生成调用总数（模型原始输出，非执行兜底后的结果） |
| schema 合规率 | **100%**（347/347） | 原始参数满足生产工具 schema 的调用数 / 生成调用总数。含必填字段齐全、类型正确、枚举内取值、无多余字段；未知工具名也计为不合规 |
| 参数字段准确率 | **98.6%**（364/369） | 通过断言的字段数 / 已判定的字段断言总数。断言按 `argumentRules` 逐字段评判（exact/range/semantic 等）；semantic 未判定的不计入分母 |
| 整调用参数准确率 | 97.8%（223/228） | 全部字段断言均通过的配对调用数 / 可判定的配对调用总数。一个调用只要有一个字段错即整条计错 |
| 联合成功率 | **95.2%**（217/228） | 工具选择与参数全部正确的运行次数 / 可判定的运行次数。选择与参数都过关才算成功——防止「选对工具但参数错」被参数指标掩盖 |
| 误调用率 | 7.4%（4/54） | 不应调用工具却生成了调用的运行次数 / 不应调用工具的运行总数（54 次 = 18 个 no_tool 类用例 × 3）。越低越好 |
| 未定（联合） | 84 次 | semantic 判官未给出结论或无配对调用的运行数。不计入联合成功率分母，不视为通过或失败 |

## 剩余 19 次失败（真实问题，未放宽）

| 用例 | 次数 | 问题 |
| --- | --- | --- |
| open-page-008 | 3/3 | **幻觉 URL**：用户没给网址，模型自己拼出 `baike.baidu.com/item/量子纠缠` 传给 `open_page`（金标是 search） |
| set-reminder-012 | 3/3 | **该澄清时乱翻记录**：「别提醒我了」（无已设提醒）应说明无可取消，却调 `recall_memory` |

| two-turn-008 | 3/3 | 用 `recall_memory` 翻旧对话代替 `get_time` 取当前时间；其中 1 次还把「明早八点」算成 61200 秒（17h，实际应为 39600 秒/11h） |
| multi-tool-003 | 3/3 | **漏调**：查新电影+带娃去处两件事，两轮预算全花在 `get_time` 上，一次 search 都没发 |

| search-005 | 1/3 | 偶发：连调两次 `get_time` 后收尾，search 始终没发 |

## 结论

- **参数生成能力扎实**：JSON 合法率与 schema 合规率均 100%，字段准确率 98.6%——模型给出的参数格式、类型、取值几乎不出错。
- **短板在决策行为**，且集中在两类：①「没给信息时编造」（幻觉 URL、脑补提醒时刻）；②「该问用户时自作主张」（用 recall_memory 替代澄清或直接说明）。
- precision（82.4%）与选择准确率（93.9%）的差距即「无害但多余的调用」：过度 `get_time` 与同意图双搜索是普遍习惯，功能正确但增加延迟与额度消耗。若要优化成本，可在 `get_time` 工具描述中追加「用户消息已含明确日期/年份时无需调用」，并在 `agent_judge` 提示词约束同意图单次搜索。
