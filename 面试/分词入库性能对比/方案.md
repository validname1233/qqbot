# 实验方案：长期记忆关键词检索——实时分词 vs 分词入库

## 1. 背景与动机

当前长期记忆的混合检索（向量 RAG + 关键词 BM25）中，关键词通道**不入库**：每次 `search()` 时用 `Intl.Segmenter` 对该 key 下全部记忆的 `content` 现场分词，再算 BM25。理由是「每 key 最多 30 条，分词开销可忽略」。

这个假设在当前规模下成立，但它是用「每次检索 O(N × 分词)」换「零存储、零迁移」。本实验定量验证：**把分词结果落库（写入时一次分词、检索时直接读）到底比实时分词快多少？在什么规模下差异开始显著？** 给出数据支撑的结论，而不是拍脑袋。

## 2. 实验设计

### 变量控制

- 唯一变量：分词时机（检索时实时分词 / 写入时分词后落库读取）
- 固定量：同一份语料、同一个分词器（`Intl.Segmenter`）、同一 BM25 实现、同一查询集
- 分词器本身就是模块级单例（ICU 资源复用），排除初始化开销干扰

### 对照组实现

| 组别 | 做法 |
|---|---|
| A（现状） | 检索时对每条候选的 `content` 调 `tokenize()` |
| B（落库） | `add()` 时 `tokenize(content)` 存入新列（如 `tokens TEXT`，JSON 数组），检索时 `JSON.parse` 直接读 |

### 规模梯度

内存记忆数按 key 分档：**30 / 300 / 3000 / 30000 条**（30 是线上真实上限，往后是压力推演）。每条 `content` 长度取真实记忆的量级（10~50 字）。

### 测量指标

- 单次 `search()` 关键词通道总耗时（毫秒），预热后取 **1000 次均值 + P50/P95**
- 顺带记录：分词耗时占比 vs BM25 计算耗时占比（确认瓶颈真的是分词，而不是打分）

### 执行步骤

1. 写一个 benchmark 脚本（tsx 跑，如 `benchmark/tokenizer-bench.ts`）：生成语料 → 两组各预热 100 次 → 各测 1000 次取统计量
2. 每个规模梯度重复 3 轮，取均值，观察波动
3. 记录原始数据到表格，附实验环境（Node 版本、CPU、是否小核等）

## 3. 预期与分析框架（实验前写下，实验后对照）

- 预期 B（落库）随规模增大优势线性扩大：A 组耗时 ∝ N（每条都要分词），B 组耗时 ∝ N 但常数远小（JSON.parse 比 ICU 分词快一个量级以上）
- 预期在 30 条规模，两组都在亚毫秒级，差异无实际意义 → **支撑「现状设计在小规模下合理」的结论**
- 预期在 3000+ 条规模，A 组开始进入毫秒~十毫秒级 → 给出「何时值得迁移到落库方案」的阈值

## 4. 结论的呈现（面试话术骨架）

> 我们的记忆检索用了混合召回，关键词通道当时面临「分词结果入不入库」的取舍。我没有直接拍板，而是做了个对照实验：结果表明在当前规模（30 条/key）实时分词只有 X µs，落库收益 < Y%，所以选择了零迁移成本的现状；但如果规模到 Z 条，数据表明应该切换到写入时分词落库。这个阈值现在是实验数据而不是猜测。

## 5. 成本与排期

- benchmark 脚本 + 落库原型改动：约半天
- 跑数据 + 写结论：约 1 小时
- 不动线上代码：实验在独立脚本/独立 sqlite 文件里做，跑完即弃
